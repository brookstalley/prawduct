# Prawduct Changelog

Consumer-facing release notes for the Prawduct governance plugin. The
version-delta banner (a SessionStart hook) shows the headline for each version a
repo crosses since it was last opened — so an auto-update is always visible,
never silent. This file ships **inside the plugin**: it never lands in a
consuming repo's tree, so it creates zero commit/merge noise downstream.

The full internal development log (with blast-radius and rationale) lives in the
Prawduct repo's `.prawduct/change-log.md`; this file is the public digest. The
release process keeps the two in sync (one headline per shipped release).

## v3.2.3

**Learnings now fire where the mistake gets made rather than waiting in a file to be read — and every turn ends by telling you where things stand.** A corpus of 159 learnings was not changing behaviour, and the diagnosis was *delivery*, not authoring: the rule that would have caught four false claims in a consuming repo was already there, already general, already well-worded. A rule read at session start competes with the whole rest of the context by the time the claim gets written. So two rules moved out of storage and into the code path that runs at the moment they apply — *green is evidence only about what could have made it red* now prints at `test-evidence record` when the record shows judged code changed, and *a resolution is a claim about the tree* prints at `critic-begin --mode verify-resolutions`. **Known limitation, stated rather than discovered:** the first line is gated on Python-symbol matching, so it does not fire in a Swift, Rust, C# or TypeScript product yet.

**`audit-learnings` gained `superseded-by=`.** Retiring a rule because a broader one replaced it is what every consolidation is, and it was previously an unauditable hand-edit — which is a large part of how a corpus reaches 159 rules with near-duplicate families in it, since adding is cheap and merging is not. The retired entry's historical copy names its replacement, so a reader who remembers the old rule finds a forwarding address rather than a hole. It fails closed on every ambiguity: unresolvable, ambiguous, self-referential and empty pointers all error rather than retire. Prawduct's own corpus went **159 → 149** using it, with every retired rule's distinguishing instance preserved in its successor.

**Agents now close a turn with a fixed three-part block — `STATE`, `NEXT`, `CLEAR`.** Both reports behind this came from consuming repos, and neither was about a gate being wrong. A correct "safe to `/clear`" sentence sitting in the middle of a long closing summary is a signal not sent, because someone returning to a wall of text reads the bottom and nothing else. The larger half: after a 30–120 minute build your question is not *may I clear?* — it is *did it work, what happens next, and am I the blocker?* You should notice this at the end of every work cycle.

**Two new `## Direction` norms.** *Goals and verification bind; prescribed method is advice* — where a governing artifact prescribes **how**, that is the author's guess made before the code was read, and a builder who finds a better route takes it and records why (verification structure is carved out and still binds). *Every fact has one home; every other mention is a reference to it* — reframing the review question from "do these agree?" to "why are there two?".

**If you are about to migrate a backlog to GitHub Issues, read this one.** Prawduct migrated its own — **371 items, 0 stranded, 0 collisions** — which is the first time the path ran at real scale, and it surfaced a defect in the instructions rather than the code: the scrub runbook told you to apply post-import dispositions **before** running `verify-migration`, and that ordering turns owner-approved merges into a false failure, because the gate compares each item against its *source* status. Step ordering is corrected. The service remains **opt-in** — your backlog does not migrate on upgrade, and nothing changes until you run the migration yourself. The completeness gate also now catches an item that arrived at the wrong status, which it previously could not see.

## v3.2.2

**Review depth is now a risk question rather than a file count — and no repo is reviewed less than before.** The Critic's coordinator (three parallel reviewers) used to fire at 5+ changed files. It now fires when a change touches a **risk surface**, or changes 12+ *judgeable* files. If you have declared nothing, nothing gets cheaper: prawduct's own defaults still escalate, and beneath them the old 5-file rule stands untouched. **What can change without you asking is depth going UP** — a two-file change touching your `skills/`, a `*hook*` script, or a contract path you listed in `boundary-patterns.md` now draws three reviewers instead of one. Declaring `risk_surfaces:` in `project-state.yaml` is how you tell prawduct where your own risk lives; the template shows the shape. This replaced a rule that counted files without asking what they were — measured against 82 recorded reviews, keying on file count alone would have sent 54% of historical blocking findings to a single reviewer, because record-heavy changes are usually *governance* changes and that is where the blockers are.

**Fast reviews got much cheaper.** A `chunk` or `verify-resolutions` review runs three goals but was loading the full seven-goal protocol to do it — **~10,500 tokens down to ~1,875, an 83% cut**. These are the reviews you run between chunks, so this is the wall-clock you feel most.

**Record bookkeeping is now machine-answered at dispatch instead of costing a review round.** Chunk-deliverable existence, `governed_by:` gaps against a cited artifact's norms, suite-total test claims in prose, and `learnings.md` entry shape are all checked in code and handed to the reviewer as answers. Two further checks were built, measured at zero true positives, and deleted rather than kept.

**Also:** the FILE disposition bar is tighter (filing a finding now requires the work to be genuinely large *and* not absorbable into current work — deep context on a small problem is a FIX signal); two architectural norms now bind (prawduct guides and reviews but never implements, and is written in Python without being specific to Python — gates dispatch per file, and a language with no rules reports `unchecked` rather than silently passing); and one gate relaxation was built, tested, and reverted as unsound.

## v3.2.1
**Your Critic reviews may have been running three times slower than they needed to, and the review-cost numbers they feed could double-count.** Two fixes to the review data plane, both reaching every installed repo. **Coordinator reviews now fan out.** A `final`/`cumulative` review at 5+ changed files dispatches three reviewers, and nothing in the framework ever said to launch them together — the parallelism rode an ambient harness default that varies between sessions, so some sessions paid for three reviewers and got the wall-clock of three *sequential* reviewers. It is now specified in both dispatch surfaces and pinned by a test, so it cannot silently revert. **One review can no longer anchor two ledger events.** `review-stats` counts governance-ledger lines to report review cost and yield; the anchor had no idempotency key, so a re-materialized dispatch or a crash between the fact append and cleanup could log the same review twice and inflate exactly the numbers you would use to decide whether review is proportionate. A probe now closes that replay path — honest limit: a genuinely concurrent overlap is narrowed, not eliminated, because there is no lock yet, and that residual is tracked rather than papered over. **Also new, and inert unless you use it:** `prawduct-hook disposition` records a finding's ACCEPT/FILE answer as a fact and `render-dispositions` derives the census for a change-log entry or PR body — so the count of what a review decided stops being hand-written prose that drifts, and it reports how many findings are still undispositioned. No gate semantics change, no state format changes, and no migration is required: the new fact kind is additive and older readers coexist with it.

## v3.2.0
**The GitHub-Issues backlog service ships — dormant — and skill-only sessions stop silently skipping the reviewers.** Three releases in a row said the backlog service was "deliberately not in this release"; it is here now, and it changes nothing until you ask it to. **The backlog service** lands as `plugin/lib/backlog/` with `/prawduct:backlog` repointed onto a GitHub-Issues adapter, but routing is opt-in per repo on a single `backlog_service_repo` key in `.prawduct/project-state.yaml`. Unset — the default, and what `init-product` writes for new products — means the markdown backend, byte-for-byte the behaviour you have now; the migration advisory does not fire on upgrade. **If you do nothing, you see no backlog change.** The cutover path itself is deliberately still held: its blockers are open, prawduct has not migrated its own backlog, and the honest state is "the subsystem is present and inert" rather than "the migration is proven." Everything the service touches was taught to *state* dormancy rather than be quietly wrong about it — the PR path stops resolving `closes:` against a frozen markdown file, the janitor's Backlog Health reports which backend it actually read, and the backlog checks say when they cannot know. **The defect worth upgrading for is separate: skill-only sessions have been skipping the reviewers since the plugin relocation.** A session whose work ran entirely through skills could reach session end without the review gates engaging — a documented safety net that had quietly stopped being load-bearing. Alongside it, `verify-chunk-refs` was verifying **one** file reference for an entire release and reporting `ok`, which is worse than reporting nothing. **Review machinery** — the composed-coverage gate was probing an equivalence relation one pair at a time (quadratic in changed files; now it isn't), the review loop had **no exit condition** and relied on the builder to supply one, and the Critic's "file the rest" disposition was a backlog pump the framework was running on itself: findings are now *dispositioned* — fixed, accepted with a reason, or filed — rather than filed by default. **Release governance (mostly ours, one consumer note).** The release runbook could publish work that was not fit to ship: its only precondition asked *"is anything unreleased?"*, never *"is everything fit to ship?"*, and on v3.1.2 those diverged — following it literally would have published a subsystem with all four of its go-live blockers open. There is now a Phase 0 releasability gate (`check-releasability`) that enumerates every release-pending scope and fails closed, a second runbook for the pruned-promotion shape that prawduct has now used twice, and an amended promotion norm: `main`'s tree is a *fully classified* snapshot of `develop` — every scope shipped or withheld behind a named blocker — with content-identity as the expected outcome of a whole-develop promotion rather than the invariant. **Consumer note, stated rather than buried:** `check-releasability` is prawduct-release-specific and ships in every product's CLI, where it has nothing to do; it is inert unless invoked. Finally, `.prawduct/.handoff-notes.md` is now *prepared and reconciled* rather than proposed and stacked, so forward context stops growing a new layer every session. No gate semantics or state formats change for consuming repos, and no migration is required. Both release runbooks ship with `last_verified: null` — this release wrote the pruned procedure and, being a whole-develop promotion, did not execute it.

## v3.1.2
**`claude --resume` no longer destroys the session evidence it resumes, and the Critic's per-reviewer consolidation trigger fires for the first time since it shipped.** Two things that had been quietly wrong for every consumer. **Session boundaries** — `clear --session-start` was registered on `startup|resume|clear`, so resuming a session ran a full *boundary* reset on a session that had not ended: it folded your model-authored handoff notes into a handoff, archived the reflection ledger away mid-session, and re-captured all three session anchors, which silently narrowed the session Critic gate's jurisdiction to post-resume work only. `fork` (`--fork-session`, `/fork`, `/branch`) had been getting no hook at all — and because it allocates a new session id while the parent is often still running, it is the source where a boundary reset would destroy a **live** session's evidence rather than a finished one's. Orientation and boundary are now separate acts, split by matcher: `startup|clear` runs the boundary, `resume|compact|fork` runs orientation only. Verified end-to-end against the real CLI, and the guard is a partition property over a pinned roster of all five documented sources rather than a spot-check — a spot-check on `compact` is exactly what let `fork` go unnoticed. The handoff also gains a **forward channel**: `.prawduct/.handoff-notes.md` is yours to write and is never machine-overwritten, where the generated `.session-handoff.md` previously clobbered model-authored context unconditionally — preserved only when the machine had nothing to say, i.e. exactly when it mattered least. An undelivered note is announced to the next agent instead of vanishing. **Consumer-visible tradeoff (deliberate):** a `.gates-waived` waiver now survives an unbounded number of continuations and clears only at a boundary — correct, since a waiver is session-scoped and the session continues, but longer-lived than before. **The Critic's `SubagentStop` trigger had never fired** — not in any repo, on any release that shipped it. Its matcher was the bare `critic-reviewer`; for `SubagentStop` a matcher of only letters, digits, `_`, `-`, spaces, `,` and `|` is a literal (one exact string, or a `|`/`,`-separated list of exact strings), while the runtime `agent_type` of a plugin subagent is the plugin-scoped `prawduct:critic-reviewer` — so the two could never compare equal. No reviews were lost, because the session-end backstop still blocked on the lingering marker; what you actually got was a documented safety step turned load-bearing. CLAUDE.md describes running `critic-consolidate` before reading `.critic-findings.json` as "an idempotent no-op when the trigger already landed it" — it never landed it, so anyone who skipped that step read the **previous** review's findings. Fixed to `(^|:)critic-reviewer$` and pinned by a test that encodes the documented matcher rule, so a future simplification back to the bare name breaks loudly. Rounding it out: the build-plan "which chunk is current" question now has one answer instead of three, the handoff stops reporting a finished plan as active, and the methodology guides name the handoff's forward channel rather than only the file the agent must not write. No gate semantics or state formats change. The GitHub-Issues backlog service is still deliberately **not** in this release — its migration path remains unproven end-to-end and ships when it is.

## v3.1.1
**The plugin stopped shipping prawduct's own internal state to your repo.** `marketplace.json` declared `"source": "./"`, so the entire prawduct repository became the distributed plugin — its backlog, learnings, change-log, every build and release plan, its test suite and internal requirements docs, roughly 4.9 MB of *another product's* documentation sitting in your plugin cache, in a directory skills legitimately tell a model to read. Nothing was secret, but a broad glob under `${CLAUDE_PLUGIN_ROOT}` in your repo could return prawduct's open backlog items as though they were yours, and confidently wrong context is the failure this framework exists to prevent. The plugin now installs from a curated root: **109 files, 1.7 MB**, containing only what you actually run. Verified by real install rather than assertion, and pinned by a test that asserts the boundary in both directions. One caveat if you are upgrading rather than installing fresh: plugin caches are version-keyed, so every prior version directory stays on disk alongside the new one and still holds the old contents. What loads is clean; the stale copies are inert. They accumulate per config directory, so if you run more than one Claude Code profile check each — `du -sh ~/.claude*/plugins/cache/prawduct/` — and delete the version directories below `3.1.1`. Two sampled machines measured ~90 MB each — one across four profiles, one across two — so treat it as per-profile-per-machine accumulation rather than a fixed amount. `claude plugin prune` does not remove them. One new capability and a batch of review-machinery fixes round it out. **`/prawduct:runbook`** — the framework pointed at runbooks in three templates (operational spec, observability strategy, failure-recovery spec) and never said how to write one; it now ships `docs/runbook-authoring.md` (rules plus the evidence behind them), `templates/runbook.md`, and a skill that surveys, authors, and reviews. The guide was validated by *use*, not by reading: fresh agents authored real runbooks from it and their output — not an analytic audit — decided its final shape. Deriving prawduct's own release runbook from it immediately found two version files the release process had never named, one of them three releases stale. **Review machinery** — `critic-consolidate`'s incomplete no-op now reports whether reviewers are in flight or dead instead of a bare `0/3 partials`, which was being read as "the fork died" and answered with a duplicate roster at double cost; a waiting session is told to stay audible rather than idle its prompt cache into expiry; `verify-chunk-refs` stops raising false `missing-ref` on `path:line` citations and chunk-local `new` declarations, and its `cannot-verify:` exit is now BLOCKING rather than silent; the cumulative-critic gate explains a stale `origin/<base>` instead of failing opaquely. **Four defects filed upstream by a governed product** are fixed — `critic-consolidate` fail-closing on a file-less finding, `verify-chunk-refs` mis-parsing `## Chunk N (ID)` headings, `verify-resolutions` mis-anchoring so the cumulative gate stayed `uncovered`, and `critic-begin` blind to a wrong worktree. Plus the **SessionStart banner names which plugin code is actually loaded** (local checkout vs marketplace copy), and the Stop hook names the tree its gates actually evaluated. No gate semantics or state formats change. The GitHub-Issues backlog service is deliberately **not** in this release — it remains unproven end-to-end and ships when it is.

## v3.1.0
Two features and a posture release. **Structural coverage** — the framework can now see what was *never created*: a three-layer advisory chain keys off what a product *is* (its recorded structural characteristics) to expect what it should therefore *have* (seven strategy-class artifacts), staged one nudge at a time, dismissible, never blocking. Minimal-documentation products satisfy the whole chain in three cheap steps (record characteristics; `coverage-scaffold --apply`, where a one-line "(not relevant — reason)" stub IS coverage; a doctor-confirmed "none to ratify") — prawduct is opinionated that absence be a recorded decision, not that documentation be voluminous. **Norm lifecycle** — norms bind, descriptions track: `## Direction` statements in governing artifacts now carry normative authority with an owner-ratification flow (surfaced by exception, never a flat wall), Critic/PR enforcement scoped to adoption (a norm-less repo gets NOTEs, never blocks), and time-domain health sweeps. **Merge commits are now the default everywhere** — `gh pr merge --merge` in the PR skill *and* an ambient standing rule (CLAUDE.md, both session digests): never squash/rebase-merge unless `project-preferences.md` says so or you ask; a failing `--merge` is surfaced, never silently downgraded; squash-configured branches are single-use (squash strands a reused branch's merge-base, causing re-review of already-merged work — the bias itself is a model prior at unguided decision points, which is why the counter is ambient). **Test evidence meets real environments** — `test-evidence record`'s interpreter fallback can no longer persist a wrong-environment false-red (refused loudly with migration guidance), is deprecated-by-nudge, and the new `test_commands:` list lets a polyglot product (iOS+Android game; SQL+Python+React app) declare one environment-aware invocation per suite with counts aggregated into one record — misparses refuse loudly, never partial; `--from-junit` is repeatable to match. Plus **Principle 24 — Retrieval Over Generation** (before a consequential decision, do the cheapest check that could change it — read the mechanism before tuning it, search practice before working around a behavior), the seventh strategy-class authoring template (`architecture.md`), and prawduct's own 20-norm ratified registry.

## v3.0.5
The SessionStart briefing no longer **enumerates sibling worktrees**. When a repo had multiple git worktrees, the briefing listed each sibling as `- <branch> @ <path>` — which read as a menu of adoptable work and could lure a session into working in a worktree it did not launch in, colliding with that worktree's own session. The enumeration is removed; the briefing now orients the agent to its own worktree only ("work and gates are scoped to THIS worktree only; other worktrees belong to their own sessions; do not read or modify them"). Worktrees remain discoverable on demand via `git worktree list`, and gate scoping is unchanged. A single-worktree repo sees no difference.

## v3.0.4
Durable artifacts now stay self-contained — an **ephemeral-reference firewall** keeps build-cycle scaffolding out of durable product artifacts. Chunk labels ("chunk 03"), build-plan names, and work-cycle names are the most ephemeral things in the system — deleted at merge/release or swept by the janitor, and not even unique (every project mints a "chunk 03") — so a code comment or long-lived spec that references one becomes a dangling pointer the moment the plan is gone. The rule is installed across the standard carrier surfaces: a Principle 13 (Coherent Artifacts) clause, a builder rule in the building guide, the always-injected session digest (so it reaches migrated repos), and a **Critic Goal 4 check** (a *product* durable artifact — a comment, docstring, or long-lived spec — anchoring its meaning on an ephemeral build id → WARNING). The load-bearing distinction is **product-artifact vs build-cycle bookkeeping**, not durable-vs-ephemeral files: change-log `chunks=`, backlog `closed-by:`, and operator-verification legitimately cite chunks because there the identifier *is* the record of the work. No gate semantics or state formats change for consuming repos — this adds one review check plus authoring guidance; a deterministic grep tripwire was deliberately deferred (case-law-first).

## v3.0.3
Test-evidence freshness is now **tree-validated**, not just session-scoped. `tests_are_current` previously keyed only on WHEN a run happened (the session timestamp), so a restart with no code change, a `.prawduct/*.yaml` governance-metadata edit, or a doc-only edit all re-staled evidence and forced a full-suite re-run — v3 had tree-anchored REVIEW evidence but left TEST evidence on the timestamp model. Now an **additive** tree-validity clause makes `test-status` read *current* iff the run is session-fresh **OR** the judgeable-scoped working tree is byte-identical to the tree the recorded run ran against (`evidence_tree`, captured at `record`; skipped for the `--from-counts` hand-count on-ramp, which carries no tree). It is a pure disjunction that only ever relaxes stale→current — structurally incapable of the false-STALE class that retired the earlier content-hash fingerprint and `git_sha` — and it classifies paths (`is_judgeable_path`), never file contents. Net effect: a restart, a governance-metadata edit, or a doc-only change no longer forces a redundant re-run, while any judgeable-path change still stales evidence and demands a fresh run. **Consumer-visible tradeoff (owner-accepted):** freshness now tracks the tree, not the clock, so an unchanged-tree session no longer *incidentally* re-runs the suite as an environment-drift/flake safety net — a dependency or toolchain change under an otherwise-unchanged tree won't trigger a re-run on its own. Zero-touch upgrade: `evidence_tree` is optional, pre-clause and hand-counted records fall back to the session-fresh clause, and a downgrade ignores the field — so both ship and unship are safe.

## v3.0.2
A declared `test_command:` no longer forces a full-suite re-run just to stamp test evidence. The cheap ingest on-ramps now compose with a declared command: `--from-junit` ingests the JUnit report the declared command already emitted (the command must emit JUnit, so the report is honest machine-backed evidence), and `--no-rerun`/`--restamp` refresh the timestamp and coverage half without a run. Only `--from-counts` stays rejected alongside a declared command — hand-typed counts are the one on-ramp with no artifact and reopen the scoped-subset trap the knob closes, so its error now redirects you to `--from-junit`. The run-path checks (the `{junit_xml}` placeholder, no extra pytest args) apply only when the suite is actually run. Surfaced by a v3.x product session re-running a 17,777-test suite twice per stamp.

## v3.0.1
Reviewers now run on the **session model** — reviewer-model tiering is removed. Model choice previously lived in skill prose that mapped a diff's risk "tier" to a model (the Critic coordinator pinned `opus`; both the Critic and PR reviewers escalated to Fable on the `escalate` tier), and because `escalate` fires for nearly any declared risk surface, reviews escalated to Fable constantly. That intelligent switching is gone: the Critic and PR reviewers inherit whatever model the session is on (opus reviews as opus, fable as fable), with no `model:` override. The `classify-diff-risk` command, the Critic `--tier` telemetry, and `review-stats` model-family aggregation are retained (inert) so the mechanism can be restored later; nothing in gate semantics or state formats changes for consuming repos.

## v3.0.0
Review evidence becomes a composable fact store — a breaking rewrite of the review data plane that is nonetheless a **zero-touch upgrade for consuming repos** (no migration commit, no repo diff, no manual step). Since v2, review results lived in single-slot, per-worktree files judged by a mode label and modification time; that model forced a chunk-reviewed branch into a redundant cumulative re-review (CRT-J4PM), wedged the gate when two predicates drew the metadata boundary differently and left no exit (CRT-5D8Q), let a perfectly good review go "stale" at every session boundary, and left worktrees blind to each other's evidence — and because models hand-wrote the protocol files, one malformed write could silently lose an entire review. Now review results are **append-only facts** in a store shared by every worktree of the clone (`<git-common-dir>/prawduct/evidence.jsonl`, tree-keyed), and the Critic, PR, and Stop gates **answer by composing those facts over a range of git trees** (the PR gate spans merge-base tree → HEAD tree; the Stop gate spans session-base tree → working tree) — no mode labels, no modification times, no `extends_cumulative` chain bookkeeping. The review lifecycle is **code-written end to end**: `critic-begin` writes the dispatch manifest and `critic-consolidate` appends the fact and regenerates `.critic-findings.json` as a derived view no gate reads — the model contributes only its judgment partials, so no hand-written file sits in the write path. The major-version bump reflects the internal data-plane break (gate attribution `since: 3.0.0`), but the **upgrade is zero-touch**: the store initializes lazily so no consumer needs a migration commit, v2-era single-slot state files are ignored with a block-toward-a-fresh-review remedy, and a schema-ahead fact fails both gates closed with an explicit update remedy. On the first session against v3.0.0 a repo simply takes a fresh review under the new data plane; nothing else changes. Also in 3.0: a new **`.gitignore` contract-drift advisory** nudges reconciliation at session start when a repo's `.gitignore` drifts from the framework's session-file contract (a prawduct upgrade that extended the contract, a fresh clone, or a hand-edit), self-resolving the moment the committed `.gitignore` is reconciled — the same observable-state pattern as the upstream-bug probe.

## v2.3.3
A Critic reviewer partial reporting `"files": []` on a finding no longer aborts the whole consolidation. `critic-consolidate` fail-closed on the empty-list encoding of "no files" while accepting the omitted-key form — a semantically-null distinction that could discard an entire completed review (the exact silently-lost-review class the module exists to prevent, reported by a consuming repo). The validator now tolerates the encoding variant and normalization collapses it; fail-closed remains for genuine ambiguity (missing judgment fields, commit mismatches, staleness). No changes to gate semantics or state formats for consuming repos.

## v2.3.2
No more bookkeeping-only PRs on protected branches. Every framework step that required a **post-merge commit on the integration branch** is retired: the merge flow's `stamp-merged` chore commit is gone (a statusless *tagged* change-log entry is now first-class release-pending state — its presence on the integration branch IS the proof of merge; `status=merged` in existing logs stays accepted indefinitely as a legacy synonym), and `/prawduct:pr`'s create flow gains **Step 1d — "the PR carries its own bookkeeping"**: backlog archives, the change-log status, derived views, and (trunk repos) `status=shipped` + build-plan retirement all ride in the feature branch, atomic with the merge. Post-merge steps now commit nothing; missed bookkeeping folds into the next PR — never a housekeeping-only PR, never a direct push to a protected base. `prawduct-hook stamp-merged` still works but announces its deprecation (hard removal is deferred to a future major). The change-log template's status guidance was corrected (it recommended values `regen-views` rejects as fatal and instructed post-merge stamping). Release integrity is unchanged: the change-log entry probe, the "flip every unreleased entry" release rule, and fail-closed regen validation all remain, and batched releases now enumerate statusless scopes directly. If your repo's agent memory or learnings tell it to "run stamp-merged after merging" or "open a follow-up PR to flip statuses," that guidance is obsolete — statuses converge at release (gitflow) or ride in the closing PR (trunk).

## v2.3.1
Coordinator Critic reviews can no longer be silently lost. Claude Code v2.1.198 (2026-07-01) made `Agent` subagents background-by-default, which structurally broke the Critic's `final` (medium/large) and `cumulative` coordinator: the forked skill dispatched its three reviewers and **never resumed** to write `.critic-findings.json`, append the ledger anchor, or clear `.critic-active` — the review ran, was lost, and surfaced later only as a `check-cumulative-critic` deadlock (CRT-9K7T, reproducibly hit by consuming repos). The redesign decouples model judgment from persistence: reviewers are now a dedicated **`critic-reviewer` agent type** (restricted tools make no-test-execution structural) that each write a per-role findings **partial**; a deterministic, idempotent, fail-closed **`prawduct-hook critic-consolidate`** merges them into the canonical findings + ledger anchor — **no model in the write path** — triggered per-reviewer by a new `SubagentStop` hook and floored by a session-end backstop that self-heals from complete partials or blocks naming the missing reviewer. Reviewer responsibilities are wired per role (sustainability owns the Learnings/Backlog cross-checks, design the framework checks), `critic-begin` resets stale partials so an aborted review can't contaminate the next one, and builders should run `critic-consolidate` (idempotent no-op) before reading findings after a coordinator review. The findings/ledger schema is unchanged — downstream gates and consuming repos need no migration. Single-pass modes (`chunk`, `verify-resolutions`, small `final`) are unaffected.
A leaner methodology and a consolidated guide surface. **Heads-up — the four delegator skills `/prawduct:building`, `/prawduct:discovery`, `/prawduct:planning`, and `/prawduct:reflection` are removed.** Each was a thin wrapper that only pointed at its methodology guide; they now route through one reader — **`/prawduct:methodology <topic>`** (e.g. `/prawduct:methodology building`). The always-injected session digest already directs you there, so the change is mostly invisible in practice; typing an old command from habit returns "skill not found" — use the `/prawduct:methodology` form instead. Alongside the fold, the governance cycle's prose was reconciled (five self-contradictions now read one way at every site), single-sourced (the mode×type review matrix and the fallback rule each live in exactly one place), and compressed **−30.3%** with **no rule, gate semantic, or checkable bar dropped**; the build-plan template is now a filled example rather than 200 placeholders, and the agent stance is rewritten advisor-first (the expert take — risks, the stronger/simpler alternative, a recommendation — leads; compliance second). The `/prawduct:pr` merge flow now keeps the build plan when a feature→`develop` merge lands ahead of a batched `develop→main` release (deleting it only when the merge *is* the release). And the structural test suite ignores leftover `.claude/worktrees/` workflow checkouts. Plugin-governed repos: no behavioral change.
