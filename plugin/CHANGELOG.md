# Prawduct Changelog

Consumer-facing release notes for the Prawduct governance plugin. The
version-delta banner (a SessionStart hook) shows the headline for each version a
repo crosses since it was last opened — so an auto-update is always visible,
never silent. This file ships **inside the plugin**: it never lands in a
consuming repo's tree, so it creates zero commit/merge noise downstream.

The full internal development log (with blast-radius and rationale) lives in the
Prawduct repo's `.prawduct/change-log.md`; this file is the public digest. The
release process keeps the two in sync (one headline per shipped release).

## v3.2.8

A build plan's progress checkboxes now mean exactly what they say — `views_enabled` and `regen-views` are retired, and finished plans get an archive instead of sitting in `artifacts/` forever.

Until now a plan's `## Status` block could be one of two different things depending on a setting most repos never knew they had. With `views_enabled` on, the boxes were a *generated view* that only flipped at release, so ticking one by hand did nothing and an in-flight chunk always read as unfinished; with it off, the boxes were the plan's own content. Two meanings, one appearance, and nothing on the page telling you which you were looking at. The setting is gone and only the second meaning remains: **tick a box when its chunk is done, and nothing will overwrite it.** The session gates read those boxes, so this is the reading that was already load-bearing.

`regen-views` and `stamp-merged` still exist and still exit 0 — they print a notice and do nothing, and their removal waits for a major version, so a script or release checklist that calls them will not break mid-run. Release notes live in the change log, which is where they were derived from all along.

Two `/prawduct:doctor` repairs land with it, both preview-first and both taking a single confirmation for the whole job rather than prompting per file. `prawduct-hook lifecycle-repair` removes the dead setting and its generated block, labels a derived `release-notes.md` as the history it is, and deletes the per-plan notes that told readers not to hand-edit checkboxes — that last one is the only piece that still changed behaviour, because a reader who believes it leaves finished work unmarked. `prawduct-hook plan-backfill` moves plans that already shipped into an `archive/` beside them, deciding "shipped" mechanically from the release recorded in your change log. A product that does not tag releases has nothing moved: the set is proposed and you confirm it.

Archiving deliberately does **not** require or correct checkboxes. A plan whose work was descoped can never satisfy "all boxes ticked", and those are exactly the plans that pile up reading as active — so an archived plan may carry unticked boxes, and that is preserved as a fact about how the work ended.

## v3.2.7

An excellent issue title stopped being a suggestion — and a bad row can no longer end a migration.

The issue standard's four §1 title rules were implemented and enforced nowhere: `file` audited
*after* creating the issue, `update` never checked a title at all, and the importer never called
them. That is how a 396-item migration reached GitHub carrying parsed titles up to 2319 characters
against a 72-character budget — only the handful breaching GitHub's own 256 cap ever announced
themselves. All three write paths refuse now. The importer validates the **whole corpus before its
first write**, so a non-conforming source fails in the first second with every offending title
named and nothing created, and the scrub pre-pass is where you fix them.

On `update` the refusal deliberately gates only a title you are **writing**. Changing an unrelated
field on an item whose stored title predates the rule still succeeds, with an advisory line saying
the title was left alone. The narrow scope is the point: an agent, not a human, sits at that write,
so a broader gate would not have blocked those items — it would have made an agent quietly retitle
them while archiving them, which is retro-conformance by the back door.

The importer also stopped treating one rejected row as fatal. A per-item validation failure is
recorded and the run continues; a revoked token or a deleted repo still cuts cleanly, because those
describe the run rather than the item. Five consecutive rejections stop it, since consecutive means
the corpus.

Shipping the length rule alone would have made backlogs *worse* — a scrub rewriting titles one at a
time cannot see that three issues are one defect, and a tighter symptom title entrenches the split.
So the dedup sweep and the migration scrub now ask the altitude question: **would a single change
close all of these?**

Also in this release: the Critic asks the coverage gate before spending a review round, and records
every refusal so the guard can eventually be judged on evidence; a reviewer's partial findings are
bound to the review that dispatched it, so a concurrent dispatch cannot mix them; and the backlog
importer gained a real title boundary, ending the run-on titles at their source.

## v3.2.6

A second Critic dispatch can no longer destroy the review already running — and every state it
refuses now names a command that clears it.

`critic-begin` used to archive an in-flight review's partials and overwrite its manifest with no
check that a review was running. Dispatching over one erased completed findings, and left the
displaced reviewers writing into the new review's directory — where their partials consolidated as
a review that never read those files. Seen three times in the wild; the worst case lost a
three-reviewer review carrying two blocking findings. It refuses now, on a live review marker or on
a complete set of reviewer reports at any age, and `prawduct-hook critic-discard` is the
archive-first way out of the one state nothing else could clear. An orphaned leftover from a review
that genuinely died is still swept, exactly as before.

Not a v3.2.5 regression despite arriving right after it — the gap was present in 3.2.3, 3.2.4 and
3.2.5 alike.

## v3.2.5

**A review round now has a price you can see before the commit that buys it — and a write that would have vanished with a disposable subagent worktree is refused instead of silently lost.**

**v3.2.4 shipped the fix for the over-running review loop, and a consuming repo on v3.2.4 read those carriers and ran six rounds anyway.** That is the datum this release answers, and the answer is not more prose. **`prawduct-hook cost-of-commit`** is the first mechanism that says whether a commit buys a Critic round *before* you make it, rather than diagnosing it afterwards — and it asks `coverage_algebra.is_judgeable_path`, the same predicate the gate charges on, so the two cannot disagree. It prints and advises; it gates nothing, and no caller is required to consult it.

**The price is derived, never quoted.** `telemetry.round_price` reads your own ledger at call time with a sample floor, so the figure is yours rather than a number someone typed into a document — and it states that `duration_seconds` is a reviewer self-estimate, so it is not defended as measured. The `uncovered:` gate message now leads with **which round this is** (`coverage.count_branch_rounds`), so round five stops reading like round one; rounds are attributed by commit lineage, which undercounts at the merge-base by documented choice. And the fix/accept/file trio gains the option it never named: **the ride-along** — carrying a small fix into the next chunk's commit costs nothing extra. There is also a new leg at the **PR-review** layer, which previously carried no such carrier at all: the reviewer is now told, above every finding-producing section, that its own non-blocking findings cost the builder a delta round.

**This scope's own review caught it committing its own failure mode, three ways.** `cost-of-commit` priced a *directory* argument `free` when git could not be read — a builder holding an `index.lock` was told the commit was free — so the "unknown, never free" asymmetry three docstrings claimed was true of the path form only; both forms now degrade to `unknown` and carry the reason. The no-hardcoded-duration guard matched *line shapes*, so it saw `print(...)` and nothing else, and let through exactly the `return`-statement shapes the new code uses; it walks the AST now. Two seconds-to-minutes renderers shipped in one bundle and only one handled the sub-minute case, so the surface that literally states the price could say "about 0 min". And the protocol edited in the last chunk still charged a non-blocking fix "a full Critic round", contradicting the three other carriers that quote the delta pass — a reviewer who believes each NOTE costs a cumulative files *fewer* findings than it should.

**If you follow prawduct's own advice to run parallel chunks in isolated worktrees, your governance writes may have been silently discarded.** `methodology/building.md` recommends `isolation: "worktree"`, which puts a subagent in a worktree forked from HEAD **of which only the code commit is merged back**. prawduct had no representation of that: `resolve_project_dir` followed the session in and governed the worktree as an ordinary peer checkout, so an agent obeying prawduct's own rule — *file it via `/prawduct:backlog`* — produced a write that died at the merge and was told it had succeeded. Reported from a product repo (#594). `gitstate.is_ephemeral_worktree` is the missing predicate, a pre-dispatch guard refuses the write rather than losing it, evidence facts now carry visible worktree provenance, and the delegation guidance states the snapshot and the shared index.

**Relatedly: `.critic-findings.json` survived every dispatch carrying nothing that marked it stale**, and the fix initially reached the direct reader but not the one it was written for. The session briefing's summariser reads the same file and rebuilds the section field by field, so it dropped all three supersession keys and presented a superseded review's counts and next action as current — to the cross-session builder, who by that code's own comment is *definitionally the one who lost the reviewer's report*, and so exactly the reader who cannot check a review id they never saw. The notice now leads the section, ahead of the summary it qualifies. A new **Backlog filing** norm ships alongside: a strong bias to fix rather than file, with a new backlog item justified only when a finding is both orthogonal to the current work and medium or larger.

**Also:** the release-verification workflow added in v3.2.4 could not run until a promotion carried it to the default branch, so its acceptance could only be met by shipping it. It has now run three ways, and that residual is discharged. Repo-local to prawduct; nothing consumer-facing depends on it.

**No gate semantics change for consuming repos, no persisted state formats change, and no migration is required.** The one behaviour that can turn a previously-succeeding call into a failure is the ephemeral-worktree refusal — and on exactly that path the prior behaviour was silent data loss, so a refusal costs a write that would have been lost anyway.

## v3.2.4

**The Critic review loop now tells you when it is over — and the governance checks that had gone silently dark now say so instead.** A consuming repo running v3.2.3 spent **ten Critic rounds on one branch**, rounds five onward fixing warnings that gated nothing. v3.2.3 already said the right thing about when a review ends — in `building.md` and `review-cycle.md`, both of which that session never opened, because the branch had no build plan and so the builder never entered the cycle that would have made it read either. Every carrier was a **pull** carrier; the one runtime carrier appeared in seven reviewer contexts and zero builder contexts. Three carriers now **push** instead. `.critic-findings.json` gains a code-computed `next_action` in the file the builder opens by contract — *zero blocking: the review is over, these gate nothing, here is the `disposition --accept` command with this review's id already in it*. `critic-consolidate` prints the same line as `NEXT-ACTION:`, and both protocol files order the reviewer to relay it verbatim as the last line of their report — which is what closes the single-pass hole, since the reviewer is the one running the command and otherwise its output reaches nobody. And the cumulative gate now **diagnoses fix churn**: when everything that changed since the last review sits in files that review's own findings named, and it left nothing blocking, the gate says so and names `disposition` rather than offering a generic "review again". The discriminator is always what moved the tree, never a round counter — a post-merge round that a counter would call waste is not waste, because the merge brought unreviewed lines in.

**Two narrower supply-side fixes ship with it.** `verify-resolutions` exists to answer one question — were the named findings resolved? — and it was also walking the fix delta at full severity, handing back WARNING/NOTE findings that are definitionally round N+2's inventory. New findings in that mode are now **BLOCKING-only**; anything lesser is reported as an OBSERVATION in prose, where it informs without becoming work. Five classes stay blocking regardless (a weakened or deleted test, a dropped requirement, changed behavior with no test, security in changed code, fix-by-fudging) — and the directive now says which of those it is *citing* and which it is *escalating*, because the change's own review proved the original "these are already BLOCKING-rated" claim false for two of the five. A safety argument resting on a false claim is not a safety argument. Separately, a finding whose only subject is an inert count is capped at NOTE, and `numeric counts` was removed from the Goal 1 target list — leaving it there made the count finding an *instruction* rather than an accident.

**If you write `**Why:**` instead of `Why:`, four norm signals have been silently dark in your repo.** All five emphasis forms of `Why` / `Status` / `Rulings` / `Retroactivity` now count. The same pass settled what a `## Direction` norm entry *is*, mechanically: **field-bearing**, not Why-bearing. A failing test forced that correction and the fixture was not edited to accommodate the code — a Why-only definition makes doctor Health Check #10 vacuous by construction, since the whyless entries it exists to flag would stop being entries at all.

**A `## Direction` heading is not a norm registry, and its absence is not health.** Field-reported from an unrelated product's onboarding, where the session walked into both halves in sequence — the second while fixing the first. A heading with nothing under it certified as a ratified registry, so a repo whose only `## Direction` section was a prioritised list of undone work would have had doctor check #10 reporting findings against that roadmap indefinitely. And the *absence* of a heading permanently silenced the norm-health sweep for any product that homes its norms in the preferences Enforcement table — a legitimate homing that got no reminder at all, ever, with no signal that it was missing.

**The fix above reaches new onboards only, so this release also ships the repair for everyone else.** `init_product` copies a template only into a destination that does not exist, so **every already-onboarded repo** still carries the two illustrative rows the norm-index template used to ship with — still reads as having a ratified norm registry, and is still nudged about a sweep it owes nothing to. `prawduct-hook norm-index-scaffold` detects them and doctor **Health Check #14** offers to remove them: reported, never applied unasked. Detection is exact-match against the rows prawduct actually shipped rather than a guess at what a placeholder looks like, so a scaffold row you have since edited is yours and is left alone.

**A `verify-resolutions` review could persist its resolutions against a tree in which none of the fixes exist.** "Has a commit landed since the prior review?" was answered by tree inequality alone — and that question has two answers that look identical and mean opposite things. The second (the prior review vouched for a **dirty** tree, and nothing has been committed since) is not an edge case: it is the ordinary shape of a `chunk`-mode review, measured at **136 of 402 review facts in one clone's store, roughly a third**. Read as a committed delta the interval inverts: `files_changed` describes the chunk being deleted rather than its content, record-lint grades pre-fix content and reports findings already discharged on disk, and — the load-bearing one — the resolution facts, which lift BLOCKING findings, land against the tree from before the fixes. Unsound, not merely noisy. The repair changes behaviour **only** when the working tree is dirty, and adds, removes and retypes no fact-schema field.

**Two runtime assumptions that held only on the machine they were written on.** `atomic_write_text` wrote at the *locale* encoding while every reader opens utf-8 — latent because the early callers write ASCII JSON, and `.session-handoff.md` is not one of those and routinely carries em-dashes; on a non-UTF-8 locale the round trip was lossy and non-ASCII raised at the write. And `audit-learnings`' sentinel runner spawned a bare `python3`, which under any virtualenv is a different interpreter from the one running the audit — so every sentinel reported failing. That one is worse than a noisy diagnostic: the audit decides which learnings are *structurally enforced*, so a false-failing sentinel argues for retiring a rule that is in fact still enforced.

**If you keep a prawduct checkout alongside the installed plugin, your reviews may not have been recorded.** Inside a framework checkout, a bare `prawduct-hook` on `$PATH` resolves to whatever plugin the environment installed — in the observed instance, a sibling worktree's checkout. `critic-begin` ran that foreign binary and wrote **no** kernel-v3 manifest: no error, no manifest, and the `SubagentStop` consolidation no-opped the same way, leaving reviews unpersisted. A governance write that reports nothing while doing nothing. The guard keys on **binary identity**, not version equality — deliberately, because a checkout is routinely ahead of its own manifest between releases, so a version comparison would have passed the very skew it was written to catch. Posture follows what the command produces: an agent-invoked governance write refuses and names the binary to run; a harness-invoked hook takes a loud stderr note and proceeds, because a refusal a hook cannot act on would break SessionStart in every framework checkout. **This release is when that fix goes live** — a guard shipped inside the binary cannot protect an invocation of a binary that predates it.

**New: `prawduct-hook check-released vX.Y.Z` verifies a release from the outside.** Every version file present in the tag's tree agrees with it — read at the tag's own tree, never your checkout — the tag is contained in `origin/main`, and a GitHub Release exists. Run it against any release before this one and it fails, because a pushed tag lands on `/tags` and prawduct's Releases page stayed empty for every one of them. That is the defect reported as "no tag on GitHub", and nothing in the release process could see it: every check was a git command run by the person doing the release, so nothing ever asked what a *consumer* receives. **Three outcomes, not two** — exit 0 verified, 1 a check failed, **3 nothing failed but a check could not run** (no `gh`, no `origin/main`). Folding 3 into *passed* is how it first shipped in review, and it would have gone green over an empty Releases page. The command is operator-invoked and gates nothing.

**Your product declares which files carry its version.** `check-released` initially applied prawduct's own layout to every governed product, so a product using setuptools-scm, or carrying a tooling-only `pyproject.toml`, was graded against a layout it never claimed and told `not-released`. Set `release_version_files:` in `.prawduct/project-state.yaml` — path, format, and the **key path** where the version lives. **The posture splits on provenance:** a *declared* file that is absent, or present without its declared key, is a real defect and reaches `failed` — you said you ship that file. Undeclared, the built-in list is a **guess**, so it may only reach `ok` or `unverifiable`, never `failed`; a disagreement found through the guess is still reported in full, with the one edit that would make it a failure named. The declaration is read from the tag's tree, so reorganising your layout cannot retroactively fail an old release, and a release cut before the key existed grades through the fallback. Two further false reds closed: `git rev-parse` exits 128 for both "no such tag" and "not a git repository", and every non-zero was read as the first — so the check produced a confident `not-released` about a release it had never assessed, from a directory that could not have looked at one. TOML reading now delegates to stdlib `tomllib`, which costs an honest `unverifiable` on Python 3.10 and **deletes** the hand-rolled parser rather than teaching it about tables.

**Also:** prawduct had no `.github/` of any kind, so every release it ever cut shipped on a suite that ran when a human chose to run it. There is now CI on every push and pull request across a 3.10-and-3.14 matrix — the declared floor and current — plus a tag-triggered job that runs `check-released`. The first CI run was red on three latent defects that no local run could have shown, none of them in the feature. **CI verifies a release; it never publishes one** — an owner ruling, pinned by a guard test, because publishing notifies watchers, is not cleanly retractable, and a tag-push trigger has no human present when it fires. No gate semantics change for consuming repos, no persisted state formats change, and no migration is required.

## v3.2.3

**Learnings now fire where the mistake gets made rather than waiting in a file to be read — and every turn ends by telling you where things stand.** A corpus of 159 learnings was not changing behaviour, and the diagnosis was *delivery*, not authoring: the rule that would have caught four false claims in a consuming repo was already there, already general, already well-worded. A rule read at session start competes with the whole rest of the context by the time the claim gets written. So two rules moved out of storage and into the code path that runs at the moment they apply — *green is evidence only about what could have made it red* now prints at `test-evidence record` when the record shows judged code changed, and *a resolution is a claim about the tree* prints at `critic-begin --mode verify-resolutions`. **A limitation that was real when this was drafted and is closed in the same release:** the first directive was gated on Python-symbol matching, so it did not fire in a Swift, Go, Rust, C# or TypeScript product. It now triggers on any changed file that needs review coverage — see *"One of the two learnings this release moved into the code path was firing only in Python products"* below.

**`audit-learnings` gained `superseded-by=`.** Retiring a rule because a broader one replaced it is what every consolidation is, and it was previously an unauditable hand-edit — which is a large part of how a corpus reaches 159 rules with near-duplicate families in it, since adding is cheap and merging is not. The retired entry's historical copy names its replacement, so a reader who remembers the old rule finds a forwarding address rather than a hole. It fails closed on every ambiguity: unresolvable, ambiguous, self-referential and empty pointers all error rather than retire. Prawduct's own corpus went **159 → 149** using it, with every retired rule's distinguishing instance preserved in its successor.

**Agents now close a turn with a fixed three-part block — `STATE`, `NEXT`, `CLEAR`.** Both reports behind this came from consuming repos, and neither was about a gate being wrong. A correct "safe to `/clear`" sentence sitting in the middle of a long closing summary is a signal not sent, because someone returning to a wall of text reads the bottom and nothing else. The larger half: after a 30–120 minute build your question is not *may I clear?* — it is *did it work, what happens next, and am I the blocker?* You should notice this at the end of every work cycle.

**Two new `## Direction` norms.** *Goals and verification bind; prescribed method is advice* — where a governing artifact prescribes **how**, that is the author's guess made before the code was read, and a builder who finds a better route takes it and records why (verification structure is carved out and still binds). *Every fact has one home; every other mention is a reference to it* — reframing the review question from "do these agree?" to "why are there two?".

**If you are about to migrate a backlog to GitHub Issues, read this one.** Prawduct migrated its own — **371 items, 0 stranded, 0 collisions** — which is the first time the path ran at real scale, and it surfaced a defect in the instructions rather than the code: the scrub runbook told you to apply post-import dispositions **before** running `verify-migration`, and that ordering turns owner-approved merges into a false failure, because the gate compares each item against its *source* status. Step ordering is corrected. The service remains **opt-in** — your backlog does not migrate on upgrade, and nothing changes until you run the migration yourself. The completeness gate also now catches an item that arrived at the wrong status, which it previously could not see.

**Prawduct now tells *you* when it updated itself — and surfaces advisories that need a decision.** Everything prawduct said about itself, it said to stdout, which this project's own norm defines as the *agent's* channel; the version banner then marked itself shown, so it never rendered again. An auto-updating install announced each release exactly once, to nobody who could act on it. There is now a relay directive at each emission site: the version-delta block asks the agent to tell you what changed, and the advisory block does the same for anything at `warn` or `urgent`. Both fire only when there is news — `info` advisories are deliberately excluded, because a channel that nags every session is one you learn to skip, and that would cost the `warn` case the attention it exists for.

**`test-evidence record` counts test cases instead of trusting a reporter's `tests=` attribute** (thanks to **@Jason-Vaughan** for the report and the fix). That attribute means different things to different runners — all descendants under Ant-style conventions, direct children under `node:test` — so no way of summing it is right for both, and a suite with nested describes could record 6 real tests as 2, with the error growing as nesting deepened. Counting leaf `<testcase>` elements is correct under both with no reporter detection. Top-level suites that report only attributes and no cases still fall back to those attributes, decided **per suite** rather than once per run, so a summary-only environment ingested alongside a normal one keeps its failures rather than silently contributing zero. (A summary-only suite *nested inside* a leaf-bearing one is a known exception and still contributes zero.)

**If the Critic looked dead to you, it probably wasn't.** "The Critic died" reports traced to three compounding false signals rather than a dead review. The liveness marker carried a `pid` belonging to the short-lived dispatch process, dead within milliseconds of every *healthy* review; no reviewer wrote anything observable until it finished, so "zero partials" eight minutes in read as "nobody started"; and a re-dispatch overwrote the first review's manifest, erasing the evidence that it had ever run. One fix per signal: the `pid` field is gone, each reviewer writes a marker when it starts, and a re-dispatch archives rather than clobbers. If you have been re-dispatching reviews that were still running, this is why — and it was costing you double.

**The Critic now blocks on cross-component message contracts.** In chunk mode, Goal 1 covers whether the signal one component sends is the signal another awaits. The filing case was a two-process app whose consumer waited on a terminal message the producer's success path never sent: types matched, and unit and IPC tests were green because the fixtures synthesized the very signal the real producer omitted, so in production the flow hung forever. It was caught only because someone hand-wrote a pointed reviewer prompt — making detection depend on the prompt rather than the protocol. Two smaller Critic fixes ship with it: `discovery.md` now asks where your risk surfaces are (declaring nothing silently kept you at the floor and never told you it could be otherwise), and a BLOCKING finding that is *superseded* rather than resolved no longer strands its own advice.

**Migrating a backlog now verifies before it disposes of anything.** `verify-migration` compared each migrated item against the *source markdown*, so an owner-approved fold of a duplicate registered as a failed migration — and the scrub runbook told you to apply those dispositions first. Both were defects prawduct found by running its own cutover and had fixed only for itself while the fleet still shipped them. Alongside: `regen-views` always writes now, so one bad scope no longer freezes every view; a review records which plan it is of and which tree it read; and an issue with no prawduct provenance is no longer dropped from `counts` entirely, which had made the items least likely to be looked at the only ones the tooling could not see.

**A drifted install reference now surfaces itself at session start.** A repo can commit an install reference pinned to a fixed release ref, or with `autoUpdate: false`, or with `enabledPlugins` switched off entirely — and nothing said so. `/prawduct:doctor` asserts the contract, but you have to run it, and nobody health-checks a repo that appears to be working. An advisory now fires on the drift and clears itself when the committed file is fixed. **What the drift costs is narrower than it sounds:** the committed reference and your machine's `known_marketplaces.json` are decoupled, so a repo pinned at an old ref still runs the current plugin on a machine that is already configured. The drift is inert for you and strands the *next clone* — which is exactly why nobody notices it.

**If your repo was onboarded before this release, `/prawduct:learnings` has been pointing you at something you never received.** The skill points at a descent-obligation marker in your own `learnings.md` rather than restating it — one fact, one home. But only `init-product` ever wrote that marker, and only into a `learnings.md` that did not exist yet, so **every already-onboarded repo lacks it** and nothing backfilled it: not onboarding, not migrating, not a re-run. The defect was closed for the empty set and open for the real one, and it survived because this framework's own repo has the marker — its state stood in for the propagated contract until someone looked elsewhere. `/prawduct:doctor` now detects it as **Health Check #13** and offers the repair, printing the exact block at the exact line and writing only on your yes. A marker that is present but appended to the *end* of the file is reported as **misplaced rather than moved for you** — inserting a block the framework already ships to new products is bounded and reviewable; relocating a line you wrote is not. **Alongside, two smaller surfaces stopped answering confidently for a state you were not in:** `/prawduct:doctor`'s coverage report graded a freshly-onboarded repo as *degraded* while the nudge it claims to mirror correctly stayed silent — it was re-deriving a layer instead of asking the probe, and a repo with no source and no `docs/` is owed nothing yet. It now calls the probe, and both output modes distinguish "nothing is owed yet" from "everything is satisfied," which had previously printed as the same clean bill (`--json` gains an additive `discovery_expected` key). And a link in shipped documentation resolved to a path that exists in no consumer's plugin cache; a new check now verifies that intra-repo path references actually resolve, keyed on the *forms* that mean "go read this" — tool grants, command position, markdown links — rather than on anything that merely looks like a path, so prose discussing a filename is not a false positive.

**One of the two learnings this release moved into the code path was firing only in Python products.** *Green is evidence only about what could have made it red* triggered off a signal that a helper populates by grepping **Python** symbols, so in a Swift, Go, Rust, C# or TypeScript product that signal is empty on every run and the directive was **silently dark** — which is the one failure a directive cannot report about itself, and a direct violation of this framework's own standing rule that it must never be specific to Python. It now also triggers on any changed file that needs review coverage, reusing the single predicate the review machinery already uses to answer that question. That choice matters more than it looks: matching a list of source extensions would have reproduced the same defect one language at a time, whereas the predicate classifies by *exclusion* — framework metadata and unprotected prose are out, everything else is in — so a language nobody has heard of fires the directive rather than going dark. The widening is a strict addition to the old trigger, not a replacement, so nothing that fired before stops firing.

## v3.2.2

**Review depth is now a risk question rather than a file count — and no repo is reviewed less than before.** The Critic's coordinator (three parallel reviewers) used to fire at 5+ changed files. It now fires when a change touches a **risk surface**, or changes 12+ *judgeable* files. If you have declared nothing, nothing gets cheaper: prawduct's own defaults still escalate, and beneath them the old 5-file rule stands untouched. **What can change without you asking is depth going UP** — a two-file change touching your `skills/`, a `*hook*` script, or a contract path you listed in `boundary-patterns.md` now draws three reviewers instead of one. Declaring `risk_surfaces:` in `project-state.yaml` is how you tell prawduct where your own risk lives; the template shows the shape. (1) **API design (produced) is now a first-class cross-cutting concern.** When a product exposes a programmatic surface — a network service, a library/SDK, an on-device interface, or a CLI (not just HTTP/REST) — its versioning, deprecation, and error-model decisions are surfaced in discovery, captured as decision records (`design_decisions.api_versioning_approach` + `api_error_model_approach`), guided in planning/building, and gated by the Critic: a chunk declaring `**Exposed API:** <name>` needs a recorded versioning + error-model decision (or a dated deferral) or the Critic WARNs. Retroactive detection arrives via a new `api-versioning` post-sync advisory probe, a `/prawduct:doctor` health check (#9), and a `/prawduct:janitor` "API Design & Versioning Hygiene" theme; a new transport-neutral `api-contract.md` template documents the contract. The stance is **force the decision, don't mandate the answer** — "none — internal-only" is a valid recorded decision, and a deferral must be dated with a revisit trigger. (2) **The `/prawduct:doctor` vs `/prawduct:janitor` boundary is now documented** (`docs/doctor-vs-janitor.md`): doctor checks whether prawduct governance/install is correctly set up (it reports and guides); janitor maintains the product's own codebase craft (it surveys and fixes). A placement rule says which skill a new concern belongs to — and the one genuinely-shared concern (API versioning) and the previously-unlinked gitignore split are now cross-referenced in both skills. No breaking changes for consuming repos.

## v2.1.8
A batch release — worktree support, hot-path speedups, hook/test-evidence robustness, and three review-governance refinements. (1) **Governance composes with git worktrees.** New `resolve_project_dir` makes the hooks follow the session into its worktree (`git rev-parse --show-toplevel`, preferred over the `CLAUDE_PROJECT_DIR` launch-dir pin **only** when cwd is a worktree of the same repo — shared `--git-common-dir` guard, fails open on any git error), so worktree-written reflection / Critic / cumulative records are no longer invisible to the Stop and cumulative-Critic gates — worktree work cycles run on-protocol instead of falling back to review-in-primary / raw `gh`. (2) **Faster session start/stop.** The `clear`/`stop` hot paths batch their git subprocess fan-out — `_untrack_session_files` collapses 15+N calls into two, the status-family probes share one `git status --porcelain` capture, and `_has_product_code` prunes `node_modules`/`.git` at the directory level — dropping `clear` from 25 to 11 git subprocesses (matters most on large monorepos). (3) **Test-evidence `record` is more honest.** The misleading dead-read `git_sha` is retired, `record --from-junit` ingests an existing JUnit run instead of re-running the suite, and zero test discovery now fails loud instead of writing empty coverage halves silently. (4) **Hook-CLI robustness bundle** — flag-only subcommands reject unknown args (exit 2) instead of swallowing them, a non-executable `test_command` exits cleanly instead of tracebacking, `stamp-merged` tolerates an `origin/`-prefixed base branch, two more state writes go atomic, and `verify-chunk-refs` stops crying wolf on template/URL tokens and intentionally-gitignored managed paths. (5) **Review-governance refinements:** the PR reviewer's Learnings/Backlog cross-checks are scoped to the consumed Critic record (no duplicate scanning across two agents), `review-stats` folds model-id aliases to one family per model so the model dimension isn't fragmented, and the Critic review-protocol token ceiling is relieved 3120 → 3350. No breaking changes for consuming repos.

## v2.1.7
Backlog `closed-by:` provenance is now consistent across the skill contract and the item template. The field records what shipped an item, but its guidance had drifted: v2.1.6's "archive the item in its closing PR" rule told builders to use `closed-by=<scope>`, yet the field's own definition still read `<chunk-id|tag>` and never said what to use for **non-chunk** work — so a standalone refactor/chore committed directly fell through to a bare commit SHA, which a commit can't contain and a `git commit --amend` rewrites into a dangling ref, forcing an extra "fix closed-by" follow-up commit (the exact churn v2.1.6 set out to remove). All four contract sites — the when-to-mark-shipped rule, the item-shape definition, the `update` step, and the template legend — now state one rule: `closed-by` is a handle that exists *before* the commit recording it (a chunk id, the branch/feature **scope** name, or a release tag), never a bare commit SHA or a PR number that isn't assigned until the PR opens; for non-chunk work, use the branch/scope name. The `update` step now warns on a bare SHA and substitutes the scope name. Doc-only — `closed-by` is human-readable provenance (nothing parses it), so no behavior change for consuming repos beyond clearer, drift-free guidance.

Upstream bug-reporting channel plus on-branch backlog archiving — two shipped features. ## v2.1.5
Reviewer-model dispatch now survives a model being withdrawn. The Critic and PR reviewer previously pinned specific model aliases (`fable` for escalated/governance-critical reviews, `opus` otherwise) as literal values in their dispatch prose — so when a model is temporarily pulled from the harness (as Fable was), an escalate-tier review would break, or worse, silently fall through to whatever model the session happens to be running (the wrong tier — a withdrawn `model:` override resolves to the inherited/session model rather than erroring). All three dispatch surfaces now express **ordered tier chains** with an explicit fallback rule: dispatch on the first model the harness lists as valid, and if the preferred tier is withdrawn/unrecognized or errors on dispatch, fall back to the next (`escalate`: fable→opus; `standard`: opus→sonnet). Prose-only — no behavior change for consuming repos beyond more resilient review dispatch when the model lineup changes.

## v2.1.3
Gate hardening — three independent fixes from the 2026-06-09/10 framework audits. (1) **The session Critic-freshness gate is now one shared function.** The mtime-vs-session-start freshness check had been duplicated between the stop hook and the session-start advisory, and the copies had diverged: the advisory was missing the verify-resolutions scope check, so it could report a stale, scope-exceeded record as satisfying. Both consumers now delegate to `gates.critic_findings_satisfy_session_gate`; the advisory gains the scope check, an empty `.session-start` marker now fails closed, and parity tests guard against re-divergence. (2) **`.prawduct` state writes are atomic.** A shared `atomic_write_text` (tmp sibling + `os.replace`) closes the torn-write window on `.session-start`, `.session-git-baseline`, `.session-handoff.md`, and `.advisories.json` for concurrent sessions; `prawduct-hook clear` now survives a read-only `.prawduct` (best-effort with consequence-naming notes instead of a traceback). (3) **`/prawduct:critic <mode>` honors an explicit mode argument.** The skill forwarded nothing because it self-parsed `$ARGUMENTS`, which the harness never substitutes for Skill-tool-invoked fork skills (claude-code#34164); it now forwards invocation args verbatim to `prawduct-hook infer-critic-mode`, which owns the full precedence (explicit > plan-override > inference).

## v2.1.2
Three fixes from the 2026-06-10 whole-framework audit — two gate-soundness holes and the biggest context-economy cost. (1) **The PR gate's ledger fallback now requires same-session freshness.** The fallback (which rescues a cumulative review after a later chunk review overwrites the findings file) accepted the newest qualifying ledger event with no recency bound, so a days-old cumulative from prior work could vouch for a new bundle whenever only `.md` changed since. It now requires the event's `ts >= .session-start` and fails closed — re-run `/prawduct:critic cumulative` this session if the gate tells you the only candidate predates it. (2) **A mis-set `active_build_plan` pointer can no longer silently blind governance.** The natural repo-relative spelling (`.prawduct/artifacts/…`) now resolves correctly in both resolvers, a pointer to a genuinely missing file gets a loud session-briefing warning naming the consequence (Critic gate, mode inference, and chunk-ref checks see no active plan), and the field is finally documented in the project-state template. (3) **`learnings.md` lookups got ~60% cheaper.** The framework's own learnings file had grown to ~80KB of narrative; entries are compacted back to their When-X-do-Y-because-Z rules (narrative preserved verbatim in `learnings-detail.md` under the same heading), and the session briefing now nudges any repo whose learnings.md exceeds 40KB. Bonus fix found on the way: the briefing's "Learnings (N rules)" line counted only bullet-format rules and silently showed nothing on entry-format files — it now counts `## ` entries.

## v2.1.1
The change-log lifecycle stops dropping work silently. Three failures observed across recent releases are closed: (1) **the statusless→merged stamp is now mechanical** — new `prawduct-hook stamp-merged` runs in the `/prawduct:pr` merge flow (convergent and idempotent, refuses to run anywhere but the integration branch), so entries no longer reach release-prep statusless and get skipped by a literal reading of the release checklist (v2.0.14 shipped 8 of 10 entries that way); the release checklist itself now says flip **every unreleased entry, statusless OR merged**. (2) **A code-changing branch can no longer merge without a change-log entry** — `prawduct-hook check-change-log-entry` gates `/prawduct:pr create`: any non-`.md` diff must ADD an entry header (doc-only branches exempt; fails closed on un-evaluable git state). (3) **Multiple tag lines per entry are unioned, not half-parsed** — `parse_change_log` previously honored only the first `<!-- prawduct: ... -->` line and silently dropped the rest (a `chunks=` tag nearly shipped unflipped at v2.1.0); now chunks union across lines and `regen-views` warns so you merge them. Plus: scope→plan validation now also covers statusless entries, catching a bad `scope=` before release instead of at it.

## v2.1.0
A review-governance release: reviews get **cheaper, risk-proportional, and observable** — plus hot-path session fixes. (1) **The re-review treadmill is gone (CRT-4J8W).** Fixing anything after a cumulative review used to re-stale the PR gate and cost a FULL bundle re-review (~4-10 min); now the gate accepts a **cumulative + verify-resolutions chain** — fix, commit, run `/prawduct:critic verify-resolutions`, and a 1-2 minute delta review extends the cumulative's vouching to HEAD (fail-closed on any scope gap). (2) **One full review per plan, not two:** a `Type: cumulative-final` last chunk lets the PR-gating cumulative BE the final review, and the **PR reviewer now consumes-and-audits the Critic record** (≥2 adversarial spot-checks) instead of re-deriving code soundness over the same diff. (3) **Reviews scale to risk:** reviewers default to opus (~4x faster per a captured A/B/C experiment), and `classify-diff-risk` escalates the model when the diff touches declared risk surfaces (gates, hooks, skills). (4) **Review work is now measurable:** an append-only governance ledger records every Critic/PR review (mode, model, duration, findings yield) and `prawduct-hook review-stats` aggregates cost/yield — proportionality tuning is evidence-driven now. (5) **Gate soundness for products:** the coverage gate only blocks on files it can actually judge (`changes_unjudged`), `test-evidence record` honors a declared `test_command:`/`tests_dirs:` (uv venvs, monorepos — no more wrapper scripts), build plans are tracked artifacts (the gitignore default + session untracking that broke multi-clone repos is retired and self-heals via `doctor`), and gate error messages teach the correct sequencing instead of leaving you to trial-and-error. (6) **Session hot-path fixes:** the version banner reads the real version again (a path-depth bug had it silently reporting "dev"), turn-end no longer runs a `gh pr list` network call on no-change sessions, git-quoted paths with spaces no longer break doc-only classification, and the work-model probe stops false-firing on acknowledgments/questions (common-English frequency floor + firing threshold). (7) **Less duplicated always-on context in the framework repo itself:** a slim session digest (~40% of full) when the governed repo is prawduct; product repos keep the full digest verbatim.

## v2.0.17
Two governance fixes that close review-gate holes. (1) **Your backlog now actually gets nudged to migrate.** After adopting a new prawduct version with an unstructured (legacy-format) backlog, you were supposed to see a session-start advisory pointing you to `/prawduct:backlog migrate` — but the probe that raises it (`legacy-backlog-format`) was never registered in the plugin runtime. It was the single production probe back in v1.7.0, got deleted with the file-sync engine, and the v0.3 backlog rework rebuilt only the *other* three probes, silently leaving the primary one out. It's restored: a backlog with more than five items none carrying a `[PFX-XXXX]` id now surfaces the migrate nudge, which clears itself once `backlog_format_version: 2` is recorded (what `/prawduct:backlog migrate` writes on completion). (2) **The PR-boundary "trivial" fast-path is retired.** `/prawduct:pr` had a fast-path that, based on the *fileset alone* (a change touching only existing files), would skip **both** the cumulative-Critic gate and the independent PR reviewer — so a substantial multi-chunk feature that only modified existing files could sail through with no review. Fileset-eligibility is a *necessary* but not *sufficient* signal of triviality, so the fast-path is gone; code PRs always get the full review now. The sound **doc-only** fast-path (an all-`.md` diff) and the per-chunk `Type: trivial` enforcement are unchanged.

## v2.0.16
Two follow-up fixes to the v2.0.15 backlog rework and the Critic. (1) **`/backlog migrate` now refreshes the schema legend, not just your items.** Adopting a new backlog field (v2.0.15's `stage:`/`refs:`/`accepted-by:`) backfilled your *items* but left the `backlog.md` header legend — authored once at onboarding — documenting the *old* schema, so a reader hit `stage: ready` with no key explaining it. `migrate` (and the triage method) now reconcile the legend to the current field set: **additive and non-destructive** (it fills in missing field docs and never touches a local extension like a `kind:` facet), idempotent, and it runs even when there are no legacy items. The optional-fields list in the skill that had omitted `stage:`/`refs:` is fixed too. (2) **The Critic picks the right mode on a feature branch again (CRT-7B4M).** On a `views_enabled` branch the build-plan Status checkboxes are a derived view that only flips at release, so they read all-unchecked during development — and `infer-critic-mode` was reading the *current* chunk from them, so it ran Chunk 01's mode on every chunk and could never detect the last chunk. It now derives chunk progress from git (the `Chunk <n>` commit subjects on the branch) when the checkboxes are an unflipped derived view, and degrades to the old behavior whenever the git signal doesn't apply — never worse than before.

## v2.0.15
The backlog gets a major rework — it now pulls its weight in multi-agent and lifecycle-aware workflows instead of sitting beside the work cycle. Five changes you'll feel: (1) **`accepted-by`** — a soft claim so a second agent or teammate doesn't pick up an item you're already on (`/prawduct:backlog pick`/`list` skip claimed items; it doesn't expire and isn't a hard lock — git is eventually-consistent — but it makes double-picks visible). (2) **`stage:`** — items now carry a lifecycle stage (`idea → research → requirements → design → ready`), and `pick` *routes* an early-stage or unstaged item to discovery/planning rather than letting you write code against an undocumented requirement (the Principle 6 hole the work-model feature started closing). (3) **Archive discipline** — "done" means the item moves to `## Archive`, never a strikethrough left inline (which silently cost context tokens every session); `/backlog migrate` now sweeps up existing strikeouts, and the janitor's new **Backlog Health** step surfaces stale/duplicate/unstaged items and proposes an archive split past ~200 entries. (4) **Stale-completion detection** — the Critic (C-B1–C-B4) and the PR reviewer (R-1/R-2) now flag backlog items your work appears to have resolved but left open, and dangling references — without ever inferring status (you still make the call). (5) **`/backlog import`** brings an existing `TODO.md`/`BACKLOG.md` into structured form, and three advisory probes nudge when an external backlog exists, the old section schema lingers, or a large backlog hasn't been groomed in 90 days. Under the hood: a real `lib/backlog.py` parser substrate (the count in your session briefing now derives from it), a `refs:` field linking items to their requirement/design docs, and `/backlog dedup`. Adopting is opt-in and additive — existing backlogs keep working untouched; run `/prawduct:backlog migrate` and the triage steps to bring one up to the new standard.

## v2.0.14
The independent Critic can no longer clobber the session it reviews. The Critic runs as a forked agent *directed* not to run executables, but the coordinator subagents it dispatches inherit the session's normal tool access — and in one incident a review subagent ran `prawduct-hook clear`, which is destructive: it archived the builder's in-progress reflection, reset the git baseline, and made fresh test evidence read "stale." Prawduct now enforces the real invariant — *an independent reviewer must never mutate the session it reviews* — at the mutation site: while a review is active (bracketed by new `critic-begin`/`critic-end` markers), a bare `prawduct-hook clear` refuses with an actionable override. The guard self-heals three ways (a 30-minute TTL, the next session-start sweep, and an explicit override) and fails *open* if the lib can't load, so it can never permanently block a session. Under the hood, this release also lands a large internal refactor (STH-9V4K): the monolithic governance hook was split into focused `lib/` modules — no change to how repos are governed, but a more maintainable, testable runtime. Two smaller fixes round it out: `/prawduct:pr` now redirects a `develop`→`main` release promotion to the documented release process instead of running feature-PR gates, and the build-plan chunk-reference check no longer trips on glob patterns written as prose.

## v2.0.13
Prawduct now catches *undocumented requirements* before they turn into code. Until now the framework guarded against requirement **loss** — it wouldn't let you silently drop one — but not requirement **absence**: you could describe a brand-new concept or domain model in a prompt and flow it straight into code with no requirement ever written down. A new deterministic check runs as you submit each prompt: it builds a lightweight vocabulary index from your governing artifacts (headings, bold terms, and an optional `vocabulary:` frontmatter list) and, when a prompt introduces salient terms no artifact covers, injects a quiet pre-turn nudge to locate or write the parent requirement first. It's fail-soft and only active in onboarded repos (gated on `.prawduct/`), and Principle 6 now states the rule both ways — never silently *drop* a requirement, and never silently *invent* one.

## v2.0.12
Turn Prawduct off in a repo with one command. Since the plugin installs for your whole machine, its commands and hooks load in every repo you open. The new **`/prawduct:repo-disable`** writes a per-repo `enabledPlugins` override that disables Prawduct here — `/prawduct:*` commands, hooks, and banner — either `committed` (`.claude/settings.json`, for everyone who clones the repo) or `local` (`.claude/settings.local.json`, auto-gitignored, just you). It preserves all your other settings and refuses to touch a malformed settings file. It takes effect after `/reload-plugins` or a restart. There's intentionally no re-enable command — once disabled, the plugin's own commands no longer load — so you re-enable by editing the file's `enabledPlugins` back to `"prawduct@prawduct": true` (the skill spells out the exact steps), or via Claude Code's native `/plugin` menu.

## v2.0.11
Prawduct now stays quiet in repos it doesn't govern.
