You are managing prawduct product-repo health under the **plugin** distribution model. Prawduct is installed as a Claude Code plugin (dev-time governance); a product commits only the install *reference* plus its own `.prawduct/` state — no framework files. Every flow operates on the consumer's own repo, plus the machine-level state prawduct's own install leaves behind (its install record and its plugin caches): there is no framework checkout to call back to.

This skill is for a repo that is **already onboarded**. To set up a new or existing repo, use **`/prawduct:onboard`** instead.

## Scope & boundary

`doctor` owns **prawduct governance/install conformance** — is *this repo* correctly set up and
governed (install reference, distribution, anchor, core state, discovery captured, gitignore
contract, recorded decisions), and is prawduct's own installation on this machine sound? It **reports and guides**; it does not fix the product's own code.
For the product's **own codebase craft** — code/docs/tests/dependency quality and currency — use
**`/prawduct:janitor`**. Full split, and the rule for where a new concern belongs: `docs/doctor-vs-janitor.md`.

## Context Detection

1. If an explicit target path was provided → `doctor` runs in the *current* product repo, not on a target path. If they meant to **set up** that path, send them to **`/prawduct:onboard <path>`**; if they meant to **health-check a different** repo, have them `cd` there and re-run. Either way, stop here.
2. Else if the current directory has `.prawduct/` (is a product repo) → **Health Check**, and route to Enable-Gate / Verify / Ratify-Norms on explicit request.
3. Else → ask the user what they want to do.

## Health Check Flow (current dir is a product repo)

Plugin-native — the *subject* of every check is the consumer's OWN `.prawduct/` and `.claude/`, read with Read / Glob, except where a check names the machine as its subject. **A check that could not run is degraded because ungraded:** when a command exits "could not run", reports `unknown` or `null`, or the file it grades is undecodable, say the check declined — never that it passed — because a check that could not run otherwise reads exactly like one that found nothing. Each check below names its could-not-run statuses; a check that says it never degrades the repo says instead what to report when it cannot run. Check:

1. **Install reference** — the consumer's `.claude/settings.json` matches the whole install contract. Run `prawduct-hook print-install-reference` and compare every leaf of the JSON it prints: that output is the contract, so do not grade from memory or from the plugin's source. (Shape only — illustrative, not the set: `enabledPlugins["prawduct@prawduct"]`, and `source` and `autoUpdate` under `extraKnownMarketplaces.prawduct`.) Missing or drifted → the next clone seeds from it and has no marketplace to resolve `claude plugin install prawduct@prawduct` against (Check #4 is where a clone learns the install is still theirs to run). The `install-reference` / `contract-drift` advisory routes here, so grade every field it can report.

    A non-zero exit means the plugin's own install reference could not be read — a broken plugin install, not a repo defect. Report the check **degraded because ungraded**, quote its stderr, and do not fall back to the illustrative fields above.
2. **Distribution recorded** — `project-state.yaml` has `distribution: plugin`. (Absent → a legacy file-sync hook may still be governing; recommend `/prawduct:migrate`.)
3. **No stale file-sync residue** — no committed `tools/product-hook`, `tools/lib/`, framework `.claude/skills/critic/`, or `.prawduct/sync-manifest.json`. (Present → migration is incomplete; recommend `/prawduct:migrate`.)
4. **Static governance anchor** — run `prawduct-hook reanchor` and relay its status. The marker's presence is not the check: the anchor is the only governance text a clone without the plugin loads, so what it says matters. Report **healthy** on `ok`, and **degraded** on every other status, each routing differently:
    - `stale` — the anchor is one *prawduct* shipped before one of the current text's load-bearing sentences — the plugin-absent notice, or the rule that review rigor is stage-keyed; the command's detail names which. Prawduct's to fix: offer the repair.
    - `stale-modified` — it lacks one of those sentences (the detail names which) and matches nothing prawduct shipped, so it has been edited here. **Yours to reword, not prawduct's to replace** — the repair declines it by design, and reporting it as repairable would be an offer that cannot be honoured.
    - `absent` — no anchor at all (a repo that never onboarded, or whose `CLAUDE.md` lost it). The repair inserts one.
    - `legacy-block` — the repo still carries the pre-2.0 `PRAWDUCT:BEGIN/END` block and has not cut over. Re-anchoring it would mean stripping that block and rewriting the prose around it, which is **`/prawduct:migrate`'s act** and takes its own approval; the repair declines it and routes there.
    - `unreadable` — `CLAUDE.md` is not decodable text; the command exits **1**. Degraded because ungraded.
    - `unwritable` — only from `--apply`: the file read fine and the **write** failed, so nothing changed. A separate status from `unreadable` on purpose — one status meaning both would send the owner to fix the wrong file.

    **The repair is offered, never applied for them:** the dry run prints the entire replacement, and the owner runs `prawduct-hook reanchor --apply` — this edits the product's own `CLAUDE.md`, so it takes an informed confirmation naming what changes. One confirmation covers the whole act; never walk them through it line by line. It swaps a known anchor for the current one and rewrites nothing else, line endings included.
5. **Core state present** — `.prawduct/` has `project-state.yaml`, `backlog.md`, `change-log.md`, and `artifacts/`, and the rules corpus is at `.claude/rules/learnings/` with a `core.md` in it. Missing core state: `prawduct-hook init-product` scaffolds it; a repo still holding the legacy learnings corpus runs `learnings-migrate` (the session-start directive names the steps). A corpus the briefing reports `OVER LIMIT` (rules over one line, bodies, or `core.md` over its cap): recommend compacting it outside this health check. `prawduct-hook learnings-compact --plan` writes the worksheet, the agent decides each rule, the owner approves any drops, and `--apply` writes it as one commit.
6. **Discovery captured** — if the repo shows product-definition work (source code, or markdown under `docs/`), `project-state.yaml` should have `classification` and `product_definition` filled, not template-default (`domain: null` / `vision: null`). Template-default state alongside real product work means discovery was skipped — the docs-first / brownfield onboarding gap the **DISCOVERY NOT CAPTURED** session-briefing nudge also flags. Recommend **`/prawduct:methodology discovery`** (reconciliation mode reads the existing docs/code and backfills `project-state.yaml`). A repo with no product work yet is fine — discovery comes when building starts.
7. **External backlog files** — if `TODO.md` / `BACKLOG.md` / `ROADMAP.md` / `IDEAS.md` exist in the repo root or `.github/` and aren't recorded in `backlog_external_imports`, report them and recommend **`/prawduct:backlog import <path>`** (don't auto-import — the user confirms). This is the explicit health-check surface for the same signal the `external-backlog-detected` session-start advisory raises ambiently; both resolve on `backlog_external_imports`.
8. **Gitignore contract** — `.gitignore` should carry the session-file entries and must NOT ignore retired entries (`.prawduct/artifacts/build-plan.md` — build plans are tracked artifacts; an ignored plan plus the tracked `active_build_plan:` pointer breaks every other clone). **Grade it with `prawduct-hook update-gitignore --dry-run`, always — never with the bare command.** The bare form *writes*, and this is a health check: an operator who ran a read-only report and got a modified working tree cannot tell which of its findings were true before it ran. The dry run answers the same three questions (`would un-ignore:`, `would ignore:`, and either `would update .gitignore` or `no changes needed`) and leaves the file byte-identical, so it is what the check is graded on. Report **degraded** when it says it would change anything, relaying each line. **Then offer the repair** — `prawduct-hook update-gitignore`, which is the same command without the flag — and say what it will do before running it: it edits a tracked file, so the operator gets the preview and says yes. After an apply, relay any `unignored:` paths and advise `git add` on those that exist on disk. This checks the prawduct *contract* only; general gitignore hygiene (build artifacts, editor files, secrets) is the janitor's Version Control Hygiene theme (`docs/doctor-vs-janitor.md`).
9. **API versioning decision** — if the repo exposes an API (`classification.structural.exposes_programmatic_interface: true`, or a Glob-able `openapi`/`swagger` spec or `*.proto` file in the tree — the `api-versioning` advisory additionally scans source for web-framework imports, which this read/Glob-only check does not) but no versioning decision is recorded (`api_versioning_decided` unset *and* `design_decisions.api_versioning_approach` null), report **degraded** and recommend recording the decision — a versioning + deprecation scheme, or an explicit dated deferral with a revisit trigger (`/prawduct:methodology discovery` / `/prawduct:methodology planning` capture it; `templates/api-contract.md` details it). Read-and-guide only — present the one-line `project-state.yaml` edit, don't auto-edit (consistent with #6/#7 and Enable-Gate). This is the on-demand health-check surface for the same signal the `api-versioning` session-start advisory raises ambiently; both resolve on a recorded decision. "API" is any programmatic surface others call (network service, library/SDK, on-device/platform, CLI) — an internal-only surface records "none — internal-only" and is healthy.
10. **Norm-registry integrity** — when the product has ratified norms (`## Direction` sections in `.prawduct/artifacts/*.md`, or norm rows in the preferences Enforcement table — `/prawduct:methodology norms`), check each: every Direction entry carries a **Why** (citing backlog ids *literally* where the rationale rests on tracked work — the citation is what makes decay mechanically detectable); every `Status: in-transition` entry names a live tracking backlog item; every Enforcement row names a mechanism that actually exists (a named-but-never-built mechanism is the aspirational failure with extra steps); pointer rows point at a Direction section that exists; and `project-state.yaml` classification matches observable code signals (e.g. `has_multiple_party_types: false` alongside a login/auth surface suggests a characteristic flipped without the recorded decision — `/prawduct:methodology norms` § Ambient norms). A product with **no** ratified norms is not a finding here — that is the Ratification Flow's cue (the `norm-registry-unratified` advisory raises it ambiently). Report degraded with the specific entries; the fixes are owner decisions (backfill the why, re-point the row, amend the norm), never auto-edits.
11. **Strategy-class artifact coverage** — run `prawduct-hook coverage-status` and relay the chain it reports; it reads the same expectation table as the `strategy-artifact-missing` / discovery-not-captured advisories. The layers stage the fixes. **Layer 0**: structural characteristics are not recorded → `/prawduct:methodology discovery`. **Layer 1**: expected strategy-class artifacts are missing → author each via `/prawduct:methodology planning`, or stub them with `prawduct-hook coverage-scaffold --apply`. **Layer 2**: the artifacts exist but the norms are unratified → the Norm Ratification Flow. Layers 0 and 1 are mutually exclusive; layer 2 can be active beside layer 1, and the command names the highest-priority active layer as the primary fix. Report **degraded** when any layer is active and **healthy** when none is, with one exception: when `discovery_expected` is false (`--json`; the human line says so), say "the coverage chain has not engaged yet" rather than calling the repo healthy. `discovery_expected: null` (or `structural_recorded: null`) means the staging check could not run: degraded because ungraded. The scan reads source by suffix, so a repo in an unlisted language reads as unstarted. A `(not relevant — <reason>)` stub counts as coverage, and whether a stubbed decision is sound is the Critic's call. Offer `coverage-scaffold` (dry run first; `--apply` writes neutral stubs and never overwrites); the owner runs `--apply` and fills each stub.
12. **Backlog label taxonomy (post-cutover only)** — read the top-level `backlog_service_repo` scalar. **Unset → skip** (the repo is on the markdown backend — no GitHub, possibly not even a git remote — and has no taxonomy to reconcile; this is healthy, not a finding). **Set to `owner/repo` → offer `reconcile-labels`** as a repair. `reconcile-labels` re-establishes the `<facet>:`-namespaced base taxonomy (creating only what's missing — e.g. a base label a human deleted) and reports the coexistence picture (which foreign, non-prawduct labels it left untouched). It is **idempotent and collision-free** — never deletes or modifies an existing label, so a re-run on a healthy repo creates nothing. Needs `gh` authenticated against that repo; if `gh` is unavailable, report the repair is pending and move on (don't fail the health check on it). Run `prawduct-hook backlog reconcile-labels --repo <owner/repo>` and relay `created` / `foreign_untouched` from the result. This is a governance repair (the label surface, not product code), like `update-gitignore` — doctor runs it; it does not touch product source.

14. **Leftover norm-index scaffold rows** — run `prawduct-hook norm-index-scaffold` and relay its status. Two *illustrative* Enforcement rows from older templates have non-empty `Audit home` / `Why` cells, so `norm-health-sweep-overdue` reads them as homed norms and nudges about a sweep the repo does not owe. Report **degraded** on `leftover`, naming the lines, and **healthy** on `ok`. `absent` (no `project-preferences.md`) is **degraded**, because no other check reports its absence; point at `/prawduct:methodology discovery`, which authors it. `unreadable` and `unwritable` (read fine, but the **write** failed and nothing changed) both exit **1** and are degraded because ungraded. Detection is exact-match on the rows prawduct shipped, so an authored or edited row is left alone. **The repair is offered, never applied for them:** the dry run names the file and each line, and the owner runs `prawduct-hook norm-index-scaffold --apply`. The repair is delete-only: it removes those rows and rewrites nothing else, line endings included.

15. **Retired `project-state.yaml` residue** — run `prawduct-hook lifecycle-repair` (dry run) and relay what it reports. The residue is the retired `views_enabled` setting, its `scope_rollups:` block, a derived `release-notes.md`, per-plan "do not hand-edit these checkboxes" notes, and the `build_state.test_tracking` block (removed whole, with any `assertion_count` / `test_files` / `history` beside it). **Report degraded when the dry run lists any edit**, and lead with the two that change behaviour. First, the plan note is obeyed by readers while the session gates read those boxes. Second, a stale `test_tracking` number invites an agent to "correct" it, and each correction is a commit that buys a review round. Name where the real figure lives: the test evidence store (`prawduct-hook test-evidence record`, read back with `test-status`). Also degraded: `retired_flag: present` in `--json` (name the key and its line; it came back by someone copying an older state file); a non-empty `unreadable` list (name each path and say the check was partial, because the walk skipped them and "no edits needed" does not cover them); and an undecodable state file (degraded because ungraded). `unscoped` plans are **healthy**. They are still checked for residue, and `--apply` cannot clear the listing, so relay the count and the paths, say that adding a `scope:` is the owner's call, and move on. The repair is offered, never applied for them: see the Lifecycle Convergence Flow.

16. **Live plans whose Status was generated** — the same dry run lists these separately (`plans_to_review` in `--json`), and they are **report-only, permanently**. A generated Status block is stale on an in-flight chunk; only a session with the work in context can say which chunk is actually done, and the session gates read that state — so a model must not write it. Relay the plan and the specific chunks and stop there. Report degraded while any are listed.

    **Say this out loud when you relay it, because the list is not durable.** Detection keys on the same `## Status` note that the repair deletes, so the list is printed on the dry run and on the apply run and then **never again** — it goes quiet when the repair runs, not when anyone settles a plan. An operator who scrolls past it during the apply run has lost it, and nothing will raise it a second time. So: relay it *before* offering `--apply`, and if the operator is not going to act on it now, tell them to copy the list somewhere first. Writing the answer for them is the one thing that stays forbidden; making sure they still have the question is not.

17. **Change-log merge attribute (a recommendation, not a conformance check)** — run `git check-attr merge -- .prawduct/change-log.md`. Anything other than `union` → recommend adding the line `.prawduct/change-log.md merge=union` to `.gitattributes` and committing it: every branch prepends its entry to the same first lines, so merging an advanced base conflicts there every time, and the union driver keeps both sides' entries instead. **Recommend and print the line; never write `.gitattributes`** — it is not in the plugin's write set, which is what makes running prawduct a safe trust decision. If the command cannot run, say the attribute was **not checked** rather than reporting it fine — "no attribute" and "could not ask" are the same empty answer otherwise. This is the on-demand surface for the same signal the ambient `gitattributes` advisory raises, and both resolve on the same state (what git answers); the advisory is the primary surface because doctor is rarely run. **Neither a missing attribute nor an unavailable check degrades the repo** — the attribute is advice a repo is free to decline, and grading it would make optional advice behave like the install contract.

18. **Delegation policy unrecorded (a recommendation, not a conformance check)** — read `project-preferences.md`'s `Delegation`, `Delegate verification` and `Inner-loop verification` rows, and branch per row rather than on the set. `Delegation approval` is not in the trigger set: it ships filled with a default, so reading it would make every freshly scaffolded repo look recorded — what excludes a row is shipping filled, not being a third. **`Delegation: off` ends the check**: say nothing and propose nothing further. A filled row is reported as recorded and left alone; a blank one beside it is still a candidate. When all three are filled the check ends. A durable `Delegation approval` yes is `methodology/planning.md`'s offer, not doctor's. **For each unset row — or absent row, since this file is scaffolded once and never regenerated** — look for what this repo already encodes about running part of its suite: test markers or groups in the test config, a named script, a build-tool target, a CI job that runs a subset. The same findings answer `Inner-loop verification` (what to run while iterating and at each chunk's Verify), worded as the narrowest thing that proves a change. **Propose only what you actually found, quoting the repo's own names and naming the file each came from.** If you found nothing, say so and propose nothing, because a proposal that fires everywhere carries no information. **Never degrade the repo on this, and never grade it at all**: an absent policy is not a defect. The promotion is offered, never applied: see the Delegation Policy Flow.

19. **The install record matches this checkout, and the hooks actually ran** — the install reference (#1) says the plugin *should* load; this asks what the harness actually recorded. Two halves, and they fail independently. **The record:** run `prawduct-hook check-plugin-active --path . --context doctor` and route on its status — `active` is healthy; `inactive` is **degraded**, NOT broken (see below), and you relay the command's own `--context doctor` text; `unknown` (exit **3**) means the check could not run — degraded because ungraded. **The hooks:** `.prawduct/.session-start` should exist; it is written by the SessionStart hook on every session, so its absence means that hook has never completed in this clone even though the skills plainly load — report **degraded** and name it, because a repo whose skills work and whose hooks do not has no Stop gates while every artifact says it does.

    **Why `inactive` is degraded here and broken at onboard — the two are not the same finding.** You are reading this from inside a session where the plugin loaded, because `/prawduct:doctor` *is* a plugin skill. So `inactive` cannot mean "this repo is ungoverned"; it can only mean the manifest holds no record naming this exact path — a git worktree, or a checkout that was moved, renamed, or is reached through a symlink. Reporting **broken** and relaying onboard's "will start a session with NO governance" would send an operator to reinstall a working install, which is the false accusation this whole check is built to avoid. Pass `--context doctor` and the command words it correctly for you; do not paraphrase the onboard wording from memory.

    **Know what this check cannot see, and say so rather than overclaiming.** You are running inside a session where the plugin loaded, so the catastrophic case — a repo that looks fully onboarded while nothing loads at all — is invisible from here by construction: `/prawduct:doctor` is itself a plugin skill, and in that repo it cannot be invoked. That case belongs to `/prawduct:onboard`'s final step, which runs from *outside* the target. This check covers the residue: a stale or partial install in a repo that does load.

20. **Risk surfaces readable** — the same `prawduct-hook coverage-status --json` run as #11 carries `risk_surfaces.status`: `declared`, `undeclared`, `unparseable`, `not-owed`, or `null` when the check could not run. **Only `unparseable` is a finding** — the key is there in a shape the reader refuses (flow style, `null`, nested items), and until it is a block sequence of plain strings the Critic escalates every review rather than read a syntax slip as low risk: report **degraded** and relay the `fix`. `undeclared` is **healthy** — nothing asks a product to declare risk surfaces, and an absent key keeps the built-in and contract-path escalation. Never prompt for the key. `null` is degraded because ungraded. Read-and-guide: present the corrected block and let the owner write it.

21. **Unused plugin cache directories (a recommendation, not a conformance check)** — run `prawduct-hook stale-plugin-caches` and relay its report. Claude Code keeps every prawduct version it ever installed, in every config profile on the machine, and nothing removes them; older ones still carry prawduct's own internal state, so this is another product's material sitting readable in every profile, not only disk. The command lists the version directories no install record uses, with their sizes and a delete command for each. **Relay the commands; never run them.** These directories belong to the machine, not this repo, and only the operator knows which Claude Code sessions are open: a running session keeps using the version it started with, so tell them to close every session in a profile before deleting its directories, as the report says. A profile the report marks **not graded** (its `installed_plugins.json` is missing or unreadable) has nothing in it called unused, by design; say so rather than counting it clean. If the command exits non-zero or cannot be invoked, say the caches were **not checked**; never report that there are none. **Never degrade the repo on this** — it is machine hygiene a repo cannot fix, and grading it would make every repo on a crowded machine look unhealthy.

Classify and report:
- **healthy**: install reference + `distribution: plugin` + no residue + core state present + discovery captured (or no product work yet) → "Your prawduct plugin setup is healthy."
- **degraded**: governance works but something is off (an anchor that is missing, stale, locally edited, or ungradable — Check #4 names which, and they route differently; a missing non-critical file, discovery uncaptured despite product work, a `risk_surfaces:` key prawduct cannot read (Check #20), an exposed API with no recorded versioning decision, norm-registry integrity findings, an active strategy-class coverage layer, a check that could not run, an install record that does not name this checkout, or a SessionStart hook that has never completed in this clone) — list each with its implication and the fix.
- **broken**: no install reference, or file-sync residue still committed — recommend `/prawduct:migrate` (or installing the plugin first). Note that #19's `inactive` is **not** in this class: reached from inside a session the plugin loaded, it is a stale install record, not an ungoverned repo.

## Lifecycle Convergence Flow (Health Check #15/#16's repair)

Brings a repo onto the current governance-artifact model: checkboxes that mean what they say, and finished plans in an archive rather than in the live directory. Two commands, and **the order matters** — run them this way round:

1. **`prawduct-hook plan-backfill`** — moves plans that already shipped into an `archive/` beside them. Dry run first; it names every plan and the release that carried it. Run it *before* the repair, because the repair edits live plans and most of these are about to stop being live: the other order produces a diff on every one of them and then archives the file you just edited.

    **Read the `NOT moving` list, and relay it.** The preview separates plans it will archive from plans the change log says shipped but which it **refuses** — a name already taken in the archive, a plan already carrying a terminal state, one it cannot read, or one whose own `## Status` does not evidence completion (unticked chunks, named; or no readable roster at all). Those need a person, and they are the ones that otherwise stay live silently while the run reports a clean sweep. On `--apply` a non-empty list is also a **non-zero exit**: work the change log says shipped did not move.
2. **`prawduct-hook lifecycle-repair`** — removes the dead setting and its generated block, removes the retired `build_state.test_tracking` block whole, labels a derived `release-notes.md` as history, and deletes the "do not hand-edit" notes from the plans that are *still* live. Dry run first.

**One confirmation covers the whole act, and per-file prompting is forbidden here** — not merely discouraged. `security-model.md` § Direction says a destructive or irreversible operation takes one informed confirmation naming its blast radius, *not* a per-action gate, because confirmation fatigue is itself a safety regression. So: show the operator the complete dry-run output — every file, every reason, once — take a single yes, then run both with `--apply`. Never walk them through file by file.

What to say when you present it, in plain language and without prawduct-internal names: these are ordinary file edits and file moves that version control can undo; a finished plan is archived, never deleted, and it keeps everything it says.

**Two things this flow deliberately does not do.** It never ticks or corrects a checkbox: Health Check #16's plans are reported for a human and left alone, and an archived plan keeps its unticked boxes on purpose. And `plan-backfill` archives a plan only when the plan's own `## Status` evidences completion, because a scope that shipped partially is not a finished plan. A descoped plan is archived **superseded**, which needs a human to name the reason. `prawduct-hook archive-plan <path>` asks no completeness question and is the route for that case.

**A product with no release tags** gets nothing moved by `plan-backfill` — it says so and lists the live plans instead. That is not a clean result; it means the mechanical test cannot answer here and the operator decides which plans are done, archiving each with `prawduct-hook archive-plan <path>`.

## Norm Ratification Flow (the `norm-registry-unratified` advisory's landing target)

Turns the direction a product's owner **already declared** into ratified norms — `## Direction` sections and Enforcement rows (`/prawduct:methodology norms` § Adoption). Binding force comes from the owner's declaration; ratification *records* it, never creates it. Detection and surfacing are automatic (the advisory + session briefing); execution stays on-demand and **ratification stays with the owner** — auto-binding norms would be a norm-birth decision made by default. **Doctor's write rule, which this flow and the Delegation Policy Flow both obey and nothing else in this skill does:** it writes only what the owner confirmed, only into `.prawduct/` governance state — artifacts and the `project-state.yaml` outcome scalar — additively and non-destructively; never product code, never a rewrite of product content. Every other flow reads and guides.

1. **Read** the product's strategy-class artifacts (`observability-strategy.md`, `security-model.md`, `architecture.md`, `api-contract.md`, `nonfunctional-requirements.md`, `operational-spec.md`, `data-model.md` — whichever exist in `.prawduct/artifacts/`), `project-preferences.md`, and the rules corpus under `.claude/rules/learnings/`.
2. **Propose and triage candidate norms.** Draft each as a statement a decision plainly stands behind (the `/prawduct:methodology norms` normative/descriptive test: "if the code changed and this sentence were updated to match, would a decision have been silently unmade?") — statement + why + status (`steady-state`, or `in-transition` naming the tracking backlog item; cite backlog ids literally in whys where the rationale rests on tracked work). Classify conservatively — genuinely ambiguous prose is a *needs-a-ruling* item (below), not an asserted candidate. Then **tag each candidate by how much owner attention it needs** — a mature product yields dozens of candidates, and a flat list buries the few that carry a real decision under the many that are obvious:
   - **clear-to-ratify** — a decision plainly stands behind it, the statement matches the code *today*, and the why is obvious. Confirmed in bulk, never discussed one by one.
   - **needs-a-ruling** — the candidate carries a fork only the owner can resolve. The recurring kinds: **aspirational** (the statement outruns the code → the honest form is `in-transition` + a tracking item, or a narrower scope — the owner picks); **practice-not-written** (ratifying would bind a habit that was never a written rule — binding force is itself the decision); **wording/scope fork** (the drafted statement is too strong, slightly false, or scoped wrong); **collision/ambiguous** (two candidate whys conflict, or the normative/descriptive call is genuinely unclear); **whyless** (the rationale can't be stated without the owner — backfill first). Each is surfaced with its specific fork and your recommendation.
3. **Surface by exception — never a flat wall.** Present the two tiers asymmetrically so the owner's attention lands on the decisions, not the rubber-stamps:
   - **needs-a-ruling candidates: individually**, each with its fork and a recommendation. These are the point of the flow.
   - **clear-to-ratify candidates: one bulk-confirm line** — name them compactly ("these N load-bearing-but-obvious norms") and ask for a single "confirm, or veto any." Never expand them into a per-norm interrogation.
   - **Above ~6 total candidates the flat dump is banned** — surface-by-exception is mandatory, not a nicety. A flat block of twenty candidates is the failure this step exists to prevent: the owner bounces off it, or rubber-stamps the lot — which silently defeats owner-ratification, the whole reason the flow is owner-driven. At/below ~6, a single grouped block is fine — provided any needs-a-ruling items still surface their fork; the cap governs when exception-surfacing becomes *mandatory*, never whether a real ruling may be bundled away.
   - **The guard: bulk-confirm is still an *explicit* confirm.** A clear-to-ratify tier presented but not affirmed is **not** ratified — the owner's "confirm" (or per-item veto) is what binds; silence ratifies nothing (no auto-ratification, per Adoption). The failure mode is symmetric — a wall on one side, a one-norm-per-message interrogation on the other; do neither.
4. **Write the ratified norms** — only what the owner confirmed: a `## Direction` section in the artifact each norm governs (the original narrative prose stays — the Direction entry is the ratified form beside it, per `/prawduct:methodology norms` § Anatomy), plus an Enforcement row per norm (pointer rows for artifact-homed norms; assign each row's mechanism and audit home — a mechanism that doesn't exist yet is filed as backlog work at birth). If the Enforcement table predates the norm columns, extend it via the legend-refresh pattern — add the `Audit home` and `Why` columns additively, preserving every existing row.
5. **Record the outcome** — set `norm_registry_ratified: <today>` (top-level scalar) in `project-state.yaml`. A descriptive suffix is fine (`2026-07-17 — 20 norms…`) but the value must **lead with the date**: it seeds the Norm Health sweep baseline, so a freshly-ratified registry isn't immediately flagged `norm-health-sweep-overdue`. A **"no norms to ratify"** outcome is valid (proportionality) and records `norm_registry_ratified: none — no norms to ratify` instead (dateless — and with no norms under *either* homing there is no sweep to seed; the absence of `## Direction` sections alone would not settle it, since a product may home its norms entirely in the Enforcement table). Either answer is shared state: one teammate's ratification clears the advisory for everyone on next sync.

## Delegation Policy Flow (Health Check #18's promotion)

Turns a regime this repo **already runs** into rows the next session reads, in one step: what you found, one confirmation, written. The failure it exists to end is exact — the right rule stated by the owner in session after session and never becoming durable anywhere.

**Write the rows even when they are absent, not only when they are blank.** `project-preferences.md` is scaffolded once at onboard and never regenerated, so the shipped template's delegation rows reach *new* repos and nothing else. An already-onboarded repo has no such rows at all, and this flow is the only path by which it gets them. Add the rows under `## Workflow` if they are missing.

1. **Show what you found and where** — the repo's own names for the things it already does, each with the file it came from. The owner is checking a claim, not trusting a summary, and a proposal they cannot check is one they can only rubber-stamp.
2. **Draft in the repo's vocabulary, not prawduct's.** At most four rows: whether delegating is worth it here at all, what a delegate may run to prove its own change, what to run while iterating and at each chunk's Verify before the declared suite runs at the boundary, before the work lands, and whether delegating is pre-approved. **Draft only the rows the evidence supports** — a row nothing was observed for is a guess written in the owner's voice, and it is worse than a blank because the next session reads it as a decision.
3. **One confirmation covers the set, and per-row prompting is forbidden** — the same rule as Lifecycle Convergence, for the same reason: confirmation fatigue is itself a safety regression (`security-model.md` § Direction). Four rows is below the threshold at which the Norm Ratification Flow's surface-by-exception becomes mandatory, so one grouped block is the right shape here — provided each row still shows the evidence behind it, and any row you are genuinely unsure of leads with that.
4. **Write only what they confirmed.** The rows under `## Workflow`, plus the Enforcement rows the template's own note assigns: **one** for the delegation policy `Delegation` and `Delegate verification` state together — not one per row, since near-identical handles for one policy is the index bloat `one home per fact` resists — and **one of its own** for `Inner-loop verification`, which governs the owner's loop rather than a delegate's and is a policy in its own right. `Delegation approval` is a setting like `PR creation`, not a norm, and takes no row of its own. Mechanism `Critic` (a policy in prose is judgment-required, so nothing mechanical can grade it), audit home `janitor` (no mechanical hook is named, and naming one you have not built is how a norm becomes aspirational), and the why is the owner's own sentence. **The Enforcement row is a handle, not a second copy of the policy** — it names the preference and points at its `## Workflow` row. Match the columns the repo's table actually has; where it predates the norm columns, extend it by the same legend-refresh the Norm Ratification Flow uses rather than inventing a second pattern for it. Additive throughout: never rewrite a row the owner already filled.
5. **A decline writes nothing, and say what that means.** The offer returns at the next `/prawduct:doctor`, because nothing recorded a decision — and `Delegation: off` is the row that ends it for good. Say both, or a "no" quietly becomes a standing re-ask.
6. **`Delegation approval: pre-approved` is where a durable yes lands.** When the owner says delegating here is simply fine to get on with, that is the row — and it is what stops `methodology/planning.md`'s partition ask from returning with every plan.

## Enable-Gate Flow (coverage F4 / operator-verification F10)

Plugin-native — enabling a gate is a `project-state.yaml` flag flip (no migrate subcommand, no sync). This flow **reads and guides**; it does not edit `project-state.yaml` (doctor writes only a decision an owner confirmed inside the flow that asked for it — the Norm Ratification and Delegation Policy flows; enabling a BLOCKING gate is not one of those). Read the current value first, confirm intent (surface the BLOCKING consequence), then present the exact one-line edit for the user (or the main session) to apply.

### Coverage (F4 — symbol-coverage enforcement)
Set `coverage_required: true` in `.prawduct/project-state.yaml`. **Consequence:** the Critic's Goal 1 then BLOCKS on any changed file the verifier can judge that is missing from `.test-evidence.json`'s `changes_referenced` (unjudgeable files — non-code, symbol-less, deleted — land in `changes_unjudged` and are reported, not gated). (`/prawduct:methodology building` "Test Discipline" explains the evidence shape; `bin/test-reference-verify` is the Python symbol floor — stronger language-native tools give `coverage_level: executed`.)

### Operator verification (F10 — pre-merge human-verification gate)
Set `operator_verification_required: true` in `.prawduct/project-state.yaml`; entries accumulate in `.prawduct/operator-verification.md` as visual / live-integration chunks enqueue them. **Consequence:** `/prawduct:pr create` then BLOCKS while any entry's status is `pending`; the per-PR override is `/prawduct:pr create --accept-pending-verification "rationale"` (rationale recorded back into each entry).

## Verify Flow (drain operator-verification queue)

Drains a single pending entry in `.prawduct/operator-verification.md` after the human-verification step is genuinely complete. Plugin-native — operates only on the repo's own `.prawduct/`.

1. Confirm the user has actually performed the verification described in the entry's `**Verify:**` checklist — `verify` is a deliberate user action, not a session-time auto-flip.
2. Run: `prawduct-hook verify-operator-verification <VRF-id>`
3. Relay the `previous_status → status` line ("pending → verified") and the action line. If the entry was already verified, the command is a no-op and surfaces a note.
4. **On exit 1, relay the message verbatim and read it before advising** — exit 1 covers every refusal this command makes (an unknown or mistyped VRF id, no queue file, the accepted-entry refusal, a lib that would not import), so the code alone does not say what went wrong. **When the message says the entry's status line could not be read** — not on a line of its own, an unrecognised word, or missing — nothing was written, re-running cannot change the outcome, and only the operator's hand edit will: relay the edit the message names and stop. Do not edit the queue yourself; it is an operator-authored record. Leave every other exit-1 cause to what the message says, and retry where that is the actual remedy.

Refuses to verify an `accepted` entry — `accepted` means the gate was overridden via `--accept-pending-verification`; flipping to verified would erase the override rationale. Edit the file by hand if the verification is now genuine.
