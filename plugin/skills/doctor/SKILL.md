You are managing prawduct product-repo health under the **plugin** distribution model. Prawduct is installed as a Claude Code plugin (dev-time governance); a product commits only the install *reference* plus its own `.prawduct/` state — no framework files. Every flow operates on the consumer's own repo: there is no framework checkout to call back to.

This skill is for a repo that is **already onboarded**. To set up a new or existing repo, use **`/prawduct:onboard`** instead.

## Scope & boundary

`doctor` owns **prawduct governance/install conformance** — is *this repo* correctly set up and
governed (install reference, distribution, anchor, core state, discovery captured, gitignore
contract, recorded decisions)? It **reports and guides**; it does not fix the product's own code.
For the product's **own codebase craft** — code/docs/tests/dependency quality and currency — use
**`/prawduct:janitor`**. Full split, and the rule for where a new concern belongs: `docs/doctor-vs-janitor.md`.

## Context Detection

1. If an explicit target path was provided → `doctor` runs in the *current* product repo, not on a target path. If they meant to **set up** that path, send them to **`/prawduct:onboard <path>`**; if they meant to **health-check a different** repo, have them `cd` there and re-run. Either way, stop here.
2. Else if the current directory has `.prawduct/` (is a product repo) → **Health Check**, and route to Enable-Gate / Verify / Audit-Learnings on explicit request.
3. Else → ask the user what they want to do.

## Health Check Flow (current dir is a product repo)

Plugin-native — the *subject* of every check is the consumer's OWN `.prawduct/` and `.claude/`, read with Read / Glob, and there is nothing to sync. One check reads a value **out of the plugin** (#1's contract, via `${CLAUDE_PLUGIN_ROOT}`) rather than transcribing it; that is a plugin-bundled constant, not a file-sync path to resolve. Check:

1. **Install reference** — the consumer's `.claude/settings.json` matches the whole install contract. **Read the contract from `${CLAUDE_PLUGIN_ROOT}/lib/migrate_plugin.py` `INSTALL_REFERENCE` and compare every leaf in it; do not check from a list here.** (At time of writing that is `enabledPlugins["prawduct@prawduct"]`, and under `extraKnownMarketplaces.prawduct`: `source.source`, `source.repo`, `source.ref`, `autoUpdate` — illustrative, not the set, and the constant wins where they differ. If the constant is genuinely unreadable, say so in the report rather than silently grading against this list.) Missing or drifted → contributors won't get governance on clone. Check every leaf, not just the familiar two: the ambient `install-reference` / `contract-drift` advisory routes here as its recommended action and fires on all of them, so any field it can report and this check cannot repair is a nudge that reports healthy when you follow it.
2. **Distribution recorded** — `project-state.yaml` has `distribution: plugin`. (Absent → a legacy file-sync hook may still be governing; recommend `/prawduct:migrate`.)
3. **No stale file-sync residue** — no committed `tools/product-hook`, `tools/lib/`, framework `.claude/skills/critic/`, or `.prawduct/sync-manifest.json`. (Present → migration is incomplete; recommend `/prawduct:migrate`.)
4. **Static governance anchor** — `CLAUDE.md` contains the `PRAWDUCT:ANCHOR` marker (the thin governed-by-plugin anchor a migrated repo keeps).
5. **Core state present** — `.prawduct/` has `project-state.yaml`, `learnings.md`, `backlog.md`, `change-log.md`, and `artifacts/`.
6. **Discovery captured** — if the repo shows product-definition work (source code, or markdown under `docs/`), `project-state.yaml` should have `classification` and `product_definition` filled, not template-default (`domain: null` / `vision: null`). Template-default state alongside real product work means discovery was skipped — the docs-first / brownfield onboarding gap the **DISCOVERY NOT CAPTURED** session-briefing nudge also flags. Recommend **`/prawduct:methodology discovery`** (reconciliation mode reads the existing docs/code and backfills `project-state.yaml`). A repo with no product work yet is fine — discovery comes when building starts.
7. **External backlog files** — if `TODO.md` / `BACKLOG.md` / `ROADMAP.md` / `IDEAS.md` exist in the repo root or `.github/` and aren't recorded in `backlog_external_imports`, report them and recommend **`/prawduct:backlog import <path>`** (don't auto-import — the user confirms). This is the explicit health-check surface for the same signal the `external-backlog-detected` session-start advisory raises ambiently; both resolve on `backlog_external_imports`.
8. **Gitignore contract** — `.gitignore` should carry the session-file entries and must NOT ignore retired entries (`.prawduct/artifacts/build-plan.md` — build plans are tracked artifacts; an ignored plan plus the tracked `active_build_plan:` pointer breaks every other clone). Stale line present or session entries missing → run `prawduct-hook update-gitignore` (it prints any `unignored:` paths — advise `git add` on those that exist on disk). This checks the prawduct *contract* only; general gitignore hygiene (build artifacts, editor files, secrets) is the janitor's Version Control Hygiene theme (`docs/doctor-vs-janitor.md`).
9. **API versioning decision** — if the repo exposes an API (`classification.structural.exposes_programmatic_interface: true`, or a Glob-able `openapi`/`swagger` spec or `*.proto` file in the tree — the `api-versioning` advisory additionally scans source for web-framework imports, which this read/Glob-only check does not) but no versioning decision is recorded (`api_versioning_decided` unset *and* `design_decisions.api_versioning_approach` null), report **degraded** and recommend recording the decision — a versioning + deprecation scheme, or an explicit dated deferral with a revisit trigger (`/prawduct:methodology discovery` / `/prawduct:methodology planning` capture it; `templates/api-contract.md` details it). Read-and-guide only — present the one-line `project-state.yaml` edit, don't auto-edit (consistent with #6/#7 and Enable-Gate). This is the on-demand health-check surface for the same signal the `api-versioning` session-start advisory raises ambiently; both resolve on a recorded decision. "API" is any programmatic surface others call (network service, library/SDK, on-device/platform, CLI) — an internal-only surface records "none — internal-only" and is healthy.
10. **Norm-registry integrity** — when the product has ratified norms (`## Direction` sections in `.prawduct/artifacts/*.md`, or norm rows in the preferences Enforcement table — `/prawduct:methodology norms`), check each: every Direction entry carries a **Why** (citing backlog ids *literally* where the rationale rests on tracked work — the citation is what makes decay mechanically detectable); every `Status: in-transition` entry names a live tracking backlog item; every Enforcement row names a mechanism that actually exists (a named-but-never-built mechanism is the aspirational failure with extra steps); pointer rows point at a Direction section that exists; and `project-state.yaml` classification matches observable code signals (e.g. `has_multiple_party_types: false` alongside a login/auth surface suggests a characteristic flipped without the recorded decision — `/prawduct:methodology norms` § Ambient norms). A product with **no** ratified norms is not a finding here — that is the Ratification Flow's cue (the `norm-registry-unratified` advisory raises it ambiently). Report degraded with the specific entries; the fixes are owner decisions (backfill the why, re-point the row, amend the norm), never auto-edits.
11. **Strategy-class artifact coverage** — run `prawduct-hook coverage-status` and relay the three-layer chain it reports (it reads the SAME expectation table the ambient `strategy-artifact-missing` / discovery-not-captured advisories fire on, so the health check can't drift from the nudge). The chain **stages** the fixes 0→1→2 (layers 0↔1 are mutually exclusive — never both, and possibly neither; layer 2's gate is independent, so during *partial* authoring layer 1 and layer 2 can both be active — `coverage-status` names the highest-priority active layer as the primary fix): **layer 0** (structural characteristics not recorded → `/prawduct:methodology discovery`); **layer 1** (characteristics recorded but expected strategy-class artifacts missing → author each via `/prawduct:methodology planning`, or drop stubs in one act with `prawduct-hook coverage-scaffold --apply`); **layer 2** (artifacts exist but norms unratified → the Norm Ratification Flow above). Report **degraded** when any layer is active, naming the layer and the fix path the command prints; **healthy** when the active layer is none — but **"no active layer" has two meanings and they are not the same report.** When `discovery_expected` is false (`--json`; the human line says so in prose) the chain has not *engaged* yet: no source or `docs/` this scan recognises, so nothing is owed and nothing is satisfied. Say "the coverage chain has not engaged yet" rather than grading a repo healthy on a chain that never asked it anything. **`false` and `null` are different answers** — `discovery_expected: null` (equally `structural_recorded: null`) means the staging check could not run at all, so report **degraded because ungraded**: say the check declined, never that the chain has not engaged, which would be a confident answer for a state nothing was checked in. The bare human form says this unmissably ("unknown (staging check unavailable)"); the gap is only on the `--json` route — and note that the scan reads source by suffix, so a repo in an unlisted language reads as unstarted (`#561`). Coverage is satisfied by each artifact *existing* — a deliberate `(not relevant — <reason>)` stub counts — so the fix is cheap; whether a stubbed-out decision is sound (a high-risk product stubbing its security model) is the Critic's call, not this check's. Read-and-guide: present the fix, and offer `coverage-scaffold` (dry run first — it lists what it would create; `--apply` writes neutral stubs, never overwriting, never deciding relevance for the owner), but the owner runs `--apply` and fills each stub.
12. **Backlog label taxonomy (post-cutover only)** — read the top-level `backlog_service_repo` scalar. **Unset → skip** (the repo is on the markdown backend — no GitHub, possibly not even a git remote — and has no taxonomy to reconcile; this is healthy, not a finding). **Set to `owner/repo` → offer `reconcile-labels`** as a repair: this is doctor's ownership of provisioning (GV6) — onboard provisions at adoption, scrub at migration, doctor *reconciles* on repair. `reconcile-labels` re-establishes the `<facet>:`-namespaced base taxonomy (creating only what's missing — e.g. a base label a human deleted) and reports the coexistence picture (which foreign, non-prawduct labels it left untouched). It is **idempotent and collision-free** — never deletes or modifies an existing label, so a re-run on a healthy repo creates nothing. Needs `gh` authenticated against that repo; if `gh` is unavailable, report the repair is pending and move on (don't fail the health check on it). Run `prawduct-hook backlog reconcile-labels --repo <owner/repo>` and relay `created` / `foreign_untouched` from the result. This is a governance repair (the label surface, not product code), like `update-gitignore` — doctor runs it; it does not touch product source.

13. **Descent obligation in `learnings.md`** — run `prawduct-hook learnings-obligation` and relay its status. `/prawduct:learnings` ends by telling its caller to apply the obligation *stated in this product's own `learnings.md`*, marked `prawduct:descent-obligation` — a pointer, so the statement has one home instead of a copy per product. Only `init-product`'s starter corpus ever wrote that marker, and only into a file that did not yet exist, so a repo onboarded before it, migrated, or with a hand-authored learnings file holds an instruction aimed at nothing. Report **degraded** on `missing` (no marker) or `misplaced` (the first marker at or below the first `## ` rule — a reader who meets the obligation *after* the rules it governs has met it too late, which is the inertness the statement exists to prevent); **healthy** on `ok`. `absent` (no `learnings.md`) is #5's finding, not this one's. `unreadable` (the file is not decodable text — the command exits **1**, "could not run") is **degraded because ungraded**: say the check declined, never that it passed, because a check that could not run is otherwise indistinguishable from one that did and found nothing. **The repair is offered, never applied for them:** the dry run prints the exact block and the exact line, and the owner runs `prawduct-hook learnings-obligation --apply` — this edits the product's own authored corpus, so it takes an informed confirmation naming what changes. It **inserts only**; it never rewrites, reorders or removes a line, which is why a `misplaced` marker is reported for the owner to move rather than moved for them.

14. **Leftover norm-index scaffold rows** — run `prawduct-hook norm-index-scaffold` and relay its status. The Enforcement norm index used to ship two *illustrative* rows whose `Audit home` / `Why` cells are non-empty placeholders. The template stopped shipping them, but `init-product` copies templates only into destinations that do not exist, so **the fix reached new onboards and nothing else**: an already-onboarded repo still carries them, they read as homed norms to `norm-health-sweep-overdue`, and the repo is nudged about a Norm Health sweep it owes nothing to. Report **degraded** on `leftover`, naming the lines; **healthy** on `ok`. **`absent` (no `project-preferences.md`) is a finding — report it here.** It was previously deferred to Check #5, which enumerates `project-state.yaml`, `learnings.md`, `backlog.md`, `change-log.md` and `artifacts/` and never looks at this file — so a missing preferences file was graded healthy by every check in the flow. Report **degraded** and point at `/prawduct:methodology discovery` (it authors the file); a product with no preferences has no norm index, no Enforcement mechanisms and nothing for Check #10 to grade. `unreadable` (the file is not decodable text) and `unwritable` (read fine, **write** failed — nothing changed) both exit **1**, "could not run", and are **degraded because ungraded**: say the check declined, never that it passed, because a check that could not run is otherwise indistinguishable from one that did and found nothing. They are separate statuses on purpose — one status meaning both would describe a failed repair as an unreadable file, sending the owner to fix the wrong thing. **Detection is exact-match on the rows prawduct shipped**, never a guess at what a placeholder looks like — an authored row that happens to be italic, or a scaffold row a human has edited, is theirs and is left alone. **The repair is offered, never applied for them:** the dry run names the file and each line, and the owner runs `prawduct-hook norm-index-scaffold --apply` — this edits the product's own authored preferences file, so it takes an informed confirmation naming what changes. It is **delete-only**: it removes those rows and rewrites nothing else, line endings included.

15. **Retired derived-view residue** — run `prawduct-hook lifecycle-repair` (dry run) and relay what it reports. Build-plan `## Status` checkboxes used to be a *generated view* in repos where `views_enabled` was on, and that setting, the `scope_rollups:` block it fed, a regenerated `release-notes.md`, and the per-plan notes saying "do not hand-edit these checkboxes" all outlived it. **Report degraded when the dry run lists any edit.** Three of the four are inert — nothing reads them — but the fourth still changes behaviour, and that is the one to lead with: a note telling a reader the boxes are generated is *obeyed*, and the session gates read those boxes, so a repo that keeps it converges its data and still behaves the old way. **The retired flag reappearing is its own finding** (`retired_flag: present` in `--json`): report degraded and name the key and its line, because a flag comes back by someone copying an older state file, not by anyone deciding to reinstate it. **A non-empty `unreadable` list is its own finding, and it outranks a clean `edits`.** Those are plans under `artifacts/` that could not be decoded as text; the walk that builds `edits` skips them by design, so the sweep reported on a set it did not fully read — and "no edits needed" over a file nothing opened is indistinguishable from a converged repo. Report **degraded**, name each path, and say the check was partial; never report converged while the list is non-empty. Same rule for the state file itself being undecodable: **degraded because ungraded** — say the check declined, never that it passed. The repair is offered, never applied for them: see the Lifecycle Convergence Flow.

16. **Live plans whose Status was generated** — the same dry run lists these separately (`plans_to_review` in `--json`), and they are **report-only, permanently**. A generated Status block is stale on an in-flight chunk; only a session with the work in context can say which chunk is actually done, and the session gates read that state — so a model must not write it. Relay the plan and the specific chunks and stop there. Report degraded while any are listed.

    **Say this out loud when you relay it, because the list is not durable.** Detection keys on the same `## Status` note that the repair deletes, so the list is printed on the dry run and on the apply run and then **never again** — it goes quiet when the repair runs, not when anyone settles a plan. An operator who scrolls past it during the apply run has lost it, and nothing will raise it a second time. So: relay it *before* offering `--apply`, and if the operator is not going to act on it now, tell them to copy the list somewhere first. Writing the answer for them is the one thing that stays forbidden; making sure they still have the question is not.

17. **Change-log merge attribute (a recommendation, not a conformance check)** — run `git check-attr merge -- .prawduct/change-log.md`. Anything other than `union` → recommend adding the line `.prawduct/change-log.md merge=union` to `.gitattributes` and committing it: every branch prepends its entry to the same first lines, so merging an advanced base conflicts there every time, and the union driver keeps both sides' entries instead. **Recommend and print the line; never write `.gitattributes`** — it is not in the plugin's write set, which is what makes running prawduct a safe trust decision. If the command cannot run, say the attribute was **not checked** rather than reporting it fine — "no attribute" and "could not ask" are the same empty answer otherwise. This is the on-demand surface for the same signal the ambient `gitattributes` advisory raises, and both resolve on the same state (what git answers); the advisory is the primary surface because doctor is rarely run. **Neither a missing attribute nor an unavailable check degrades the repo** — the attribute is advice a repo is free to decline, and grading it would make optional advice behave like the install contract.

Classify and report:
- **healthy**: install reference + `distribution: plugin` + no residue + core state present + discovery captured (or no product work yet) → "Your prawduct plugin setup is healthy."
- **degraded**: governance works but something is off (missing anchor, a missing non-critical file, discovery uncaptured despite product work, an exposed API with no recorded versioning decision, norm-registry integrity findings, an active strategy-class coverage layer, a learnings corpus whose descent obligation is missing or below the first rule, or a check that could not run) — list each with its implication and the fix.
- **broken**: no install reference, or file-sync residue still committed — recommend `/prawduct:migrate` (or installing the plugin first).

## Lifecycle Convergence Flow (Health Check #15/#16's repair)

Brings a repo onto the current governance-artifact model: checkboxes that mean what they say, and finished plans in an archive rather than in the live directory. Two commands, and **the order matters** — run them this way round:

1. **`prawduct-hook plan-backfill`** — moves plans that already shipped into an `archive/` beside them. Dry run first; it names every plan and the release that carried it. Run it *before* the repair, because the repair edits live plans and most of these are about to stop being live: the other order produces a diff on every one of them and then archives the file you just edited.

    **Read the `NOT moving` list, and relay it.** The preview separates plans it will archive from plans the change log says shipped but which it **refuses** — a name already taken in the archive, a plan already carrying a terminal state, one it cannot read, or one whose own `## Status` does not evidence completion (unticked chunks, named; or no readable roster at all). Those need a person, and they are the ones that otherwise stay live silently while the run reports a clean sweep. On `--apply` a non-empty list is also a **non-zero exit**: work the change log says shipped did not move.
2. **`prawduct-hook lifecycle-repair`** — removes the dead setting and its generated block, labels a derived `release-notes.md` as history, and deletes the "do not hand-edit" notes from the plans that are *still* live. Dry run first.

**One confirmation covers the whole act, and per-file prompting is forbidden here** — not merely discouraged. `security-model.md` § Direction says a destructive or irreversible operation takes one informed confirmation naming its blast radius, *not* a per-action gate, because confirmation fatigue is itself a safety regression. So: show the operator the complete dry-run output — every file, every reason, once — take a single yes, then run both with `--apply`. Never walk them through file by file.

What to say when you present it, in plain language and without prawduct-internal names: these are ordinary file edits and file moves that version control can undo; a finished plan is archived, never deleted, and it keeps everything it says.

**Two things this flow deliberately does not do.** It never ticks or corrects a checkbox — Health Check #16's plans are reported for a human and left alone. And it never *corrects* a checkbox on the way in — an archived plan may carry unticked boxes, and that is preserved on purpose. What changed at v3.3.1 (#634): the **mechanical sweep** now declines a plan it cannot evidence as finished, naming the chunk, because selection by change-log `release=` answers "did the scope ship" and never "did the plan finish" — and those come apart whenever a scope ships partially, which archived two unbuilt chunks as shipped in a real product. The descoped plan this paragraph used to worry about is still one command from its end of life: it was never meant to be archived *completed*, but **superseded**, which needs a human to name the reason — so `archive-plan <path>` asks no completeness question at all and is the right route for exactly that case.

**A product with no release tags** gets nothing moved by `plan-backfill` — it says so and lists the live plans instead. That is not a clean result; it means the mechanical test cannot answer here and the operator decides which plans are done, archiving each with `prawduct-hook archive-plan <path>`.

## Norm Ratification Flow (the `norm-registry-unratified` advisory's landing target)

Turns the direction a product's owner **already declared** into ratified norms — `## Direction` sections and Enforcement rows (`/prawduct:methodology norms` § Adoption). Binding force comes from the owner's declaration; ratification *records* it, never creates it. Detection and surfacing are automatic (the advisory + session briefing); execution stays on-demand and **ratification stays with the owner** — auto-binding norms would be a norm-birth decision made by default. This is the one doctor flow that writes: it records the owner's confirmed decisions into governance state — `.prawduct/` artifacts and the `project-state.yaml` outcome scalar — additively and non-destructively; never product code, never a rewrite of product content.

1. **Read** the product's strategy-class artifacts (`observability-strategy.md`, `security-model.md`, `architecture.md`, `api-contract.md`, `nonfunctional-requirements.md`, `operational-spec.md`, `data-model.md` — whichever exist in `.prawduct/artifacts/`), `project-preferences.md`, and `.prawduct/learnings.md`.
2. **Propose and triage candidate norms.** Draft each as a statement a decision plainly stands behind (the `/prawduct:methodology norms` normative/descriptive test: "if the code changed and this sentence were updated to match, would a decision have been silently unmade?") — statement + why + status (`steady-state`, or `in-transition` naming the tracking backlog item; cite backlog ids literally in whys where the rationale rests on tracked work). Classify conservatively — genuinely ambiguous prose is a *needs-a-ruling* item (below), not an asserted candidate. Then **tag each candidate by how much owner attention it needs** — a mature product yields dozens of candidates, and a flat list buries the few that carry a real decision under the many that are obvious:
   - **clear-to-ratify** — a decision plainly stands behind it, the statement matches the code *today*, and the why is obvious. Confirmed in bulk, never discussed one by one.
   - **needs-a-ruling** — the candidate carries a fork only the owner can resolve. The recurring kinds: **aspirational** (the statement outruns the code → the honest form is `in-transition` + a tracking item, or a narrower scope — the owner picks); **practice-not-written** (ratifying would bind a habit that was never a written rule — binding force is itself the decision); **wording/scope fork** (the drafted statement is too strong, slightly false, or scoped wrong); **collision/ambiguous** (two candidate whys conflict, or the normative/descriptive call is genuinely unclear); **whyless** (the rationale can't be stated without the owner — backfill first). Each is surfaced with its specific fork and your recommendation.
3. **Surface by exception — never a flat wall.** Present the two tiers asymmetrically so the owner's attention lands on the decisions, not the rubber-stamps:
   - **needs-a-ruling candidates: individually**, each with its fork and a recommendation. These are the point of the flow.
   - **clear-to-ratify candidates: one bulk-confirm line** — name them compactly ("these N load-bearing-but-obvious norms") and ask for a single "confirm, or veto any." Never expand them into a per-norm interrogation.
   - **Above ~6 total candidates the flat dump is banned** — surface-by-exception is mandatory, not a nicety. A flat block of twenty candidates is the failure this step exists to prevent: the owner bounces off it, or rubber-stamps the lot — which silently defeats owner-ratification, the whole reason the flow is owner-driven. At/below ~6, a single grouped block is fine — provided any needs-a-ruling items still surface their fork; the cap governs when exception-surfacing becomes *mandatory*, never whether a real ruling may be bundled away.
   - **The guard: bulk-confirm is still an *explicit* confirm.** A clear-to-ratify tier presented but not affirmed is **not** ratified — the owner's "confirm" (or per-item veto) is what binds; silence ratifies nothing (no auto-ratification, per Adoption). The failure mode is symmetric — a wall on one side, a one-norm-per-message interrogation on the other; do neither.
4. **Write the ratified norms** — only what the owner confirmed: a `## Direction` section in the artifact each norm governs (the original narrative prose stays — the Direction entry is the ratified form beside it, per `/prawduct:methodology norms` § Anatomy), plus an Enforcement row per norm (pointer rows for artifact-homed norms; assign each row's mechanism and audit home — a mechanism that doesn't exist yet is filed as backlog work at birth). If the Enforcement table predates the norm columns, extend it via the legend-refresh pattern — add the `Audit home` and `Why` columns additively, preserving every existing row.
5. **Record the outcome** — set `norm_registry_ratified: <today>` (top-level scalar) in `project-state.yaml`. A descriptive suffix is fine (`2026-07-17 — 20 norms…`) but the value must **lead with the date**: it seeds the Norm Health sweep baseline, so a freshly-ratified registry isn't immediately flagged `norm-health-sweep-overdue`. A **"no norms to ratify"** outcome is valid (proportionality) and records `norm_registry_ratified: none — no norms to ratify` instead (dateless — and with no norms under *either* homing there is no sweep to seed; the absence of `## Direction` sections alone would not settle it, since a product may home its norms entirely in the Enforcement table). Either answer is shared state: one teammate's ratification clears the advisory for everyone on next sync.

## Enable-Gate Flow (coverage F4 / operator-verification F10)

Plugin-native — enabling a gate is a `project-state.yaml` flag flip (no migrate subcommand, no sync). This flow **reads and guides**; it does not edit `project-state.yaml` (the Norm Ratification Flow is the skill's one write path, and it writes only owner-confirmed decisions). Read the current value first, confirm intent (surface the BLOCKING consequence), then present the exact one-line edit for the user (or the main session) to apply.

### Coverage (F4 — symbol-coverage enforcement)
Set `coverage_required: true` in `.prawduct/project-state.yaml`. **Consequence:** the Critic's Goal 1 then BLOCKS on any changed file the verifier can judge that is missing from `.test-evidence.json`'s `changes_referenced` (unjudgeable files — non-code, symbol-less, deleted — land in `changes_unjudged` and are reported, not gated). (`/prawduct:methodology building` "Coverage Evidence" explains the evidence shape; `bin/test-reference-verify` is the Python symbol floor — stronger language-native tools give `coverage_level: executed`.)

### Operator verification (F10 — pre-merge human-verification gate)
Set `operator_verification_required: true` in `.prawduct/project-state.yaml`; entries accumulate in `.prawduct/operator-verification.md` as visual / live-integration chunks enqueue them. **Consequence:** `/prawduct:pr create` then BLOCKS while any entry's status is `pending`; the per-PR override is `/prawduct:pr create --accept-pending-verification "rationale"` (rationale recorded back into each entry).

(There is no `--enable-settings-layout` in the plugin world — "settings layout" was a file-sync `.claude/settings.json` normalization; under the plugin the only settings concern is the committed install reference, which Health Check validates.)

## Verify Flow (drain operator-verification queue)

Drains a single pending entry in `.prawduct/operator-verification.md` after the human-verification step is genuinely complete. Plugin-native — operates only on the repo's own `.prawduct/`.

1. Confirm the user has actually performed the verification described in the entry's `**Verify:**` checklist — `verify` is a deliberate user action, not a session-time auto-flip.
2. Run: `prawduct-hook verify-operator-verification <VRF-id>`
3. Relay the `previous_status → status` line ("pending → verified") and the action line. If the entry was already verified, the command is a no-op and surfaces a note.

Refuses to verify an `accepted` entry — `accepted` means the gate was overridden via `--accept-pending-verification`; flipping to verified would erase the override rationale. Edit the file by hand if the verification is now genuine.

## Audit-Learnings Flow (lifecycle metadata triage)

Plugin-native — `prawduct-hook audit-learnings` walks the repo's own `.prawduct/learnings.md`, reads the optional per-entry metadata comment, and reports promotion candidates (advisory), retirement candidates, and stale single-confirmation entries (>90 days old).

The metadata comment is a single line placed immediately after each `## Title`:

```markdown
## My learning
<!-- prawduct-learning: confirmations=2; created=2026-02-22; sentinel=tests/test_critic.py::test_summaries_check -->

Body of the learning…
```

All fields are optional. An entry without the comment is treated as "active, no lifecycle metadata" and stays untouched.

**Two retirement routes, never both on one entry.** `sentinel=<test id>` retires a rule because the failure mode it warned about is now structurally enforced by a passing test. `superseded-by=<heading prefix>` retires it because a **broader rule replaced it** — which is what every consolidation is, and without it consolidation is an unauditable hand-edit. The retired entry's historical copy names its replacement, so a reader who remembers the old rule finds a forwarding address rather than a hole.

Supersession is fail-closed on every ambiguity, like a failing sentinel: the prefix must match exactly one *other* heading (case-sensitively). Unresolvable, ambiguous, self-referential, or empty → an `errors` entry, and the rule is **not** retired. An entry declaring both keys errors and retires under neither — picking one silently would let a failing sentinel be bypassed by adding a supersession key.

Each `retirements` record carries `reason` (`sentinel` | `superseded-by`); branch on that rather than probing which keys are populated.

Use when the user asks to "audit learnings", "retire structurally-enforced learnings", "check lifecycle metadata", or similar.

1. Run: `prawduct-hook audit-learnings --json`
2. Relay each list — surface promotion candidates as advisory ("the rule has been confirmed twice — consider whether it belongs in `learnings.md` or can move to historical detail"), retirement candidates pending `--apply` (say which route: "the declared sentinel passes", or "superseded by *<resolved heading>*"), stale flags ("the entry is over 90 days old with no second confirmation — has the rule held up?"), and errors (failing sentinels, malformed dates, unresolvable or ambiguous supersession pointers, entries declaring both routes).
3. If the user confirms intent to retire, re-run with `--apply`: `prawduct-hook audit-learnings --apply --json`. The `--apply` invocation mutates two files: `.prawduct/learnings.md` (entry removed) and `.prawduct/learnings-detail.md` (entry appended under the "Historical (structurally enforced)" section, carrying a one-line retirement note that states its route — and, for a supersession, names the replacement).

**A retired entry sheds its lifecycle comment.** `superseded-by=` / `sentinel=` are directives for the *active* corpus; carried into `learnings-detail.md` they are inert, because `audit-learnings` parses `learnings.md` and nothing else — and an inert comment in the detail file has previously disabled the whole mechanism. The retirement note replaces it.

The audit is read-only by default. Promotion is always advisory — `learnings.md` doesn't have a sectioned active/promoted split; the count just surfaces in the report. Retirement is the only mutation, and only when `--apply` is passed AND the entry's route is satisfied (sentinel passes, or the supersession pointer resolves).

## Important Notes

- Onboarding lives in **`/prawduct:onboard`** (scaffold a new or existing repo via `prawduct-hook init-product`, or route a pre-2.0 file-sync repo to `/prawduct:migrate`). This skill (`doctor`) covers an already-onboarded repo: health-check, enable-gate, verify, audit-learnings, ratify-norms.
- Health Check and Audit-Learnings decide from the consumer's OWN `.prawduct/` — no framework checkout, no sync.
- Enabling a gate is a `project-state.yaml` flag flip; the BLOCKING consequence is immediate on the next relevant gate (governance is modeled as CI — see `/prawduct:methodology`).
- Hooks and governance activate in the target's own Claude Code session, not the current one.
