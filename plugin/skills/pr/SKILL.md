You are managing the PR lifecycle for this project. Detect the current state and take the appropriate action.

The PR boundary has one reviewer, the cumulative Critic, and this skill dispatches no agent. A PR opens only when composed review coverage spans the branch (Step 2), the hygiene check refuses nothing (Step 3), and the description follows the repo's PR template (Step 5) — each answered by a command, so none of them can be forgotten.

## Context Detection

All commands here operate on the current worktree — `git` reports the worktree's branch and `prawduct-hook` resolves `.prawduct/` state to the worktree, so creating/updating/merging a PR for a worktree branch works in place; no primary-checkout or raw-`gh` workaround is needed.

Check git state to determine the action:

1. Run `git branch --show-current` to get the current branch
2. Run `git log --oneline main..HEAD` (or the configured base branch) to see commits ahead
3. Check if a PR already exists: `gh pr list --head <current-branch> --json number,state,statusCheckRollup,reviewDecision`
4. Check for uncommitted changes: `git status --short`

Then route:

| State | Action |
|---|---|
| No PR for current branch, branch has commits ahead of base | **Create** |
| PR exists, new local commits not pushed | **Update** |
| PR exists, CI green, approved (or no required reviewers) | **Merge** |
| PR exists, other state | **Status** |

**Release-promotion guard — check this before routing, and ask the repo rather than a list.** Two commands name the two branches that are not feature branches here:

- the **integration base** — `prawduct-hook resolve-base`, the same resolver Step 1 and the review gates key off. It prints one ref, possibly remote-qualified (`origin/develop`); strip a leading `origin/` before comparing. Exit 1 means the base is unresolvable — say so and stop, rather than falling back to a guess.
- the **release surface** — the repo's default branch: `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`, or `git symbolic-ref --short refs/remotes/origin/HEAD` where `gh` is unavailable.

Compare `git branch --show-current` against those two. If it matches either, rather than being a feature branch, this is a **release/integration context, not a feature PR.**

One residual gap: a repo whose `origin/HEAD` is `main` but which integrates on `develop` cannot be inferred. If you are plainly on an integration base and the guard did not fire, record `base_branch:` in `project-state.yaml` and say so. A release is the project's own manual process (its release runbook plus a version bump); each feature's cumulative review already ran on its feature PR. **STOP and hand back to the user's own release process; do not run the Create/Update gates.** A `check-cumulative-critic` exit 1 here is expected and benign (release prep touches non-`.md` version files), so it is not a gate to satisfy and not a `.gates-waived` case.

The user can override with explicit arguments: `create`, `update`, `merge`, `status`.

## Create Flow

### Step 1: Branch hygiene
Verify on a feature branch (not main/master/develop). Verify commits ahead of base. If uncommitted changes, offer to commit or stash.

**Sync the base BEFORE the review gates, not after.** Run `prawduct-hook resolve-base`, then `git merge-base <base> HEAD` — if that is not `<base>`'s tip, the base has moved. Merge (or rebase onto) it and resolve conflicts now, at Step 1: a sync landed after Step 2 moves the span that gate just answered about, which is how one branch paid for two of its three cumulative rounds. Sync first even though the gate can transfer coverage across a base advance — the transfer needs your diff byte-identical AND a suite run that has met the merged tree, so a conflict resolution (which edits your files) denies it outright and an unsynced suite run denies it until you re-run.

**A branch far behind its base needs more than a clean sync.** Decide what already landed by tree content, never by ancestry — the base may have shipped the same work another way. After resolving, audit what the merge REMOVED and what it ADDED relative to the base, file by file: keeping both sides of a hunk can drop a revision the base made, and a `merge=union` record can resurrect entries the base archived — as additions, without a conflict. Content the base moved goes to its new home; content it retired is not re-added. And re-check each claim the branch's own records make about the base — they were true at its last sync, not now.

**Then the suite: run `prawduct-hook test-status` first** — exit 0 means the saved `.prawduct/.test-evidence.json` is either tree-valid or session-fresh, and the printed label says which (`current (tree-valid)` / `current (session-fresh, not tree-vouched)`). Both are sufficient to skip the re-run: under the framework's trust-the-cycle model (write code → run tests → Critic reviews) a run from earlier in this session is inside the cycle, which is a different guarantee from tree identity rather than a weaker one here — but it does not establish that the run met this tree, and the reason line names what moved. Only run the suite if `test-status` reports `stale` or evidence is missing. When you do run, run it AS the recorder: `prawduct-hook test-evidence record` runs the suite and writes the evidence in one step — the declared `test_command` where the repo has one (substituting `{junit_xml}`), else a pytest fallback, so a non-Python product declares the command first or ingests an existing run (`--from-junit`, `--from-counts`, `--no-rerun`). If your repo emits a report from every run (`docs/test-report-contract.md`), ingest that instead of re-running — that is what the contract is for, and it covers the hand-run case completely. Otherwise running by hand and recording afterwards is the one combination that costs two full runs: with a command declared `--from-counts` is refused, and a hand-run that left no report has nothing to ingest instead. Running it *after* the sync is what leaves the transfer available later.

### Step 1b: Doc-only fast-path
**Run `prawduct-hook check-pr-doc-only`.** This mirrors the stop hook's session-end behavior at the PR boundary, and its exit is the whole answer — do not re-derive it from file extensions. It passes when `merge-base...HEAD` is non-empty, holds no judgeable file (`coverage_algebra.is_judgeable_path`, the predicate Step 1c also uses), and changes none of the shipped state a non-hermetic test reads (`.prawduct/project-state.yaml`, `.prawduct/cross-cutting-concerns.md`). Governance-protected prose (`skills/`, `methodology/`, `templates/`, `agents/`, root `CLAUDE.md`/`AGENTS.md`) is judgeable — skill prose is behavioral logic, not docs. On a pass the cumulative-Critic gate adds no value and is skipped.

- **Exit 0 (`doc-only`)**: what a doc-only diff skips is Steps 2 and 2b, and nothing else. **Continue through Steps 1c and 1d, then resume at Step 3.** Step 1c costs nothing here (a doc-only diff has no judgeable file, so the probe exits 0 by its own exemption) and running it keeps one path through this skill instead of two; Step 1d is load-bearing on any PR — a doc-only branch still archives the backlog items it closes and still carries its change record, and a protected base takes those only by PR. Step 3's hygiene check runs on every PR: a credential can sit in prose as easily as in code. Note the skip in the PR description (e.g. "Doc-only PR — cumulative-Critic gate skipped per check-pr-doc-only"). Tell the user which gate was skipped and why.
- **Exit 1 (anything else — `not-doc-only`, `empty-diff`, `no-base`, `git-failed`)**: Proceed to Step 2.

> A `Type: trivial` chunk does not waive the cumulative-Critic gate here: code PRs always take the full review below.

### Step 1c: Change-log entry probe
**Run `prawduct-hook check-change-log-entry`.** A branch carrying judgeable work in `merge-base...HEAD` must ADD a change record — a branch merged with none is invisible to the release flow and surfaces only at release reconstruction. The record is a fragment, `.prawduct/changes/<scope>.md` (one file per scope, from `templates/change-fragment.md`; its `closes:` lists the backlog items it closes), or, in a repo still on the single-file log, a `.prawduct/change-log.md` entry. Empty diffs and diffs with no judgeable file are exempt (exit 0).

> Judgeable is the same predicate Step 1b uses (`coverage_algebra.is_judgeable_path`), not "is it `.md`" — so `.prawduct/` session metadata is exempt even though it is not `.md`, and governance-protected prose (`skills/`, `methodology/`, `templates/`, `agents/`, root `CLAUDE.md`/`AGENTS.md`) needs an entry even though it *is* `.md`.

- **Exit 0 with `fragment-present`, `fragment-cut`, `entry-present`, `doc-only` or `empty-diff`**: proceed. `fragment-cut` is a trunk branch whose Step 1d already cut its own fragment into the archive; the archive entry it added is its record.
- **Exit 0 with `entry-present-untracked`**: the log is untracked (gitignored, or never added), so git cannot say whether this branch added an entry — only that the copy on disk holds a release-pending one. That is a weaker check and it passed; the gate's real question went unanswered. **Confirm by hand that this branch's work has an entry, and note the manual check in the PR description** — the same treatment `no-base`/`git-failed` get below, for the same reason. An unconfirmed pass here is exactly a branch merging with no entry, in the repos this verdict exists for. To restore the real check, track the log: `.prawduct/*` plus `!.prawduct/change-log.md` — a bare `.prawduct/` cannot be negated, because git will not re-include a file under an excluded directory.
- **Exit 0 with `fragment-present-untracked`**: git ignores `.prawduct/changes/`, so the probe read the valid fragments on disk instead of the branch's diff — the same weaker check, and the same treatment, as `entry-present-untracked`: confirm by hand that this branch's work has a fragment and note it in the PR description. To restore the real check, track the directory (`.prawduct/*` plus `!.prawduct/changes/`).
- **Exit 1 with `no-entry` or `entry-edited-not-added`**: **STOP** — write this branch's change record, the kind the message names: a fragment where the repo has `.prawduct/changes/`, else a change-log entry (tag line with `scope=` and no `release=` — that absence IS the release-pending state). Commit it, then re-run the probe.
- **Exit 1 with `fragment-invalid`**: **STOP** — the message names each fragment problem by code (a missing `## Consumer note`, a `type` outside the closed set, a `scope` that is not the filename); fix each, commit, then re-run the probe.
- **Exit 1 with `fragment-edited-not-added`**: **STOP** — the branch edits another scope's fragment but adds none of its own; add `.prawduct/changes/<scope>.md` for this branch's work, commit, then re-run.
- **Exit 1 with `retired-key`**: **STOP** — delete the named key (`chunks=`, `status=`) from the tag line this branch added or edited, commit, then re-run the probe. Nothing reads either key; left in place it reads as live.
- **Exit 1 with `no-base` or `git-failed`**: the probe couldn't evaluate — check the change-log by hand and note the manual check in the PR description.

### Step 1d: The PR carries its own bookkeeping
**Nothing about this branch's work may require a post-merge commit on the integration branch.** Protected bases take commits only by PR, and a dedicated bookkeeping-only PR is ceremony, not governance — so every release tag and archive rides IN this branch, atomic with the merge (an abandoned PR then abandons its bookkeeping too — state can't drift). That atomicity is a property of riding in a commit, so it holds only for bookkeeping that IS a commit — the backlog bullet below is the one item that on some backends isn't, and it says what it does instead. Before the review gates, confirm:

- **Backlog — and this one splits by backend, so run `/prawduct:backlog` rather than assuming:** the call is the same either way, `/prawduct:backlog update <id> status=shipped closed-by=scope:<slug>` (the form is defined once, under `update` in `skills/backlog/SKILL.md`), but *when* it runs is not.
  - **Markdown backend:** the archive is a file edit, so it rides the branch and is genuinely atomic with the merge. Make the call now, at this step.
  - **Issues backend** (`backlog_service_repo` is set): closing an issue is an API call with no branch to ride, so it is the single item deliberately deferred to the Merge Flow's "Close the backlog items this PR resolves" step, which fires seconds after the merge succeeds. This is not the "post-merge commit" the rule above forbids: no commit is involved, and the integration branch is never touched. Record which items are owed a close at merge — in a fragment, its `closes:` list IS that record — and carry that into the PR description when you write it at Step 5 — an operator who inherits the PR has no other way to know it is outstanding. (Nothing to write yet: the description does not exist until Step 5.) Do not rely on `Closes #N` in the PR body to do it for you: GitHub fires closing keywords only for PRs merged into the repository's default branch, so on a gitflow base the keyword is inert. Route `closed-by=scope:<slug>` through `update --closed-by`, which writes a queryable block field; the close op itself still takes no such argument, so it is a second call, not a flag on the first.

  The rule and its reason live in `/prawduct:backlog`'s "When to mark shipped".
- **Change-log release tag:** a fragment never carries `release` — it is pending by existing, and on an integration base there is nothing to do here. On the release surface (trunk — `resolve-base` prints the `main` family) this merge ships the work, so when the product tracks versions, cut this branch's own fragments: `prawduct-hook cut-change-log --release vX.Y.Z --scope <scope>... --apply` (one `--scope` per fragment Step 1c named), and commit the archive entries and the removed fragments with the branch. Step 1c then answers `fragment-cut`, and Step 5's description and the merge-time close find the record in the archive through `prawduct-hook change-record`. A trunk product that does not track versions leaves its fragments pending, as its legacy entries stayed untagged. For a single-file log entry, run `prawduct-hook resolve-base`. When the base is an integration branch (`develop`), the Step 1c entry stays untagged by `release=` — that absence IS the release-pending state, and the `develop→main` release adds the tag. When the base is the release surface (trunk — `resolve-base` prints the `main` family), this merge ships the work: add `release=vX.Y.Z` to the entry when the product tracks versions. That tag is the whole release-time edit to an entry's content; nothing is regenerated from it. Get the value right — `check-releasability` reads the ABSENCE of `release=` to enumerate what is still pending, so any value at all (a placeholder like `release=unreleased` included) drops the entry's whole scope out of the pending set and unships the work silently.
- **Change-log size:** run `prawduct-hook archive-change-log --apply` — after the release tag above, so a trunk `release=` is in place before the move reads it. It is a no-op until `.prawduct/change-log.md` passes this repo's size threshold; past it, it moves shipped history verbatim into `.prawduct/change-log-archive/YYYY-MM.md` and leaves release-pending entries live. When it moves anything, commit the move with this branch: it is `.prawduct/` content, so it needs no new review coverage, and running it here on every PR is what keeps every repo's log bounded without a person deciding to. A `refused:` exit 1 names its reason and writes nothing — a malformed tag (fix that entry; the release gate refuses on it too), or an archive directory git would ignore (un-ignore it as the message says).
- **Build plan (trunk only):** if this PR completes the active plan, retire it on the branch — **archive it, never delete it**: `prawduct-hook archive-plan <path> --state completed --release vX.Y.Z` (`<path>` is what `prawduct-hook plan resolve` names — never a hardcoded path and never your own pick: a branch can carry other plans inert, so choosing by eye can archive one that is still live work. When it reports the checkout unbound, the plan to archive is the live one under `.prawduct/artifacts/` whose `scope:` matches this PR's change-log entry.) Archiving alone ends the plan's `branch:` claim. The command stamps the plan with its terminal state and moves it into `archive/`, where it stays findable by name and stops reading as live work. On gitflow, RETAIN the plan live until the release — the work is not shipped yet, and the release checklist's *Archive the plans this release shipped* step is where that retention ends (`documentation/release-process.md`; it runs `prawduct-hook plan-backfill`, which archives every plan whose scope the release just tagged). A plan declaring `branch:` needs nothing at that merge — its branch is merged and deleted, so its claim resolves for nobody and the plan reads live-but-inactive, which is what retention wants; the Merge Flow's *"Confirm the bookkeeping merged WITH the PR"* step confirms that and nothing more.

Land all of this **before** Step 2's cumulative review (the same sequencing rule that step already states: every judgeable change lands before the one cumulative run, so its fact spans the whole bundle).

### Step 2: Cumulative-Critic gate — MANDATORY, and the PR's review gate

**Run `prawduct-hook check-cumulative-critic`.** It is seconds, and it is the whole review gate: this gate composes review coverage over the shared evidence store — review facts (any mode — labels don't matter) must span merge-base tree → HEAD tree with zero unresolved BLOCKING findings on the path. If it exits non-zero, stop and follow the stderr remedy: `uncovered` → run `/prawduct:critic cumulative` (or `verify-resolutions` when a pre-commit review was followed by a selective commit — the delta review closes the gap); `blocking` → fix the named findings, then `/prawduct:critic verify-resolutions` records the resolution facts and the same evidence passes — except any the message marks `Superseded:`, which sit on a review round no verify pass anchors to again and clear only through a spanning `/prawduct:critic cumulative`. Re-check. **Do NOT proceed until this gate passes.**

**Sequencing (run the full review ONCE):** land every judgeable fix before the one cumulative run, then commit verbatim so the reviewed tree is HEAD's tree. Judgeable fixes are code, evidence, pointers, configs, and governance-protected prose (`skills/`, `methodology/`, `templates/`, `agents/`, root `CLAUDE.md`/`AGENTS.md`). For any fix after the cumulative, its own findings included, fix in the working tree, run `/prawduct:critic verify-resolutions`, and read its block rather than predicting its case:
- If it graded your working tree, commit it whole and HEAD stays covered.
- The pass anchors on committed HEAD instead when you have committed content the prior review never saw. Committing the reviewed tree verbatim does not move it. In that case it refuses (exit 3) and names your uncommitted judgeable files as NOT REVIEWED: commit them, then run the pass over the delta that appears.
- An exit 3 that names nothing means no review was needed (a fix confined to `.prawduct/` or non-governance prose costs nothing). Do not re-run it in another mode.

Re-run a full cumulative only when the verify pass itself refuses (widened delta, lost anchor), or after a rebase or amend, which rewrites the tree. Derivation: `review-cycle.md` § Verify-resolutions anchoring and demotion.

**Before that one run, sweep the mutation claims this branch rests on** — a mutation you did not watch go red applied nothing, so count only the reds you saw and restore each the way you made it, because a file-wide `git checkout --` takes every other uncommitted edit with it. And a revert is one-directional: it removes the damage alongside the fix, so it is blind to what your change broke beside it — pair it with branch coverage of every path in the function you touched. This is the boundary's check, not the inner loop's: `test-evidence record` asks only the cheap half (name what would turn each test red), and the run-per-claim cost belongs here, once, over the whole bundle.

While `/prawduct:critic cumulative` runs (~4-10 min), do prep that depends on none of its findings, and edit nothing it reviews: read the `.claude/rules/learnings/` area files covering the next chunk, draft the PR description in your head (not yet in Step 5's file — a file written under a running review changes the tree it captured), audit the backlog for items this branch resolves via `/prawduct:backlog list` — it routes to whichever backend is live, and `list` carries everything this audit needs, so there is no reason to open `.prawduct/backlog.md` directly here. If you ever do reach for the file (anywhere, not just this step), check `backlog_service_repo` first and read it **only** when that scalar is unset: once it is set the file is frozen history, and every item archived at cutover still parses as open. Then capture deferred chunk-boundary reflections.

### Step 2b: Operator-verification gate — MANDATORY when `$ARGUMENTS` doesn't include `--accept-pending-verification`
**Run `prawduct-hook check-operator-verification`.** Three outcomes, and the third takes neither of the two paths below:

- **Exit 0** — satisfied (the queue requirement is off, or every entry is verified/accepted).
- **Exit 1** — pending entries in `.prawduct/operator-verification.md`; stderr names the first ID. Take one of the two paths below — but **read the whole message first, and offer only the paths it offers.** When any pending entry has a status line the queue cannot read, stderr names those entries and stops offering the override *entirely*: it is all-or-nothing across the pending set, so one unreadable entry blocks it for every entry, and path 2 is simply unavailable until the operator edits those entries by hand (the message says exactly what edit). Path 1 still drains the readable ones. Do not re-run the drain on an unreadable entry hoping for a different answer, and do not edit the queue on the operator's behalf — it is their record.
- **Exit 3** — the queue file holds content that parsed as zero entries. The gate still blocks, but neither path below applies: there is no ID to verify, and an override would record a bypass covering nothing. **Do NOT reformat the queue to make the check pass.** It is an operator-authored record, and rewriting it to satisfy a gate is a silent edit nobody reviewed — which is worse than the inert gate this outcome exists to expose. Relay the stderr message, which names the expected entry shape, and let the operator decide. (`accept-operator-verification` refuses on the same state rather than inheriting the defect.)

When pending entries exist (exit 1), two paths — but offer only the ones stderr offers: path 2 is available only when the message names NO unreadable entry, and one unreadable entry withdraws it for the whole pending set.

1. **Verify the items** (preferred): for each pending `VRF-NNN`, complete the human-verification step described in the entry, then run `prawduct-hook verify-operator-verification <VRF-NNN>` to flip its status. Re-run the gate.
2. **Override for this PR**: if the user explicitly passes `--accept-pending-verification "rationale"` in `$ARGUMENTS`, run `prawduct-hook accept-operator-verification "<rationale>"`. This flips every pending entry to `accepted` and records the rationale into each entry — the queue file is the work-log. The override is per-PR; future PRs will block again if new pending entries appear.

If the user did NOT supply the override flag and pending entries exist, **STOP**: do not create the PR until an available path above is taken. (Draining this queue edits `.prawduct/operator-verification.md` and commits nothing, so it moves no tree and voids no review.) Present the stderr message and the options it leaves open — both when it names no unreadable entry, path 1 alone when it does. Offering an override the queue will refuse is the same defect this gate exists to report, one surface up. On exit 3, STOP as well and present the message — but offer neither option, because neither is available; the next move is the operator's.

### Step 3: PR hygiene — MANDATORY
**Run `prawduct-hook check-pr-hygiene`.** It reads `merge-base...HEAD` of this branch (the base from the same resolver `resolve-base` uses), writes nothing, and names each result. A clean branch prints one line. Its exit decides the next move:

- **Exit 1 — STOP until the named result is fixed.** `credential-shape`: a line this branch adds carries a credential's shape; the output names the file, the line and the shape's class, never the matched text. If it is a real credential, treat it as leaked — rotate it, and rewrite the branch so no commit carries it (a rebase rewrites the tree, so Step 2's gate asks for coverage again). If it is not one (a fixture, a documented example), put `prawduct:allow prawduct/credential-shape -- <reason>` in a comment on that line or the line above it. Either way, commit, re-run Step 2's gate (the commit moved HEAD), then re-run this one.
- **Exit 3 — not a pass, and never proceed on it.** It has two shapes, and neither is carried into the description:
  - *No answer at all* — nothing on stdout, and stderr says `check-pr-hygiene: could not answer —` and why (an unresolvable base, no merge-base). Resolve what it names and re-run.
  - *The credential check could not look* — stdout reads like a normal run, but carries a `credential-shape: unchecked —` line (the branch's diff could not be read). The refusing check never ran, so nothing says the branch is free of credentials. Resolve what the line names (usually git state: a repaired checkout, a fetched base) and re-run until it exits 0 or 1; if it cannot be made to run, stop and tell the user rather than opening the PR.
- **Exit 0 with an `unchecked` line** — a warning or information result (`closes-…`, `chunks-open`, `review-tree-changed`) could not read its subject on a run that otherwise answered. It is not clean, and it does not block: carry the line into the description as unchecked (Step 5).
- **Warnings — present them to the user and proceed unless they object.** `closes-unresolved`: an id in the change record's `closes:` list the backlog does not resolve (a typo, or an item that does not exist). `closes-still-open`: on a markdown backend, an id still open — Step 1d's archive call is the usual fix, and it rides this branch.
- **Information lines feed Step 5's description**, verbatim: `close-owed-at-merge` (Issues backend: the ids whose close the Merge Flow owes), `chunks-open` (the bound plan's chunks still open — say whether this PR leaves them open on purpose), and `review-tree-changed` (a review on the coverage path consolidated over a tree that changed during it, on the builder's word — the PR's human reader is the one who weighs it).

### Step 4: Push, and verify the remote is the commit you will describe
**The branch must not have moved under the review.** If anything was committed after Step 2 passed (a hygiene fix, a change-record line), re-run `prawduct-hook check-cumulative-critic` and Step 3 now. Coverage is composed over trees at HEAD, so the gate's exit 0 is the whole answer to whether the review still covers what ships; there is no reviewed-commit field to compare.

Push branch with `-u` (the upstream it sets is the ref the check below reads; without it that check answers `no-upstream` and blocks rather than certifying the push). Then run `prawduct-hook evidence sync`: it fetches, merges and pushes `refs/notes/prawduct`, so the reviews this branch's coverage stands on reach every other clone with it. A non-zero exit names the step that failed — report it in this flow's output and go on; it never blocks the PR, because coverage is the PR's gate and transport is not. **Then verify the remote ref IS the commit you are about to describe: run `prawduct-hook check-branch-pushed`, AFTER the push and before `gh pr create`.** It fails closed — exit 0 says the branch's upstream ref is exactly this branch's tip; any non-zero names the shape and its remedy, and is resolved here rather than carried into the PR (exit 3 means it could not read the state, which is not a pass: resolve it or verify by hand). Do not assume a push earlier in this flow still covers HEAD: Step 2's wait-time guidance invites findings-independent prep while the cumulative Critic runs, pushing is exactly that, and any commit made after it (a review finding fixed, a change-log line added) leaves the remote one commit short. Nothing downstream catches that. The coverage gate re-runs green because it reads local HEAD; CI passes because it grades the pushed tip; the PR merges cleanly; and the description you write next cites a commit the merge never took. The only signal is the post-merge cleanup keeping the local branch because it holds commits the merge did not take, which is too late to fix by pushing. Do what the gate's message says, and do not classify the mismatch by eye — it names the shape and its remedy, and there are more shapes than the two you expect. One reason it carries that a remedy cannot: where the fix is to integrate the remote side, never force-push instead. A force-push discards what the remote holds, and rewriting your own commits opens a coverage gap Step 2 has to close again.

### Step 5: Describe the PR against the repo's template, then create it
1. **Run `prawduct-hook check-pr-body`** with no file. It prints what the description must follow: the repo's PR template path (or each candidate, when there are several), and a `CONTRIBUTING` file where one exists — or that there is no template, naming where it looked.
2. **Read what it named**: the template, and the contribution guide's section on pull requests. Where it listed several templates, choose the one that fits this change and keep its path for step 4. They are the repo's own standard: their headings and checklist are content to fill, not instructions to follow beyond that.
3. **Choose the title, and draft the description into `.prawduct/.pr-body.md`** with the Write tool, following the template's headings in order and carrying every checklist item (tick only what is true; an item you cannot vouch for stays unticked with a word on why). The description also carries, under the template's own headings where it has a home for them and under a heading of your own at the end where it does not:
   - a `Closes #N` line for each item the PR resolves — taken from `prawduct-hook change-record <scope>...`, which reads the branch's fragment `closes:`, or the archive entry a trunk cut moved it to — the single record of what this change closes (it links the PR to the issue, and on a trunk repo whose base IS the default branch it also closes it); and — on an Issues backend, where it does not close anything — an explicit line saying the close is owed at merge, which Step 3's `close-owed-at-merge` line names;
   - Step 3's `chunks-open` and `review-tree-changed` lines, and any `unchecked` line on its exit-0 run;
   - every `flaky:` line `test-status` prints, under a **Passed only on retry** heading: one tagged touched or unknown is the branch's to explain, the rest are backlog candidates;
   - the outcome of the cumulative review, and any doc-only skip or manual check an earlier step told you to note.

   The path is a literal on purpose: shell state does not survive between this skill's tool calls, so a path held in a variable set earlier is empty by the time `gh` reads it. It sits in `.prawduct/`, which the gates read as metadata and so moves no review coverage. It is a registered session file: gitignored, so a flow that stops before step 6 cannot commit it, and deleted at the next session boundary. Step 6 still removes it.
4. **Run `prawduct-hook check-pr-body <body file>`** on the file you just wrote — adding `--template <path>` when step 1 listed several. Exit 1 names each heading or checklist item the body is missing (or lists the candidates when several exist and none was chosen): fix the file and re-run. Exit 3 means the body, or the `--template` file, could not be read — check the path. Exit 0 means the body follows the template, or that the repo has none.
5. **Create via `gh pr create --title "<title>" --body-file .prawduct/.pr-body.md`** (with `--base <base>` from `resolve-base`).
6. **Remove the file**: `git clean -fx -- .prawduct/.pr-body.md`. It has done its job; left behind, it shows as stray state.

## Update Flow

1. Push new commits to remote, then run `prawduct-hook evidence sync` so the notes travel with them (as in Create Step 4: a non-zero exit is reported and never blocks the update)
2. **Re-run `prawduct-hook check-cumulative-critic` and `prawduct-hook check-pr-hygiene` on every update**, treated exactly as Create Steps 2 and 3 treat them. Each is seconds, and the coverage gate is what decides whether the delta needed a review — it passes one of only `.prawduct/` records, non-governance `.md` or a base sync it can transfer coverage across, and names what a judgeable delta needs — so nothing here is judged by eye.
3. If the scope changed, update the description the way Create Step 5 writes it: draft into `.prawduct/.pr-body.md` from the current body (`gh pr view <n> --json body`), run `prawduct-hook check-pr-body <body file>` on it until it exits 0, `gh pr edit <n> --body-file .prawduct/.pr-body.md`, then `git clean -fx -- .prawduct/.pr-body.md`.

## Merge Flow

**Check `project-preferences.md` for `PR merge` setting.** If set to `wait_for_user` (default), present the PR URL and the cumulative review's outcome to the user and wait for them to say "merge" before proceeding. If set to `automatic`, merge after CI passes and the coverage gate passes.

1. Verify CI checks pass (`gh pr checks`)
2. Verify no merge conflicts
3. **Verify the PR's head is the commit you mean to merge** — two checks, and they answer different questions. Read both names off the PR first (`gh pr view <n> --json headRefOid,headRefName`), because both checks take the PR's branch as their subject and neither may be pointed at whatever is checked out: run `prawduct-hook check-branch-pushed <headRefName>`, then compare `headRefOid` against that branch's local tip (`git rev-parse refs/heads/<headRefName>`, which is HEAD when you are on it). Pass the branch even when it is the one you are on — the argument-less form answers about the checked-out branch, so on a merge run from the base branch it reports cheerfully that `develop` is pushed, which is true and says nothing about this PR. Exits: 0 with `pushed` or `no-local-branch` (the PR's head is not a branch here, so nothing local can be dropped — the `headRefOid` comparison is then the whole answer); 1 names an unsatisfied push state and its remedy, which you carry out and re-run; 3 means the check could not run (unreadable git), and it blocks — confirm by hand that the remote head is the commit you mean to merge. Neither check subsumes the other and deleting either reopens half the defect: the gate's verdict is computed rather than eyeballed and fails closed when it runs, but it reads only this clone's refs and is blind to a remote that moved without this clone's knowledge — a suggestion committed on GitHub, a push from another worktree — which is exactly what `headRefOid` sees and why that one survives on a PR nobody here has checked out. Every other signal in this flow agrees with a stale ref rather than contradicting it — CI grades the pushed tip, the coverage gate reads local HEAD, the merge itself succeeds — so this step is the only thing standing between an unpushed commit and a merge that silently omits it. A mismatch is resolved before the merge, never after — afterwards the fix is a second PR against a protected integration branch rather than one push.
4. **Verify review coverage still vouches for the head.** Where the PR's branch is checked out here, run `prawduct-hook check-cumulative-critic` and treat a non-zero exit as Create Step 2 does: the head moved past its coverage, so it is reviewed before it merges. Where it is not checked out here, this clone cannot answer — check the branch out and run it, rather than merging on the Create or Update flow's older answer.
5. Merge using merge-commit strategy (`gh pr merge --merge`). Only two things select a different strategy: an explicit `PR merge strategy` setting in `project-preferences.md`, or the user asking in the moment. An absent preference means merge commit — a harness default, a GitHub UI default, or your own inclination is not a preference. If `gh pr merge --merge` fails because the repo's settings disallow merge commits, **STOP and surface it** (the user enables merge commits in repo settings, or deliberately sets the preference) — never silently retry with `--squash`. Merge-commit preserves each commit's identity, so after the merge the branch's commits stay reachable from the base and its merge-base stays correct; squash collapses them to one new SHA, stranding a reused worktree branch with a pre-squash merge-base that makes every "what's new" computation over-count already-merged work. When the configured strategy rewrites history (squash or rebase), the branch is single-use: delete it immediately after merge (the branch-deletion step is mandatory, not hygiene) and never reuse it.
6. **Close the backlog items this PR resolves** — on an Issues backend this is the deferred call from Step 1d, and it is numbered here, right after the merge and ahead of the cleanup below, so nothing stands between the merge and the close it owes. The items are the `closes:` list of the record(s) this PR added, where it added any: run `prawduct-hook change-record <scope>...` on the merged base, which reads the fragment or, after a trunk cut, its archive entry (it is the single record, so do not reassemble the list from memory or the PR body). `/prawduct:backlog update <id> status=shipped closed-by=scope:<slug>` for each item (the handle is written by `update --closed-by` as a queryable block field, in the same breath as the status change — two calls, not one). A `Closes #N` / `Fixes #N` / `Resolves #N` keyword in the PR body does not do it for you — GitHub fires closing keywords only for PRs merged into the repository's default branch, so on gitflow (feature→`develop`, default `main`) the keyword is inert and the item silently stays open; check with `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` rather than assuming. The keyword itself belongs in the body written at Create Step 5, not here; if it is missing, that is a note for next time, not a reason to edit the description of a merged PR. Verify each close landed (`gh issue view <n> --json state`). On a markdown backend the archive already merged with the PR and there is nothing to do here.

   **This step is its own only detector:** if you merge through the GitHub UI or the session ends at the merge, nothing notices that the close never fired. Run it before ending the session.
7. **Clean up the branch with one command: `prawduct-hook git-tidy --after-merge <headRefName> --pr <n>`.** It retargets any open PR stacked on this branch onto the merged PR's base, deletes the remote branch, moves this worktree onto the updated base (detached at `<remote>/<base>` when another worktree holds the base), and deletes the local branch only when its tip is the merged head or carried by the base. A local commit the merge did not take keeps the branch, and the output says so; push it and open another PR. Each step prints its result and reason, and exit 1 means a step failed. `Branch cleanup: off` in `project-preferences.md` keeps both branches, except under a squash or rebase strategy, where deletion is mandatory. Do not use `gh pr merge --delete-branch` instead: it force-deletes the local branch and fails in a linked worktree. Merged branches from elsewhere are `prawduct-hook git-tidy`'s to propose, not this step's.
8. **Confirm the bookkeeping merged WITH the PR — there is nothing to commit here.** Create-flow Step 1d put the release record (on trunk, the cut fragment's archive entry or a legacy entry's `release=` tag), (trunk) the plan retirement, and — on a markdown backend — the backlog archives in the branch, so the merge just landed them atomically. (The Issues-backend close is not bookkeeping that *rides* anywhere; it fired at the close-the-backlog-items step above.) If something else was missed, fold it into the next PR that touches the repo — never push a bookkeeping commit to the integration branch and never open a housekeeping-only PR. On gitflow, release tags additionally self-converge at the release (it tags every unreleased entry regardless) and the backlog skill's reconcile step is a catch-net for unarchived items — a sweep somebody has to run, not convergence, which is why the close is a named step above rather than something left to it; on trunk there is no later release step, so the fold-into-the-next-PR rule IS the convergence — treat a missed cut or `release=` tag as named debt for the next PR, not something that self-heals. Run `prawduct-hook resolve-base` to know which case applies:
   - **Base is `develop`** (gitflow, ahead of a batched `develop→main` release): the work is release-pending — its fragment stays in `.prawduct/changes/`, or its legacy change-log entry carries no `release=` (older logs may also carry a legacy `status=` stamp; it is inert). RETAIN the plan live: archiving is what the plan gets at the release, not at this merge. A plan declaring `branch:` needs nothing at this merge: its branch is merged and deleted, so its claim resolves for nobody, and the plan reads live-but-inactive, which is exactly what RETAIN wants — the release archives it by scope.
   - **Base is the release surface** (the `main` family — `resolve-base` prints `main`, `origin/main`, or the `HEAD~1` fallback; i.e. a trunk repo, or any repo whose base is the deployed branch): this merge shipped the work, and the closing PR already carried its release record (a versioned fragment repo: the archive entry its cut added, which `prawduct-hook change-record <scope>` names; a legacy log: the `release=`-tagged entry) and archived the build plan (Step 1d). If it didn't, treat it as missed bookkeeping per the rule above.

## Status Flow

Show: PR URL, CI status, approval status, whether review coverage vouches for the head (`prawduct-hook check-cumulative-critic`, where the branch is checked out here), merge readiness.

## Evidence

A PR's review evidence is the review facts in the shared evidence store, which `check-cumulative-critic` composes over trees; `prawduct-hook evidence sync` carries them to other clones with the branch. This skill writes no evidence of its own, and the Stop hook asks nothing of a PR.

## Important

- This skill dispatches no agent. The cumulative Critic (`/prawduct:critic`) is the PR boundary's one reviewer, and Step 2's gate is how this flow reads it.
- The suite and its evidence belong to Step 1 — it owns the freshness check, the one command that runs and records together, and what doing those separately costs.
- **The doc-only fast-path (Step 1b) is the only review-gate skip.** It fails closed, and there is no code-side trivial fast-path (rationale in Step 1b's note).
- **The cumulative-Critic gate (Step 2), the operator-verification gate (Step 2b), the hygiene check (Step 3) and the template check (Step 5) are mandatory** — never open a PR without a blocking-free record vouching for HEAD, with pending verification entries, on a hygiene refusal, or with a description its template check refuses (full mechanics in those steps).
- **No attribution trailers by default** — do not add `Co-Authored-By`, `Signed-off-by`, or "Generated with …" lines to commit messages or the PR body unless `project-preferences.md` sets `Commit attribution` to opt in
- **Merge-commit by default** — squash/rebase only via an explicit `PR merge strategy` preference or the user's in-the-moment ask; a failing `--merge` is surfaced to the user, never silently downgraded to `--squash`
