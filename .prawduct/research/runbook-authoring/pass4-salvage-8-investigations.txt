* [HIGH] MOBILE — A shipped mobile binary cannot be recalled. Halting a Google Play staged rollout only stops *new* users from receiving the version; every user who already got it stays on it. Halt is therefore a blast-radius freeze, not a rollback, and it is reversible (resumable) rather than terminal.
  SOURCE: Google Play Console Help, "Release app updates with staged rollouts" — https://support.google.com/googleplay/android-developer/answer/6346149 (fetched 2026-07-20)
  QUOTE: When you halt a staged rollout, no additional users will receive the app version in your existing staged rollout. ... Users who already received the app version in your staged rollout version will remain on that version. ... If you find your existing Android App Bundle doesn't have any issues, you can resume a halted staged rollout.
  TRANSFERABLE RULE: A runbook must state, for its own platform, whether the STOP action removes the bad change from users already on it, or only prevents further exposure. If it only prevents further exposure, the runbook must carry a second, separate procedure for the already-affected population — never treat 'halted' as 'resolved'.

* [HIGH] MOBILE — Apple's phased release is a fixed 7-day schedule the developer does not set, pausable for a cumulative 30 days, and it never gates manual downloads: any user can pull the new version at any time regardless of the phase percentage. So the phase percentage bounds automatic-update exposure only.
  SOURCE: Apple, App Store Connect Help, "Release a version update in phases" — https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/ (fetched 2026-07-20)
  QUOTE: Keep in mind that apps and app updates in phased release can be manually downloaded from the App Store by anyone at any time. ... During phased release, you may pause the release for up to 30 days, with no limit on the number of pauses. ... If you resume a release that was previously paused, your phased release will pick up on the day it was left off when it was paused.
  TRANSFERABLE RULE: Where a rollout control is enforced by a third party, the runbook must record the exact schedule, the pause budget, and the leak paths the control does NOT cover — and the incident procedure must assume some users are already on the bad version outside the controlled percentage.

* [HIGH] MOBILE — Forcing users off a bad version requires a mechanism that was compiled into the *previous* shipped binary. Google's in-app update API distinguishes flexible (usable during download) from immediate (fullscreen, blocks continued use), and only the immediate flow compels the user to move.
  SOURCE: Android Developers, "Support in-app updates" — https://developer.android.com/guide/playcore/in-app-updates (fetched 2026-07-20)
  QUOTE: Immediate updates are fullscreen UX flows that require the user to update and restart the app in order to continue using it. ... This UX flow is best for cases where an update is critical to the core functionality of your app.
  TRANSFERABLE RULE: If the recovery action depends on client-side code, the runbook must name the client version in which that capability first shipped, because clients older than that version are unreachable by the procedure. Capability-to-fix must be provisioned before the incident, not during it.

* [HIGH] DATA PIPELINES — Re-run safety is an authoring property of the task, not a property of the scheduler. Airflow's official guidance mandates deterministic, idempotent tasks and gives concrete prohibitions: no bare INSERT (use UPSERT), never read 'latest' data, never call now() inside a task.
  SOURCE: Apache Airflow docs, "Best Practices" — https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html (fetched 2026-07-20)
  QUOTE: Airflow can retry a task if it fails. Thus, the tasks should produce the same outcome on every re-run. ... Do not use INSERT during a task re-run, an INSERT statement might lead to duplicate rows in your database. Replace it with UPSERT. ... Read and write in a specific partition. Never read the latest available data in a task. Someone may update the input data between re-runs, which results in different outputs.
  TRANSFERABLE RULE: Any runbook step that may be executed more than once (retry, resume, backfill, partial re-run) must state its re-run semantics explicitly — safe to repeat, or safe only after a named cleanup step. 'Re-run the job' is an unsafe instruction unless idempotency is asserted at that step.

* [HIGH] DATA PIPELINES — Correctness is time-dependent in a way that server rollback is not: the watermark is an estimate, not a guarantee, and records arriving after it are classified as late. Recovery procedures must therefore reason about which time windows were already closed when the fault occurred.
  SOURCE: Apache Beam documentation, "Basics of the Beam model" — https://beam.apache.org/documentation/basics/ (fetched 2026-07-20)
  QUOTE: A watermark is a guess as to when all data in a certain window is expected to have arrived in the pipeline. ... After the watermark progresses past the end of a window, any further element that arrives with a timestamp in that window is considered late data.
  TRANSFERABLE RULE: When a system's output depends on completeness-over-time, the runbook must record the time boundary of the damage (which windows/partitions/intervals are affected), not just the wall-clock start and end of the incident — and must say what happens to records that arrive after a window was declared complete.

* [HIGH] FRONTEND — Purging the CDN does not reach the client. AWS's own guidance is to prefer versioned filenames over invalidation precisely because a viewer may keep serving the stale file from a local or corporate-proxy cache after the invalidation completes.
  SOURCE: Amazon CloudFront Developer Guide, "Invalidate files to remove content" — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html (fetched 2026-07-20)
  QUOTE: If you want to update your files frequently, we recommend that you primarily use file versioning for the following reasons: Versioning enables you to control which file a request returns even when the user has a version cached either locally or behind a corporate caching proxy. If you invalidate the file, the user might continue to see the old version until it expires from those caches.
  TRANSFERABLE RULE: A runbook must distinguish caches you can purge from caches you cannot, and must not declare the fix propagated on the strength of a purge you control. Where client-held copies exist, add an explicit step that changes the identity of the resource (new name/version) rather than its contents.

* [HIGH] FRONTEND — A web deploy does not necessarily reach an open session: an updated service worker waits, and by default only activates once every tab controlled by the old one is closed. The obvious workaround (skipWaiting) is documented by Google as potentially harmful because it swaps the worker mid-page-life.
  SOURCE: Chrome for Developers / Workbox, "The service worker lifecycle" — https://developer.chrome.com/docs/workbox/service-worker-lifecycle/ (fetched 2026-07-20)
  QUOTE: By default, a new service worker will activate when no clients are being controlled by the old one. This occurs when all open tabs for the relevant website are closed. ... You can speed up activation of updated service workers by calling [self.skipWaiting], but this may be a bad idea. The old service worker may have handled fetches during page startup, but the new service worker then takes control later on. This can break [stuff like lazily-loaded subresources] until the next navigation request.
  TRANSFERABLE RULE: Where clients hold executing code, the runbook must define what 'deployed' means for an already-open session, and must name the event that actually transfers control (reload, tab close, restart). Verification must sample a client that was open before the fix, not only a freshly loaded one.

* [HIGH] DISTRIBUTED BACKEND (the contrast case) — Server-side is the domain where exposure is directly dialable and the arithmetic of blast radius is explicit; Google defines canarying as partial and time-limited, and shows the exposure calculation (a 20%-failing candidate on a 5% canary yields 1% overall errors). The workbook also treats 'no rollback available' as a distinct, worse mode requiring a roll-forward fix under outage conditions.
  SOURCE: Google SRE Workbook, Chapter 16, "Canarying Releases" — https://sre.google/workbook/canarying-releases/ (fetched 2026-07-20)
  QUOTE: We define canarying as a partial and time-limited deployment of a change in a service and its evaluation. ... If we deploy the candidate from our trivial example, we would risk failing 20% of requests. If we instead use a canary population of 5%, we serve 20% errors for 5% of traffic, resulting in a 1% overall error rate. ... When using metrics to evaluate canary success, make sure the intervals of your metrics are either the same as or less than your canary duration.
  TRANSFERABLE RULE: INVARIANT ACROSS ALL FOUR DOMAINS — every operational procedure, regardless of technology, must state five things: (1) the exposure control and its arithmetic (what fraction of users/records the change can damage before you stop); (2) the observation window, with the explicit rule that the evaluation interval must be no shorter than the metric's own resolution; (3) the undo, named honestly as either true reversal or as forward-fix/exposure-freeze — and if the platform offers no reversal, that must be written down rather than assumed; (4) the population already affected before the stop took effect, and a separate remedy for it; (5) verification performed against real post-fix state rather than against the act of deploying. What VARIES is only the substrate: mobile's undo is a store-mediated freeze plus a forward release under third-party review latency; data's undo is an idempotent backfill bounded by time windows and watermarks; frontend's undo must defeat caches and running client code it does not own; distributed backend is the only one where the undo is genuinely a dial the operator turns.

* [HIGH] AWS's Feb 28, 2017 S3 us-east-1 outage began with an authorized operator following an *established playbook* — the playbook was present and sanctioned; the defect was that it exposed a free-text capacity-removal argument with no bound on blast radius. AWS's remediation was to move the safety check out of the human step and into the tool (rate-limit removal; refuse to take any subsystem below minimum required capacity).
  SOURCE: Amazon Web Services, "Summary of the Amazon S3 Service Disruption in the Northern Virginia (US-EAST-1) Region" (Feb 28, 2017) — https://aws.amazon.com/message/41926/ (fetched)
  QUOTE: At 9:37AM PST, an authorized S3 team member using an established playbook executed a command which was intended to remove a small number of servers for one of the S3 subsystems that is used by the S3 billing process. Unfortunately, one of the inputs to the command was entered incorrectly and a larger set of servers was removed than intended. … We have modified this tool to remove capacity more slowly and added safeguards to prevent capacity from being removed when it will take any subsystem below its minimum required capacity level. This will prevent an incorrect input from triggering a similar event in the future. We are also auditing our other operational tools to ensure we have similar safety checks.
  TRANSFERABLE RULE: A runbook step that can destroy capacity or data must not rely on the operator typing the right operand. Bound the blast radius in the tool the step invokes (rate limit, minimum-remaining floor, refusal below a safety threshold) so an incorrect input is rejected rather than executed. Corollary: when one playbook is found to have this shape, audit the sibling playbooks for the same shape.

* [HIGH] GitLab.com's Jan 31, 2017 database loss turned on two runbook defects: (a) the engineering runbook did not document that the recovery tool blocks *silently* with no output, so an engineer read normal behavior as a hung process and escalated to a destructive step; and (b) the restore path itself was neither automated nor documented properly. Separately, the 'standard backup procedure' had been failing silently for an unknown period because of a PostgreSQL version mismatch, and its own failure notifications were being rejected.
  SOURCE: GitLab, "Postmortem of database outage of January 31" (published Feb 10, 2017) — https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/ (fetched)
  QUOTE: It would later be revealed by another engineer (who wasn't around at the time) that this is normal behaviour: pg_basebackup will wait for the primary to start sending over replication data and it will sit and wait silently until that time. Unfortunately this was not clearly documented in our engineering runbooks nor in the official pg_basebackup document. … Restoring this required manual work as this was not automated, nor was it documented properly. … The standard backup procedure uses pg_dump to perform a logical backup of the database. This procedure failed silently because it was using PostgreSQL 9.2, while GitLab.com runs on PostgreSQL 9.6. … Notifications were sent upon failure, but because of the Emails being rejected there was no indication of failure.
  TRANSFERABLE RULE: For every step that invokes a tool, the runbook must state the expected observable signal — including 'this step produces no output and may appear hung for N minutes' — so silence is not misread as failure. And a recovery procedure that has never been executed end-to-end against the real target is an untested claim: schedule an exercise that proves it, and route its failure notifications to a channel whose delivery is itself monitored.

* [HIGH] Atlassian's April 5, 2022 multi-week outage (883 sites deleted) had two independent procedural defects. The peer-review procedure for the deletion script inspected the *endpoint* but not the *class of the identifiers* passed to it; the staging test mandated by change management was structurally incapable of catching the error because the production IDs did not exist in staging. Separately, the recovery runbooks existed only for smaller-scope deletions and did not cover site-level restore at this scale.
  SOURCE: Atlassian, "Post-Incident Review of the April 2022 Atlassian outage" — https://www.atlassian.com/engineering/post-incident-review-april-2022-outage (fetched)
  QUOTE: The script that was executed followed our standard peer-review process, which focused on which endpoint was being called and how. It did not cross-check the provided cloud site IDs to validate whether they referred to the app or to the entire site. The script was tested in Staging per our standard change management processes, however, it would not have detected that the IDs input were incorrect as the IDs did not exist in the Staging environment. … the site-level deletion did not have runbooks that could be quickly automated for the scale of this event which required tooling and automation across all the products and services to happen in a coordinated way.
  TRANSFERABLE RULE: A review step in a runbook must name what it verifies about the *operands*, not only the operation — e.g. 'confirm each ID resolves to an object of the expected type and scope before running.' And a rehearsal step whose environment cannot contain the real inputs proves nothing: say explicitly what the dry run does and does not cover. Recovery runbooks must declare the scope they were exercised at; a procedure validated for one tenant is not a procedure for a thousand.

* [HIGH] In Cloudflare's July 2, 2019 global outage, the written Standard Operating Procedure was itself listed among the causes: the SOP *permitted* a non-emergency WAF rule change to go straight to global production, bypassing the staged DOG/PIG/Canary path used for all other Cloudflare software. The documented rollback plan was also a contributing factor because it was too slow to execute under incident conditions.
  SOURCE: Cloudflare, John Graham-Cumming, "Details of the Cloudflare outage on July 2, 2019" — https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/ (fetched)
  QUOTE: The SOP for a rule change specifically allows it to be pushed globally. This is very different from all the software we release at Cloudflare where the SOP first pushes software to an internal dogfooding network point of presence (PoP) … Everything that occurred up to the point the rules were deployed was done "correctly": a pull request was raised, it was approved, CI/CD built the code and tested it, a change request was submitted with an SOP detailing rollout and rollback, and the rollout was executed. … The SOP allowed a non-emergency rule change to go globally into production without a staged rollout. The rollback plan required running the complete WAF build twice taking too long. … We had difficulty accessing our own systems because of the outage and the bypass procedure wasn't well-trained on.
  TRANSFERABLE RULE: A correctly followed procedure can still be the cause — audit the procedure's own rollout scope and rollback latency, not just compliance with it. Concretely: (1) a routine change and an emergency change need separate, explicitly labelled paths, and the routine one must be staged; (2) the documented rollback must be measurably faster than the failure it undoes; (3) any step depending on the system under repair (login, ticketing, build) needs a stated bypass that is rehearsed, not just written.

* [HIGH] The TSB's official findings for Swissair Flight 111 (Sep 2, 1998) name checklist design as a risk factor twice: the applicable Smoke/Fumes of Unknown Origin checklist could take 20 to 30 minutes to complete — long enough for the hazard it addresses to escalate — and the critical action (begin preparing for a landing) was placed at the *end* of the checklist, which the TSB found de-emphasized it.
  SOURCE: Transportation Safety Board of Canada, Aviation Investigation Report A98H0003, §3.2 "Findings as to risk" — https://www.tsb.gc.ca/eng/rapports-reports/aviation/1998/a98h0003/a98h0003.html (fetched and extracted)
  QUOTE: Regulations do not require that checklists for isolating smoke or odours that could be related to an overheating condition be designed to be completed in a time frame that minimizes the possibility of an in-flight fire being ignited or sustained. As is the case with similar checklists in other aircraft, the applicable checklist for the MD-11 could take 20 to 30 minutes to complete. The time required to complete such checklists could allow anomalies, such as overheating components, to develop into ignition sources. … Neither the Swissair nor Boeing Smoke/Fumes of Unknown Origin Checklist emphasized the need to immediately start preparations for a landing by including this consideration at the beginning of the checklist. Including this item at the end of the checklist de-emphasizes the importance of anticipating that any unknown smoke condition in an aircraft can worsen rapidly.
  TRANSFERABLE RULE: Order emergency-procedure steps by urgency and irreversibility, not by diagnostic tidiness: the action that buys time or preserves options goes first, before the isolation/diagnosis sequence. And time-budget the procedure against the hazard — if the checklist takes longer to run than the failure takes to become unrecoverable, the checklist is a defect regardless of the correctness of its steps.

* [HIGH] The CSB found that BP's written ISOM raffinate startup procedure for the March 23, 2005 Texas City explosion (15 killed) was deficient in specific, enumerable ways: it lacked instructions the board operator needed, it had not been updated as the unit changed, it contained an undefined acceptance term ('adequate' staffing), and — most directly relevant to operations work — it had no instructions for halting the startup partway and resuming it later with a different crew, which is exactly what happened. Management nevertheless certified the procedures annually as up to date.
  SOURCE: U.S. Chemical Safety and Hazard Investigation Board, Investigation Report No. 2005-04-I-TX, "Refinery Explosion and Fire, BP Texas City" (final report 3/20/2007), §3.1.3 "Startup Procedure Lacked Sufficient Instructions," p. 77 — https://www.csb.gov/assets/1/20/csbfinalreportbp.pdf (downloaded and text-extracted)
  QUOTE: The ISOM raffinate section startup procedure lacked sufficient instructions for the Board Operator to safely and successfully start up the unit. … The procedure also did not include instructions on halting unit operations in the middle of the startup process, as was done during the early morning hours on March 23, 2005, nor did it provide instruction for recommencing startup several hours later by a different operating crew. The hazards and safety implications of a partial startup/shutdown/re-startup were not addressed and specific steps to initiate such activities were not provided. BP's raffinate startup procedure included a step to determine and ensure adequate staffing for the startup; however, "adequate" was not defined in the procedure. … Despite these deficiencies, Texas City managers certified the procedures annually as up-to-date and complete. … Management did not ensure that the startup procedure was regularly updated, even though the startup process had evolved and changed over time with modifications to the unit's equipment, design, and purpose.
  TRANSFERABLE RULE: Three rules. (1) A multi-step procedure must specify how to suspend and resume it, including handoff to a different operator — the abandoned-midway state is a real state and needs its own steps. (2) Every acceptance word in a step must be defined in the step ('adequate', 'stable', 'healthy' are defects). (3) A periodic sign-off that a procedure is current is not evidence that it is current; tie procedure review to changes in the system it operates, and record what changed.

* [HIGH] The National Commission on the Deepwater Horizon blowout (April 20, 2010) found that the negative-pressure test — the test that would have revealed the failed cement job — had no standard written procedure or interpretation criteria at any level: not in MMS regulations, not in industry protocols, not internally at BP or Transocean, and not in the site-specific instructions given to the crew. It further found no policy requiring escalation when the data was confusing.
  SOURCE: National Commission on the BP Deepwater Horizon Oil Spill and Offshore Drilling, "Deep Water: The Gulf Oil Disaster and the Future of Offshore Drilling" (Jan 2011), Chapter Four, pp. 119–120 — https://www.govinfo.gov/content/pkg/GPO-OILCOMMISSION/pdf/GPO-OILCOMMISSION.pdf (downloaded and text-extracted)
  QUOTE: The Commission has identified a number of potential factors that may have contributed to the failure to properly conduct and interpret the negative pressure test that night: • First, there was no standard procedure for running or interpreting the test in either MMS regulations or written industry protocols. Indeed, the regulations and standards did not require BP to run a negative-pressure test at all. • Second, BP and Transocean had no internal procedures for running or interpreting negative-pressure tests, and had not formally trained their personnel in how to do so. • Third, the BP Macondo team did not provide the Well Site Leaders or rig crew with specific procedures for performing the negative-pressure test at Macondo. • Fourth, BP did not have in place (or did not enforce) any policy that would have required personnel to call back to shore for a second opinion about confusing data.
  TRANSFERABLE RULE: Any verification step in a runbook must ship with its acceptance criteria written into the step — what reading counts as pass, what counts as fail — and with a named escalation path for readings that satisfy neither. A step that says 'verify X' without stating the numeric or observable pass condition invites the operator to rationalize an anomaly into a success. When two independent indicators disagree, the procedure must mandate stop-and-escalate rather than leaving reconciliation to on-the-spot judgment.

* [HIGH] The SEC's settled order against Knight Capital (Aug 1, 2012; $460M loss in ~45 minutes) makes procedural absence a regulatory finding: no written deployment procedure requiring a second technician to check that the code reached all eight servers, and no incident-response procedure telling staff when to disconnect a malfunctioning system. In the absence of the latter, responders uninstalled the new code from the seven correctly deployed servers — an action the SEC records as having worsened the event.
  SOURCE: U.S. Securities and Exchange Commission, In the Matter of Knight Capital Americas LLC, Admin. Proc. File No. 3-15570, Exchange Act Release No. 70694 (Oct. 16, 2013), ¶¶ 15, 26, 27, 41–42 — https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf (downloaded and text-extracted)
  QUOTE: Knight did not have a second technician review this deployment and no one at Knight realized that the Power Peg code had not been removed from the eighth server, nor the new RLP code added. Knight had no written procedures that required such a review. … Knight did not have written code development and deployment procedures for SMARS (although other groups at Knight had written procedures) … On August 1, Knight did not have supervisory procedures concerning incident response. … In one of its attempts to address the problem, Knight uninstalled the new RLP code from the seven servers where it had been deployed correctly.   TRANSFERABLE RULE: Two rules. (1) A deployment runbook must include an explicit post-step that enumerates the targets and confirms each one received the change — 'deployed' is not the same as 'deployed everywhere', and the check must be performed by someone other than the deployer. * [HIGH] FAA doctrine states memory items should be avoided where possible, and when unavoidable are capped at fewer than three items and forbidden from containing conditional/decision logic. This is the only exact numeric limit I found in a regulator document. Note the hedge: the AC says 'should' throughout — it is an acceptable-means advisory circular, not a mandate — and it gives no stated basis (no cited research or memory-capacity rationale) for the number three.
  SOURCE: FAA Advisory Circular 120-71B, 'Standard Operating Procedures and Pilot Monitoring Duties for Flight Deck Crewmembers', dated 1/10/17, paragraph 4.2.5 — https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-71B.pdf (fetched via curl; PDF converted with pdftotext)
  QUOTE: 4.2.5 Memory Items. Memory items should be avoided whenever possible. If the procedure must include memory items, they should be clearly identified, emphasized in training, less than three items, and should not contain conditional decision steps.
  TRANSFERABLE RULE: Steps a human must execute from memory (before opening the runbook) are a last resort: keep them under three, mark them explicitly as memory steps, drill them, and never put a branch/conditional inside them. Any 'if X then Y' belongs in the written procedure, not in the memorized prologue.

* [HIGH] For normal procedures the FAA describes a do-confirm structure as the working default: the operator performs a memorized 'flow' to configure the system, and the checklist that follows is deliberately a SUBSET of the flow — the most critical items — whose job is to confirm the flow was done correctly, executed as challenge-and-response between two people.
  SOURCE: FAA AC 120-71B, paragraphs 5.1.2 and 5.1.4 — https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-71B.pdf
  QUOTE: 5.1.2 Type of List and Manner of Execution. For most normal procedures on the flight deck, a "flow" is conducted as a sequence of actions done from memory to configure the aircraft and its systems. The flow is followed by a checklist containing a subset of items from the flow that may be the most critical items within that flow and items that confirm the flow was done correctly. … The pilot responsible for leading the checklist begins by calling out (or "challenging") the first item on the list. The other pilot verifies that the item has been done correctly and provides the relevant response.
  TRANSFERABLE RULE: For routine, frequently-executed work, do not write a step-by-step script for the whole task. Write the full flow once for training, then make the operational checklist a short verification list containing only the critical, failure-consequential items — and phrase each as a challenge whose expected state is stated, so a second party can confirm it.

* [HIGH] FAA doctrine directs that abnormal/emergency procedures be organized and indexed by the observable triggering condition (the symptom the operator actually perceives), explicitly NOT by the subsystem that is probably at fault.
  SOURCE: FAA AC 120-71B, paragraph 4.2.1 — https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-71B.pdf
  QUOTE: 4.2.1 General Organization. Procedures should be organized as simply as possible by order of tasking. Normal procedures are typically organized in sequence by phase of flight. When applicable, abnormal, non-normal, and emergency procedures should be organized by the triggering condition (e.g., smoke in the flight deck) rather than the potentially related system (e.g., electrical system).
  TRANSFERABLE RULE: Index incident runbooks by the symptom the on-call person sees ("queue depth climbing", "5xx spike"), not by the component you believe is broken. The responder has the symptom, not the diagnosis, at the moment of lookup.

* [HIGH] The canonical NASA analysis names the two methods and identifies the property that actually distinguishes them: challenge-response ('challenge-verification-response') is a BACKUP over a configuration already achieved from memory, so it carries configuration redundancy; do-list ('call-do-response') has the list lead and direct the operator step-by-step, which ELIMINATES that redundancy — so an error can pass unnoticed once the sequence is interrupted. In a Boeing tabulation of 20 airlines the split was 12 challenge-and-response, 1 do-list, 7 combined.
  SOURCE: Degani, A. & Wiener, E. L., 'Human Factors of Flight-Deck Checklists: The Normal Checklist', NASA Contractor Report 177549, May 1990, §3.1.4 and Table A — https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf
  QUOTE: Challenge-Response. In this method, which can be more accurately termed "challenge-verification-response," the checklist is a backup for the initial configuration of the plane. Here, the pilots use their memory and other techniques to configure the plane. After completing the initial configuration, the pilots use the checklist to verify that several critical items have been correctly accomplished. … Do-list. This method can be better termed "call-do-response." In this method, the checklist is used to "lead" and direct the pilot in configuring the aircraft using a step-by-step, "cook book" approach. Therefore, the configuration redundancy employed in the challenge-response method is eliminated here. … Most do-list checklists of transport aircraft are generally very detailed and time-consuming. In addition, due to the elimination of the configuration redundancy, a mistake can easily pass unnoticed once the sequence is interrupted.
  TRANSFERABLE RULE: Choose the format by what error it catches. Do-confirm gives you two independent shots at the same state (act from expertise, then verify) — use it where the operator is competent and the risk is omission. Read-do gives you exactly one shot and loses all redundancy — so when you use it, treat interruption as the primary hazard and add explicit place-keeping (numbered steps, a resume point, a stated completion call). Whitespace in this quote is normalized from an OCR'd scan; wording is exact.

* [HIGH] The closest thing I found to an explicit selection rule is Degani & Wiener's observation of practice plus its rationale: non-normal/failure procedures are performed as read-do 'action lists', and the reason given is that these procedures exist because of the absolute necessity of correct sequencing, where a sequence error can produce an irreversible action. This is stated as an empirical characterization of how failure checklists are done and why sequence deficiencies matter there — not as a normative 'you shall use read-do' rule.
  SOURCE: Degani, A. & Wiener, E. L., 'On the Design of Flight-Deck Procedures', NASA (NTRS 19940029437), §7.2.3 'Sequencing of Actions Within a Procedure' — https://ntrs.nasa.gov/api/citations/19940029437/downloads/19940029437.pdf
  QUOTE: Sequencing is the internal mechanism that drives many cockpit procedures -- especially critical and time dependent procedures. Sometimes the only reason for a procedure is the absolute necessity of a correct sequencing of actions (e.g., engine start procedure, engine fire procedure, generator fail procedure, etc.). … With respect to emergency procedures, these deficiencies are very critical because of the time limitation, workload, and level of stress involved in dealing with an emergency. In addition, failure checklists are mostly performed as "action lists," i.e., an item is read (or recalled from memory) and immediately performed. In this case a sequential mistake can lead a crew member to take an irreversible action.
  TRANSFERABLE RULE: Selection rule: if the procedure's value IS the exact ordering, if steps are irreversible, or if it is rare/high-stress and the operator cannot be assumed to hold it in memory — write it read-do (read the step, then do it). If the operator performs it routinely and the risk is forgetting an item rather than mis-ordering — write it do-confirm. Whitespace normalized from OCR; wording exact.

* [HIGH] NASA's authoritative review states plainly that the criteria for deciding which items must be memory items are NOT scientifically established — the field has no definitive answer — while noting the industry direction of travel is to MINIMIZE memory items. It also states no guidance exists on the tradeoff between brevity and sufficiency in emergency checklists.
  SOURCE: Burian, B. K., Barshi, I. & Dismukes, K., 'The Challenge of Aviation Emergency and Abnormal Situations', NASA/TM-2005-213462, June 2005, 'Design of Emergency and Abnormal Checklists and Procedures', pp. 9-10 — https://ntrs.nasa.gov/api/citations/20060023295/downloads/20060023295.pdf
  QUOTE: Checklists should be written so as to minimize the memory load on pilots. … For example, some crew actions in response to highly time-critical situations may require their performance from memory, without reference to a printed checklist. However, under stress, normally reliable memory processes can fail. Which items on a checklist absolutely must be performed by memory, if any, and which should or could be performed by reference to a printed checklist? The research community has yet to provide checklist designers with definitive answers. Nonetheless, several airlines and some manufacturers are revising their procedures to minimize the use of memory checklist items (Berman and Geven, 2005). … Unfortunately, no guidance or standards exist for checklist developers concerning the best balance between minimal length of checklists and providing sufficient information.
  TRANSFERABLE RULE: Do not claim a principled basis for which steps are memorized versus read — aviation does not have one either. Default to minimizing memorized steps and justify each one individually by time-criticality, and treat 'how short should this runbook be' as an explicit judgment call to document, not a solved question.

* [HIGH] The operative criterion for a memory item is time-criticality, not importance: an action becomes a memory item only when the situation leaves insufficient time to reference the printed checklist. FAA Order 8900.1's definition of an immediate action item (quoted in this NASA report) sets a high bar — the consequence of delay must be loss of control, crew incapacitation, or loss of a system such that continued safe flight is improbable. In practice, this NASA study found the industry applies the criterion inconsistently: memory-item counts per QRH ranged from 1 to 87, and the number of checklists carrying them ranged from 1 to 22, with no research basis for the choices.
  SOURCE: Burian, B. K., 'Factors Affecting the Use of Emergency and Abnormal Checklists: Implications for Current and NextGen Operations', NASA/TM-2014-218382, July 2014 — glossary (pp. xii, xiv), Executive Summary, and §3.2 — https://ntrs.nasa.gov/api/citations/20190002686/downloads/20190002686.pdf
  QUOTE: Memory items: Actions or information that must be performed or recalled from memory because a critical situation exists in which insufficient time is available for reference to a printed checklist. … Immediate action items: "An action that must be taken in response to a nonroutine event so quickly that reference to a checklist is not practical because of a potential loss of aircraft control, incapacitation of a crewmember, damage to or loss of an aircraft component or system—which would make continued safe flight improbable." (FAA, 2007a, 3-3128) … The number of checklists with Memory Items across all QRHs ranges from 1 to 22. … The total number of Memory Items (across all checklists in each QRH) ranges from 1 to 87. … A high degree of variability was identified across the air carrier participants, even within aircraft type, with regard to which checklists warrant memory items and how many are necessary. This is not surprising as it appears that no research has been conducted which would help manufacturers and air carriers make these kinds of determinations.
  TRANSFERABLE RULE: Promote a step to 'do this from memory before opening the runbook' on one test only: would the delay of opening the runbook itself cause irreversible loss? Criticality alone is not sufficient — a critical step you have time to read is a read step. Also: three named tiers exist in practice (memory / immediate-action-but-may-be-read-from-a-card / reference), and the middle tier is the one whose meaning drifts between teams, so define your tiers explicitly if you use more than two.

* [HIGH] Counting memory items understates their cost, because in practice they are not all simple actions. Of 239 memory items coded across eleven QRHs, 79% (n=190) were challenge-response action items and 8% (n=20) sentence-form action items, but 12% were NOT action items at all — conditionals, timers, critical notes, explanatory text — and 24 of the 190 (13%) required cross-crew confirmation before acting. Chained checklists could require recalling as many as 17 items with no printed reference.
  SOURCE: Burian, B. K., NASA/TM-2014-218382, §3.2.2 Findings, pp. 27-29 — https://ntrs.nasa.gov/api/citations/20190002686/downloads/20190002686.pdf
  QUOTE: Thus, in some cases the pilots may be expected to be able to recall as many as 17 different items without reference to a printed checklist or QRC. … Indeed, most of the 239 Memory Items coded in this study were challenge-response Action Items (n = 190; 79%) or sentence form Action Items (n = 20; 8%). However, 24 (13%) of the 190 challenge-response Action Items require that both crew members confirm that the correct lever, handle, or switch has been identified before the action is taken … Furthermore, 12% of the 239 Memory Items coded are item types different than Action Items, such as Conditional Items (e.g., If condition XYZ exists…), Delaying or Timer Items … Although all these non-Action Items are considered Memory Items, pilots and checklist developers often forget to think of them as such and do not appreciate the extra cognitive load they place on pilots during a particularly stressful time.
  TRANSFERABLE RULE: When you budget memorized steps, count the conditionals, waits, and warnings as memorized steps too — not just the actions. A 'three memory items' procedure that also requires recalling a branch condition and a 30-second wait is really a five-item memory load. And for destructive actions (delete, failover, cut traffic), require an explicit second-party confirmation of the target identity before the action — but recognize that confirmation is itself a memorized coordination step and costs budget.

* [HIGH] Interruptions as short as ~3-4 seconds measurably destroy place-keeping in a sequential procedure. In a controlled study (N reported in paper; JEP:General), interruptions averaging 4.4 s tripled sequence-error rates on post-interruption trials versus baseline, and interruptions averaging 2.8 s (about the duration of one step) doubled them. Critically, NON-sequence errors were unaffected — the damage is specifically to knowing WHERE YOU ARE, not to general attention or competence.
  SOURCE: Altmann EM, Trafton JG, Hambrick DZ. "Momentary interruptions can derail the train of thought." Journal of Experimental Psychology: General. 2014 Feb;143(1):215-26. doi:10.1037/a0030986. PMID: 23294345. Fetched: https://pubmed.ncbi.nlm.nih.gov/23294345/
  QUOTE: We investigated the effect of short interruptions on performance of a task that required participants to maintain their place in a sequence of steps each with their own performance requirements. Interruptions averaging 4.4 s long tripled the rate of sequence errors on post-interruption trials relative to baseline trials. Interruptions averaging 2.8 s long--about the time to perform a step in the interrupted task--doubled the rate of sequence errors. Nonsequence errors showed no interruption effects, suggesting that global attentional processes were not disrupted.
  TRANSFERABLE RULE: Design the document so that the reader's place is recoverable from the PAGE, never from memory. Every step must carry a persistent, unambiguous, externally visible position marker (stable step numbers that never renumber, a checkable box per step, a visible progress/step-count), because the reader's internal place-marker is destroyed by interruptions far shorter than any you can prevent. Corollary: never write a step whose meaning depends on the reader remembering what the previous step did.

* [HIGH] The cost of an interruption is directly measurable as "resumption lag," and it roughly doubles normal step-to-step time. External cues visible immediately BEFORE the interruption reduce that lag — but only if the reader gets 6-8 seconds of warning to encode them. With only 2 or 4 seconds of warning, cue availability had no effect at all.
  SOURCE: Altmann EM, Trafton JG. "Task Interruption: Resumption Lag and the Role of Cues." Proceedings of the Annual Meeting of the Cognitive Science Society, 26(26), 2004, pp. 43-48. Fetched full text PDF: https://escholarship.org/uc/item/18b4r661
  QUOTE: In absolute terms, the resumption lag was 3.8 s – double the 1.9 s inter-action interval, which was measured rather conservatively by excluding all inter-action intervals under 1 s. […] For 2- and 4-second interruption lags, there was no effect of cue availability, Fs<1. For the 6-second interruption lag, the cue-availability effect was marginal, F(1,22)=4.1, p=.056. For the 8-second interruption lag, the cue-availability effect was reliable, F(1,22)=5.7, p<.03. […] the various cognitive operations required to locate and encode retrieval cues during the interruption lag take somewhere between 6 and 8 seconds to complete (in our task environment).
  TRANSFERABLE RULE: Put the resumption cue in the document, permanently, rather than relying on the reader to construct one in the moment — because the moment is usually too short (under ~6 s) for cue encoding to work. Concretely: give every step a self-contained restatement of the state it assumes and the state it produces, so re-entry at any step needs no reconstruction of history. NOTE THE HEDGE: the authors' own cross-experiment omnibus test found the cue effect only marginal (F(1,88)=3.6, p=.060), and they call the work "exploratory"; the 6-8 s figure is qualified as "in our task environment" and should not be treated as a universal constant.

* [HIGH] Resumption cost scales with both the DURATION and the COGNITIVE DEMAND of the interruption, up to at least 1 minute, and rehearsal of the suspended goal mitigates the decay. This is the mechanism (memory-for-goals) behind place-loss, and the authors explicitly extend it to real operational settings.
  SOURCE: Monk CA, Trafton JG, Boehm-Davis DA. "The effect of interruption duration and demand on resuming suspended goals." Journal of Experimental Psychology: Applied. 2008;14(4):299-313. doi:10.1037/a0014402. PMID: 19102614. Fetched via Europe PMC REST API: https://www.ebi.ac.uk/europepmc/webservices/rest/search?query=%22The+effect+of+interruption+duration+and+demand+on+resuming+suspended+goals%22&format=json&resultType=core
  QUOTE: Three experiments using an interleaved tasks interruption paradigm showed that longer and more demanding interruptions led to longer resumption times in a hierarchical, interactive task. The resumption time profile for durations up to 1 min supported the role of decay in defining resumption costs, and the interaction between duration and demand supported the importance of goal rehearsal in mitigating decay. These findings supported the memory for goals model, and had practical implications for context where tasks are frequently interleaved such as office settings, driving, emergency rooms, and aircraft cockpits.
  TRANSFERABLE RULE: Build rehearsal into the document rather than hoping the reader does it. Bound each procedure into short, self-contained blocks with an explicit "state now" checkpoint at each block boundary — a restatement the reader re-reads on return. The longer and more demanding the expected interruption, the more state the checkpoint must restate. Never assume a returning reader retains anything not written down.

* [HIGH] Fatigue attacks place-keeping SPECIFICALLY and directly — not merely via general sleepiness — and the researchers' own stated recommendation is operational, not just theoretical: sleep-deprived people should not run interruption-prone, high-consequence procedures, or should run them only briefly. A follow-up study found 200 mg caffeine restored vigilant attention but did NOT significantly restore place-keeping.
  SOURCE: (a) Stepan ME, Fenn KM, Altmann EM. "Effects of sleep deprivation on procedural errors." J Exp Psychol Gen. 2019;148(10):1828-1833. doi:10.1037/xge0000495. PMID: 30265024. (b) Stepan ME, Altmann EM, Fenn KM. "Caffeine selectively mitigates cognitive deficits caused by sleep deprivation." J Exp Psychol Learn Mem Cogn. 2021;47:1371-1382. doi:10.1037/xlm0001023. PMID: 34014758. Both fetched via Europe PMC REST API: https://www.ebi.ac.uk/europepmc/webservices/rest/search?query=AUTH%3A%22Stepan+ME%22+AND+%22sleep+deprivation%22+AND+procedural&format=json&resultType=core
  QUOTE: In a large sample (N = 234), we tested effects of 24-hr of sleep deprivation on error rates in a procedural task that requires memory maintenance of task-relevant information. […] Among sleep-deprived participants who could still perform the task, error rates were elevated, and errors reflecting memory failures increased with time-on-task. The results suggest that sleep-deprived individuals should not perform procedural tasks associated with interruptions and costly errors—or, if they must, they should perform such tasks only for short periods. […] [2021] Caffeine counteracted this impairment in vigilant attention but did not significantly affect placekeeping for most participants […] suggests that caffeine has limited potential to reduce procedural error rates in occupational settings.

(1) Keep any single unbroken procedural block SHORT, because error rates from memory failure rise with time-on-task under fatigue — put a hard stopping/handoff point every few steps rather than one 40-step wall. (2) Design for the degraded reader as the DEFAULT case, not the exception: the standard mitigations a tired operator will actually reach for (caffeine, 'just focus') do not restore place-keeping. The document must carry the place, because the reader cannot.

* [HIGH] Aviation human-factors research recommends ordering procedure steps so the most critical ones are executed BEFORE an interruption is likely to arrive, and explicitly ranks this above the otherwise-preferred logical/spatial ordering when the two conflict. It also recommends chunking long procedures and writing an explicit completion call as the final item, because a paper procedure gives no indication that it is finished.
  SOURCE: Degani A, Wiener EL. "Human Factors of Flight-Deck Checklists: The Normal Checklist." NASA Contractor Report 177549, Contract NCC2-377, May 1990. Appendix A (Proposed Guidelines), pp. 66-67, and §5.3, p. 31. Fetched: https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf

[…] (7) A long checklist should be subdivided to smaller task-checklists or chunks that can be associated with systems and functions within the cockpit. […] (6) The completion call of a task-checklist should be written as the last item on the checklist, allowing all crew members to move mentally from the checklist to other activities with the assurance of all pilots that the task-checklist has been completed. […] [§5.3] The lack of indication that a task-checklist is fully completed is one of the handicaps of the paper checklist.
  TRANSFERABLE RULE: Order steps by interruption-survival, not just by logic: put the irreversible/highest-consequence steps as early as the dependencies allow, so a reader who is pulled away has already banked them. Split any long procedure into named blocks short enough to finish in one sitting. End every block with an explicit, written completion statement as its own final numbered item — completion must be an affirmative recorded act, not the absence of remaining steps. * [HIGH] The single most common step-level ambiguity found in real operational checklists is a response that merely acknowledges the step ("set", "check", "completed") rather than stating the observed value. The authors argue the response should always report the actual status or value, and cite a field report where "checked and set" was said reflexively over an incorrect setting that was only caught during takeoff roll.
  SOURCE: Degani A, Wiener EL. "Human Factors of Flight-Deck Checklists: The Normal Checklist." NASA CR-177549, May 1990, §6.2.3 "Checklist Ambiguity", p. 41, and Appendix A guideline (4), p. 66. Fetched: https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf
  QUOTE: Many checklists examined by the authors employ the ambiguous responses "set", "check", "completed," etc. to indicate that an item is accomplished. […] I strongly feel that we need to back the response portion of our checklist with "what you see" responses not just "checked and set," etc. For example "Altimeters 30.10" and not "checked"; airspeed/EPR 125/2.00. It takes as much time to say it like it is as to say "checked and set." The problem is "checked" and "set" can be said too easily without any sound verification... (ASRS #76798) […] (4) Checklist responses should portray the desired status or the value of the item being considered (not just "checked" or "set").
  TRANSFERABLE RULE: Write every verification step so that satisfying it requires REPORTING AN OBSERVED VALUE, not asserting completion. Bad: "Verify the service is healthy." Good: "Record the value of <health field>; it must read <expected>." This is the highest-leverage single rule against misreading a step: an acknowledgment can be given reflexively without looking, a transcribed value cannot. * [HIGH] A standards body (W3C) specifies exact, testable typographic minimums for readable blocks of text — including a hard line-length ceiling of 80 characters — but note the conformance split: the line-length/leading/justification rules are Level AAA (the highest, least commonly required tier), while the text-spacing tolerances are Level AA.
  SOURCE: W3C. Web Content Accessibility Guidelines (WCAG) 2.2, SC 1.4.8 Visual Presentation (Level AAA), SC 1.4.12 Text Spacing (Level AA), SC 3.1.5 Reading Level (Level AAA). Fetched: https://www.w3.org/TR/WCAG22/
  QUOTE: [1.4.8, Level AAA] Width is no more than 80 characters or glyphs (40 if CJK). Text is not justified (aligned to both the left and the right margins). […] [1.4.12, Level AA] Line height (line spacing) to at least 1.5 times the font size; Spacing following paragraphs to at least 2 times the font size; Letter spacing (tracking) to at least 0.12 times the font size; Word spacing to at least 0.16 times the font size.
  TRANSFERABLE RULE: Hard limits for a runbook: lines no wider than 80 characters; no justified text (ragged right only — justification creates irregular word-spacing rivers that promote line-skipping); line-height at least 1.5x font size; paragraph/step separation at least 2x font size so consecutive steps cannot visually merge. The 80-char and generous inter-step spacing rules are the direct structural defenses against a reader's eye returning to the WRONG LINE after looking away — which is exactly the conflate-two-steps failure mode.

* [MEDIUM] Cognitive load theory holds that requiring a reader to mentally integrate two spatially separated information sources imposes extraneous load (split-attention), and that adding information which is not essential also imposes extraneous load by interfering with the essential material (redundancy). IMPORTANT CAVEAT the source itself states: which strategy helps depends on the reader's expertise (expertise reversal).
  SOURCE: Castro-Alonso JC, de Koning BB, Fiorella L, Paas F. "Five Strategies for Optimizing Instructional Materials: Instructor- and Learner-Managed Cognitive Load." Educational Psychology Review. 2021;33:1379-1407. doi:10.1007/s10648-021-09606-9. PMCID: PMC7940870. Fetched: https://pmc.ncbi.nlm.nih.gov/articles/PMC7940870/
  QUOTE: To learn from such a format, learners must split their attention between the textual and graphical representations and are required to mentally integrate these two information sources to construct an adequate and coherent mental representation. […] According to cognitive load theory, redundant information creates extraneous cognitive load because it interferes with processing the essential information. […] The expertise reversal effect suggests that instructor-managed solutions may be most effective for novice learners, whereas learner-managed solutions may be most effective for more advanced students.
  TRANSFERABLE RULE: Two rules, but flagged as INFERRED TRANSFER — this evidence base is about LEARNING outcomes, not about executing a procedure under stress; I found no primary study demonstrating these effects for procedural execution. (1) Anti-split-attention: put everything a step needs INSIDE that step — the exact command, the expected output, the rollback — never 'see section 4.2' or a diagram three pages away; a reader who must cross-reference loses their place at the cross-reference. (2) Anti-redundancy: strip rationale, background, and alternative approaches out of the executable path into a separate section; every non-essential word in a step is an opportunity to misread it. The expertise-reversal caveat means a runbook aimed at a novice on-call responder should be more explicit than one aimed at its author.

  TRANSFERABLE RULE: Every procedure ends with a mandatory close-out block, executed before the system is handed back: (1) remove/account for everything the procedure introduced (temporary debug builds, test fixtures, jumpers, bypass flags, scaffolding credentials), (2) affirmatively confirm the system is structurally whole, (3) confirm no one else is mid-operation on it, (4) notify dependents before re-enabling. Close-out is a numbered step list, not a sentence saying "clean up."

* [HIGH] MIL-STD-40051-2A mandates that *every* work package carry an INITIAL SETUP block enumerating test equipment, tools and special tools, materials/parts (including expendables, mandatory replacement parts and Critical Safety Items), personnel required (with count and skill), references, required equipment conditions, special environmental conditions, drawings, and estimated time. * [HIGH] MIL-STD-40051-2A fixes the *position* of hazard information relative to the thing it protects: a warning/caution attached to a step shall precede that step (whereas one attached to a whole task or procedure follows the title). It further mandates severity ordering (warnings, then cautions, then notes) and forbids layouts that separate a warning from the text it applies to across a page break.
  SOURCE: MIL-STD-40051-2A, 21 July 2010, clause 4.8.7.4 "Display of warnings, cautions, and notes" (items a, b; see also item j). Fetched from https://www.cvgstrategy.com/wp-content/uploads/2013/08/MIL-STD-40051-2A.pdf
  QUOTE: a. Warnings, cautions, and notes shall appear as follows: (1) For tasks, they shall follow the title of the associated task. (2) For procedures, they shall follow the title of the associated procedure. (3) For steps, they shall precede the associated step. b. If multiple warnings, cautions, and notes apply to the same text, warnings shall appear first, cautions shall appear second, and notes shall appear last. […] j.   TRANSFERABLE RULE: A hazard notice attaches to the smallest unit it governs and is rendered immediately *before* that unit — never after it, never only in a preamble the reader has already scrolled past. Scope-wide hazards go under the section title; step-specific hazards go directly above the step. When several apply, order them by severity (irreversible-harm first). Never allow a notice to be visually separated from its step (page break, collapsed block, scroll boundary).

* [HIGH] The S1000D procedural schema makes preliminary requirements and close-out requirements structurally unskippable: a <procedure> element's content model requires <preliminaryRqmts> and <closeRqmts> (neither carries minOccurs="0"), and inside preliminaryRqmts the required conditions, support equipment, supplies, spares and safety elements are likewise mandatory. Each of those categories is an <xs:choice> between an explicit "none" element (noConds, noSupportEquips, noSupplies, noSpares, noSafety) and the actual list — so a document that simply omits spares or safety is schema-invalid; the author must positively assert "none required". * [HIGH] US DOE's human-performance handbook gives an operational definition a runbook can key off: a "critical step" is one whose incorrect performance causes irreversible harm — "an immediate negative consequence that cannot be reversed or undone" — and "irreversible" is defined as results "that cannot be returned to original conditions by reversing the initiating actions." It recommends (as good practice, not as a requirement) two-person controls specifically at these points: peer-check for "[i]rreversible or otherwise unwanted actions", and concurrent verification "for actions that could lead to irreversible consequences", with the procedure itself serving as the signed record of that verification. The handbook explicitly states its practices "are intended to be illustrative, not definitive."
  SOURCE: DOE-HDBK-1028-2009, June 2009, "Human Performance Improvement Handbook, Volume 2: Human Performance Tools for Individuals, Work Teams, and Management", U.S. Department of Energy — Attachment 1 definitions (pp. 128–129) and "Concurrent Verification"/"Peer-Checking" sections (pp. 42–43). DISTRIBUTION STATEMENT A. Fetched via Wayback: http://web.archive.org/web/20170219055709if_/https://www.standards.doe.gov/standards-documents/1000/1028-BHdbk-2009-v2/@@images/file
  QUOTE: Critical step – A procedural step or series of steps or an action that, if performed improperly, will cause irreversible harm to plant equipment or people, or that will significantly affect facility operation. An action that if performed improperly has an immediate negative consequence that cannot be reversed or undone. […] Irreversible – Actions and related results that cannot be returned to original conditions by reversing the initiating actions. […] CV is usually reserved for key components, where an error with the action could result in possibly irreversible harm. The primary intent of verification is to confirm the final condition of the equipment. When used conscientiously, CV provides a means to identify an error in the act of establishing the new equipment or component condition.
  TRANSFERABLE RULE: Classify and visibly mark every step as reversible or critical (irreversible), using a stated test: "if done wrong, can the initiating action be reversed to restore the original condition?" For each critical step the runbook must name the second pair of eyes and record the confirmation in the runbook itself (a signed/initialled checkpoint), and must state the consequence of getting it wrong. Marking is done at authoring time, before the operator is under time pressure.

* [HIGH] NIST's platform firmware guidelines impose two requirements a cloud runbook typically has no analogue for: (1) an update to critical data "shall be validated … prior to committing" — validation is required as a distinct phase before the point of no return, not after; and (2) even the update mechanism itself must survive interruption — during an update of the root/chain of trust for update, the component "shall always be operational or recoverable upon a subsequent reboot even in the event of an unexpected, catastrophic event (e.g., power loss in the middle of a flash write operation)." Note SP 800-193 is a NIST Special Publication (guidelines); its "shall" statements are normative within the document's own conformance framing rather than law.
  SOURCE: NIST Special Publication 800-193, "Platform Firmware Resiliency Guidelines", Andrew Regenscheid, May 2018 — §4.2.4 item 2 (Protection of Critical Data) and §4.1.2 item 2 (Root of Trust for Update). Fetched: https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-193.pdf
  QUOTE: Critical data updates shall be validated either by the device or a symbiont's host device prior to committing changes to critical data to ensure that the new data is well-formed. Examples of validation can include range or bounds checking, format checking, etc. […] During such an update, the RTU or CTU shall always be operational or recoverable upon a subsequent reboot even in the event of an unexpected, catastrophic event (e.g., power loss in the middle of a flash write operation).
  TRANSFERABLE RULE: Split every irreversible operation into a verify phase and a commit phase, and make the runbook's verify phase check the *payload itself* (signature, checksum, format, bounds, target-device match) before the commit command is typed. Then state explicitly what happens if the commit is interrupted mid-way — if the answer is "the unit is unusable", that is a design defect to escalate, not a step to write around. The runbook should name the interruption window and how to shorten or survive it (battery/UPS, staged write, second bank).

* [HIGH] RFC 9019 states that IoT devices "must not fail when a disruption, such as a power failure or network interruption, occurs during the update process", and — usefully for procedure authors — enumerates that there are exactly two recovery strategies for invalid firmware: the bootloader can select a different valid image already on the device, or it can obtain a new valid one. It also notes the assumption that the bootloader itself "or a minimal part of it, will not be updated since a failed update of the bootloader poses a reliability risk." Status caveat: RFC 9019 is Informational and contains no RFC 2119/BCP 14 keyword boilerplate, so "must" here is prose emphasis, not a normative keyword.
  SOURCE: RFC 9019, "A Firmware Update Architecture for Internet of Things", B. Moran, H. Tschofenig, D. Brown, M. Meriac, IETF, April 2021, Category: Informational — §3 (Installation) and §4/§4.1 (Invoking the Firmware / The Bootloader). Fetched: https://www.rfc-editor.org/rfc/rfc9019.txt
  QUOTE: Devices must not fail when a disruption, such as a power failure or network interruption, occurs during the update process. […] If the bootloader concludes that the newly available firmware image is invalid, a recovery strategy is necessary. There are only two approaches for recovering from invalid firmware: either the bootloader must be able to select different, valid firmware or it must be able to obtain new, valid firmware. […] In general, it is assumed that the bootloader itself, or a minimal part of it, will not be updated since a failed update of the bootloader poses a reliability risk.
  TRANSFERABLE RULE: A runbook for an irreversible operation must name its recovery path before the first irreversible step, and the path must be one of exactly two kinds: fall back to a known-good artifact already present on the target, or re-obtain a known-good artifact through a channel that still works after the failure. Write down which one applies, what physical access or hardware it needs (serial cable, JTAG, recovery button, RMA), and who is authorized to invoke it. If neither path exists, say so in the runbook as a stop-ship condition. Never place the recovery mechanism itself inside the scope of the change.
