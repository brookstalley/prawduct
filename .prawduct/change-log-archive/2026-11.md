## 2026-11-22: delegate briefs name a scratch subdirectory, and the revisit-due advisory names both kinds of date

<!-- prawduct: type=fix | scope=delegate-scratch-and-revisit-wording | closes=brookstalley/prawduct#1210 | release=v3.9.0 -->

Parallel delegates all used the session's one scratch directory, and the delegation guide's brief
checklist never mentioned it. Delegates running at the same time overwrote each other's
same-named files, including the backups a mutate-and-restore check depends on. The
ownership-boundary item in `delegation.md` "What a brief must say" now includes the delegate's own
scratch subdirectory, and the anti-patterns gain its tell: two briefs in one wave that name no
scratch location, or the same one.

The `revisit-due` advisory called every past `revisit:` date an expired exception and asked the
owner to renew it or let it lapse. The field also carries dated re-checks, such as a measurement
booked for a date (#981), and for those the answer is to do the work. The advisory's summary and
owner line now name both kinds of date, and so do the field's operational descriptions: the
backlog skill, the scaffolded backlog legend, the backlog data model and the probe's docstrings.
Design rationale that describes only the exception use is left as written, because it is still true. The advisory's evidence line is
unchanged, so its id is stable and an open advisory is not re-minted.

**Consumer note:**

When you delegate to parallel subagents, give each one its own scratch subdirectory in its brief.
The `revisit-due` advisory now says a past `revisit:` date may be work scheduled for that date
rather than an expired exception. Its id is unchanged, so a dismissal still holds.

## 2026-11-22: a `none:` consumer note wrapped onto a second line is still read as none

<!-- prawduct: type=fix | scope=none-reason-wraps | release=v3.9.0 -->

`none: <reason>` in a fragment's consumer note was matched against one line only. Fragment prose
wraps at the file's width, so a reason wrapped onto a second line read as consumer text, and the
release cut published "none: …" into the changelog as if it were a note for consumers. Three of
this release's own fragments hit it, found in the cut's preview. The match now spans lines, and the
reason is printed with its line breaks collapsed. A real note that merely contains "none:" further
down is unaffected. A `none:` note followed by a separate paragraph is now refused
(`none-with-note`): the cut would otherwise drop that paragraph without a word.

**Consumer note:**

A `none:` consumer note in a change fragment may now wrap onto more than one line; the release cut
still reads it as none and publishes nothing for it. A `none:` note followed by a blank line and
more text is refused as `none-with-note`: write the note for consumers, or keep only the reason.

## 2026-11-18: changing an advisory's literal evidence now fails a test until its probe version moves

<!-- prawduct: type=fix | scope=advisory-evidence-pins | closes=brookstalley/prawduct#1192 | release=v3.9.0 -->

An advisory's id hashes its probe version with its evidence. New evidence under an old version
therefore mints a new id that reads as an accident: the open advisory is resolved as if its
condition had cleared, instead of being superseded by the refined one. The advisory spec says to bump
the version, and that was a rule to remember at the edit. `tests/test_advisory_evidence_pins.py` now
pins every probe candidate whose evidence is spelled as literals or module constants: a changed
digest under an unchanged version fails, and the failure names the remedy. Candidates whose evidence
is built from live data are counted rather than pinned, so a literal moved behind a helper shows up
as a changed count. `advisory_store.registered_versions()` reads the version each type is stamped
with, without running a probe.

The case that prompted this, the gitignore probe's `contract-ignored-by-rule` evidence reworded under
version 1, needs no bump: that advisory type has not shipped in a release, so no released id can go
stale.

**Consumer note:**

none: a test-only guard; no advisory id changes

## 2026-11-18: An earlier review round's open findings are no longer hidden behind the newest review

<!-- prawduct: type=fix | scope=branch-review-set | closes=brookstalley/prawduct#334 | release=v3.9.0 -->

Three surfaces read the newest review in place of the branch's reviews. A finding left open on an
earlier round was invisible to the census, named by no `verify-resolutions` roll-call, and routed by
the gate to a whole spanning `cumulative`. The census, the handoff and the round budget now compose
over one set, `coverage.branch_review_ids`. It holds the review facts anchored on
`merge_base..HEAD`. When that span holds no commits, it holds this worktree's review facts, narrowed
as the last paragraph describes. The round budget already counted over that set and now takes it
from the same owner, passing its scope. Its `review_ids` are unchanged.

**Render.** `render-dispositions` with no flags renders every review in the branch's set. When the
set is unavailable or empty, it renders the newest review and prints one stderr line saying so.
`--review` and `--scope` are unchanged. The census summary adds `open_blocking`,
`open_blocking_basis` and `undispositioned_warning`, and the report schema moves to 3. Both changes
are additive.

**Write.** `carried_blocking` returns every blocker the gate still counts at the tree the verify
pass anchors on, an earlier round's included. The verify dispatch's roll-call, the consolidation
`NOT DONE` line and the derived findings cache all carry them. A verify dispatch counts them as
actionable, so it is no longer refused as "nothing to verify" when the only open blocker is an
earlier round's. The verify pass's interval anchor is unchanged.

**Gate.** `check-cumulative-critic` no longer says "no verify-resolutions pass will name again" for
a superseded blocker the roll-call names. It says to run verify-resolutions instead. A blocker the
roll-call would not name still routes to a spanning `cumulative`.

**Read.** The session handoff's `## Critic Findings` section adds one line under the newest
review's record. That line comes from facts over the branch's set and gives the open blocking count,
the undispositioned warning count and the number of rounds. When the store is unreadable or the set
cannot be derived, the line says so and does not report the branch clean.

**One predicate for "open", and a bounded fallback.** The roll-call, the `NOT DONE` line, the
verify dispatch's count, the gate's remedy and the census ask the gate's own question,
`coverage.open_blockers`. The handoff line does not: composing it is a coverage walk measured at
~75s on a cold verdict memo, which SessionStart would pay, so that line counts blockers with no
resolution fact, says so, and names `check-cumulative-critic` for the gate's count. It reads the coverage verdict from
the merge base through `coverage_algebra.blockers_counted`. A blocker is open only while the gate
counts it. A resolution fact clears it, and so does a clean spanning review whose composed path
never stands at the blocker's tree. Before this, a blocker with no resolution fact counted as open
even after such a review. The gate passed, but the roll-call still named the blocker, a verify
round was dispatched for nothing, consolidation wrote a false `NOT DONE`, and the handoff and the
census reported it open. The census summary's new `open_blocking_basis` says whether its count came
from the gate or, when no path composes, from resolution facts alone.

With an empty span, the worktree fallback no longer returns every review the worktree ever
recorded. That pool was over a thousand facts in a long-lived checkout, across all scopes and all
time. The fallback now keeps only the reviews linked to HEAD's tree, using the same review-link
rule, `coverage_algebra.linked_reviews`, that the verify anchor, `review_chain` and the
extended-interval walk now share. The round budget passes its scope instead and is bounded by that
scope. One consolidation also resolves the merge base and walks the lineage only once.

**Consumer note:**

A bare `render-dispositions` now lists every review on the branch, not just the newest one, so a
change-log entry or PR body pasted from it can grow. Pass `--review <id>` to get the old
single-review table. A `--json` consumer sees `schema_version: 3`, which has three new summary keys
and no removed ones.

## 2026-11-18: plan status credits a chunk whose review was extended by a verify pass, or whose commit came in through a delegate merge

<!-- prawduct: type=fix | scope=chunk-credit-merged-verified | closes=brookstalley/prawduct#1191,brookstalley/prawduct#1199 | release=v3.9.0 -->

`prawduct-hook plan status` left two kinds of reviewed chunk `open`, even though
`check-cumulative-critic` covered them.

- **A verify pass extending a dirty-tree chunk review (#1191).** A `verify-resolutions` pass over
  a review of uncommitted work records no `base_commit`, because the writer copies the prior
  review's `head_commit` and a dirty-tree review has none. A span with no `base_commit` carried
  nothing, so committing the verified tree verbatim as `(Chunk N)` credited no chunk. Such a pass
  now spans from the anchor of the review it extends. The link is the one `critic_mode.review_chain`
  follows: a review's `base_tree` is the head tree of the newest review before it. The credit
  holds only while every review on that line is a coverage edge and certifies by the usual rule.
  Its blocking findings must be resolved and its anchor must be on the branch. The chunk's commit
  carries work from both intervals.
- **A delegate's chunk commit merged with `--no-ff` (#1199).** A span read the interval along
  first parents only, which drops the delegate's `(Chunk N)` commit on the merge's second parent.
  The merge commit's own subject is unscoped, so it counts for nothing either. A merge now adds the
  first-parent commits of the side it brought in, unless that side is the base's own work. The base's
  own work is a merged-in tip on the plan's base's first-parent history. A delegate's tip is never
  there, either before the plan merges or after. A merge of the base still carries nothing. When
  the base resolves to no ref, or git cannot answer, the side carries nothing.

The fact's `chunks_proposed` is unchanged: a `chunk`-mode proposal still names chunks by
Deliverables path alone. The chunk is credited by span, as `plan status` reports.

**Consumer note:**

`plan status` may now show as done a chunk it showed as open: one verified by a
`verify-resolutions` pass and then committed, or one built by a delegate and merged into the plan's
branch with a merge commit. No action needed.

## 2026-11-18: a class finding records its members, and a fixed claim that skips one is not recorded

<!-- prawduct: type=feature | scope=class-finding-members | closes=brookstalley/prawduct#847 | release=v3.9.0 -->

A reviewer could rate a finding `class`, list its members in prose, and watch the builder fix the
member it led with: `verify-resolutions` graded the finding, and the next round found the members
nobody touched. On the 2026-09-19 `test-report-scope` branch that cost three rounds where one would
have done.

**Measured first.** `tools/measure-class-member-closure.py` reads every clone's evidence store under
a root (read-only, aggregate output, review facts since 2026-08-04, deduplicated by fact id). It
counts (a) class-framed findings naming two or more sites, and (b) of those, the ones a later
same-scope BLOCKING finding named a listed member of. The decision reading, fixed before the data,
matches on identifier sites; a path-inclusive ceiling and a labelled-class, code-shaped floor are
printed beside it. Run on 2026-11-18 over the fleet (14 clones, 5,389 review facts over 3.5
months; one more clone holding an evidence store is not an onboarded product and was left out
with `--exclude`, and including it moves no figure across the bar): (a) 3,273 of 3,396 class-framed findings (96%); (b) 370, about 105 a month, with the floor at
about 40 a month and the ceiling at about 169. The bar was 3 a month, and even the floor clears it,
so **D2 is built (go)**. Re-derive with `tools/measure-class-member-closure.py --exclude <that clone>
--control-scope test-report-scope`. The positive control is that branch's facts in this repo's store.
The tool counts round 3 to 4 (a class finding's `TestTheClassifier`/`_Config` members raised again)
and round 4 to 5 (`target.parent.mkdir`, the OSError source the fix left outside the `try`). Its
first run missed the second event, because a dotted identifier read as a file name. That was fixed
and pinned before the figures above were taken. (b) is a floor on the incident's shape: the
`ignore_glob` member was listed under an `instance` label, which the tool does not count.

**D1.** A partial finding may carry `scope` (`instance`|`class`|`none`), `closure` (one sentence:
the property that decides membership) and `members` (`[{id, site, note?}]`). They round-trip into
the review fact and `.critic-findings.json`. A malformed part is dropped with a warning and never
refuses the consolidation, and `validate-partial` shows the warning to the reviewer while it can
still fix the file. `FINDING_SCOPE_DIRECTIVE`, `review-protocol.md` and `critic-reviewer.md` ask for
the fields. An old-shape partial merges byte-identically.

**D2.** A `fixed` resolution of a finding with recorded members is appended only when its own
`members` answers every id: `fixed`, or `waived` with a rationale. Otherwise consolidate appends no
resolution fact, the finding keeps blocking, and `NEXT-ACTION` names the unanswered ids. The fact is
withheld rather than marked partial: `coverage_algebra.resolution_index` lifts on any `fixed` fact,
so a partial marker would open the gate under an older plugin. A finding without members, and a
finding-level waiver, resolve as before.

**D3.** The verify dispatch's roll-call lists each carried finding's closure and members by id and
site, and says how a resolution answers them. It shows a `class` finding with no members as
"class, unbounded — closes only by a construction".

**Consumer note:**

A finding whose reviewer listed `members` now needs every member answered before a `fixed`
resolution is recorded. Until then, consolidate's `NEXT-ACTION` names the unanswered ids. Findings
without members, and every existing record, behave as before.

## 2026-11-18: an in-flight delegate is safe to clear once the forward notes say what it is doing and why

<!-- prawduct: type=fix | scope=clear-verdict-delegates | closes=brookstalley/prawduct#1190 | release=v3.9.0 -->

The session-hygiene guide said a delegate "dies with the session", so any delegate kept the
session at `DO NOT CLEAR`, and agents justified the hold with a claim they could not back. A clear
stops no background agent, and its completion still arrives. What a clear loses is the context: the
completion lands in a session that no longer knows what the agent was for. The clear verdict's
delegate rule now keys on that. A delegate holds the session only while the conversation is the
sole record of what it is doing and why. It is `SAFE TO CLEAR` once the forward notes carry, for each
delegate, what it is working on and why (the goal its brief served, not a task number), its worktree
and branch, where its result lands, and what integration it owes. The guide defines "work a clear
would kill" as work whose result a clear loses, not a process a clear stops. The live-review rule
keeps `DO NOT CLEAR`, now for the reason that holds: the review is not recorded until it is
consolidated.

**Consumer note:**

Agents in governed repos may now close `SAFE TO CLEAR` while delegates are still running, provided
`.prawduct/.handoff-notes.md` says what each one is doing and why, where its result lands and what
integration it owes. A live Critic review still keeps the session open.

## 2026-11-18: a closes id the local backlog cache lacks reads unchecked, and a rebuild no longer strands another repo's cache

<!-- prawduct: type=fix | scope=closes-cache-miss | closes=brookstalley/prawduct#1195 | release=v3.9.0 -->

`check-pr-hygiene` reported `closes-unresolved` for any id missing from the local backlog cache,
so an open issue the cache had lost read like a bad id. It now reports `closes-unresolved` only for a
spelling no backlog could resolve. A well-formed id the cache lacks, whether an issue id or a `PFX`
alias, reads `unchecked`. That line names `prawduct-hook backlog sync --rebuild --repo <scope>` and
`backlog get`. An id on another repo also reads `unchecked`, naming `backlog get` for that id, since
the single-repo cache never holds it. The check stays offline.

How the cache went partial: the store is shared by the whole clone and holds one repo. A rebuild
deleted every item but rewrote only its own scope's watermark. Another scope's watermark survived
over items that were gone, and that scope's next incremental sync fetched only issues changed since.
Everything older stayed missing. Local clones whose `backlog_service_repo` had moved showed this:
cursor rows for the old scopes, with zero items behind them. A rebuild now drops every other scope's
watermark in the same transaction. An incremental sync that finds a second watermark, left by an
earlier plugin, rebuilds once and says why.

**Consumer note:**

A clone whose backlog cache holds watermarks for more than one repo rebuilds its cache on the next
sync, once. No action needed.

An id spelled with different case (`Owner/Repo#N`) is this repo's item: GitHub owner and repo names are
case-insensitive, so the scope comparison is too.

## 2026-11-18: a Critic control's firings now persist a structured check field, so their yield is countable

<!-- prawduct: type=feature | scope=control-check-field | closes=brookstalley/prawduct#548 | release=v3.9.0 -->

A control's yield was recoverable only from the free-text title token the reviewer writes
(`scope-trace:`, `rule-unenforced:` …), and a capitalised, colon-less or filename-led title missed
a naive query. The new `plugin/lib/control_checks.py` holds the closed registry `KNOWN_CHECKS`:
`cross-component-contract`, `scope-trace`, `rule-unenforced`, plus `read-cost`, which shipped after
the issue was filed. Its `derive_check` reads a title's token case-insensitively, with or without
the colon, and after an optional leading file reference. Consolidation stamps the result as `check`
on each review fact finding and observation. `.critic-findings.json` copies it, and so does the
`review.critic` ledger row. Reviewers write nothing new. A title with no token gets no key. The
field is additive, so `evidence.SCHEMA_VERSION` does not move.

The token is read at the title's lead only, not anywhere in it. On 2026-11-18 this clone's
evidence store held 8 titles, among 172 that carry a token, which name a control while reporting a
defect about it ("The scope-trace: retire rule's numerator is already polluted"). Counting those is
what pollutes a retirement numerator; `tests/test_control_checks.py` pins five of them as fixtures.

`tests/test_control_yield_tokens.py` now fails if any shipped prose instructs a yield token that is missing from the registry, or if the registry names one that no
prose instructs. `tools/pr-review-yield.py` reports counts by check and severity. It derives the
check on read for rows recorded before the field existed. With `--event review.critic` it reads the
Critic's rows instead; re-run it for the current counts.

The issue's PR-path step (stamping `check` in `ledger-append --event review.pr`) has no writer left
to change. That kind was retired with the PR reviewer (#1129) and is refused at the CLI.

**Consumer note:**

none: review records gain an optional `check` key, and readers that ignore unknown keys are unaffected

## 2026-11-18: a failing background counts refresh leaves a record, and the briefing says stuck instead of warming

<!-- prawduct: type=fix | scope=detached-refresh-outcome | closes=brookstalley/prawduct#755 | release=v3.9.0 -->

The session-start counts refresh runs detached with its stderr discarded. When it failed, it wrote
nothing, so a refresh that had failed for a week looked exactly like one just started. The briefing
printed `counts warming` at every session start. `refresh-counts` now records each attempt in the
counts snapshot: `last_attempt_at` and `last_error`. A failure records them whether it came back as
an error or was raised, and a success clears the error. The last good counts are never overwritten.
This mirrors the cache sync's attempt record (#625).

The briefing reads that record. With no counts and a recorded failure, it says `counts stuck` and
gives the error and the command to run. With counts and a failing refresh, it adds `refresh failing`
to the pending line. That includes a zero-pending snapshot, which used to print nothing. A test lists
every detached warm (`transport.spawn_detached` caller) against the test proving it records a
failure, so adding a new one without an outcome record fails the suite.

**Consumer note:**

none: the new snapshot fields are additive, and a snapshot written before them reads as it did

## 2026-11-18: every verify-resolutions demotion now names the mode to re-dispatch in

<!-- prawduct: type=fix | scope=exit1-covering-mode | closes=brookstalley/prawduct#662 | release=v3.9.0 -->

`critic-begin --mode verify-resolutions` has two kinds of demotion. Exit 2 (the delta widened) already
named a covering mode. The exit-1 anchor refusals gave a reason and nothing else: no prior review on
this lineage, a prior fact with no `head_tree`, and a prior tree that cannot be diffed. The skill then
told the reader to apply the demotion property by hand, and two of those triggers (a branch switch,
rewritten history) are by construction the committed-work case. A `final` re-dispatched there reviews
only what the working tree happens to hold.

Each of those refusals now returns `kind: "anchor-unusable"`, still at exit 1, with `fallback_mode`, and
its reason names the re-dispatch. The mode comes from the recommender exit 2 already used, now called
`covering_fallback_mode` because it serves both kinds of demotion. It is asked with "committed work
moved" assumed, so `working_tree_interval_base` decides from the store's review facts and not from the
anchor that failed. A new arm handles a covered HEAD, where the last reviewed state is HEAD's own tree:
the committed work is covered, so it names `final` and no longer falls through to a whole-branch
`cumulative`. That arm applies at exit 2 as well. An unusable evidence store keeps exit 6 and names no
mode. The critic skill's exit table and `review-cycle.md`'s Demotion rows now say to re-dispatch in the
named mode.

**Consumer note:**

A `verify-resolutions` that cannot use its anchor now prints `Re-dispatch as `<mode>`` in its exit-1
reason. Re-dispatch in that mode. Exit codes do not change.

## 2026-11-18: building.md now says the test gate and a Critic review may run together, and where they reconcile

<!-- prawduct: type=docs | scope=gate-review-concurrency | closes=brookstalley/prawduct#678 | release=v3.9.0 -->

Nothing said whether the suite and a review could overlap, so builders ran them one after the
other. The open question was whether recording the suite during a live review voids the review,
because `critic-begin` snapshots the working tree. It does not. The recorder writes only
`.prawduct/.test-evidence.json`, the test report and its scope record, which are session files that
consolidation exempts by path, plus the evidence store under the git directory. A reviewer that
reads `test-status` during the run sees `running:`, which the protocol treats as never a finding.

`building.md` § The Critic now says to start `test-evidence record` first and then dispatch. Two
orderings still hold. A suite that leaves behind any file git does not ignore moves the reviewed
tree, and consolidation refuses the review. `verify-resolutions` refuses to dispatch while a record
is in flight, so it runs after the record. Both reconcile at `/prawduct:pr` Steps 1-2 (`test-status`,
then the coverage gate), not inside the review.

**Consumer note:**

none: guidance on ordering; neither the gate nor the review changed

## 2026-11-18: git-tidy removes a merged worktree that holds submodules, once their commits are published

<!-- prawduct: type=fix | scope=git-tidy-submodule-worktrees | closes=brookstalley/prawduct#1187 | release=v3.9.0 -->

Git refuses to remove any worktree that holds submodules unless forced, so `git-tidy --reap`, and
`--apply` for an idle sibling, failed on a delegate that had added one. Forcing it is not safe in
general: a submodule's repository lives under the worktree's own git directory, so a forced removal
deletes any submodule commit that no remote has, even though the superproject's merge still points
at it. git-tidy now removes such a worktree with `--force` only after a further proof: each
submodule is clean, read with `--ignore-submodules=none` so that a `submodule.*.ignore` setting
cannot hide changes, and nothing any of its refs reaches (branches, tags, its stash, HEAD) is
missing from its remote-tracking branches. Absorbed, embedded and deinitialised submodules are all
checked. If the proof fails, the worktree is kept, and the reason names the submodule and, for work
already published under a tag, the command to remove the worktree by hand. A worktree without submodules
is never forced. This departs from #1041's rule that worktrees are never forced; the owner confirmed the
departure on 2026-11-18, and it is recorded in #1041's requirements.

**Consumer note:**

`prawduct-hook git-tidy --reap <worktree>` now removes a merged, clean delegate worktree that
contains submodules, instead of failing with git's "working trees containing submodules cannot be
moved or removed". When a submodule holds commits none of its remote-tracking branches reach, it
keeps the worktree and says to push or drop them, or, if they are already published (a release tag),
to remove the worktree by hand with the command it prints.

## 2026-11-18: a requirement that surfaces mid-build now has a one-line record, a home, and an impact walk

<!-- prawduct: type=feature | scope=late-requirement-capture | closes=brookstalley/prawduct#1034 | release=v3.9.0 -->

A requirement that surfaced mid-build had no home, so it was usually gone by the next session. The
governance ROI study found late requirements to be the largest cause of rework that was not a fix,
and most of them could not have been known in advance, so this makes them cheap to absorb rather
than trying to find them earlier.

`building.md` § "A Requirement Surfaced Mid-Build" now says where the record goes: a
`## Late requirements` section in the governing requirements artifact `prawduct-hook jurisdiction`
ranks first, or the active build plan when the product has none. It gives the one-line shape
`- **LR-<n>** (<date> · why: <operating|new-consumer|owner-change|constraint> · surfaced: <chunk or sha>) — <sentence>.`,
and says a contradicted record gains `SUPERSEDED <date>: <reason>` instead of being edited. It adds
two triggers: an owner statement that changes behaviour, and a defect whose root cause is a missing
requirement. It also describes the impact walk: under the record, list each candidate site as
`change` or `checked, unaffected`, drawing candidates from `jurisdiction`, from plan chunks and
backlog items that name the area, and from `git grep`. The section also states what the walk cannot
find, which is a paraphrased restatement.

`plugin/lib/late_requirements.py` is the one parser for that shape (`parse`, `scan`, `LateReq`). The
new `late-requirement-record` record-lint check uses it. The check grades only the lines a change
added: all four fields present, `why` from the fixed set, and the id unique across the product. It
is rated WARNING and reaches the Critic through the existing record-lint relay. It searches the
product for the section only when the diff added a record, so a product that captures none pays
nothing and sees nothing.

**Consumer note:**

none: a methodology step; its check fires only on lines inside a `## Late requirements` section, which no product has until it writes one

## 2026-11-18: The governance ledger says it holds reviews, never their outcomes, and names the command that shows a finding's outcome

<!-- prawduct: type=fix | scope=ledger-outcomes | closes=brookstalley/prawduct#606 | release=v3.9.0 -->

#606 read `.prawduct/.governance-ledger.jsonl` as the shared audit trail. It saw every finding
raised and none discharged. The issue allowed two fixes: mirror `resolution` and `disposition`
facts into the ledger, or say where the ledger is described that it holds reviews only. This
change says so. It mirrors nothing.

**Why not mirror.** The issue's premise was that the ledger is committed and shared. It is not. It
has been in the managed gitignore (`core.GITIGNORE_ENTRIES`) since the commit that created it,
and it is per worktree. (#606 measured it committed in the reporting repo, which the managed gitignore does not intend.) So a
mirrored outcome would reach only readers in one worktree, and each of them can already read the

## 2026-11-18: a file this session wrote with Bash or a delegate stays its own work when you commit it from a terminal beside another session

<!-- prawduct: type=fix | scope=stop-span-bash-authorship | closes=brookstalley/prawduct#1184 | release=v3.9.0 -->

When a second session was writing in the same checkout, the Stop span dropped a commit made
while this session ran no tool call, unless one of its files was named by this session's Edit,
Write, MultiEdit or NotebookEdit calls. A file the session wrote another way did not count: with
Bash (`sed -i`, a heredoc, a code generator), through a delegate subagent, or from a background
command. A terminal commit of such a file was dropped, so the reflection and Critic Stop gates
did not fire on the session's own work. The drop's only trace was a stderr line at a clean Stop,
which nobody reads.

A commit is now also kept when one of its files was last written while this session had a tool
call or `!` command running, before the commit was made. The time is read from the file in the checkout: its modification
time, and on POSIX its inode change time, which a rename moves. This is the same test the
commit's own moment already got, applied to the moment its file was written. It covers every
way a session writes, because each write happens inside one of its calls.

#1071's protection still holds. A file another session wrote while this one ran nothing is not
this session's, and that session's commit of it is still dropped. A file written at a moment
both sessions were acting cannot be told apart, and it stays counted, as a commit made at such a
moment already did. The reviewer's other proposal was to keep any file that was uncommitted at
one of this session's earlier Stops. It was not taken: both sessions share one working tree, so
the other session's uncommitted files show at this session's Stops too. Keeping them would
attribute nearly every commit the other session made, which is the error #1071 fixed.

Two cases are still judged on the commit's moment and the edit tools alone: a file written
again since, by anyone, and a deleted file, which leaves no time to read.

Each dropped commit is now recorded once per session as an `other-session-commit` stop
observation (`gates.record_dropped_commits`; `evidence.append_stop_observation` takes a
`dedupe_key` and `known_facts`). It carries the sha and how many files the commit touched, never their names.
`prawduct-hook stats` counts it, and `prawduct-hook evidence list --kind guard-refusal` lists
it. The stderr line stays, and it still rides the block text when another gate blocks.

`tests/test_reflection_gate.py` (`TestAFileThisSessionWroteByAnyMeans`) pins these cases: a
terminal commit of a file written during a Bash call or a delegate's call stays counted; the
same file written between calls is dropped; a renamed file counts by its inode change; a drop
seen at two Stops is recorded once and `stats` counts it; each record that does not land is named;
and the telemetry doc's row names the check and reason. The first three and the dedupe were seen
red before the fix. The inode-change read, the dedupe and the Stop call site were each removed in
turn and seen to fail.

Review fixes. The first cut read a file's last write wherever it fell. This session rewriting
the other session's committed file later moved that time into one of its calls: `git
checkout`, `git stash pop`, a formatter, or `cp` over the file. The other session's commit then
came back into this session's span, which is #1071's error again. A write now counts only when
it came before the commit, because a write after a commit cannot be what the commit recorded.
Both times come from this machine's clock, so no allowance for skew is needed beyond git's
whole-second commit stamps. The cost: if this session later rewrites its own committed file with
the same bytes, that commit is judged on its moment and the edit tools alone. It is then
dropped, and the drop is named and recorded.

The record of a dropped commit was deduped on the `.session-start` stamp. Every session in a
checkout writes that one marker, and only a session sharing its checkout drops a commit. So a
second session's drop of the same commit deduped away, and `stats` undercounted. The record is
now deduped on the session's transcript path, which is hashed into the record's id and not
stored. With no transcript, nothing is recorded and the stderr note says so. No drop is made
without a transcript, so in practice this does not happen. Recording also read the whole
clone-wide evidence store once per dropped commit at every Stop. It now reads it once per Stop.

The note for a record that did not land stays on stderr, and it rides the block text when
another gate blocks. The user cannot act on a missed telemetry record, and the note would repeat
at every Stop until the record lands. The Stop hook handles its other telemetry misses the same
way (`learning.written`, `_record_stop_observation`).

New tests in the same class: their commit's file, rewritten by this session after the commit, is
still dropped; two sessions dropping one commit leave two records; the store is read once per
Stop; with no session identity nothing is recorded and the note says so; and an unreadable
store names each commit and raises nothing. Each was seen red
with its fix removed, including the `known_facts` pass-through in `evidence` and the transcript
path at the `cmd_stop` call site.

**Consumer note:**

If you run two Claude Code sessions in the same checkout, a file a session wrote through Bash,
a delegate subagent or a background command now counts as its own work when you commit it from
a terminal, as long as that write came before the commit. Before, that commit was left out, and
the reflection and Critic Stop gates did not ask about it. A commit left out as the other session's is now also recorded, once, as an
`other-session-commit` observation that `prawduct-hook stats` counts.

## 2026-11-18: one non-UTF-8 byte in a repo no longer makes prawduct's git reads fail

<!-- prawduct: type=fix | scope=subprocess-utf8-decoding | closes=brookstalley/prawduct#1188 | release=v3.9.0 -->

Every subprocess the plugin runs used to decode its output with the locale's codec and strict
errors, so one byte of a legacy encoding in git output made the call fail. A vendored C header with
Windows-1251 comments, for example, turned the whole branch diff into "could not be read", so
`check-pr-hygiene` exited 3 and checked no other file for credentials.

Every such call (git, gh and the interpreter probe) now decodes as UTF-8 without failing:
`surrogateescape`, which keeps the original bytes so a pathname survives the trip back into a git
argument, or `replace` where the output is only displayed (the plugin banner). The encoding side
follows the same rule, so the failure does not just move to the first write. Files the plugin writes
use `backslashreplace` and stay valid UTF-8, with such a byte shown as `\udce9`. The session's
`git status` baseline keeps git's exact bytes, because the Stop gate compares it with fresh
output. Hashes keep the bytes too. `prawduct-hook` and `test-reference-verify` print such a byte as
`\udce9` instead of crashing. A test reads every subprocess call, text write and `.encode()` in the
plugin, and fails on one that would raise on a byte that is not UTF-8 or that it cannot read.

**Consumer note:**

A branch whose diff carries non-UTF-8 content is now checked by `check-pr-hygiene`, so
`/prawduct:pr create` no longer stops on it, and a credential elsewhere on that branch is now
reported. In a repo with `core.quotePath=false`, a changed file whose name is not UTF-8 no longer
stops session start or the handoff; the handoff lists it with the byte escaped. Any other command
that hit such content (a review's diff, a file shown from HEAD) now reads it instead of reporting
the read as failed.

## 2026-11-15: the backlog cache drops a deleted issue, `related` links are written on both items, and two silent decode losses now warn

<!-- prawduct: type=fix | scope=backlog-service | closes=brookstalley/prawduct#1080,brookstalley/prawduct#835 | release=v3.9.0 -->

Three backlog-service bugs where the answer looked right and was not.

**A deleted issue stayed open in the cache (#1080).** GitHub answers a hard-deleted issue with
410 Gone. The transport only recognised 404, so a 410 was treated as a retryable outage, and the
deleted issue stayed in the local cache as an open item, showing up in `pick`, `find` and dedup.
A 410 is now a terminal `not_found` (exit 3, not retryable, with `details.http_status: 410`), and
`get` removes that one item from the cache. A plain 404 still does not evict, because it also
means "no access". If the cache cannot be updated, `get` says so in a warning and still reports
`not_found`. `sync` is unchanged and still never sweeps for deletions: a deleted issue nobody
`get`s stays until `sync --rebuild`. The cache spec records this.

is a line in each item's body block, and `link` and `unlink` only touched the first item. The edge
was visible from the source and invisible from the target. Both items are now written, each side
idempotent on its own and each mirrored into the cache. If the second write fails after the first
landed, the call never goes quiet. A retryable failure returns an error with `details.partial: true`
(`written`, `unwritten`), and running the same command again completes only the missing side. A
permanent failure on the target, typically a cross-repo item this identity cannot write, returns
ok with `target_written: false` and a warning, so links to upstream issues keep working. The first
write is never rolled back. Edges already written one-sided are not repaired by this change:
re-running `link` on each pair fills in the target.

**Two decode losses now warn (#745, partly).** An open item with no `stage:` label, and an item
whose `prawduct:` block is gone, used to decode silently into plain defaults. Both now carry a
warning on `get` and the other reads. The returned values do not change, and `file` does not warn
about what the filer just chose. The third leg, a soft facet (`area`, `impact`, ...) deleted in
the GitHub UI, is not built: telling "deleted" from "never set" needs a record of the old value,
and where that record comes from is an open question on the issue. #745 stays open.

## 2026-11-15: another session's commits in the same checkout no longer count as this session's work, and excused paths report each free step's files

<!-- prawduct: type=fix | scope=gate-span-and-coverage-slips | closes=brookstalley/prawduct#1071,brookstalley/prawduct#1159 | release=v3.9.0 -->

**Another session's commits (#1071).** The Stop hook decides whether a session changed
judgeable code from what changed since the session started. When a second session committed in
the same checkout, its commits landed in that span. Both sessions move the one HEAD, so the
reflog read that already drops pulled, merged and switched-to history could not tell them apart.
A session that wrote nothing could then be blocked by the reflection gate, and by the Critic
gate's trigger, which reads the same span.

The span now drops a commit only when three things are all true. First, another session's
transcript in this checkout's host transcript folder was written since this session started
(only file times are read). Second, this session's own transcript, named in the Stop payload,
shows no tool call and no `!` command running when the commit was made. Third, this session
wrote none of the commit's files: none is one its Edit, Write, MultiEdit or NotebookEdit calls
targeted, and none was last written, before the commit, while one of its tool calls or `!` commands ran (#1184,
`stop-span-bash-authorship`).

The third test is there because the first two say who ran `git commit`, and the gates ask who
wrote the change. A user who commits the session's edits from a terminal between turns runs it
with no tool call open, and those files would otherwise leave the span and disarm the
reflection and Critic gates. A `!git commit` is not a tool call either. The transcript records
its input as a user message opening `<bash-input>`, stamped when entered, and its output as one
opening `<bash-stdout>`, stamped when it ended. The time between the two counts as this session
acting, and a `!` command with no output yet counts as running. Background commands and agents
count as running until the end, because they outlive their call. A worktree delegate's commits
fall inside the call that ran it, so merged-back delegate work still counts. Edited files are
matched as files of this checkout, with both paths resolved, so an edit in another checkout
saves nothing.

A dropped commit is not silent. `session_work_span` returns a `dropped` list with each commit's
sha, files and the reason, and the Stop hook writes one line naming them. That line goes to
stderr and, when another gate blocks, into the block text. It repeats on every turn while the
commit is in the span, so it is not shown to the user at a clean Stop.

Every case that cannot be settled keeps the commit counted:

- the payload has no transcript path, or the transcript is missing;
- no other session wrote beside this one;
- the transcript has no tool call, has a result for a call it never opened, or has a broken line
  before its last one;
- the commit predates the transcript's first record;
- git cannot list the commit's files.

**Cost.** The transcript is read only when another session was writing. Otherwise the added
cost is one folder listing, and only once HEAD's tree has moved. A long session's transcript
reaches tens of MB, so what was parsed is kept in `.prawduct/.session-activity.json`, a new
gitignored session file. Entries are keyed by transcript path, device, inode and byte offset.
Each Stop then parses only the bytes appended since the last Stop, plus 256 bytes before the
offset to confirm the file was not rewritten. A replaced, truncated or rewritten transcript, or
a missing or unreadable cache, costs one full read and never a different answer. The cache
grows with the number of tool calls and edited paths, not with tool output. It keeps at most 8
transcripts and evicts the least recently read. Over this machine's 17 largest transcripts and
`!`-mode transcripts (up to 47.8 MB), a read resumed from the cache gave the same answer as a
full read. Each cache entry was 4–123 KB. A Stop with nothing appended took 1–4 ms against
50–170 ms for a full read. The commits made while this session was idle add one batched
`git diff-tree`. The readers live in the host seam (`lib/host.py`: `other_session_wrote_since`,
`session_tool_activity`, and the event's new `transcript_path`). `gates.session_work_span`
takes the path, and `cmd_stop` passes it.

What is still counted: uncommitted or untracked files another session leaves in the shared
checkout, and the readers that run without a Stop payload (the briefing, and the `clear-verdict`
observation). The Critic gate's imported-history excuse is also unchanged.

`tests/test_reflection_gate.py` (`TestAnotherSessionInThisCheckout`) pins both directions in a
real repo: #1071's repro is silent, and this session's own commit and a merged-back delegate
commit still block with the other session's commit beside them. It also pins each case that
keeps the commit counted, and that the transcript is not opened when no other session wrote.
`TestADropAsksWhoAuthoredTheWork` pins a terminal commit of an edited file and a `!git commit`
as counted, and a foreign commit as dropped and named at Stop. `TestTheTranscriptReadIsBounded`
counts the bytes a second Stop reads from the transcript. Each guard was seen to fail with that
guard removed. `tests/test_host_seam.py` pins the two readers, the payload field, and that a
read resumed from the cache at any byte gives the full read's answer. The readers were also run over this machine's real transcripts:
42 files, a 7.8 MB one in 70 ms, and the only unreadable ones were sessions with no tool calls.

**Coverage algebra slips (#1159).** `excused_gap_verdict` returned paths whose free steps lacked
`files` when free edges came from tree keys, the form every gate uses. That broke the documented
`{kind: free, src, dst, files}` shape. Covered and blocked excused paths now fill those files in
the same way `coverage_verdict` does for its own path. Nothing read them yet. A test asserts the
shape in both free-edge forms, and the generated-graph test checks each free step's files. The
`_merge_base_verdict` docstring now says the pairwise free-edge probe lives in the evidence graph
rather than in `_find_path`.

**Consumer note:**

If you run two Claude Code sessions in the same checkout, a session that changed nothing is no
longer asked for a reflection just because the other session committed. A session whose commit
touches a file it wrote is still asked, including when you commit that work yourself from a
terminal or with `!git commit`. A file it wrote is one its edit tools (Edit, Write, MultiEdit,
NotebookEdit) named, or one last written before the commit while it had a tool call or `!` command running: through
Bash, a delegate subagent or a background command. A file last written by someone else while
this session ran nothing is not its own. A commit left out this way is named on one line in the
Stop hook's output and recorded once as an `other-session-commit` observation that
`prawduct-hook stats` counts.
`update_gitignore` adds `.prawduct/.session-activity.json` to your `.gitignore` at the next
session start.

## 2026-11-15: The gitignore check now asks git what is ignored, so a wholesale `.prawduct/` rule is neither a pile of "missing" entries nor invisible

<!-- prawduct: type=fix | scope=gitignore-contract-semantics | closes=brookstalley/prawduct#762 | release=v3.9.0 -->

Prawduct checks that a repo's `.gitignore` ignores its session files and does not ignore the files
that must be committed. It did that by comparing literal lines, so a single rule like `.prawduct/`,
which already covers every session entry, matched none of them. The check failed in both directions:
it called the session entries missing (and the repair would then have appended all of them again),
and it never noticed that the same rule hides files prawduct needs committed, such as
`.prawduct/project-state.yaml`, the change fragments and the build plan. #762 reported it from a repo whose `.gitignore` was
exactly `.prawduct/` and `__pycache__/`.

**What changed.** `core._contract_diff` now asks `git check-ignore` which paths would be ignored,
instead of comparing strings. A session entry counts as covered when any rule in a `.gitignore`
ignores it, and a negated re-include (`!.prawduct/backlog.md`) counts. Where there is no work tree
yet (onboarding a directory before `git init`), it asks git about a scratch repo holding only the
`.gitignore` text, so the answer is the same. Only a `.gitignore` inside the repo counts,
decided by path: a rule in `.git/info/exclude` or in your global excludes file belongs to this
machine, not to the next clone, and that holds even when the global file is itself named
`.gitignore` (`core.excludesFile=~/.gitignore`), which used to pass as shared.

**It reports, and does not rewrite your rule.** When a rule of yours hides a file that must be
committed, `prawduct-hook update-gitignore` prints `cannot fix automatically:`, names the rule and
its line, and gives the exact lines to paste: delete the rule, or replace `.prawduct/` with
`.prawduct/*` followed by one `!` line for each thing a plugin-governed repo commits under it (a bare
directory rule cannot be negated, so it is replaced, not added to). A `.claude/` rule becomes
`.claude/*`, `!.claude/settings.json` and `!.claude/rules/`, so personal skills stay ignored. What
counts as committed is one list, `core.V2_COMMITTED_PATHS`, taken from what a v2 repo scaffolds and
writes: `project-state.yaml`, `backlog.md`, `changes/`, `artifacts/`, `AGENTS.md`, `CLAUDE.md`,
`.claude/settings.json`, `.claude/rules/`, plus the release, runbook, change-log-archive and
operator-verification state once it exists. It is not the 1.x file-sync registry (`MANAGED_FILES`),
which `migrate` deletes and a plugin repo never has; that registry keeps only its migration role,
the literal lines the repair strips. `.prawduct/releases/` and `project-state.yaml` are committed by
decision, and the remedy re-includes all of it, so narrowing a rule today does not hide a file a
feature writes later. The same sentence reaches the session advisory
(`contract-ignored-by-rule`, owner-only, cleared once the rule is narrowed), onboarding's output
(`ignored_by_rule`), and the doctor skill's gitignore check. The repair command still removes only
lines that literally name a managed file, and it adds no line a broader rule already covers, which
also stops onboarding from appending the version marker beside a wholesale rule.

**Boundary.** If git cannot be run at all, the check falls back to the old literal comparison, says
so (`basis: literal`, and a `note:` from `update-gitignore`), and cannot see a wholesale rule. Git
names only the last rule matching a path, so a file that both a literal line and a wholesale rule
hide can surface under the wholesale rule one run after the literal line is stripped.

`tests/test_gitignore_contract_semantics.py` pastes the advised lines into a real repo and asks git
about every committed path, so clearing the advisory is not mistaken for un-hiding the files. It uses the issue's own `.gitignore`, in a real repo and
in a directory with no repo, and covers both directions, negation, per-clone excludes, nested
`.gitignore` files, the no-git fallback, the probe, the command's output, onboarding, and that
following the printed advice clears the report. `tests/test_gitignore_management.py` keeps its
checks; one equality assertion now also names the two new result keys.

**Consumer note:**

If your `.gitignore` has a rule like `.prawduct/` or `.claude/`, you will now be told that it hides
files prawduct needs committed, with the lines to use instead. Nothing edits that rule for you.
Session entries that such a rule already covers are no longer reported missing or appended again.

## 2026-11-15: releases and the PR gate read change fragments only and refuse a change log with unreleased entries, and a pruned release declares its collateral before the cut

Two changes to the release tooling.

`check-releasability` and `cut-change-log` now take the pending set from `.prawduct/changes/` and
nothing else. Before, they also read release-pending entries from `.prawduct/change-log.md`, so
nothing pushed a repo to move onto fragments, and the legacy reader could not be retired.

release accepts it. `init-product` on a repo that keeps the log still leaves it there, because the

No test read this repo's own pending fragments, so two broken ones merged unnoticed, either of
which would have stopped the next release: one wrote `closes:` as a YAML block list, and two named a
scope that was not their filename. A test now validates every file in `.prawduct/changes/` against

## 2026-11-15: the paired native review runs in its own worktree, so it can no longer detach your branch during a Critic review

<!-- prawduct: type=fix | scope=review-never-moves-head | closes=brookstalley/prawduct#1177 | release=v3.9.0 -->

During a Critic review on a development build, the session's checkout could go from its feature
branch to a detached HEAD at that branch's own tip. Commits made after that landed on no branch,
and a push sent the old branch. The cause was the paired native review. The host's
`/code-review` checks out the commit it is reviewing, and it ran in the session's own checkout.

The native review's wrapper is now dispatched with `isolation: "worktree"`. Its first step,
`native-review prepare`, refuses to go on if it is standing in the session's checkout, or in any
tree but a clean, disposable one of the same repository. Otherwise it detaches the wrapper's own
worktree at the reviewed head, so the review reads the reviewed code there and has nothing to
check out. A run that read its own tree records `tree_moved: false`, because nothing could change
under it.

The wrapper writes the review's text inside its own worktree, at the path `prepare` prints. The
host refuses an isolated agent's Write to the session's files, and the first live run lost its
text that way. `native-review record` runs from the session's checkout. It copies the text into
the session's `.prawduct/.native-reviews/` and deletes the copy in the review's worktree, then
puts that worktree back on the commit it was made at. The host removes an agent's worktree only
when it is unchanged as the agent ends. `--text-file <absolute path>` records a text saved
anywhere else. If the review's worktree is still on disk after its text has landed, the review's
`NEXT-ACTION` names it. When the worktree is unchanged, it also gives a removal command that
checks again before it acts, so it never removes a worktree or branch that gained work since.

A detection guard backs this up for any cause. If HEAD has been detached from the branch a review
began on, three places say so and give the recovery command. They are the review's `NEXT-ACTION`
(within an hour of the dispatch), `critic-consolidate`'s output and `native-review record`'s
output. The command is `git branch -f <branch> HEAD && git switch <branch>` when commits landed
on the detached HEAD.

none: the native review pairs only on development builds; a released plugin never runs it

## 2026-11-15: A record attempt that fails no longer leaves the old green vouching, and an old report no longer vouches for a newer tree

<!-- prawduct: type=fix | scope=test-evidence-no-stale-green | closes=brookstalley/prawduct#679,brookstalley/prawduct#848,brookstalley/prawduct#1178 | release=v3.9.0 -->

Two fixes to `prawduct-hook test-evidence record`. In both, test evidence claimed more than the
run behind it could show.

**A refused or interrupted record now voids the standing record (#679).** `record` rewrote
`.prawduct/.test-evidence.json` only when a record landed. Every refusal (exit 2) returned
earlier, and a run killed mid-suite never reached the write, so an earlier green went on vouching
for a tree whose latest run had failed or never finished. `test-status`, the Stop gate,
`/prawduct:pr` and `/prawduct:critic` all read green. Now, once the arguments have been checked
and before a suite runs or a report is read, `record` marks the standing record void. A record
that lands replaces it. Anything else leaves it void: a refusal, a crash, or Ctrl-C on a hung
suite.

The void keeps the earlier counts, drops the tree, and takes the current time. It carries
`degraded`, the field every reader already refuses through `gates.run_refusal`, so no reader had
to change. `void` names the attempt for the recorder itself. Because the void is the newest word,
a green `test-run` fact for the same tree from another worktree cannot answer over it.
`--no-rerun` refuses to restamp a void record. Usage errors refuse before the void and leave a
good record untouched. `--from-counts` and `--no-rerun` run nothing and do not void.

**`test-status` tells a run in progress from one that died, and can wait for it (#1178).** The void
also carries `in_progress`: the recorder's pid, host, machine, start time and command. While that
process is alive, `test-status` prints `running:` with the elapsed time and, when the last record
has a duration, that duration as an estimate (never a percentage). Once the recorder is gone and
nothing landed, it prints `stale (interrupted):`. A pid is checked against the process's start time
(`ps -o etime`), so a reused pid does not read as the recorder, and an unreaped zombie reads as
gone. A refusal also reads as interrupted, since its recorder has exited. A worktree's first run
shows too: with no usable record to void, the attempt writes a stub with zero counts that every
reader refuses, so a refused first attempt reads as interrupted, where it used to leave no record.

Every state that cannot be checked has an end. "Machine" is the boot (and, on Linux, the pid
namespace), not the hostname, which macOS changes with the network. A recorder on another machine,
or a live pid `ps` could not confirm, reads as running only until it is three times the last run's
duration old (at least 30 minutes), then as interrupted. Its refusal names that time and says that
if no run is going there, the suite can be run now.

Every remedy comes from one owner. `gates.suite_remedy` reads the record's state (running,
interrupted, failing, degraded, not current) and gives the remedy for it. The `verify-resolutions`
refusal (exit 7), `check-releasability`'s `unproven-suite:` line and both gates' coverage-transfer
note print it, instead of each adding its own "run the suite", which told a run in progress to
start a second one. The exit-7 guard's recorded `reason` is that same state, so `running` and
`interrupted` join its slugs. `ps` runs once per verdict rather than once per reader.
`test-status --wait [--timeout N]` (default 300s,
at most 3600s) blocks until the record lands or the recorder dies, then prints the verdict. A

## 2026-11-11: A turn that needs the user now ends with its asks, under a fixed header after the closing line

<!-- prawduct: type=feature | scope=asks-last | release=v3.9.0 -->

The owner ruled on 2026-11-11 (`.prawduct/owner-rulings.md`) that anything the user must act on
is the last thing a turn shows, and prominent. They had read a turn that listed its one ask and
then closed `YOUR TURN` · `DO NOT CLEAR` with the reason "The one ask above is for you.", and
found it hard to parse.

**The shape.** The one-line close keeps its labels. When the turn needs the user, the close comes
first, then a blank line, then the asks block, which ends the turn: `**Needs you:**` on a line of
its own, then each ask in full, numbered, with a recommendation. The close's reason never points

with an asks block is read from the line just before the header. The reading stays narrow,
because a `RUNNING` · `DO NOT CLEAR` close defers the reflection and Critic gates:

- Only a line that leads with `Needs you:` opens the block; markdown emphasis or code ticks may
  come first. A quoted line (in a code fence, a blockquote or an indented code block) is never
  the header or the close, so a turn that quotes the layout to explain it is not read as one.
- The close must be the last non-blank line before the header.
- No line inside the block is read as the close; a close-shaped line there means the turn
  states no verdict.
- Two header lines, or a header with nothing before it, give no verdict.
- When a header is present, the older three-paragraph form is not read.

owner), records a close whose reason points

never blocks. It follows `clear-reason`: one matcher in `standing_block`
(`positional_pointer_match`, kinds in `POSITIONAL_POINTER_KINDS`), one wrapper in `gates`

## 2026-11-11: CI runs the suite on testament's pool, and on the job when it cannot

<!-- prawduct: type=feature | scope=ci-testament | release=v3.9.0 -->

The owner asked on 2026-11-11 for CI to use testament and supplied a client key for it. Until
now `.github/workflows/tests.yml` ran `python -m pytest` on GitHub's runner, a different machine,
interpreter build and selection from the one a developer's `testament run` uses.

### The runner decides where the suite runs (Chunk 01)

`tools/ci-suite.py` has two stages, which the workflow runs as two jobs. The `pool` stage, given
the pool's key, downloads the pool's published CLI build from the pool's console with that key
(testament's source is private, so a public repository's job cannot install it from source),
checks it against the digest the pool names, installs it into an environment of its own, runs
`testament run --no-fallback`, and answers one word: whether the pool ran the suite. The `tests`
stage reads that word. When the pool ran the suite it runs the tests `.testament.toml` selects
out, by negating the manifest's own marker expression, so the two runs are the whole suite and
the markers are named in one file. On any other word, an empty one included, it runs the whole
suite.

With no key the `pool` stage passes and says so; a pull request from a fork is that case. A pool
that cannot give a verdict twice, a console that cannot be reached or is busy, or a run that does
not finish within ten minutes over both attempts also passes, with a warning. A pool that refuses
the key, a missing setting, a build that will not install, or an ending the runner cannot read
fails the `pool` stage: only a red job tells the owner that CI has stopped using the pool. In each of those cases
the `tests` stage still runs the whole suite, so the tree gets its verdict.

The run's summary names failing tests and never a runner.

### The workflow, its pins and its descriptions (Chunk 02)

`tests.yml` gains a `pool` job, the only one given the key, and the `pytest` job now runs after
it whatever its result. The two are separate jobs because the boundary review found that a step
is not a boundary: the first version ran pytest as a child of the process that held the key,
with the key stripped from the child's environment, and a child can read its parent's
environment from `/proc`. So the job that holds the key installs nothing from a package index
and runs no test, and the job that installs the dev extra and runs the tests is given no secret.

The conventions test holds that no workflow triggers on `pull_request_target`, that only the
`pool` job's own step names the secret, that the `pool` job has exactly its three steps, that
the `pytest` job receives one word from it and runs whatever its result, that the token is
read-only, that the addresses are repository variables, and that the pool image's Python is the
declared floor, which on the pool path is what exercises it. The norm is a new row in
`project-preferences.md`, marked as originated by the agent.

`.testament.toml`, `pyproject.toml`, `documentation/running-tests.md` (a new "In CI" section,
with how to read a warning and a failure) and `documentation/project-structure.md` describe CI
as it now runs. The repository gained the Actions secret `TESTAMENT_KEY` and the variables
`TESTAMENT_COORDINATOR` and `TESTAMENT_CONSOLE`.

### The runner reads testament's verdict (Chunk 03)

The runner was written against testament's exit codes as they stood on 2026-11-11. testament has
since frozen its exit codes and added `verdict` to its envelope, and says to key scripts on it.
The boundary review that revived the branch found the runner misreading two endings: exit 75 (the
pool could not give a verdict) read as a refused key, so every outage would have turned CI red
and pointed at the key; and a retryable exit 2 was run again even when a test had already failed,
so a failure could pass on the second attempt and vanish. Now `passed` passes; `failed` from a
failed test or an empty selection is the tree's result and is never retried; `unavailable` is
retried once, then falls back with a warning; anything else, a missing or unknown verdict
included, fails closed.

The runner also refuses a manifest whose selection it cannot complement exactly: a second `-m`,
any other pytest flag that could narrow the run, a path after `pytest`, or a `default_selection`
other than the suite's `testpaths`. Before, the tests such a manifest dropped would have run in
neither job. The pool run starts from the repo root, a console that drops the connection
mid-download is an outage, and a test holds the `pool` job's time limit above what the runner may
wait.

none: changes how this repository tests itself; nothing under `plugin/` changed

## 2026-11-11: an unreadable reviewer partial costs one reviewer, and an inherited red baseline is waived without a round

<!-- prawduct: type=feature | scope=review-round-cost | closes=brookstalley/prawduct#961,brookstalley/prawduct#900 | release=v3.9.0 -->

Two causes made a whole Critic round buy nothing, and both are gone.

**One unreadable partial (#961).** `critic_consolidate.check_partial` is now the single verdict on
one reviewer partial. Its body, `_load_partial`, parses the file and then checks the schema, the
keyed location, the role, the dispatching review's id and the reviewed commit. `consolidate`'s
read loop and the new read-only verb `prawduct-hook validate-partial <path>` both use it, so they
cannot disagree. The reviewer agent and the Critic skill grant the verb. A reviewer validates its
own partial before it returns and fixes it until the verb exits 0.

Consolidation stays fail-closed: a review never persists with a role missing. When it refuses, its
message now says which role failed, which other partials passed and are kept on disk, which are
still unwritten, and the cheap remedy. That remedy is to re-dispatch only the failing reviewer,
with the same manifest and prompt, and not to run `critic-begin` or `critic-discard`, which would
archive the sound partials. An inline single-pass fork is told to rewrite its own partial and
re-run consolidation. The remedy's wording lives in the refusal alone, and each surface that meets
a refusal defers to it: the Critic skill tells the fork to follow its own consolidate's remedy,
`building.md` tells the main session to follow the printed remedy rather than start a fresh
review, and the Stop hook's backstop blocker says the same and that `/prawduct:critic` is refused
while the complete roster is on disk. The coordinator, which stops before consolidation and never
meets a refusal, carries no remedy.

**An inherited red baseline (#900).** The owner ruled auto-waive on 2026-10-21. A test-run fact
now carries the failing test ids, with the same cap as the per-worktree record. A reviewer lists
the ids a test-failure finding rates in an optional `failed_tests` field; both review protocols

so, so the waiver can fire at `final` and `cumulative` too. `evidence.newest_suite_run` finds the

appended, consolidate resolves the merge-base with `coverage.resolve_merge_base_tree`, the prelude
every gate uses, and writes a `waived` resolution fact, with `origin: inherited-baseline` and
`base_run`, for each BLOCKING finding whose every named id that run also failed.

The base must be genuinely before the reviewed work. There is no waiver when the base fell
through to the moving `HEAD~1` fallback, when the merge-base is not an ancestor of the review

## 2026-11-11: Reviewers and forked skills never run above Opus-class by accident

<!-- prawduct: type=feature | scope=reviewer-model-cap | closes=brookstalley/prawduct#1136 | release=v3.9.0 -->

The owner ruled on 2026-11-10: "Yes cap at opus. In fact we need to be very careful to not
accidentally spam fable subagents anywhere, given the cost." This amends the norm "Reviewers run
on the session model — no intelligent model switching": its statement stands, and the amendment
sits in its entry in `project-preferences.md` and in `nonfunctional-requirements.md` § Direction.
A session at or below Opus-class dispatches exactly as before.

### Dispatched reviewers are capped at Opus-class (Chunk 01)

`lib/model_tier.py` owns one answer: the model a reviewer runs on, given the model the dispatcher
runs as. A session whose model names Haiku, Sonnet or Opus gets no override and its reviewer
inherits the session's model; any other session — a stronger tier, an id the code does not
recognise, or no id at all — gets the Opus-class alias. `review-stats` folds model ids with the
same function, so the grouping and the cap cannot disagree about a model.

`critic-begin --session-model <id>` writes the answer into the manifest as `reviewer_model` and

the same line, before it attempts the dispatch mark, so a mark that cannot be written keeps the

The Critic skill, `coordinator.md` and the PR skill pass the answer as the Agent call's `model`,
or pass none, and name no model themselves. Both reviewer agents keep `model: inherit`.

### A capped single-pass review is handed to one dispatched reviewer (Chunk 02)

A forked skill's model is fixed in front matter, so the forked Critic cannot cap itself. When the
manifest sets `reviewer_model`, the fork reviews nothing: it skips the evidence and the diff,
dispatches each roster role through `coordinator.md` on that model — one `critic-reviewer` in role
`reviewer` for a single-pass `chunk`, `verify-resolutions`, `final` or `cumulative` — and stops.
The reviewer writes its marker and its partial, `resolutions` included on a `verify-resolutions`
dispatch, and the `SubagentStop` hook consolidates it as it does a three-reviewer roster.

The directives `critic-begin` prints for a reviewer are rendered by one function,
`critic_consolidate.dispatch_directives`, in their pinned order; the manifest carries the same list
as `dispatch_directives` when a reviewer model is set, and the handed-off reviewer reads it there.
`critic-consolidate`'s wait message tells a handed-off review's reader that it runs in the
background and consolidates on `SubagentStop`. The reviewer contract learns the `reviewer` role,
and the protocol files tell only the fork to consolidate.

### Forked utility skills name Sonnet, and review-stats counts reviews above the ceiling (Chunk 03)

`/prawduct:backlog` and `/prawduct:advisory` declare `model: sonnet` (owner ruling of

report.

## 2026-11-10: The Critic stops relaying machine checks and null cross-check notes

<!-- prawduct: type=feature | scope=critic-trim | closes=brookstalley/prawduct#1128 | release=v3.9.0 -->

Over the 60 days measured in #1128, the Critic's mandated cross-checks were 23% of all findings

writes one and a refusal would cost a whole round. It accepts an `observations` array from a

Record-lint results used to reach a gate only through a reviewer restating them as findings;
the manifest's `record_lint` rode into the fact as data no gate reads. `critic-consolidate` now

filed (a WARNING), or already `waived` by a resolution (a BLOCKING one — the only answer the gate

again. A result is matched by its check, file and details, not its line, so an answered result

promoted into the findings.

reviewer's copy is gone, and what the lint cannot judge (a recorded disposition the diff

named owner before.

dated clocks that nothing raised. In this repo there were six, including #987's escape re-run,
due 2026-11-10, whose plan named this advisory as the prompt.

After the move, the probe now reads `revisit:` from each open issue's `prawduct` block, served by
the backlog cache (`plugin/lib/norm_probes.py`). The rules are the same as the markdown arm's: a
date strictly before today, on an open item, fires; event-trigger text is the janitor's job. When
the cache cannot be read, the probe raises the shared `backlog-cache-unreadable` advisory instead
of reporting nothing due, as `dead-why` and `stalled-transition` already do. The cache spec
(§2.1, consumer 13), the post-sync advisory spec (§8.2) and the backlog-service API contract
record the restoration.

`TestSilentAgainstThisRepo` no longer counts `revisit-due` in its claim that this repo raises
no norm advisory. The probe's input is now the live tracker's dates, not committed state, so a
date passing would otherwise turn the suite red on a calendar day.

**Consumer note:**

If your backlog is on GitHub Issues, a dated `revisit:` on an open item now raises an advisory
in the session briefing once the date passes. Renew it with a fresh date, act on it, or close the
item. Items that already carry a past date will raise one advisory at your next session start.
Because the check now reads the backlog cache at every session start, a clone whose cache has
never been synced now sees the `backlog-cache-unreadable` advisory even with no norm citations;
`prawduct-hook backlog sync --repo <owner/repo>` clears it. Its wording changed, so an
earlier dismissal of it does not carry over.

## 2026-11-01: The session briefing tells a product still on the single-file change log that it can move onto fragments

<!-- prawduct: type=feature | scope=change-log-fragments-advisory | release=v3.8.1 -->

Products onboarded before change fragments shipped were not moving onto them. The migration
(`migrate-change-log`) only ever ran when the owner ran it, and the only thing that offered it was
`/prawduct:doctor` check #22. Doctor runs only when someone runs it, so a repo that never ran it
was never told. A scan of the owner's sibling repos on 2026-11-01 found 28 still on the legacy log
and two that had migrated.

A new advisory probe, `change-record:change-log-fragments-available`
(`plugin/lib/change_record_probes.py`), fires when `.prawduct/change-log.md` is committed and
`.prawduct/changes/` does not exist. It routes to `/prawduct:doctor`, where check #22 keeps the
procedure, and doctor's routing table now sends the advisory there. The apply still needs the
owner's go-ahead. Once the migration has written `.prawduct/changes/`, the advisory resolves itself.
When the committed install reference pins a release that cannot read fragments, the owner text
leads with moving the pin. The advisory is ordered before `change-log-union-merge`, because
migrating makes the union line unnecessary. When git cannot be asked whether the log is committed,
the probe prints a `NOTE:` instead of going quiet.

The advisory-copy lint (`tests/test_advisory_actionability.py`) now also refuses a `prerequisite_of`
that is not a literal tuple at its construction site. Its edge rules read the tuple from the
source, so an edge passed through a variable was checked by nothing; this probe's first draft did
exactly that.

**Consumer note:**

If your product still records changes in `.prawduct/change-log.md`, the session briefing now says
so and offers to move it onto per-change files under `.prawduct/changes/`, so branches stop
editing one shared file (which conflicts at merge, or with `merge=union` can bring archived entries
back). You see a dry run first, nothing is written until you approve it,
and the move is one commit you can revert.
