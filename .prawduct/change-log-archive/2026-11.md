## 2026-11-10: A scorer for the governance study's escape re-run (#987)

<!-- prawduct: type=chore | scope=escape-rerun | release=v3.8.1 -->

The governance ROI study scored rework only for landings up to 2026-09-10, the last date with a
full 30-day window. #987 re-runs the instrument on later landings to check whether the fast,
ungoverned repo F escapes more than governed work.

`.prawduct/research/escape-2026-10/rerun.py` scores that run without changing the instrument. It
imports `stats.mode`, `stats.CUTOFF` and `escape.WINDOW_DAYS`, and applies the study's
`edge_rates` rule to three disjoint groups: repo F, ungoverned excluding F, and governed. A
landing whose window is still open is counted as `window-open` and left out of the rate. The
script refuses a file in which any `(repo, sha)` appears twice, because a duplicate means a
`--branch` run was appended to the main run, and skipping it would hide that. `test_rerun.sh` is
its known-answer test; it failed with the guard removed before the guard went in. The study's
Re-deriving section gains the steps.

**Consumer note:**

none: research tooling in this repo's `.prawduct/research/`; nothing ships in the plugin.

## 2026-11-10: The clear-verdict check records a contradicting close instead of blocking it

<!-- prawduct: type=governance | scope=retire-clear-verdict | release=v3.8.1 -->

The `clear-verdict` Stop check blocked a turn that closed `YOUR TURN` or `COMPLETE` with
`DO NOT CLEAR`. On 3.8 it was scored about as often wrong as right. The harm it guards against is
a session kept open needlessly, so a block on every such turn cost more than it saved. The owner
retired it from blocking on 2026-11-10 (#1044) and kept the measurement.

The check now records each firing as a `stop-observed:clear-verdict` fact
(`evidence.append_stop_observation`), with the same reason and observations a block carried, and
lets the Stop through. `prawduct-hook stats` reports these under *observed only*, scored by the
same catch/slip rule and never counted as Stops blocked or guard refusals. Blocks recorded before
this change are read as before. The detection rule is unchanged. `clear-verdict` leaves the gate
registry, since it no longer blocks. `clear-reason` still blocks, and the standing-block rule
("`COMPLETE` never says `DO NOT CLEAR`") stays in the methodology.

Two formats change. `prawduct-hook stats --json` reports `schema_version` 3, adding
`stop_observations` to each version. The new `stop-observed:` facts share the evidence store's
`guard-refusal` kind, so a plugin from before this release reading the same store counts each as
a guard refusal. To roll back, reinstall the earlier release; its counts then include these
firings as refusals, and nothing else is affected.

**Consumer note:**

A turn that ends `YOUR TURN` or `COMPLETE` with `DO NOT CLEAR` is no longer sent back by the Stop
hook. Each one is still counted, and `prawduct-hook stats` lists them under "observed only".
`stats --json` is now schema 3. An older plugin sharing the clone counts these firings as guard
refusals.

## 2026-11-10: A dated revisit on a GitHub Issues backlog item now raises the revisit-due advisory

<!-- prawduct: type=fix | scope=revisit-due-issues | release=v3.8.1 -->

On a product whose backlog is on GitHub Issues, a `revisit: YYYY-MM-DD` clock never fired. The
`revisit-due` probe was switched off at the move to Issues because the field had no write path
there. #564 then shipped one (`backlog update --revisit`), but the probe stayed off. Items carried
dated clocks that nothing raised. In this repo there were six, including #987's escape re-run,
due 2026-11-10, whose plan named this advisory as the prompt.

After the move, the probe now reads `revisit:` from each open issue's `prawduct` block, served by
the backlog cache (`plugin/lib/norm_probes.py`). The rules are the same as the markdown arm's: a
date strictly before today, on an open item, fires; event-trigger text is the janitor's job. When
the cache cannot be read, the probe raises the shared `backlog-cache-unreadable` advisory instead
of reporting nothing due, as `dead-why` and `stalled-transition` already do. The cache spec
(§2.1, consumer 13), the post-sync advisory spec (§8.2) and the backlog-service API contract
record the restoration.

`TestSilentAgainstThisRepo` no longer counts `revisit-due` in its claim that this repo raises
no norm advisory. The probe's input is now the live tracker's dates, not committed state, so a
date passing would otherwise turn the suite red on a calendar day.

**Consumer note:**

If your backlog is on GitHub Issues, a dated `revisit:` on an open item now raises an advisory
in the session briefing once the date passes. Renew it with a fresh date, act on it, or close the
item. Items that already carry a past date will raise one advisory at your next session start.
Because the check now reads the backlog cache at every session start, a clone whose cache has
never been synced now sees the `backlog-cache-unreadable` advisory even with no norm citations;
`prawduct-hook backlog sync --repo <owner/repo>` clears it. Its wording changed, so an
earlier dismissal of it does not carry over.

## 2026-11-01: The session briefing tells a product still on the single-file change log that it can move onto fragments

<!-- prawduct: type=feature | scope=change-log-fragments-advisory | release=v3.8.1 -->

Products onboarded before change fragments shipped were not moving onto them. The migration
(`migrate-change-log`) only ever ran when the owner ran it, and the only thing that offered it was
`/prawduct:doctor` check #22. Doctor runs only when someone runs it, so a repo that never ran it
was never told. A scan of the owner's sibling repos on 2026-11-01 found 28 still on the legacy log
and two that had migrated.

A new advisory probe, `change-record:change-log-fragments-available`
(`plugin/lib/change_record_probes.py`), fires when `.prawduct/change-log.md` is committed and
`.prawduct/changes/` does not exist. It routes to `/prawduct:doctor`, where check #22 keeps the
procedure, and doctor's routing table now sends the advisory there. The apply still needs the
owner's go-ahead. Once the migration has written `.prawduct/changes/`, the advisory resolves itself.
When the committed install reference pins a release that cannot read fragments, the owner text
leads with moving the pin. The advisory is ordered before `change-log-union-merge`, because
migrating makes the union line unnecessary. When git cannot be asked whether the log is committed,
the probe prints a `NOTE:` instead of going quiet.

The advisory-copy lint (`tests/test_advisory_actionability.py`) now also refuses a `prerequisite_of`
that is not a literal tuple at its construction site. Its edge rules read the tuple from the
source, so an edge passed through a variable was checked by nothing; this probe's first draft did
exactly that.

**Consumer note:**

If your product still records changes in `.prawduct/change-log.md`, the session briefing now says
so and offers to move it onto per-change files under `.prawduct/changes/`, so branches stop
editing one shared file (which conflicts at merge, or with `merge=union` can bring archived entries
back). You see a dry run first, nothing is written until you approve it,
and the move is one commit you can revert.
