## 2026-10-23: git-tidy's remote calls get a network time budget instead of the local one

<!-- prawduct: type=fix | scope=network-git-budget | release=v3.7.2 -->

git-tidy's first real run against this repo failed one `git push --delete` at the 15-second
budget. That budget is priced for local file reads, and the timeout message pointed the reader at
a mounted working tree. Every git call goes through `evidence.run_git`, which now gives a
subcommand that reaches a remote (`fetch`, `push`, `ls-remote`, `pull`, `clone`) a 60-second floor.
git-tidy's `gh` calls (`pr list`, `pr view`, `pr edit --base`) take the same budget, through one
owner, `evidence.network_timeout`. `PRAWDUCT_GIT_TIMEOUT` still raises both budgets but can no
longer push a network call below the floor, and a timeout on a network call now says it was
waiting on the remote.

**Consumer note:**

- `git-tidy`'s fetch, `ls-remote`, `push --delete` and `gh` calls now wait up to 60 seconds,
  instead of 15, before counting as failed. Set `PRAWDUCT_GIT_TIMEOUT` above 60 to allow longer.
  Setting it below 60 now shortens only local git calls.

## 2026-10-22: Merged branches and dead worktrees are cleaned up, on proof that nothing is lost

<!-- prawduct: type=feature | scope=git-hygiene | closes=brookstalley/prawduct#1041 | release=v3.7.2 -->

Prawduct used to notice merged branches, stranded work and idle worktrees and clean up none of
it. The merge flow's one line of cleanup failed in a linked worktree. Now prawduct removes a
branch or worktree only when what it holds is provably carried by a long-lived branch (`main`,
`develop`, `release/*`, the remote's default branch, the configured base, and any names in a new
`Long-lived branches` preference row). For a squash or rebase merge, the proof is instead a merged
pull request whose head was this exact commit. Age and inactivity are never proof.

`prawduct-hook git-tidy` is a dry run of every such removal. Each line shows the commit, its proof
and the exact command, and the run ends with a fingerprint. `git-tidy --apply <fingerprint>`
removes exactly that set. It re-checks each proof first, deletes local branches by
compare-and-delete, and changes nothing if the set has changed. It keeps any remote branch an open
pull request uses, a dirty or locked worktree, and a detached checkout, such as the install a
plugin runs from. It never uses `-D` or `--force`.

At session start, one `tidy-available` advisory proposes the dry run, offline, and the agent
applies it on the owner's yes. `/prawduct:pr` merge now ends with
`git-tidy --after-merge <branch>`. It retargets stacked pull requests, deletes both copies of the
branch, and moves a linked worktree onto the updated base. It keeps the local branch when that
branch holds commits the merge did not take. Delegate reaping uses `git-tidy --reap <worktree>`. A
product that wants none of this sets `Branch cleanup: off`. Under a squash or rebase strategy, the
merge flow still deletes the merged branch, because those branches are single-use.

**Consumer note:**

- A repo with merged branches or dead worktrees sees one new advisory at session start,
  `tidy-available`. It changes nothing until the owner approves the dry run. Dismissing it holds
  until the set of removals changes. To turn it off, set `Branch cleanup: off` in
  `project-preferences.md`.
- `/prawduct:pr` merge now deletes the merged branch and its remote copy itself, and it works
  from a linked worktree. A local branch holding commits the merge did not take is kept and named.
- An environment branch kept level with `main`, such as `staging`, reads as merged. List it in a
  `Long-lived branches` row, and the dry run's note says so when it sees one.
- The online dry run fetches with `--prune` and calls `gh pr list` against the product's own
  repo. Without `gh`, remote deletions are listed as unchecked and not performed.

## 2026-10-22: Record-lint reports a retired claim's wording wherever it still survives

<!-- prawduct: type=feature | scope=retired-claim-survives | closes=brookstalley/prawduct#136 | release=v3.7.2 -->

When a governing record retires a claim, the old wording keeps surviving in places the author's
sweep never reached. One governed product recorded thirteen such recurrences in four sessions, and
the author's own sweep caught none. A new record-lint check, `retired-claim-survives`, makes the
literal part mechanical.

A `Retires:` field on a `## Direction` norm entry lists the retired phrasings in double quotes.
So does a `retires:` list on a `technical_decisions` / `design_decisions` record in
`project-state.yaml`. The check searches every tracked file and every open backlog issue for
those phrases and reports each survivor as a WARNING at its line. The search ignores case and
follows a phrase across a line wrap. It skips history (archives, change-logs, fragments, a frozen
`backlog.md`), the declarations themselves, and lines acknowledged with
`prawduct:allow prawduct/retired-claim-survives -- <reason>`. Files the change edits are searched
like any other. An unreadable backlog reports `unchecked`, never clean.

It catches literal survivors, including those in files being edited and in the backlog. It does
not catch paraphrase (Critic Goal 4) or a finding's sites consumed only in part
(`verify-resolutions`). The tests replay all thirteen recorded recurrences and pin both halves of
that statement.

This repo's first run made the stage-keyed norm's existing `Retires:` line live. It found nine
survivors in tracked files. Three of them are invisible to a case-sensitive, per-line grep: two
are wrapped across lines and one is lowercased. All nine were
quotations: absence tests, budget-ledger comments and the assessment that argued for the
retirement. Each carries a waiver with its reason.

- #136: `retired-claim-survives` record-lint check (`lib/retired_claims.py`), WARNING; the `Retires` field in `docs/norms.md` § Anatomy and § Amendment; its waiver id in `docs/waivers.md`

**Consumer note:**

- A new record-lint check, `retired-claim-survives`, reads `Retires:` phrases (`docs/norms.md`
  § Anatomy). A repo that declares none sees only a new zero in the review fact's `record_lint`
  counts. A repo whose norms already carry a `Retires:` line with quoted phrases gets a WARNING
  for each surviving copy at its next boundary review. Rewrite each one, or waive a quotation
  with `prawduct:allow prawduct/retired-claim-survives -- <reason>`.
- When `backlog_service_repo` is set, the check also reads every open issue from the local cache.
  A cache that was never synced, or cannot be read, reports `retired-claim-survives unchecked`
  until `prawduct-hook backlog sync` runs.

## 2026-10-21: the alignment pass judges whether the goals under the work are grounded

<!-- prawduct: type=feature | scope=goal-grounding | closes=brookstalley/prawduct#1029 | release=v3.7.2 -->

- #1029, building the settled design in `.prawduct/artifacts/goal-grounding-discovery.md`.
- At any decision that commits investment (a plan, a design artifact, an architectural choice,
  spending, an outward commitment), the agent names the product goals the work rests on and
  whether each is grounded: stated by the owner without a hedge, and still true. An ungrounded
  goal with a lot resting on it gets a one-sentence stop; one with little resting on it gets a
  recorded default. What a hedge is about decides whether it counts: product hedges do,
  solution hedges (vendor, stack) get a default. Audience is checked first. The check lives in
  `methodology/discovery.md`; building.md, planning.md and the digest point to it.
- A hedged owner answer stays open in the brief as `Hedged:`, with a revisit trigger and the
  cheap hedges taken now. It is never recorded as `null` or a `never` item. The boundary review
  rates a goal still hedged like one still inferred (WARNING).
- Drift is announced by tier (`methodology/discovery.md`): record (noted, silent), heads-up (one
  line; also when only the record lags a change the owner made out loud) and fork (drift nobody
  chose). Irreversibility raises the tier, publishing is a hard stop, and touching someone
  else's ownership is the strongest signal. Before presenting a plan, the agent reads it against
  the brief's revisit triggers and scope words.
- The session digest tells the agent to name drift from the brief when it sees it, pointing to
  the tiers. A replay of four governed products' real moments (chunk 04) drove it, and drove
  wording fixes: a recorded hedge with a lot resting on it is still raised; publishing is a hard
  stop at the act; ownership covers repo, code and data, and a fork comes before the act.
- Owner ruling, 2026-10-21: the owner can defer a high-stakes product question; the agent names
  its cost first. The hedge paragraph says so. One replay case (record lag aimed at the wrong
  line) stays short, filed as #1030.
- `tools/measure-alignment-yield.py` reports `goal_questions`: owner turns asking what the
  product or the work is trying to achieve, the control's yield (it should fall). A lead, read
  by hand. Baseline: `tools/measure-alignment-yield.py --until 2026-10-22`.

**Consumer note:**

Plans now say in their Goals response line whether any goal they rest on is ungrounded, and a
product goal you answer with a hedge ("maybe others later") is kept as an open question with a
revisit trigger instead of being settled for you. Expect an occasional one-sentence flag before a
plan when much rests on an audience or ownership question nobody has answered, naming what it
costs to leave open (you can still defer it), and a one-line
note when work moves the product away from what its brief says (more users, public exposure).

**Consumer note:**

Products can now record each change as its own file in `.prawduct/changes/` instead of editing the shared `change-log.md`, so two branches no longer conflict over the change record. New products start that way. For an existing product, `/prawduct:doctor` offers the move and makes it with your approval, as one revertible commit. Entries with no type need one `--default-type` you choose, and the dry run shows every guess first. An entry that recorded several changes under one header becomes one change each, and the dry run names any that the old log never showed as pending. On a trunk-based product that tracks versions, each PR cuts its own change record into the archive as it ships. Once a product records fragments and has nothing pending in the old log, prawduct now advises *removing* the `.prawduct/change-log.md merge=union` line it used to ask you to add, because union merges can bring archived entries back. The migration refuses until `.claude/settings.json` pins prawduct v3.7.2 or later, since older readers do not see fragments. In a product that gitignores `.prawduct/`, the PR's change-record check reads the fragment from disk and asks you to confirm it by hand.

## 2026-10-20: The PR reviewer sees a fragment's closes list as a closure claim

<!-- prawduct: type=fix | scope=payload-fragment-closes | release=v3.7.2 -->

`pr-review-payload` scanned the change record's raw text for closing keywords, and neither
spelling a record uses reached that scan: a fragment's `closes: [owner/repo#N]` puts a bracket
between the keyword and the id, and a cut archive entry writes `closes=a,b`. So on every repo
recording fragments, the branch's own closure claims read as "mentioned only" and the reviewer's
check that each claimed item is actually closed (R-2) was silently skipped. Found by the PR
reviewer on #1026. The payload now renders the record owner's parsed `closes` list
(`RecordedChange.closes`) as a claim line, for fragments and archive entries alike.

**Consumer note:**

In products that record changes as fragments, the PR reviewer now checks that every item a fragment's `closes:` list names is really closed.

- **`contribute --send`** sends only under the product's own `Stats contribution` row: `ask`
  with the previewed digest, or `always`. Every other state reads as `never` and refuses before
  the transport. The endpoint is a plugin constant, pinned to the deployed collector
  (VRF-022); an empty one refuses.
- **Delivery is at most once,** under a clone-wide lock. A window the collector provably did not
  store (refused, 503, a failed tunnel or handshake) stays pending; one that may have arrived is
  spent.
- **Surfaces:** the template ships the row unset; `/prawduct:janitor` asks once while it is unset;
  and the session briefing speaks only for an opted-in product, or for a row that is misspelled.
- **`prawduct-hook stats`** counts base-advance transfer grants apart from guard refusals, exports
  each severity's acted-on denominator, and says when a newer plugin's facts were left out.
- **Norms:** architecture's local-first rule and the security model's egress rule admit the upload
  as a third network surface, on the owner's recorded authority. The upstream-filing and
  contribution rows now share one row reader (`core.read_preference_row`).
- **Real-data check (the plan's verification strategy).** `contribute` over this clone's evidence
  store offers 13 reports, W31 to W38 of 2026. The only string values are volume bands, and the
  largest report is 535 bytes. No byte names a product, path, branch, scope or person. What a
  report does reveal is that some product ran a given plugin version that week, and a coarse
  activity profile. A collector operator could link a product's weeks by that profile, but never
  to an identity. That is the residual the audit accepted.
- **Also fixed (found by this branch's boundary run): a declared test command ending in a quoted
  argument was corrupted.** The YAML readers stripped quote characters from both ends of a value,
  so a command like `node --test 'dir/*.mjs'` came out with an unbalanced quote and
  `test-evidence record` crashed after the earlier suites had run. Now
  `core.unquote_scalar` and its hook mirror strip one pair of quotes only when they wrap the whole
  value, for both the scalar and the sequence readers. Every declared command is also split before
  any suite runs, and a bad one is refused with exit 2, naming it. The comment-truncation half of the
  same family stays #790.

## 2026-10-02: record-lint stops flagging out-of-repo refs; the PR entry probe refuses retired tag keys

<!-- prawduct: type=bugfix | scope=record-lint-945-939 | release=v3.7.0 -->

Two record-lint defects that the sibling-repo audit of 3.7.0-dev counted as review cost.

**#945, false `chunk-ref-missing`.** `_looks_like_file_path` treated three non-repo token shapes
as deliverable paths: absolute paths (a binary on a remote host), `~/` paths, and the repo's own
`owner/repo` slug. A correct plan therefore drew a BLOCKING finding. These were 12 of the 61
blocking findings on 3.7.0-dev. **Root cause:** the predicate excused only the slash-command form
of a leading `/` and had no answer for a slug, so it fell through to "path". **Fix:** a token
anchored at `/` or `~` is not a repo path. That rule covers slash-commands, so the narrower
carveout is gone. A slug is excused only when git names it as the GitHub `owner/repo` of a
configured remote, read once per repo from `git config` and parsed by the existing
`parse_remote_url`. It is not decided by shape, so `docs/api` and other repos' slugs stay
checked.

**#939, retired `chunks=` and `status=` keys on new tag lines.** The parser still accepts both
for history, and nothing told an author they are dead. The PR reviewer caught three
recurrences. **Root cause:** no check read the added tag lines. **Fix:**
`change_log.RETIRED_TAG_KEYS` is the one list of retired keys, and `retired_keys_on` reads it.
On a tracked log, the PR Step 1c entry probe refuses a retired key with `retired-key`, reading
only the tag lines the branch adds or edits. Step 1c is where the entry is written, after the
last Critic review, so a record-lint check would have run before the entry existed and caught
none of the recurrences. It was built and dropped in this change. Untouched historical entries
still parse and are never flagged. CL4 in `governance-artifact-lifecycle-requirements.md` is
amended by owner ruling to allow the probe's one tag read.
