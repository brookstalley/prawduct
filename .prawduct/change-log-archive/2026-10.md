## 2026-10-30: A consumer note that opens with a list starts below its label in the paragraphs layout

<!-- prawduct: type=fix | scope=changelog-list-notes | release=v3.8.0 -->

The cut's `paragraphs` layout renders each consumer note as `**`scope`**: {note}`. Fragment notes
are usually bullet lists, so the first bullet landed on the label line as `**`scope`**: - item`.
Markdown then renders that item as plain text after the label, and only the remaining items as a
list. Four v3.7.2 entries shipped that way, and 16 of the 29 v3.8.0 notes would have.

`consumer_digest._entry_lines` now detects a note whose first line is a CommonMark list item. When
the template puts text before `{note}` on the same line, it ends that line at the label and starts
the note after a blank line. Notes that don't open a list are unchanged, and so is a template with
nothing before `{note}`. The bullet layouts are unchanged. The four published v3.7.2 entries in
`plugin/CHANGELOG.md` are repaired the same way.

**Consumer note:**

- With `consumer_digest: layout: paragraphs`, a consumer note that starts with a list item now
  renders as a list under its label, instead of putting the first item on the label line as text.

## 2026-10-29: Clear gates count only real catches, and YOUR TURN may hold a live clear

<!-- prawduct: type=fix | scope=clear-gate-telemetry | release=v3.8.0 -->

The 3.8.0-dev field survey (2026-10-29) found two problems with the clear gates. #1044 relies on
these gates' data to decide whether to keep, narrow or retire them.

**The catch count was inflated.** `stats` counted a `clear-reason` firing as a catch whenever no
handoff notes were on disk. Ten of the eleven 3.8 firings came from one repo, and the transcripts
show question or diagnosis turns ("why is X down") in sessions that changed nothing. That
observation can't tell a read-once answer from a lost decision, so the data leaned towards keeping
the gate.

Clear-gate firings now record `session_changed`: did the session author a non-metadata change,
committed or not (`gates.session_work_span`)? A `clear-reason` firing now counts as a catch only
when notes were absent and the session changed something. A read-only session's firing is
unclassified, and so is any firing recorded before the key existed, because neither can say what a
clear would lose. The gate's behaviour is unchanged.

**`clear-verdict` refused a hold that was true.** Of the ten 3.8 firings with observations, seven
were `YOUR TURN` + `DO NOT CLEAR` while harness background work or a live Critic review was
running. Each cost a round trip that only relabelled the turn as `RUNNING`. The owner ruled to
narrow the gate now rather than wait for #1044's quarter of data.

The Stop hook now lets that pair stand when it observes the work. Only an observed True passes. A
`COMPLETE` + `DO NOT CLEAR`, a `YOUR TURN` with nothing observed (the server-or-recorder case behind
#932), and work the hook can't see (an unread delegate's finished output) still block. The digest
and `session-hygiene.md` state the amended rule: only work a clear would kill earns
`DO NOT CLEAR`, `COMPLETE` never carries it, and `YOUR TURN` carries it only beside that work, named
in the copy.

**Consumer note:**

- `YOUR TURN` + `DO NOT CLEAR` is no longer refused while a background task or a live Critic review
  is running. Name the work in the copy. With nothing running, the pair is still refused.
- `prawduct-hook stats` may report fewer `clear-reason` catches than before. Firings from sessions
  that changed nothing, and firings recorded before this release, are now unclassified.

## 2026-10-28: A Stop block says how to answer it

<!-- prawduct: type=fix | scope=block-append | closes=brookstalley/prawduct#1095 | release=v3.8.0 -->

#1095. After a Stop-hook block, the model rewrote its whole turn close instead of adding the line
the gate asked for. In the 3.8.0-dev survey every blocked turn (22 of 22) wrote a second STATE /
YOUR TURN block after its full answer, and operators read that as the hook firing twice.

Every Stop block now opens with one line, right after its heading, saying how to answer it: do
only what the items ask, end with a short note, and do not repeat the answer. A closing block is
written again only when the one above would now be wrong, because the gates read the close from
the last message only. That covers an item faulting the close itself (the clear-verdict and
clear-reason gates) and a turn that must close `RUNNING` / `DO NOT CLEAR`: to keep a deferral of
the session-end gates, or because its fix started work a clear would kill, such as a review.
`_stop_block_opening` in `prawduct-hook` is the only place either Stop block (a gate's, or an
unknown host's) gets its opening, and a test pins the line on each. `session-hygiene.md` says the
same in one sentence.

Whether blocked turns stop carrying a second close is measured by the next field survey, not by
this change's tests.

**Consumer note:**

- When the Stop hook blocks a turn, its message now says to add only what the blocking items ask
  for, without repeating the answer. Write a closing block again only when the one above would
  now be wrong: an item faults it, or you must close `RUNNING` / `DO NOT CLEAR`.

## 2026-10-28: The change-record commands keep a CRLF file CRLF when they rewrite it

<!-- prawduct: type=fix | scope=crlf-preserve | closes=brookstalley/prawduct#1073 | release=v3.8.0 -->

#1073. `core.write_all_or_none` writes exactly the text it is given (`newline=""`). Its callers
that rewrite a file built that text from a universal-newline `read_text`, so a CRLF file came out
LF: a whole-file diff. This happened on every platform. Before #733 the platform's default newline
hid it on Windows only.

- `core.read_text_and_eol` reads a file newline-preserving. It returns the text as parsers already
  saw it (`\n` only) together with the first line's ending. `core.with_eol` puts that ending back
  on the composed text. The parsers downstream are unchanged, so CRLF input parses exactly as
  before.
- `change_log_archive.bucket_write` is now the one reader of an archive month file that is about
  to be rewritten. `archive-change-log` and `cut-change-log` both go through it. The cut had its
  own copy of the read, and the issue did not name it.
- `archive-change-log` writes the live log back in its own ending. A new month file takes the live
  log's ending, since its entries moved from there.
- `migrate-change-log` writes `change-log.md` back in its own ending. The fragments it creates take
  that ending too.
- `plan new` needs no change. It creates only new files and rewrites none.
- A file with mixed endings is rewritten in its first line's ending.

**Consumer note:**

In a repo whose `.prawduct/` files use CRLF line endings, `archive-change-log`, `cut-change-log`
and `migrate-change-log` now keep CRLF in the files they rewrite. On macOS and Linux they used
to convert those files to LF, so the diff showed every line as changed.

## 2026-10-28: A second clone works from the review evidence it ingested

<!-- prawduct: type=fix | scope=second-clone-evidence | closes=brookstalley/prawduct#1057 | release=v3.8.0 -->

Found by running the full two-clone loop, which no field repo had done yet. A fresh clone that
ingests another clone's review notes already composes the same PR-gate verdict. Three surfaces
still read only what the clone itself wrote:

- **Inference asked a proxy.** Rule 2, rule 4's clean-tree redirect and an explicit mode's
  redirect named a `cumulative` unless `.critic-findings.json` recorded a cumulative at exactly
  HEAD. That cache is absent in a fresh clone, and it holds a verify pass after a cumulative
  followed by a clean verify, so both cases bought a review the PR gate did not need. Each now
  also asks the gate's own answer, `gates.branch_coverage_verdict`, using the inference's one
  store read. A covered branch on a clean tree answers `deferred` (no review owed), not an empty
  `chunk`; mid-plan, the "nothing unreviewed" answer is unchanged.
- **verify-resolutions could not run in a second clone (#1057).** Its dispatch finds the prior
  review through the cache's `fact_id`, and its reviewer joins resolutions to that same file. After
  `evidence_notes.ingest` appends records, the cache now names the newest review on this branch
  (`critic_consolidate.derive_branch_cache`): written if missing, re-pointed if it named another
  branch's review or an older one, left as written if it already names that review, and untouched
  while a review is in flight. Branch position decides "newest", because `ts` is to the second and
  ingest appends in note-read order. It uses consolidation's own `fact_to_cache_record`
  projection, carries a verify anchor's unresolved blockers, renders only this reader's schema,
  and validates before replacing anything. A failure is reported and never fails the ingest.
  Session start, `evidence ingest` and `evidence sync` all say what happened.
- **`evidence status` understated its range.** Its count of facts with no note covers this
  branch's commits only, and the line now says so: after a sync it read 0 while thousands of
  older facts had no note.

**Consumer note:**

- In a second clone of your repo, a review that ran in another clone now counts the way it does
  there. Inference no longer asks for a `cumulative` the PR gate already considers covered, and
  `/prawduct:critic verify-resolutions` works on fixes to it. Run `prawduct-hook evidence sync`
  (or start a session) to pull the other clone's reviews in.
- `evidence status`'s no-note count now says it covers only this branch's commits.

## 2026-10-27: The banner names a downgrade, and the briefing stops nagging merged plans

<!-- prawduct: type=fix | scope=briefing-banner | closes=brookstalley/prawduct#1104,brookstalley/prawduct#1106 | release=v3.8.0 -->

#1104. The session-start banner printed `↑ Prawduct updated: vA → vB` for any version change, so
moving from develop's 3.8.0-dev.2 to the 3.8.0-dev.1 beta read as an upgrade with nothing listed.
`render_delta` now compares the versions with `version_tuple`:
- a lower version prints `↓ Prawduct downgraded: vA → vB` and "changes after vB are no longer
  running", and still relays. It lists nothing: the plugin that runs after a downgrade is the
  older one, whose changelog and gates hold nothing from the range rolled back;
- a move where either side does not parse, or both sort equal, prints `Prawduct changed`, since a
  direction would come from the parser rather than the versions;
- an upgrade is unchanged.

#1106. The briefing's stale-plan scan told every session to "fix the frontmatter, or create the
branch" for a plan whose branch had been merged and deleted and that is waiting for its release.
It trusted chunk state, so any chunk-state defect (#1065, #1079) reached that message. The scan now
also asks `plan status`'s lifecycle (`plan_lifecycle.observe`) and stays silent for a plan that is
merged-unreleased, released or superseded.

Reusing the lifecycle exposed a gap in it. Its last inference, "the branch is gone and a change
record for the scope is pending, so it merged", also fired for a plan committed only on an
unmerged branch, or never committed: `plan new` writes the fragment with the plan, so a plan with
a mistyped `branch:` read as merged. The inference now holds only when the plan is in a base ref's
tree, which is where any merge (merge commit, squash or rebase) leaves it. So the briefing still flags the mistyped branch, and `plan status`,
`plan check-claims` and doctor no longer call that plan release-pending.

**Consumer note:**

After a version rollback, the session banner now says `↓ Prawduct downgraded` instead of
announcing an update. A build plan that merged and is waiting for its
release no longer gets the "not a branch in this repo … Fix the frontmatter" line in the session
briefing. A plan that is not in the base branch's tree (committed only on an unmerged branch,
or not committed yet) and whose `branch:` names a branch that does not exist still gets it. `plan status` and `plan check-claims` now report that plan as
`unknown` rather than merged-unreleased.

## 2026-10-27: Facts record the plugin build they ran on, and stats can split a version by build

<!-- prawduct: type=feature | scope=build-stamp | closes=brookstalley/prawduct#1086 | release=v3.8.0 -->

#1086. Every evidence fact's `actor.plugin` read the same `3.8.0-dev…` for every develop build and
feature-branch head, so a beta comparison blended builds. A per-merge `-dev.N` bump was the
workaround, and it costs a change record, two boundary reviews and a full suite run per bump.

### Chunk 01: `actor.build`

- `evidence.append_fact` stamps an additive `actor.build`: the plugin checkout's commit sha (12 hex
  characters), with `+dirty` when the plugin directory has modified or untracked-unignored files.
  The same omitted-not-null rule as `actor.branch` applies. A marketplace install, a plugin root whose `VERSION`
  is not tracked by the checkout around it, a checkout with no commit, and any git failure record
  no build. No schema version moves.
- It is read once per process, using two git calls (about 35 ms warm, 125 ms cold on the owner's
  machine). The calls drop git's repository-locating environment variables, so a hook run from a
  product's git hook still reads the plugin checkout, not the product.
- `actor.build` travels with the facts through the notes transport to the product's own remote,
  as `actor.branch` does (`api-contract.md`, `evidence sync`). It names a commit of the plugin, not
  of the product, so it tells that remote nothing about the product's own code.
- Its git calls run with `GIT_OPTIONAL_LOCKS=0`, so reading the build never rewrites the index of
  the checkout the plugin runs from, which is often a developer's working tree.

### Chunk 02: `stats --by-build`

- `prawduct-hook stats --by-build` adds `by_build` (`{major.minor: {build: body}}`) next to an
  unchanged `by_version`, and the human report prints one block per build. Each row is computed
  over that build's facts, so rows need not sum to the version's totals. Builds are listed in
  the order the store first saw them. A fact with no build groups as `unstamped`.
- The contribution payload still carries only `major.minor` and the dev flag. Two new tests pin
  that `build` never reaches it.

**Consumer note:**

Every evidence fact now records which plugin build wrote it when the plugin runs
from a git checkout (a dev or beta build), as `actor.build`. A marketplace install records none.
To compare builds of the same version, run `prawduct-hook stats --by-build`. The build sha now
travels with those facts wherever `evidence sync` pushes them, which is your product's own remote,
as the branch name already does. Contribution reports to prawduct are unchanged: they still carry
only the major.minor version.

## 2026-10-27: Chunk state answers a whole case table, and a review certifies the chunks its commit subjects name

<!-- prawduct: type=fix | scope=chunk-state-table | closes=brookstalley/prawduct#1079,brookstalley/prawduct#1082,brookstalley/prawduct#1092 | release=v3.8.0 -->

Chunk state derived from review facts was 3.8.0-dev's regression cluster. #1065, #1072, #1075,
#1079, #1081 and #1082 were each a different way a chunk read open, or done, when it should not,
and each fix exposed the next. #1092 asked for the derivation to be checked against every case at
once rather than closing two more instances, and this change does that.

### The case table

- `build-plan-chunk-state-table.md` "Case table" lists every situation `plan_status.chunk_states`
  answers, with its expected state. The groups cover anchor placement, after-merge reachability,
  named vs span coverage, the four review modes, the proposal, blocking findings, retraction,
  Deliverables paths, dropped chunks and imports, git failing, and what the git calls cost.
  `tests/test_chunk_state_table.py` pins each row with a test over real git fixtures.

### #1082: a review's span certifies the chunks its commit subjects name

- A chunk is done when a review fact names it, as before. Under the owner's ruling on #1082, it is
  also done when a clean, in-scope review fact that is a coverage edge has, in its own interval and
  on the branch's first-parent history, a commit whose subject carries the plan's scope and the
  chunk: `<type>(<scope>): … (Chunk N)`. The fact need not name the chunk. #1082's repro (a clean
  verify pass over chunk 03's uncommitted tree, committed verbatim as `(Chunk 03)`) now reads done.
- Touching a Deliverables path gives no span credit. In review, file-based credit certified chunks
  that were not the commit's work three ways: a path two chunks list, commits merged in from the
  base, and a commit labelled for another chunk. Reading only the branch's first-parent commits
  keeps a merge of the base out of the interval.
- A dirty-tree fact's uncommitted part counts once that exact tree is committed. Only a fact the
  coverage gate accepts as an edge may span. Naming answers first, and a span-certified `done` says
  so in its reason line. One rule decides whether a fact may certify, for naming and for a span
  alike, and a refused span records why on the chunks it would have carried.
- The review proposal still names a chunk by a Deliverables path its diff touches, but only a path
  that one chunk alone lists. When a shared path is why it named an open chunk nowhere, it says so.
- `plan retract` can withdraw a span certification while that span certifies the chunk, and a
  re-run with `--fact` answers "already".

### #1079: first-parent reachability

- After the merge deletes the branch, an anchor equal to its review's `base_commit` is refused only
  when it is on the base's first-parent history. One reachable only through a `--no-ff` merge's
  second parent is accepted: that is a dirty-tree review's branch HEAD. So is a review run over
  uncommitted work before the branch's first commit, when the commit carrying its reviewed tree
  reached the base only through the merge. When git cannot answer, the anchor is refused and the
  reason names the git failure.
- The first-parent test has one owner, `plan_status.on_first_parent`. `plan_lifecycle`'s merge
  probe calls it too, so `plan status`'s lifecycle line and `plan check-claims` read #1079's case
  as merged-unreleased. A newer review anchored at its own `base_commit` no longer hides an older
  one that proves a fast-forward from the same commit.

### The record

- `record_lint` reads a bare-path `governed_by:` entry (`- .prawduct/artifacts/x.md`) as an entry
  with no dispositions and grades it, where it used to read nothing and report no gap. An item in
  no form it reads is a `governed-by-gap` too.
- The NEXT-ACTION clause for a whole-plan review that named no chunk says it "named no chunk" and
  speaks only of the chunks still open.
- `planning.md` "Chunk state", `data-model.md` (ruling D1 gains a dated extension note citing the
  owner's ruling), `api-contract.md`, `cross-cutting-concerns.md`, `building.md`, the Critic and PR
  skills, and the docstrings describe both ways a chunk becomes done.

**Consumer note:**

A chunk now reads done in `prawduct-hook plan status` when a clean review's interval holds one of
your branch's commits whose subject carries the plan's scope and the chunk, `<type>(<scope>): …
(Chunk N)`, even if the review did not name it with `--chunks`. Before, such chunks stayed open,
`plan-backfill` refused the plan at release, and `archive-plan` stamped built work as unbuilt. If
your commit subjects do not name chunks that way, keep passing `--chunks`: touching a chunk's
Deliverables files does not count. A chunk reviewed over uncommitted work also stays done after its
branch is merged with a merge commit and deleted. Two merges still leave chunks open once the branch
is deleted, whether or not a review named them: a squash merge (the reviewed commits are on no
ref), and a fast-forward of a chunk whose only review was over uncommitted work (its anchor cannot
be told from the fork point). Nothing here closes them yet; merge with a merge commit, or keep the
branch until the release.

A `governed_by:` entry written as a bare path now reports a `governed-by-gap` warning when its
artifact has `## Direction` norms, the next time a review changes the plan. Write it as
`- artifact: <name>` with a `dispositions:` line per norm.

## 2026-10-27: prawduct needs Python 3.14, and its hooks find one when `python3` is older (#1097)

<!-- prawduct: type=feature | scope=python-floor | closes=brookstalley/prawduct#1097 | release=v3.8.0 -->

prawduct's first Python floor change: `requires-python` moves from 3.10 to 3.14, to share a floor
with testament, which needs the project's 3.14 environment to collect test timing.

Every hook and CLI entry point is started by a bare `python3`, which each machine and directory
resolves on its own. A hook that crashes on an old interpreter is a non-blocking error in Claude
Code, so raising the floor alone would have silenced governance rather than stopped it. So each
entry point (`prawduct-hook`, `test-reference-verify`, and the banner and digest SessionStart
hooks) now checks the floor before importing anything else. Below it, the entry point re-runs the
same command under a qualifying interpreter. It tries `python3.14` and newer names on PATH, probing
each one because a pyenv shim can name a version it cannot serve, then `uv python find`. When none
exists it fails loudly and never blocks. The session banner tells the agent to tell you what to
install. Every other entry point prints one `ERROR:` line naming the interpreter it found and the
fix. The Stop hook exits 1, because exit 2 would hand the agent a problem only you can fix, every
turn.

After a re-exec, `test-evidence record`'s pytest fallback (used when no `test_command` is declared)
still runs under the `python3` you invoked, not the interpreter found for the hook. The new
`prawduct-hook python-floor` reports the hooks' interpreter and any re-exec, and
`/prawduct:doctor` relays it as check 26. The CI matrix and the release-verification workflow run
3.14, and the `tomllib` fallback for 3.10 is gone.

**Consumer note:**

- **Every machine that opens a governed repo needs Python 3.14 or newer**, including repos that are
  not Python projects, because prawduct's hooks are Python. Install one so `python3.14` runs from the
  repo: `brew install python@3.14` or `uv python install 3.14`. Under pyenv, `pyenv install 3.14`
  is not enough where a `.python-version` pins an older version; also make 3.14 selectable there,
  e.g. `pyenv local <current> 3.14`. The error names any `python3.14` it found that would not run.
- Nothing else changes where `python3` already resolves to 3.14. Where it resolves lower, hooks
  re-run themselves under the 3.14 they find, at the cost of a probe and a re-exec per hook call.
  To avoid that, make `python3` resolve to 3.14 in the repo (for example a pyenv
  `.python-version`). `/prawduct:doctor` shows which case you are in.
- With no qualifying interpreter, the session opens with "PRAWDUCT GOVERNANCE IS OFF THIS
  SESSION", and no gate, review or briefing runs until one is installed and Claude Code restarts.
- If you record tests without a declared `test_command`, the pytest fallback still runs your
  invoked `python3`. Declaring `test_command` remains the robust choice.

## 2026-10-27: a pull, merge or branch switch is not session work for the Stop gates (#1071)

<!-- prawduct: type=fix | scope=session-authored-span | release=v3.8.0 -->

`gates.session_work_span` decided what a session changed by diffing its base tree (`HEAD^{tree}`
at session start) against the working tree. A `git pull`, a merge, a branch switch or a reset
moved HEAD onto history the session never wrote, and those files landed in the span. The
reflection gate then blocked sessions that wrote no code. Under an active plan, the Critic Stop
gate demanded review coverage for the imported files too. Across governed repos on 3.8.0-dev,
reflection blocks rose from about one session in ten to one in six, and about half of the new ones
came from sessions whose only change was a sync.

The span now drops history OLDER than the session that a move brought in. Every commit HEAD
reaches that was made since `.session-start` counts, so a worktree delegate's branch merged back
still fires the gates. So do the commits HEAD's reflog records the session making, the paths of a
merge it concluded by hand, and uncommitted and untracked work. The span never holds more than the
base-tree diff did. If the reflog does not reach back past the session start, holds an entry the
classifier does not recognise, or git fails, the whole base-tree span is used. The extra git calls
happen only when the span is non-empty: one `rev-parse` when HEAD's tree is unmoved, four or five
more when it moved.

**Consumer note:**

- A session that only syncs (`git pull`, merging the base branch in, switching branches) is no
  longer blocked for a reflection or a Critic review of history older than the session. Code the
  session commits or leaves uncommitted fires the gates as before.
- Commits made by anyone after the session started still count when a pull, merge or checkout
  brings them in, including another session's in a shared checkout: the rule is by age, so a
  delegate's merged-back work is never lost.

## 2026-10-27: Stop's deferred-review notice no longer appears in the transcript every turn

<!-- prawduct: type=fix | scope=stop-deferral-quiet | release=v3.8.0 -->

Between chunks of a multi-chunk plan, the Stop hook's Critic gate defers a review to the boundary
and says so: "no review covers this session's changes yet, and none is owed now… Commit and carry
on." On a turn nothing blocked, that notice went into the transcript as a `systemMessage`, every
turn the deferral held. Only the user reads that channel, and the notice gives them nothing to do.
The model never sees exit-0 output at all. Both deferral notices, the review-interval extension and
the short-plan non-final chunk, now go to the hook's stderr log at exit 0. When another gate blocks
the turn, they still appear in the block text beside the blockers, where the model reads them.

**Consumer note:**

- The `WARNING (deferred-boundary-review)` notice no longer appears in your transcript on
  turns that end normally. Nothing about when reviews are owed has changed: the boundary review
  is still required, and its gate blocks as before.

## 2026-10-27: An unloaded plugin says so at session start

<!-- prawduct: type=feature | scope=unloaded-tripwire | closes=brookstalley/prawduct#1078 | release=v3.8.0 -->

#1078. When Claude Code loaded no prawduct plugin for a governed repo, for example a fresh
`CLAUDE_CONFIG_DIR` profile with no install record, there was no banner, no Stop gate and no skill,
and nothing said so. A day of work ran ungoverned. Everything prawduct ships is delivered by the
plugin, so none of it could notice its own absence.

### Chunk 01: the tripwire hook

- A project-level SessionStart hook in the product's committed `.claude/settings.json`. Project
  hooks run whether or not any plugin loads, and a SessionStart hook's stdout reaches the agent's
  context. Both were confirmed against the Claude Code hooks documentation on 2026-10-27.
- The hook is POSIX sh around a `python3 -c` verdict that needs nothing newer than Python 3.0, so it
  does not depend on the plugin's Python floor. It reads
  `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/plugins/installed_plugins.json` by the same rule
  `plugin_activation` uses: a user-scope record, or a record whose `projectPath` is this repo,
  means installed. In a linked git worktree (`claude --worktree`), a record naming the main
  checkout counts too. The hook finds the main checkout from the worktree's `.git` file and its
  `commondir`, without running git. `plugin_activation` gained the same rule (`checkout_paths`),
  so `check-plugin-active` stops calling such a worktree inactive.
  - When the plugin is installed, it prints nothing.
  - When the file reads cleanly and has no such record, it prints a loud "PRAWDUCT GOVERNANCE IS
    NOT ACTIVE IN THIS SESSION" line with the install command.
  - Anything else prints a softer "could not verify" line, and never "not installed". That covers
    an unreadable or missing file and a malformed record. It also covers `python3` that is not on
    `PATH` or that exits non-zero, and the line names which of the two it was.
- One owner for the text: `plugin/lib/unloaded_tripwire.py`. The writers (`init-product`,
  `/prawduct:migrate`'s `transform_settings`, and a new `prawduct-hook install-tripwire [--apply]

## 2026-10-26: One flaky test costs one test's rerun, and the retry cannot hide a race the branch made

<!-- prawduct: type=feature | scope=flaky-rerun | closes=brookstalley/prawduct#1087 | release=v3.8.0 -->

#1087. `test-evidence record` needed a green run of the exact tree, so when one timing-bound test
failed under load, the only ways to clear the gate were another full suite run or `--degraded`,
which the gates read as stale. On a repo with an 18-minute suite, that lost two of six boundary
runs in one session. Now a flake costs one test's rerun. The rerun is recorded rather than
hidden, and it is judged against the branch's diff, which a test runner cannot see.

### Chunk 01: flakes are recorded

- A JUnit `<testcase>` with `<flakyFailure>`/`<flakyError>` and no final `<failure>`/`<error>`
  is Surefire's mark for a test that failed and then passed on the runner's retry. It counts as a
  pass and carries a `flaky` entry: id, first failure text (bounded), the number of failed
  attempts, the source, and the test file where the report names one. `<rerunFailure>` sits beside
  a final `<failure>`, so that test failed every attempt and stays failed.
- `flaky` is capped and sorted, and omitted when nothing flaked. It is carried by the record and
  a restamp, and by a scratch worktree's narrowed `test-run` fact, whose flakes `test-status`
  lists under that delegate's run as `that tree's flake:` lines — never `flaky:`, which the Critic
  and `/prawduct:pr` read as this checkout's run, since each was judged against that worktree's
  diff. It is kept out of the evidence schema, as `failed_tests` is: it
  is printed and carried, and a malformed value never moves a verdict.
- The record line prints `passed only on retry:`. `test-status` prints one `flaky:` line per
  flake after its verdict, and the exit code is unchanged.
- pytest-rerunfailures writes no such marker (pytest's JUnit writer drops its `rerun` reports),
  so its retries stay invisible to `--from-junit`. Corrected from #1087, which listed it.

### Chunk 02: `record --rerun-failed[=N]`

- After a live run, the recorder retries only the failing tests, by pytest node id, up to N times
  (default 1, at most 5). The retries run inside the run's tree bracket, so an edit during a
  retry still withholds `evidence_tree`. A retry that passes turns a failure into a pass carrying
  a flake (`source: "rerun"`). A test that fails every attempt, or is skipped on retry, stays
  red.
- A declared command is retried only through its own template: `test_rerun_command:`, or
  `test_rerun_commands:` aligned by position with `test_commands:` (`none` to opt a command
  out), with `{junit_xml}` and `{pytest_node_ids}`. Appending ids to a command that already names
  a selection would rerun all of it. The fallback pytest path builds its own rerun. Templates are
  checked before any suite runs.
- Not retried, with the output saying which: more than 5 failures (a broken run), a failure
  with no test id, a command with no template, or an id naming no file in the repo. The flag is
  refused with `--from-junit`, `--from-counts` and `--no-rerun`, which run nothing.

### Chunk 03: flakes are judged against the branch

- Each flake is marked `touched` when the branch's changed files (the coverage verifier's base
  and set) include its test file. The file comes from the report, made repo-relative (absolute
  paths, and paths relative to a pytest rootdir below the repo), or from the classname: pytest's
  module path, or for any other runner the class's own file, so a Surefire flake is judged by
  its `.java` file. `null` means the file or the diff could not be read; `touched_why` says
  which, and every policy treats it as touched.
- `flaky_policy: accept | warn | block` (default `warn`). The policy's answer is decided once,
  at record time, and stored as each flake's `outcome` (`noted`, `accepted`, `warn` or
  `blocked`). `block` leaves a touched flake failed, so the record is red and the exit status
  nonzero. A restamp is not judged again. An unknown value is refused before any run.
- `test-status` prints the judgment and the outcome with each flake, for example
  `[touched by this branch; flaky_policy: warn]`. The boundary Critic warns on a line carrying
  `flaky_policy: warn`, and the rule is pinned to the printed text.
- A retry clears a command only when the run's own exit status was 1 (tests failed, for pytest
  and testament). Any other status names a failure outside the tests and stands.
- A flake in an unchanged test file that covers changed code is not yet treated as touched:
  #1088.

### Chunk 04: flakes reach the handoff and the PR

The session handoff gains a "Flaky Tests" section. The PR payload's `test_evidence` section
carries the `flaky:` lines, and `/prawduct:pr` lists them in the PR body under "Passed only on
retry". The project-state keys reference, the state template, `test-report-contract.md` and
`building.md` name the new flag and keys.

**Consumer note:**

When one test fails under load, `prawduct-hook test-evidence record --rerun-failed` retries only
the failures instead of the whole suite. A test that passes on retry is recorded as a flake, not
hidden in the green. With a declared `test_command:`, add a `test_rerun_command:` that takes
`{junit_xml}` and `{pytest_node_ids}` (`test_rerun_commands:`, one per entry, for
`test_commands:`). Flakes are judged against your branch's diff: under the default
`flaky_policy: warn`, a flake in a test the branch changed draws a Critic warning, and
`flaky_policy: block` keeps it failing. Reports that mark a runner's own retries
(`<flakyFailure>`, Maven Surefire's convention) are read the same way. `test-status`, the
session handoff and the PR body now list flakes.

## 2026-10-24: a plan claims its branch, one resolver answers bound, unbound or broken, and no fallback borrows a plan for a checkout that never claimed it

<!-- prawduct: type=governance | scope=work-unit-binding | closes=brookstalley/prawduct#1007 | release=v3.8.0 -->

Which plan governs a checkout had four answers: a plan claiming the branch, the `active_build_plan`
pointer, the conventional `artifacts/build-plan.md`, and a branch-name match against plan scopes.
Each consumer walked them its own way, so a gate, a Critic review and a ledger event could name
different plans for one checkout, and a finished plan could come back into force on a branch that
never claimed it.

`work_unit.resolve()` is now the only walker, and every consumer takes its `Binding`:

- A plan claims a branch with `branch:` and may list `working-branches:`, branches that merge into
  its branch and bind to it. At most one live plan claims a checkout.
- The answer is **bound** (one claimant), **unbound** (none) or **broken** (two claimants, or a
  plan-shaped file that cannot be read). Unbound is normal and borrows no plan. A broken binding
  fails closed: it blocks what bound would have blocked and advises what it would have advised.
- A harness scratch worktree is unbound by construction, and so is a detached HEAD.
- Reviews, ledger events and gate decisions record the unit they were about, or none. Nothing
  substitutes a scope inferred from the branch name.

`prawduct-hook plan new <scope>` mints the plan and its change fragment together, so the scope is
written to both in one act. `prawduct-hook plan bind <path> --branch <name>` claims a branch for an
existing plan. `prawduct-hook plan resolve` prints the Binding for the current checkout.

Where the scope is written is validated. A fragment whose scope a plan spells differently is refused
at the place it is read, rather than first noticed by the release check. A backlog item's
`closed-by` takes `scope:<slug>`, a PR or a release tag, and refuses an unknown scope or a branch
name; a bare slug that is a known scope is accepted and stored as `scope:<slug>`.

**Consumer note:**

- The `active_build_plan` pointer and the `artifacts/build-plan.md` default path are deprecated.
  They are served only in a legacy window, for a repo in which no live plan declares `branch:`, and
  only for a plan that itself declares none. The `plan-unbound-legacy` advisory fires there and names
  the migration: `prawduct-hook plan bind <path> --branch <name>`.
- The window closes no earlier than two minor releases later, and only after
  `plan-unbound-legacy` has fired on no known consumer for a release.
- A detached HEAD now binds nothing: a checkout that resolved a plan by branch name or pointer
  before resolves to none, and gates keyed to the plan do not arm there.
- `closed-by` is validated: a branch name or an unknown `scope:` value is refused where it is written.
- A fragment whose scope near-misses a plan's is refused where it is read.
- Base-branch resolution for the gates, `check-cumulative-critic` and the PR payload consults the
  bound plan's `base:` first (then the repo's `base_branch:`, then the remote default): a stacked
  branch whose plan declares `base: feature/A` reviews against `feature/A`, not the integration
  branch. A plan declaring no `base:` resolves exactly as before.
- `verify-chunk-refs` with a chunk named but no plan bound, or a broken binding, exits 1
  `cannot-verify` instead of a false 0; with no chunk named on an unbound checkout it prints `ok`
  with the reason.
- `critic-begin` records `scope_chosen_by` as one of `binding`, `legacy-pointer`, `legacy-default`,
  `explicit-args` or `none`; `branch-name` and `not-resolved` are no longer written, and history
  that carries them still reads. A consumer filtering on `binding` alone misses every
  legacy-window and every unbound review.
- `prawduct-hook plan resolve --json` carries `case` and `base` beside the Binding's other keys. The
  `core.resolve_build_plan_path` and `buildplan_refs.resolve_branch_plan` shims are removed, not
  kept for a release.

## 2026-10-22: Merged branches and dead worktrees are cleaned up, on proof that nothing is lost

<!-- prawduct: type=feature | scope=git-hygiene | closes=brookstalley/prawduct#1041 | release=v3.7.2 -->

Prawduct used to notice merged branches, stranded work and idle worktrees and clean up none of
it. The merge flow's one line of cleanup failed in a linked worktree. Now prawduct removes a
branch or worktree only when what it holds is provably carried by a long-lived branch (`main`,
`develop`, `release/*`, the remote's default branch, the configured base, and any names in a new
`Long-lived branches` preference row). For a squash or rebase merge, the proof is instead a merged
pull request whose head was this exact commit. Age and inactivity are never proof.

`prawduct-hook git-tidy` is a dry run of every such removal. Each line shows the commit, its proof
and the exact command, and the run ends with a fingerprint. `git-tidy --apply <fingerprint>`
removes exactly that set. It re-checks each proof first, deletes local branches by
compare-and-delete, and changes nothing if the set has changed. It keeps any remote branch an open
pull request uses, a dirty or locked worktree, and a detached checkout, such as the install a
plugin runs from. It never uses `-D` or `--force`.

At session start, one `tidy-available` advisory proposes the dry run, offline, and the agent
applies it on the owner's yes. `/prawduct:pr` merge now ends with
`git-tidy --after-merge <branch>`. It retargets stacked pull requests, deletes both copies of the
branch, and moves a linked worktree onto the updated base. It keeps the local branch when that
branch holds commits the merge did not take. Delegate reaping uses `git-tidy --reap <worktree>`. A
product that wants none of this sets `Branch cleanup: off`. Under a squash or rebase strategy, the
merge flow still deletes the merged branch, because those branches are single-use.

**Consumer note:**

- A repo with merged branches or dead worktrees sees one new advisory at session start,
  `tidy-available`. It changes nothing until the owner approves the dry run. Dismissing it holds
  until the set of removals changes. To turn it off, set `Branch cleanup: off` in
  `project-preferences.md`.
- `/prawduct:pr` merge now deletes the merged branch and its remote copy itself, and it works
  from a linked worktree. A local branch holding commits the merge did not take is kept and named.
- An environment branch kept level with `main`, such as `staging`, reads as merged. List it in a
  `Long-lived branches` row, and the dry run's note says so when it sees one.
- The online dry run fetches with `--prune` and calls `gh pr list` against the product's own
  repo. Without `gh`, remote deletions are listed as unchecked and not performed.

## 2026-10-22: Record-lint reports a retired claim's wording wherever it still survives

## 2026-10-02: record-lint stops flagging out-of-repo refs; the PR entry probe refuses retired tag keys

<!-- prawduct: type=bugfix | scope=record-lint-945-939 | release=v3.7.0 -->

Two record-lint defects that the sibling-repo audit of 3.7.0-dev counted as review cost.

**#945, false `chunk-ref-missing`.** `_looks_like_file_path` treated three non-repo token shapes
as deliverable paths: absolute paths (a binary on a remote host), `~/` paths, and the repo's own
`owner/repo` slug. A correct plan therefore drew a BLOCKING finding. These were 12 of the 61
blocking findings on 3.7.0-dev. **Root cause:** the predicate excused only the slash-command form
of a leading `/` and had no answer for a slug, so it fell through to "path". **Fix:** a token
anchored at `/` or `~` is not a repo path. That rule covers slash-commands, so the narrower
carveout is gone. A slug is excused only when git names it as the GitHub `owner/repo` of a
configured remote, read once per repo from `git config` and parsed by the existing
`parse_remote_url`. It is not decided by shape, so `docs/api` and other repos' slugs stay
checked.

**#939, retired `chunks=` and `status=` keys on new tag lines.** The parser still accepts both
for history, and nothing told an author they are dead. The PR reviewer caught three
recurrences. **Root cause:** no check read the added tag lines. **Fix:**
`change_log.RETIRED_TAG_KEYS` is the one list of retired keys, and `retired_keys_on` reads it.
On a tracked log, the PR Step 1c entry probe refuses a retired key with `retired-key`, reading
only the tag lines the branch adds or edits. Step 1c is where the entry is written, after the
last Critic review, so a record-lint check would have run before the entry existed and caught
none of the recurrences. It was built and dropped in this change. Untouched historical entries
still parse and are never flagged. CL4 in `governance-artifact-lifecycle-requirements.md` is
amended by owner ruling to allow the probe's one tag read.
