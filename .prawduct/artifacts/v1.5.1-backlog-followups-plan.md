## Build Chunks

### Chunk 01: `regen-views` scope-aware Status flipping

- **Description:** `collect_shipped_chunks` in `tools/lib/views.py` (line 116) unions every change-log entry's `chunks=` tag with `status=shipped`, ignoring `scope=`. Effect: a v1.5 build-plan's Status is flipped to `[x]` by v1.4 change-log entries that share chunk numbers. Active workaround: HTML comment in v1.5 build-plan.md telling builders not to run `regen-views`. Fix-shape: detect the active build-plan's scope (parse from frontmatter `scope:` field if present, else infer from the build-plan's first chunk's tagged change-log entry, else fall back to the most recent `scope=` tag), then filter `collect_shipped_chunks` to entries with matching `scope=`. `_collect_scope_rollups` already does the grouping; reuse its data path.
- **Type:** code
- **Depends on:** none. First chunk.
- **Artifacts consumed:** `tools/lib/views.py`, `tests/test_views.py` (or wherever `apply_status_view` is tested), `.prawduct/artifacts/build-plan.md` (this v1.5.1 plan once promoted — read for scope detection).
- **Deliverables:**
  - `tools/lib/views.py`: new helper `_detect_active_scope(build_plan_content, change_log_content=None) -> str | None` — takes file contents (caller reads them; the lib stays I/O-free). Resolution order: (1) parse `scope:` from YAML frontmatter (tolerating a leading HTML comment block and YAML null literals `null`/`~`/empty as absent), (2) if absent and change-log provided, fall back to the most-recent change-log entry's `scope=` tag, (3) return None when undetectable (fail-safe: when None, `build_status_view` behaves as today — unfiltered union).
  - `tools/lib/views.py`: new helper `_parse_build_plan_frontmatter_scope(content) -> str | None` — the parser used by `_detect_active_scope` step (1).
  - `tools/lib/views.py`: `collect_shipped_chunks(entries, scope=None)` accepts a scope parameter; when set, filters entries to those with matching `scope=` tag.
  - `tools/lib/views.py`: `build_status_view(...)` calls `_detect_active_scope` and threads the result into `collect_shipped_chunks`.
  - Design simplification vs. original plan: the implementation does NOT do `## Status` first-checkbox chunk-id-range inference. That was over-engineered — explicit frontmatter or most-recent change-log scope covers the live cases; the chunk-id-range path had no consumer.
  - `templates/build-plan.md`: optional frontmatter `scope:` field documented in the HTML-comment header (recommended for multi-version products).
  - `.prawduct/artifacts/build-plan.md` (active): once Chunk 05 lands, drop the "don't run regen-views" comment from the v1.5 plan since the fix supersedes it (no-op on v1.5 — v1.5.1 plan is the one being executed).
