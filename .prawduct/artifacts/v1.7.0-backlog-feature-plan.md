## Motivation

Every Prawduct product accumulates a flat `.prawduct/backlog.md` — bullets appended by builder, critic, reflection, and janitor, with two by-convention sections (`## Active — next up`, `## Queue`), no IDs, no metadata, no grouping. The flagship repo has ~50 such items spanning months. The pain (requirements §1): picking next-work means re-reading the whole file; items don't group; dedup is manual; stale items don't surface; promotion is invisible; rich analyses get buried.

The user-facing test (requirements §1): **can someone with 30 free minutes pick a high-value item and ship it, without first spending 15 minutes triaging?**

This phase delivers the structured backlog (`[PFX-XXXX]` IDs + one-line metadata bar + free-form body, three sections Open/Promoted/Archive), the `/backlog` skill that operates on it, and the four migration probes (requirements §8.2) that nudge existing products to adopt the structure — registered against the Phase-1 advisory infrastructure shipped in v1.6.0.

## Resolved open questions (requirements §10 — decided with user this session)

- **Q1 (prefix vocabulary):** ship a starter prefix list (STH, CRT, SYN, LLM, BKL, MIG, JNT, MET…) as examples in the skill prompt, with guidance for the agent to *derive* sensible project-appropriate prefixes; allow an *optional* `backlog_prefixes:` declaration in `project-state.yaml` for validation; do not require it.
- **Q2 (archive growth):** archive stays in `backlog.md` until it exceeds ~200 entries, then the **janitor** proposes splitting to `backlog-archive.md`; `/backlog find` spans both files.
- **Q3 (NL pick parsing):** **no programmatic parser** — the LLM interprets prose natively (consequence of the skill-driven choice). The "ceiling" is a prompt instruction: if a query carries constraints beyond area/budget/type or is ambiguous, echo the interpreted filter and confirm before running. A documented `--flag` form exists for machine callers (Critic/reflection invoking `/backlog add ...`).
- **Q4 (semantic search):** none in v1 — tags + plaintext `find` are sufficient.
- **Q5 (skill architecture):** `context: fork`, single monolithic SKILL.md (watch token size; split to a dispatcher only past ~10K tokens); interactive subcommands prompt from within the fork.
- **Q6 (pick during active build plan):** `/backlog pick` **prioritizes items whose `area:`/scope overlaps the active build plan** (read via the `active_build_plan` pointer), framed as "related to your current work"; `--standalone` falls back to context-switch suggestions. (This overrides the requirements' lean of "warn and suggest standalone.")
- **Q7 (external-backlog detection scope):** scan repo root + `.github/` only; deeper paths require explicit `/backlog import <path>`.

## Architecture decisions (reasoned)

1. **Skill-driven CLI, Python probes.** The eight `/backlog` subcommands are driven by the forked SKILL.md (no Python CLI module — diverges from the advisory `advisory_cmd.py` precedent, per the user's explicit choice). The **four sync probes are necessarily Python**: they register against the Phase-1 `register_probe` registry and run inside `run_sync_advisories` → `run_all_probes`, where no skill executes. So the split is: skill-driven subcommands + Python probes only.
2. **Probe registration wiring.** Phase 1 ships an empty registry with **no import-time registration** (deliberate, per `advisory_store.py` module docstring — avoids the `__init__` re-export shadowing in learnings). Backlog probes live in a plain module `tools/lib/backlog_probes.py` that calls `register_probe("backlog", …)` at module level; `run_sync_advisories` imports that module immediately before `run_all_probes` (a "load feature probes" step). This keeps registration explicit and side-effect-free at package import.
3. **Resolution conditions in the shared answer store.** Probes read resolution facts from `project-state.yaml` (committed, shared) via `ProjectState.get(...)`: `backlog_format_version`, `backlog_external_imports`, `backlog_last_groomed_at` (advisory-spec §3.5, §7.1). The skill *writes* these facts (via Edit) when migration/import/grooming completes, so a teammate's action auto-resolves the advisory for everyone on next sync.
4. **Content-scan primitive.** `legacy-backlog-format` / `legacy-section-schema` probes need to read `backlog.md` and count items lacking `[PFX-XXXX]` / detect old section headings. The advisory spec defers "rich Codebase content scanning" to "the first feature that needs it" (Phase 2). This plan adds the minimal content-read helper the backlog probes require — in `backlog_probes.py`, not by widening the shared `Codebase` surface beyond what's needed.
5. **`/backlog` skill tool surface.** Unlike `/prawduct-advisory` (locked to `Read` + one Bash pattern), `/backlog` must *edit* `backlog.md`, `backlog-archive.md`, and `project-state.yaml`. allowed-tools: `Read, Edit, Write, Grep, Glob` plus `Bash(python3 tools/product-hook advisory*)` for the `dismiss-advisory` alias. Wider surface is inherent to a file-mutating management tool; scoped as tightly as the function allows.

## Deviations / naming collisions to keep straight

- `run_sync()` already returns a key called `advisories` — those are **place-once template-drift** advisories, unrelated to **post-sync migration advisories** (`.prawduct/.advisories.json`). Untouched here.
- The legacy `backlog.md` uses `## Active — next up` / `## Queue`; the new schema uses `## Open` / `## Promoted` / `## Archive`. The `legacy-section-schema` probe detects the old headings; migration converts them.

## Verification Strategy

Because the skill logic is not unit-testable (skill-driven), verification leans on three layers:
1. **Python unit tests** — the `legacy-backlog-format` probe (trigger/resolution/idempotency/supersession against synthetic project-state + backlog fixtures), skill registration (the exact-set tests `test_has_all_managed_files`, `test_v4_product_gets_new_skills`, manifest), template structure, project-state field reads.
2. **Fork-skill smoke (Chunk 01)** — manually invoke `/backlog add` then `/backlog list`/`find` on a scratch backlog to confirm the fork reads, generates an ID, writes the new format, prompts interactively, and reads back.
3. **Dogfood (Chunk 04)** — run `/backlog migrate` on this repo's real ~50-item backlog (success criterion S4: <30 min). This is the integration test the unit suite can't be. Then `/backlog pick` against the migrated backlog (S1: <30 sec).
