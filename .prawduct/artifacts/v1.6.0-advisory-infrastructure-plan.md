## Motivation

Two upcoming features — the backlog system (`documentation/backlog-system-requirements.md` §8.1) and prompt management (`documentation/prompt-management-requirements.md` §11.1) — each need to notice "this project should probably do X, but we won't force it" and nudge the user at session start until they act or dismiss. The pattern is general: sync runs migration probes → probes detect signals → advisories are written to a shared store → the next session briefing surfaces them → the user runs the recommended command or dismisses.

Specifying this once, as shared infrastructure, prevents the two feature build plans from each inventing their own incompatible version. `documentation/post-sync-advisory-spec.md` (v0.2) is the design; §13 stages it as **Phase 1** of a three-phase build (infra → backlog → prompts). This plan builds Phase 1.

**Why ship it as a no-op.** Per spec §13, Phase 1 ships with an empty probe roster — the storage, lifecycle, CLI, and integration are complete, but no production probe is registered, so a synced project sees zero new advisories. This keeps the first ship trivially rollback-safe and lets each feature's build plan assume the mechanism exists. The mechanism is exercised end-to-end in tests via a synthetic probe that is never registered in production.

## Deviations from the spec's illustrative code (reasoned)

The spec's §4.1/§7 sketches a `tools/lib/probes/__init__.py` module that registers probes at import time. This build plan **deviates** from that specific layout for two reasons rooted in project learnings:

1. **`__init__` re-export shadowing** — `tools/lib/__init__.py` re-exports public names from sibling modules (e.g. `core`). A `probes/__init__.py` that does registration-at-import risks the re-export shadowing collision documented in learnings. The registry therefore lives in a plain module, `tools/lib/advisory_store.py`, with explicit `register_probe`/`run_all_probes` functions — no import-time side effects in an `__init__`.
2. **`*_cmd.py` convention** — command modules carry the `*_cmd.py` suffix. The CLI dispatch module is `tools/lib/advisory_cmd.py`; the non-command store/registry/probe machinery is `tools/lib/advisory_store.py`.

These are naming/placement deviations only — the spec's *semantics* (registry, `(feature, type)` keying, deterministic candidates) are preserved verbatim.

**One naming collision to keep straight:** `run_sync()` already returns a key called `advisories` — those are **place-once template-drift** advisories ("Place-once template advisories: N" in the briefing), an unrelated concept that happens to share the word. This plan's **post-sync migration advisories** are a separate store (`.prawduct/.advisories.json`) surfaced under a separate briefing section ("ADVISORIES (post-sync, N active)"). The two never share state; the plan keeps the existing template-drift path untouched.

### Verification Strategy

Beyond unit tests, the mechanism is exercised end-to-end through a **synthetic test probe** registered only inside the test suite (never in production). The probe's trigger condition reads a fake codebase signal; its resolution condition reads a `project-state.yaml` field. Tests drive the full path: probe fires → candidate → id computed → store written → briefing renders it; then set the resolution fact → re-sync → advisory auto-resolves → briefing drops it. This proves the spine works without shipping any production probe. The no-op ship is verified by asserting that a real sync (empty production roster) produces an empty advisory store and no briefing section (Chunk 06).

### Chunk 04: Retention, compaction & schema-version tolerance

- **Description:** Add retention/compaction (spec §3.4, Q4) and schema-version read-tolerance (A7). On each sync: resolved entries are shrunk to compact form (`id`, `state`, `resolved_at`, `resolved_by`, `superseded_by`) and garbage-collected after a 30-day TTL; dismissed entries are shrunk to compact form (`id`, `state`, `dismissed_at`, `dismissed_reason`) and kept forever; soft caps per Q4 (100 active / 50 resolved-within-30d / 200 dismissed). Add schema-version handling: a store with a lower/absent `schema_version` is migrated forward or read with a clean warning, never crashed on (A7). The TTL clock uses `datetime` in product code (this is not a Workflow script — no `Date.now()` restriction).

## Out of Scope

- **Production probes** — Phase 1 registers none. The prompt-management probes (spec §8.1) ship in Phase 3; the backlog probes (spec §8.2) ship in Phase 2. Phase 1 ships the mechanism plus a test-only synthetic probe.
- **Per-feature dismissal aliases** (`/backlog dismiss-advisory`, `/llm-strategy dismiss-advisory`) — they belong to their owning features (Phase 2/3). Only the unified `/prawduct-advisory` lands in Phase 1.
- **Rich `Codebase` content scanning** — Chunk 01 defines the `Codebase` wrapper interface (`has_imports`, `has_files_matching`) to lock the probe signature, but a full content scanner is built by the first feature that needs real scanning (Phase 2/3). Phase 1 implements only what the synthetic test probe exercises.
- **Team-wide advisory state** (`dismissed_advisory_classes` in `project-state.yaml`) — per-developer is sufficient for v1 (spec §3.5, §10 Q2, §14).
- **Time-based auto-dismissal**, **cross-product aggregation**, **web UI** — spec §14, all deferred.
- **Stop-hook gating on advisories** — advisories are informational, never gates (spec §9). A feature MAY add its own gate later, justified in its own spec.
