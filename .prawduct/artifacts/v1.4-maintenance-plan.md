# Prawduct v1.4 — Maintenance Release Plan

**Status:** Proposal v2 (not yet a build plan)
**Source:** Synthesis of session reflections from discodon, discodon-brooks2, hallucinote (2026-05-18)
**Themes:** Reduce duplication where it's harmful; close enforcement gaps where they're costly; recover wasted Critic wait time

This is a proposal-grade plan. Once approved, each section becomes one or more build-plan chunks. Items are stack-ranked — sequence matters, several Tier-2 items depend on Tier-1 mechanism choices.

## Cross-cutting themes

Three patterns dominate the friction across all three product repos, and v1.4 addresses each with a different shape of fix:

1. **Artifact drift is a symptom; duplication is the cause.** Build-plan, backlog, change-log, project-state.yaml, and release notes all re-state facts that live authoritatively elsewhere. Every multi-chunk session produces Critic findings of shape "you forgot to update the surrounding artifacts." **Fix shape: fewer authoritative homes, derived views, less hand-curated summary.** (F1, F5, F6.)
2. **Per-chunk Critic catches local issues but misses cumulative breakage and class-level escapes.** Cross-chunk integration cracks, untested new code, stale build-plan symbol references — all surface only at PR-reviewer time or never. **Fix shape: add enforcement at the cost-effective gate (Critic), close specific escape paths.** (F2, F3, F4.) Note: this *adds* enforcement, not subtracts — it's a different goal from theme 1 and worth the extra Critic-step cost because the escape class is silent quality erosion.
3. **Critic wait time (~10 min) is wasted.** Cache goes cold (>5 min TTL), agents sit idle. **v1.4 fix shape: methodology guidance only (prep work happens BEFORE cumulative-Critic invocation, folded into F2).** Real wall-time recovery requires backgrounded subagent with structurally-enforced tool restrictions — Claude Code doesn't currently support this. Deferred pending F7-β investigation (see `.prawduct/artifacts/f7b-steering-investigation.md`).

## Compatibility Strategy

Three Tier-1 features (F1, F4, F5) change formats or schemas that shipping products depend on. User-stated constraint: *"Product repo backward compat is paramount; several large projects depend on prawduct."* Each affected feature follows a two-release deprecation pattern:

- **v1.4 ships dual-write support** — both old and new layouts work; new is opt-in via doctor migration command.
- **v1.4 doctor surfaces migration path** — `prawduct-doctor migrate v1.4` runs the upgrade idempotently; products that don't migrate keep working under deprecated-but-supported paths.
- **v1.4 release notes flag deprecations** — old paths logged as NOTE (not BLOCKING) when used by Critic; product authors choose when to migrate.
- **v1.5+ removes deprecated paths** — after at least one minor cycle of warnings and confirmation from existing product owners.

Per-feature compat detail:
- **F1**: `change-log.md`, `project-state.yaml.scope`, and build-plan Status remain writable; views ADD a derived layer behind a project-state opt-in (`views_enabled: true`). Products that don't enable views see zero behavioral change.
- **F4**: `.test-evidence.json` accepts old fingerprint fields AND new schema; Critic checks new fields if present, falls back to old behavior otherwise. Symbol-coverage assertion is opt-in via `coverage_required: true` in project-state.yaml until v1.5.
- **F5**: existing settings.json keeps working; new layout is opt-in via `prawduct-doctor migrate-settings`. Critic flags non-migrated settings as NOTE after v1.4.1, not before.

**Implication for scope estimate:** every Tier-1 schema feature gains 0.5–1 chunk for compat shim + migration command. Reflected in the final scope figure below.

## Tier 1 — Required for v1.4

### F1. Collapse change-log + release-notes + project-state.scope + build-plan Status into one artifact with views

**Problem.** Same facts live in 4 places. Each release cycle leaves three out of date. Hallucinote M-8 shipped a BLOCKING off-by-20 numeric error in hand-authored release notes; discodon recurs "Status row stale `[~]` not flipped" essentially every chunk.

**Solution.** One canonical work-log:
- Single `.prawduct/work-log.md` (extend `change-log.md` to be the canonical store — name preserved for compat) — append-only, tagged entries: `chunk: F1-2 | release: v1.4.0 | status: shipped | closes: #117, #763`.
- Views are read-only derivations:
  - **Build-plan Status block** → query of entries tagged with current build-plan ID
  - **Release notes** → query of entries tagged with release version, grouped by category
  - **project-state.yaml scope** → query of entries tagged `scope: vN`
- **Idempotent regeneration.** Pre-commit hook regenerates the derived blocks in-place from canonical entries every commit. Status/release-notes/scope are not blocks users hand-edit (observed across all three product repos), so silent overwrite is the right default. Doctor migration includes a one-time before/after preview so users see what becomes derived.
- `prawduct-doctor views --refresh` is available for ad-hoc regen between commits.

**Alternatives considered.**
- *Marker-validated blocks* (rejected): whitespace/ordering false positives make this fragile.
- *Hand-curated with linter warning* (rejected): preserves the drift it's meant to fix.
- *Separate derived files (e.g., `.prawduct/views/status.md`) referenced from artifacts* (rejected): adds files instead of removing them.

**Compat.** See Compatibility Strategy above — views are opt-in via `views_enabled: true` in v1.4. Default off. Products migrate explicitly via `prawduct-doctor migrate v1.4 --enable-views`.

**Pipeline coverage.** Methodology (`methodology/building.md` chunk-close step), artifact (`change-log.md` schema + views), builder (regen-on-commit hook in `tools/product-hook`), Critic (Goal 4 reads from canonical store for coherence check). Discovery layer: N/A — this is a build-time artifact concern.

**Visible costs.** Pre-commit regen latency: <100ms expected (single-pass scan of canonical store, in-place rewrite of derived blocks). Migration latency: one-time, scales with existing change-log entries.

**Why now.** This is the load-bearing fix — most other coherence items become easier or unnecessary once the duplicate sources collapse.

**Scope hint.** ~3 chunks. Chunk 1: schema + canonical store extension + one view (Status block, regen-on-commit). Chunk 2: remaining views + doctor command. Chunk 3: compat shim + migration tooling + product-repo dry-run.

### F2. Cumulative Critic gate before merge

**Problem.** Per-chunk Critic windows are scoped to chunk diff; cross-chunk integration cracks never surface until PR review or production. Promoted to learnings in discodon already; framework still treats it as optional.

**Solution.** Build-plan template's *final* chunk auto-includes `/critic --cumulative` in "Done when." Cumulative review diffs `merge-base...HEAD` for the whole branch (not chunk window). `/pr create` **refuses (BLOCKING)** to open the PR without a passing cumulative-Critic record. The per-chunk Critic stays for fast local feedback.

**Methodology note (absorbed from F7, originally a separate feature).** Add a paragraph to `methodology/building.md`: *"Cumulative-Critic takes ~10 minutes synchronously. Before invoking it, complete any prep work that doesn't depend on its findings — `/learnings` for next chunk topic, draft PR description, backlog audit, deferred chunk-boundary reflections. This doesn't shorten the wait, but ensures the agent is ready to integrate findings the moment Critic returns rather than spinning up fresh post-wait."* No wall-time savings claimed — this is workflow hygiene, not a performance feature. True wall-time recovery deferred to F7-β investigation.

**Alternatives considered.**
- *Advisory cumulative review (warning only, not blocking)* (rejected): cumulative escapes are silent quality erosion; advisory means they continue to ship.
- *Run cumulative review only when chunk count ≥ 3* (rejected): cracks emerge at 2-chunk boundaries too; threshold is arbitrary.
- *Roll cumulative review into PR-reviewer instead of Critic* (rejected): PR reviewer's lens is different (release readiness, not code correctness); they catch overlapping but non-identical classes — keep both.

**Pipeline coverage.** Methodology (`methodology/building.md` build-cycle final step), artifact (build-plan template `cumulative-final` chunk type — see F6), builder (`/pr` gate), Critic (new `--cumulative` mode in SKILL.md). Discovery: N/A.

**Visible costs.** Adds ~10 min wall-clock at end of every bundle. F7 recovers most of this via parallel work during the wait.

**Why now.** Cheap to implement, eliminates a class of escapes that currently relies on PR-reviewer goodwill.

**Scope hint.** 1 chunk. Mostly skill + template edits; minor hook check in `/pr`.

### F3. Critic verifies build-plan symbol references

**Problem.** Build-plan prose references files, functions, classes, MCP probes, backlog IDs that have been renamed, deleted, or never existed. Hallucinote independently proposed a structural test for this 3 times across the wave. Counts in audits ("30+ blocks" → 4 actual) keep wasting chunk scope.

**Solution.** Add a step to the Critic protocol: parse the build-plan section for the **chunk under review only** (not upcoming chunks — those reference symbols that legitimately don't exist yet). For each file path, function, class, or backlog ID mentioned in the current-chunk section, verify existence (file path: stat; symbol: grep/equivalent text search; backlog ID: grep backlog.md). Flag missing references as BLOCKING. Counts cease to matter — the plan stops listing them ("see grep result at chunk start") so the linter has nothing to drift against.

**Forward-reference safety.** Build-plan sections for chunks N+1 and beyond MAY reference symbols that don't exist yet (planned implementations). F3 check scopes by chunk header — section under the current chunk's H3 only. The check identifies which section is "current" via the build-plan's Status block (the active or in-progress chunk).

**Alternatives considered.**
- *Use language-server (LSP) symbol resolution* (rejected for v1.4): per-language plumbing, breaks framework's language-agnostic stance. Captured as v1.5+ enhancement (F12 in backlog).
- *Verify on commit instead of in Critic* (rejected): Critic is the cost-effective gate that already runs; pre-commit hook would duplicate effort and slow commits.
- *Make this opt-in per chunk* (rejected): every multi-chunk session in three product repos hit this; opt-in would mean opt-out by neglect, defeating the purpose.

**Pipeline coverage.** Methodology (`methodology/planning.md` build-plan authoring), artifact (build-plan template + Critic protocol), builder (chunk-start verification step), Critic (new step in Goal 4 coherence checks). Discovery: N/A.

**Visible costs.** Adds ~2–5s per Critic invocation for symbol grep over chunk-section references. Negligible vs. Critic's ~1–10 min runtime.

**Why now.** Critic already runs every chunk and is fork-context read-only — symbol existence is a read, fits the constraint. Cheapest place to put this check.

**Scope hint.** 1 chunk. Critic protocol edit + ~60 lines of helper logic (parser + scope detection + verification).

### F4. Test-evidence asserts coverage of change, not tree freshness

**Problem.** Current fingerprint (timestamp/tree-hash) is documented in `build-governance.md` but partially fictional in the implementation. Worse, it can't catch the real failure mode: new code ships with no test that exercises it. "Tests passed" gives false confidence because nothing references the new code.

**Principle (language-agnostic).** The framework asserts a contract: *every change in the diff must be exercised by at least one test in the executed run*. The framework defines the contract and evidence schema; the product chooses how to satisfy it using its language's idiomatic tooling.

**Solution.**

**F4a — Evidence contract (framework concern, language-agnostic).**
- `.test-evidence.json` schema:
  - `git_sha` (at test run)
  - `tests_executed` (list — files, IDs, or any product-chosen identifier)
  - `changes_referenced` (list of changed files or symbols that the executed tests at least textually reference; renamed from earlier draft's `changes_covered` to be honest about what's proven)
  - `verifier` (string — name of the tool/method that produced `changes_referenced`)
  - `coverage_level` (enum — `referenced` for floor verifier, `executed` for real coverage tools)
- Critic verifies: `git_sha == HEAD_at_review` AND every changed file in the diff appears in `changes_referenced` (or is explicitly excluded — docs, configs, etc.).
- A change not in `changes_referenced` → BLOCKING with message scaled to verifier:
  - At `coverage_level: referenced` → "change X is not referenced by any executed test (floor check — does not prove execution)."
  - At `coverage_level: executed` → "change X has no executing test."

**F4b — Verifier plug-point (product concern, language-specific).**
- Products provide `tools/test-reference-verify` (renamed from earlier draft's `test-coverage-verify` to match what the floor actually proves) that runs alongside the test suite and emits a `.test-evidence.json` conforming to the schema.
- Framework ships a reference verifier — naive symbol-grep over changed files. **This is a floor, not a default-good-enough.** It catches the most common failure (new code with no test that even mentions it) but is foolable: a test file can import a module and reference a symbol by name without ever executing it. Products with non-trivial coverage concerns SHOULD provide a stronger verifier (language-native coverage report, test-impact analysis, etc.) and set `coverage_level: executed` in the emitted evidence.
- Methodology doc explicitly states the floor's limitations so authors don't treat it as a coverage guarantee.
- Critic doesn't care which verifier was used — it reads the schema and validates the assertion at the declared `coverage_level`.

**F4c — Methodology principle (cross-cutting, narrative).**
Add to `methodology/building.md`: *"Design tests idiomatically for your language and toolchain. Use whatever language-native mechanisms exist (incremental test runners, file-watch caches, change-detection plugins) to avoid re-running tests when the underlying code and tests haven't changed. The framework asserts the **contract** — every change is covered by an executed test — not the **implementation**. The reference verifier is a floor; if your project's correctness matters, plug in a real coverage tool."*

**Alternatives considered.**
- *Require real coverage instrumentation as the floor* (rejected): forces language-specific tooling on every product, breaks language-agnostic stance.
- *Skip framework-level enforcement, leave to products* (rejected): the silent-failure class is exactly what the framework's safety claim is supposed to prevent. Floor-level enforcement is better than none.
- *Tree-hash fingerprint with stricter rules* (rejected): doesn't catch untested new code at all, just stale evidence. Wrong instrument.

**Compat.** See Compatibility Strategy above — old `.test-evidence.json` fingerprint fields keep working; new schema is detected by presence of `verifier` field. Symbol-reference assertion is opt-in via `coverage_required: true` in project-state.yaml. Default off in v1.4. Critic falls back to current behavior when off.

**Pipeline coverage.** Methodology (`methodology/building.md` test-design + idiomatic-tooling principle), artifact (`.test-evidence.json` schema), builder (`tools/test-reference-verify` reference + product-provided override), Critic (new check in Goal 1 reads `coverage_level` and scales severity). Discovery: N/A.

**Visible costs.** Reference verifier adds ~1–10s per test run (grep over changed-file symbols × tests). Real coverage tools cost what they cost — product's call.

**Why now.** This is the highest-quality-erosion item. The framework's primary safety claim ("Critic said tests pass") is currently falsifiable on untested new code. F4a alone closes the silent-failure path *for products that opt in*; the floor verifier limits false-confidence but doesn't eliminate it.

**Cuts that ride along (v1.5, not v1.4):** delete fingerprint references from `build-governance.md`, delete fingerprint-stale warnings from product-hook, drop tree-hash freshness mechanism. In v1.4 these are deprecated-but-supported; v1.5 removes after migration window.

**Scope hint.** 3 chunks. Chunk 1: new evidence schema (additive, compat-friendly) + reference verifier. Chunk 2: Critic check + methodology principle. Chunk 3: doc cleanup + migration tooling + product-repo dry-run.

### F5. Sync via single dispatch point — quarantine framework drift to marker commits

**Problem.** `.claude/settings.json` banner string, hook commands, statusline all sync via place-once template; each framework release leaves the file dirty in unrelated commits. Three repos show banner-rename + product-hook drift co-mingled with chunk diffs every release.

**Constraint.** `companyAnnouncements` is the user's session-start banner — version info there is *user-visible* and worth keeping. SessionStart hook output goes to the model only (previous "tell the user X via hook" attempts failed). So we can't move the banner; we have to make its churn benign.

**Solution.**
- **settings.json content gets minimized** — `hooks` block dispatches to `tools/product-hook hook <event>` exclusively (single line per event, stops changing when individual hook logic evolves); statusline (if used) calls `tools/product-hook statusline`. `companyAnnouncements` keeps the version string but everything else collapses behind dispatch.
- **All non-user-visible version-bearing strings move into `tools/product-hook`** — the file already syncs every release; one more version string there is invisible to product diffs.
- **Framework sync auto-commits drift at session start** — if `prawduct-doctor sync` detects framework-managed files changed (settings.json banner version, product-hook content, methodology files synced via `template` strategy), commit them immediately as `chore(sync): prawduct vX.Y.Z` *before* any other work. Drift becomes a single dated marker commit per upgrade, never co-mingling with chunk diffs.
- **Auto-commit preconditions (required, not optional):**
  - Working tree clean of non-framework changes — refuse if user has WIP, stashed or unstashed.
  - Branch is not in protected list (`main`, `master`, `release/*` — configurable via project-state.yaml).
  - No in-progress rebase/merge/cherry-pick (`.git/MERGE_HEAD`, `.git/REBASE_HEAD` absent).
  - On precondition failure: surface as a SessionStart NOTICE (visible to user via stdout if hook surfaces it; logged either way), skip the auto-commit, leave drift in working tree for the user to commit deliberately.
- **Investigate (open question):** does Claude Code now support any mechanism for hook output → user? If yes, future v1.5 could move version info there and drop the announcements field entirely. Until confirmed: settings.json stays the user-facing channel.

**Critic note from review:** the "settings.json minimization" half is mostly cosmetic in current product repos — hook bodies are already one-line `python3 tools/product-hook ...` dispatches. The real value of F5 is the auto-commit-on-sync mechanism. Reflected in scope below — minimization merges into the auto-commit chunk rather than standing alone.

**Alternatives considered.**
- *Stop syncing settings.json at all; document manual upgrade* (rejected): regresses self-contained-product principle; new product clones would miss banner/hook changes.
- *Move all framework-managed files behind `.prawduct/`* (rejected for v1.4): bigger refactor than v1.4 can absorb; captured as v1.5+ consideration.
- *Pre-commit hook that strips framework-managed lines from diffs* (rejected): obscures real changes from Critic and reviewers; auto-commit is more honest.

**Compat.** See Compatibility Strategy above — existing settings.json keeps working unchanged. New minimized layout is opt-in via `prawduct-doctor migrate-settings`. Critic surfaces non-migrated settings as NOTE starting v1.4.1.

**Pipeline coverage.** Methodology (no doc change — sync is infrastructure), artifact (settings.json layout + `tools/product-hook` dispatch contract), builder (auto-commit logic in doctor sync), Critic (no change — auto-commit removes the drift Critic was flagging). Discovery: N/A.

**Visible costs.** Auto-commit at session start adds <2s when drift detected; zero when clean. One additional commit per framework upgrade in product repo history (intended: that's the marker commit).

**Why now.** Once dispatching is collapsed, the only structural change per framework release is the version-bump in companyAnnouncements — predictable, mechanical, auto-committable. Product-repo commit history stops accumulating unrelated framework noise; Critic stops re-flagging the same drift every chunk.

**Scope hint.** 2 chunks (was 3 — Chunk 1 minimization merges into Chunk 2 per Critic note above). Chunk 1: sync auto-commit logic + preconditions + minimal settings.json layout adjustment. Chunk 2: migration command + product-repo dry-run + compat shim.

### F6. Proportional Critic via chunk-type declaration

**Problem.** Critic runs the same protocol regardless of chunk type. Zero-diff chunks (branch cleanup) have nothing for Critic to review; doc-only chunks need numeric verification but not test evidence; designer-handoff chunks shouldn't gate on Critic at all (currently a user-memory carveout, not a framework rule).

**Solution.** Build-plan front-matter declares `type: code | doc-only | cleanup | designer-handoff | cumulative-final` per chunk. Type defaults to `code` when omitted — most chunks declare nothing. Critic reads the type and selects protocol from a table:
- `code` → full protocol (current default behavior)
- `doc-only` → prose checks + numeric/count verification, skip test evidence and symbol coverage
- `cleanup` → structural verification (branch/file ops); skip symbol coverage; tolerate zero diff
- `designer-handoff` → declarative-only review; skip Critic gating (formalize the carveout)
- `cumulative-final` → bundle-wide review (marker that triggers F2's cumulative-Critic invocation, not a separate protocol)

**Alternatives considered.**
- *Auto-detect chunk type from diff content* (rejected for v1.4): heuristic, error-prone, hides intent. May revisit if declared types prove burdensome.
- *Single proportional-effort knob (1–5) instead of enum* (rejected): less informative for Critic; harder to map to specific protocol differences.
- *Inherit Skill-internal `chunk` vs `final` mode for everything* (rejected): conflates "how thorough is the review" with "what kind of work was done"; orthogonal concerns deserve orthogonal types.

**Pipeline coverage.** Methodology (`methodology/planning.md` chunk-type guidance), artifact (build-plan template front-matter), builder (no change — author declares), Critic (protocol selector reads `type`). Discovery: N/A.

**Visible costs.** Zero runtime cost. One additional field in build-plan front-matter (optional, defaults to `code`).

**Why now.** Embedded in P11 (Proportional Effort) but never operationalized. Kills three documented friction classes at once and pulls a quiet user-memory carveout into the framework.

**Scope hint.** 1 chunk. Mostly template + skill prose; minimal code.

## Tier 2 — Ship with v1.4 if Tier 1 lands clean

### F8. Foreign-API verification as a methodology default

**Problem.** Hallucinote Wave 2 root cause: every unit-test fake mirrored an assumed API. The build plan referenced Ableton Live MCP probes that didn't exist; handlers shipped against signatures that didn't match. Pattern recurs every time the framework wraps a foreign SDK without source verification.

**Solution.** Promote as methodology rule in `methodology/planning.md`: when wrapping a foreign API/SDK, the first chunk's first step is reading the source or running discovery probes — not drafting handlers from documentation. Build-plan template includes an optional `foreign_api: <name>` field; if present, chunk 1 must include a `verify-api` step.

**Pipeline coverage.** Methodology (`methodology/planning.md` foreign-API rule + `methodology/discovery.md` cross-reference for early identification), artifact (build-plan template optional `foreign_api` field), builder (chunk-1 verify-api step), Critic (Goal 2 checks for verify-api step when `foreign_api` declared). Discovery: build-plan-author surfaces foreign APIs during planning — this is the new discovery-stage touch.

**Visible costs.** Adds one chunk-1 step when foreign API is involved (~5–30 min for source-read or probe-run, depending on API surface). Saves chunk-rework cost when API turns out to differ from assumed shape (which is the recurring failure this addresses).

**Scope hint.** 1 chunk. Methodology + template edit; example added to one product repo.

### F9. Learnings lifecycle — structural sentinel tracker

**Problem.** 2-confirmation promotion rule is manual; "third hit, fourth hit" entries litter reflections without promotion; learnings that are now structurally enforced (e.g., by a sentinel test) keep living in `learnings.md` as comments.

**Solution.** Each `learnings.md` entry gains optional fields: `confirmations: N`, `sentinel: path/to/test::test_name`. `/janitor learnings` (or `prawduct-doctor learnings`) audits both:
- Promotes entries with `confirmations >= 2` and no sentinel into the active list
- Retires entries whose sentinel exists and passes (move to `learnings-detail.md` as historical)
- Flags entries with `confirmations: 1` older than 90 days as stale

**Alternatives considered.**
- *Sidecar metadata file (`learnings.meta.json`)* (rejected): adds a file; metadata drifts from entries; harder to read at a glance.
- *Git trailers in commits referencing learning IDs* (rejected): metadata is in commit log, not in the learnings file itself — wrong place to look for current state.
- *Auto-detect confirmations by scanning `.session-reflected` for learning-ID mentions* (deferred): clever, but `.session-reflected` decays; risks miscounting. Could layer on top of explicit field later.

**Pipeline coverage.** Methodology (`methodology/reflection.md` confirmation step), artifact (`learnings.md` schema fields), builder (manual confirmation increment by author or via janitor command), Critic (Learnings Cross-Check in final mode reads new fields). Discovery: N/A.

**Visible costs.** Janitor command runs on demand; no ongoing runtime cost. Schema migration is one-time per product repo.

**Scope hint.** 1 chunk. Schema migration helper + janitor sub-command.

### F10. Operator-verification queue

**Problem.** Every visual / Live-integration chunk ships with a "user-side smoke test recommended" caveat in ad-hoc format. No tracking of outstanding verifications; chunks get marked complete despite live-verification gap.

**Solution.** `.prawduct/operator-verification.md` — append-only queue, each entry: chunk ID, what to verify, where to look. `/pr` close **BLOCKS** if queue is non-empty (warnings are dismissible; a non-empty queue means ungated visual changes ship). Operator drains by editing the file or via `prawduct-doctor verify <id>`. Explicit override available via `/pr --accept-pending-verification` with rationale recorded in the work-log. Configurable per-product via `operator_verification_required: true|false` in project-state.yaml — default true; products without human interfaces opt out.

**Pipeline coverage.** Methodology (chunk-close step: "if visual change, append to operator-verification.md"), artifact (`.prawduct/operator-verification.md` template), builder (chunk close enqueues), Critic (Goal 2 reads queue for chunks declaring visual changes — emits NOTE if not enqueued), `/pr` (BLOCKING gate). Discovery: N/A.

**Visible costs.** One operator-side smoke-test pass per visual-affecting chunk before merge. The friction this currently absorbs implicitly is at production rather than pre-merge.

**Scope hint.** 1 chunk. Template + minor skill edit; BLOCKING gate in `/pr`.

## Cuts riding along with v1.4

These get removed (not added) as part of the relevant feature:

- **Test-evidence tree-fingerprint mechanism** (with F4) — `build-governance.md` claims, product-hook warnings, gitignore-induced stale flagging.
- **`change-log.md` as separate artifact** OR **release-notes hand-author flow** (with F1) — whichever loses the "canonical store" vote.
