# Prawduct cost/benefit audit — sibling products, 2026-10-02

`status: findings · source: user request 2026-10-02 ("audit sibling repos … cost/benefit of prawduct over versions … metrics … OPTIONALLY contribute stats") · related: #262 (TEL-7A4X), #291, #563, #724, #908, #941`

## What was read

Ten clone-shared evidence stores (`<git-common-dir>/prawduct/evidence.jsonl`; worktrees share
their main clone's store, so each product is counted once): bankmachine, cordyceps, discodon,
fabulous, faidh, hallucinote, prawduct, puzzles, samsung-frame-art-loader, swordfishing. They hold
3,726 Critic reviews, 20,108 findings, 8,701 resolution facts, 7,671 disposition facts, 220 test
runs and 156 guard refusals, written under plugin 2.3 through 3.7. Every evidence fact carries
`actor.plugin`, so **the evidence store, not the ledger, is the version-aware source**: ledger
lines still have no `plugin` field (#262 TEL1 never shipped). Five older products (metallm,
scriob, scriob2, trenchant, continuum; plugin 2.0–3.0) have ledgers but no evidence store and are
excluded from the version table.

Stop-hook blocks are recorded nowhere in prawduct's stores (#563). They were mined from Claude
Code session transcripts; see § Stop hook.

**Re-deriving these numbers.** The review figures re-derive from each product's own evidence store
with `prawduct-hook stats` (shipped by this audit's wave 1). The one-off script used here predates
that command, and the two differ only where § Proposed metric set's as-built note says. The
Stop-hook figures came from Claude Code transcripts, which are kept for about six weeks, so they
cannot be re-derived after mid-November 2026. From wave 1 on, `stats` counts Stop blocks from
recorded facts instead.

## What the numbers say

1. **Review is catching real defects, and the mix is right.** 1,291 blocking findings were fixed.
   By goal: *Nothing Is Broken* 659, *Nothing Is Missing* 314, *Nothing Is Unintended* 114,
   *Everything Is Coherent* 104. Blocking findings get fixed ~90% of the time from 3.2 on, which
   says they are rarely noise.
2. **Duplicate reviews are not a material cost.** The same head tree was reviewed again 32 times
   in 3,726 reviews, and the same (base, head, mode) only 3 times. The cost people feel as
   "duplicate review" is something else: re-review *rounds* on one work unit (median 4–5, p90
   10–16).
3. **Verify-resolutions rounds are most of the review count, but mostly do their job.** They are
   49–70% of all reviews. Their *new-finding* yield fell from 72% of rounds (3.1) to 6–16%
   (3.6–3.7), which matches its narrowing to a delta review. About a fifth of them verify no
   resolution and find nothing. That fifth is the addressable waste (#724), and it is far smaller
   than the "64% find nothing" headline, which counted only new findings and ignored the
   resolutions those rounds verify.
4. **Notes are mostly noise by revealed preference.** 50–67% of notes are accepted, not fixed,
   from 3.4 on; warnings accepted rose from 6% to 20%. That is the signal #941 wants
   `review-stats` to report, and it reads directly off the disposition facts.
5. **Wall-clock is mis-measured.** See the table footnote: the estimate overstates by 2–4×, so
   every cost argument built on `duration_seconds` (including #724's 21h figure) overstates review
   cost.
6. **The benefit we cannot see is escapes.** Nothing records a defect that review *missed* and a
   user or a later session found. Without that, "blocking fixed per hour" measures activity, not
   protection.

## Stop hook

Mined from Claude Code transcripts (`system`/`stop_hook_summary` entries; every prawduct block
carries `[prawduct vX · gate: <name>]`, so gate attribution is exact). The window runs from
2026-08-22 to 2026-10-03, because older transcripts are gone. Versions are dev builds.

- **Not excessive overall:** 65 blocks in 528 governed sessions, which is 0.12 per session and
  1.6% of stop attempts. **No loops:** no run of three or more consecutive blocks; the same gate
  blocked twice in a row only twice.
- **Rising with new gates:** blocks per session went 0.04 (3.4) → 0.10 (3.5) → 0.29 (3.6) → 0.19
  (3.7). The rise is mostly the new learnings gates and `clear-verdict`, not the Critic gate.
- **One outlier product:** puzzles had 0.29 blocks per session and 4.1% of its stops blocked (29
  blocks); prawduct itself had 0.08 and 1.1%.
- **Recorded nowhere in prawduct:** a block is invisible to `review-stats` and to the janitor.
  This audit is possible only because transcripts happen to persist, and only for about six
  weeks. That is #563.

## Proposed metric set

> **As built (wave 1, `telemetry-stats`):** the definitions live in
> `plugin/docs/governance-telemetry.md` § `prawduct-hook stats`, and they differ from this proposal
> in three places:
> - **C5 loops** are a gate blocking three or more times in one session, because a Stop that passes
>   records nothing, so "consecutive" cannot be measured.
> - **B3** is an *acted-on* rate that counts a filed finding as acted on.
> - **B6** is descoped, because ledger lines carry no plugin version.
>
> **C5 rides the `guard-refusal` sink,** not a new `gate.blocked` kind.

Every metric is computed per product, bucketed by plugin `major.minor`, and normalised per **work
unit** (a review `scope`) or per **session**.

**Cost**
- **C1 rounds per work unit:** median and p90 of reviews per scope.
- **C2 measured review time per work unit:** `dispatched_at`→`ts` only. Self-estimates are
  reported separately and labelled as estimates.
- **C3 empty rounds:** verify-resolutions rounds that verified no resolution and raised no
  blocking or warning finding.
- **C4 unchanged-tree re-reviews:** reviews whose `head_tree` was already reviewed.
- **C5 stop blocks:** blocks per session and per stop, by gate, plus loop episodes (three or more
  consecutive blocks). Needs a `gate.blocked` fact (#563).
- **C6 guard refusals per session.**

**Benefit**
- **B1 blocking fixed per work unit,** by goal.
- **B2 warnings fixed per work unit.**
- **B3 precision per severity:** fixed / (fixed + accepted + waived). This is the honest
  "actionable rate" (#941).
- **B4 red suite runs** recorded before a commit.
- **B5 escapes:** a `kind:bug` item or a fix commit whose introducing change had passed review.
  Not measurable today; this is phase 2 and needs a `found_by` field on bug intake.
- **B6 learnings fired per session** (`learning.fired`).

**Headline ratios per version:** B1 per measured review-hour; C3 share; C5 per session; B3 for
notes. A version is better when B1 per unit holds and C1, C3 and C5 fall.

## Owner decisions, 2026-10-02

- **Default:** `never`, with `/prawduct:janitor` offering the opt-in.
- **First build:** metrics, a `gate.blocked` fact (#563) and the send path. Escapes (B5) are phase 2.
- **Transport:** the owner asked for an HTTP endpoint with a privacy promise, so a standard was
  researched (below). The owner then chose a Go-style HTTP collector (§ Owner goals).

- **Local-first amendment, confirmed by the owner 2026-10-03:** "yes, with consumer consent". The
  architecture norm's admitted network surfaces may gain a third, the opt-in stats upload, on
  condition that nothing leaves a product without its owner's consent. The amendment itself is
  written in wave 2 (#949); this line is its authority.
- **Collector host, decided by the owner 2026-10-03:** Cloudflare, a Worker plus R2 on an account
  the owner owns, answering "Yes to cloudflare" to the proposal on #950. The owner's condition,
  verbatim: "Just be sure it's off by default and consuming repos must affirmatively opt in". So
  contribution is off unless a product's own `project-preferences.md` says `ask` or `always`.
  Anything else reads as `never`: an absent row, an empty row, a misspelling or an unreadable
  file. The janitor asks and never writes the row itself.

## Transport research (2026-10-02)

- **IETF DAP / Prio, run by Divvi Up (ISRG):** the only real standard with a cryptographic
  guarantee. Two non-colluding aggregators mean no server sees an individual report. However:
  - It is still an Internet-Draft (draft-19, awaiting write-up), not an RFC.
  - ISRG runs only one aggregator, so the second must be self-run (Janus) or a partner's.
    Cloudflare archived its Daphne aggregator on 2026-06-03.
  - Metrics are fixed per task (count, sum, histogram).
  - It enforces a minimum batch size, which a dozen contributing products would rarely meet.
  - Its threat model (individual measurements are sensitive) is not ours: our payload is already
    aggregate counts.
- **Go telemetry model** (`go telemetry on`, telemetry.go.dev): no cryptography. The guarantee is
  structural. Collection is local by default and upload is opt-in. Only counters on a publicly
  reviewed allowlist (`golang.org/x/telemetry/config`) are uploaded. Uploaded reports are public,
  so anyone can audit what was sent. **This is the closest precedent for prawduct.**
- **OpenTelemetry / OTLP:** a wire format with any-collector compatibility, but no privacy
  semantics. Not needed for one fixed schema.
- **A GitHub issue as transport attaches the contributor's GitHub identity,** which is worse for
  anonymity than an HTTP POST.

## Owner goals for contribution (2026-10-02, verbatim)

> "we have two critical goals: 1) collect telemetry to improve prawduct, and 2) avoid knowing
> anything about the contributor."

The transport decision is a Go-style HTTP collector, which the owner chose 2026-10-02. Goal 2
governs every choice below; where it costs goal 1, the cost is named.

## Contribution design

**Content layer: what a report can reveal.** This layer is fully in our control.
- **No identifier of any kind.** No install id, product name, path, branch, scope, sha, finding
  text or language, and no timestamp finer than the report's window.
  - *Cost:* no per-contributor trend analysis.
  - *Dedupe:* handled on the client. A report covers one **closed** window (one plugin
    `major.minor` that the product has moved past, or one ISO week). The client records locally
    which windows it has sent and never resends one.
- **Every value is a number or a closed-enum token,** from a committed allowlist schema
  (Go-telemetry style). The client validates before sending and refuses any key outside the
  schema, so free text cannot be expressed.
- **Coarsening against fingerprinting:**
  - Absolute volumes go into log-scale bands (for example reviews in 1–9, 10–49, 50–199, 200+).
  - Rates and medians are rounded.
  - Plugin version is `major.minor` only; a `-dev.N` build becomes a `dev` flag.
  - A per-window metric with a denominator below a floor (for example fewer than 5 reviews) is
    dropped rather than sent.
- **The user sees the exact bytes** before anything is sent: preview, then approve, under the
  preference `Stats contribution: never | ask | always`, default `never`.

**Network layer: what the collector sees.** The collector code is public and stores the payload
only: no IP, no headers, no arrival time, and no access logs. A plain HTTPS endpoint we operate
still *sees* the IP while the connection is open, so goal 2 holds there by policy and published
code, not by construction. The client honours `HTTPS_PROXY`, so a contributor can send via
Tor or a VPN.

**Upgrade path to "by construction":** Oblivious HTTP (RFC 9458, January 2024). A third-party
relay sees the IP but not the content; our gateway sees the content but not the IP. Public relays
are run by Cloudflare (Privacy Gateway) and Fastly, but each needs an arrangement with that
provider, so it is deferred until volume justifies it.

**Not chosen:**
- **DAP/Prio:** our payload is already aggregate, the protocol is still a draft, and it needs a
  second aggregator.
- **GitHub-issue transport:** it attaches the contributor's GitHub identity, which violates goal 2.

**Receiving side:** #262's `aggregate-review-stats` ingests local product paths plus the
collector's published reports. This amends #262 Decision 2 ("the ledger never leaves the
machine"): only the coarsened, allowlisted aggregate may leave, and only with consent.

## Program

1. **Wave 1, local metrics** (built, `telemetry-stats`). `prawduct-hook stats` (C1–C6, B1–B4; B6
   descoped), Stop blocks recorded through the `guard-refusal` sink (the gate slice of #563), a
   `session-start` fact, and measured-only time. The disposition-based acted-on rate is #941's
   honest metric, but in `stats` rather than `review-stats`.
2. **Wave 2, contribution client.** The allowlist schema, payload builder with coarsening and
   floors, client-side sent-window record, preview and consent, the preference, and the janitor
   offer.
3. **Wave 3, collector.** A worker that validates against the same schema, stores the payload
   only and publishes reports; plus aggregator ingestion. Deployment needs an account the owner
   controls.
4. **Phase 2, escapes (B5).** A `found_by` field on bug intake, then attribution to the reviewed
   change.
