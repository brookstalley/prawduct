# v2.0.0 — Plugin Distribution: Design

**Status:** Approved; build plan committed (`v2.0.0-plugin-distribution-build-plan.md`). Release/distribution model specified (§5b, added 2026-06-01 from the gitflow research).
**Requirements Confidence:** Medium-High — architecture is settled and the release surface is now specified; the remaining technical assumptions are scheduled as build-chunk spikes (Open Risks §9), not blockers. None break the architecture; they tune the release trigger.

---

## 1. Problem & Root Cause

Framework artifacts (CLAUDE.md governance block, skills, hooks, `tools/product-hook`, `tools/lib/*.py`, methodology docs, templates) are **physically committed into every consuming product repo.** Once framework files share a git tree with product files, every framework update *is* a working-tree diff, and the framework's update mechanism collides with the user's git workflow (commits, branches, stash).

The entire `sync_cmd.py` apparatus — per-file SHA-256 hashing, `<!-- PRAWDUCT:BEGIN/END -->` markers, "stale-clean" git-history walking, auto-commit of drift, protected-branch gates, `.sync-pending` markers — exists **only to referee that collision.** Remove the premise (framework files in the repo) and the entire class of stash/pop/merge papercuts disappears, and most of that machinery becomes unnecessary.

## 2. The Governing Invariant (v1 lesson — non-negotiable)

Prawduct v1 was a shared **runtime** that products depended on (framework-path, runtime hook resolution, shared mutable session state). It was abandoned because it made parallel multi-agent work impossible (race conditions, clobbering). The lesson on file: *"The framework is a generator that produces self-contained product repos, NOT a runtime that products depend on."*

A plugin **is** a shared runtime dependency — the v1 failure mode — **unless** we hold this invariant:

> **INVARIANT: The plugin ships only immutable, read-only, versioned code. ALL mutable state lives in each product repo's `.prawduct/`. No mutable state is ever shared between product repos through the plugin.**

This is what makes a plugin safe where v1 was not: per-version plugin code is immutable and identical for everyone; each repo's `.prawduct/` is its own. Parallel agents on different repos (or worktrees of one repo) never contend on shared framework state. Self-containment is preserved.

## 3. Target Architecture

The Prawduct repo **becomes** the plugin and its own git-backed marketplace.

```
prawduct/                          # the plugin repo (and marketplace host)
├── .claude-plugin/
│   ├── plugin.json                # name: "prawduct", version: from VERSION
│   └── marketplace.json           # single-plugin marketplace entry
├── hooks/
│   └── hooks.json                 # SessionStart (briefing+banner+governance), Stop (Critic gate+reflection)
├── skills/                        # framework skills → /prawduct:* (moved from .claude/skills)
├── agents/                        # critic, pr-reviewer (already here)
├── methodology/ docs/ templates/  # bundled, read by skills/hooks via ${CLAUDE_PLUGIN_ROOT}
├── lib/ + bin/prawduct-hook       # runtime governance python (today's tools/lib + product-hook),
│                                  #   reads/writes ${CLAUDE_PROJECT_DIR}/.prawduct/ only
└── VERSION
```

### What moves OUT of consuming repos (into the plugin, never committed downstream)
- All framework skills (`critic`, `pr`, `janitor`, `learnings`, `backlog`, `prawduct-advisory`, `prawduct-doctor`) → `/prawduct:*`
- The agents (critic, pr-reviewer)
- The session hooks (`product-hook` → plugin `bin/` script wired via `hooks/hooks.json`)
- The runtime python (`tools/lib/*` governance bits)
- Methodology + templates + the governance text currently in CLAUDE.md's PRAWDUCT block

### What STAYS in the consuming repo (product-owned state, in tree)
- `.prawduct/` data: `project-state.yaml`, `learnings.md`, `learnings-detail.md`, `backlog.md`, `change-log.md`, `artifacts/`, `.critic-findings.json`, session files
- The product's **own** CLAUDE.md (product-specific instructions only)
- The product's **own** skills and code
- A committed **install reference** (not framework files): a `.claude/settings.json` entry naming the prawduct marketplace + plugin, so every developer who clones the repo gets governance automatically. This is a pointer, ~5 lines — it does not change when the framework updates, so it never drifts.

| Concern | v1.x (file-sync) | v2.0 (plugin) |
|---|---|---|
| Framework code location | committed in repo | `~/.claude/plugins/cache/` (out of tree) |
| Update mechanism | sync + auto-commit, leaves drift | marketplace update, **zero repo diff** |
| Mutable state | repo `.prawduct/` | repo `.prawduct/` (unchanged) |
| Version source | sync-manifest after pull | local `plugin.json` (offline-safe) |
| Skill names | `/critic` | `/prawduct:critic` |
| Stash/pop/merge papercuts | structural | **eliminated** |

## 4. Governance Delivery: Enforcement vs. Guidance (RESOLVED by verification)

Verification settled Open Risk #1: SessionStart `additionalContext` is **supplemental context, not a replacement** for CLAUDE.md's authoritative static instructions (docs explicitly recommend CLAUDE.md for static methodology/principles, hooks for dynamic state). So we do **not** push the full governance into `additionalContext`. Instead governance splits into two layers — the cut the learnings already prescribe (*"judgment alone won't interrupt momentum; the minimum structural enforcement must survive"*):

- **Enforcement layer (authoritative, blocking):** the Critic gate and reflection gate run in the plugin's **Stop hook** — *verified to have the same blocking power as a settings.json Stop hook.* This is what actually makes governance stick, and it depends on **no committed text**. Load-bearing guarantee; survives the migration intact.
- **Guidance layer:** principles, methodology pointers, build-cycle narrative. The **full methodology lives in the plugin** (read on-demand via `/prawduct:*` skills/hooks); a SessionStart hook injects a session-start digest via `additionalContext`.
- **Thin static anchor in committed CLAUDE.md:** because `additionalContext` is supplemental, the product keeps a **small, static** governance anchor in its own CLAUDE.md — the few hardest rules ("This repo is governed by Prawduct via plugin; STOP and read the build cycle via `/prawduct:building` before writing code; enforcement runs at session end") plus a pointer to the plugin. It is small, changes *rarely* (a stable contract, not the evolving methodology), and contains **no version number** (version is injected at runtime). Small + static + version-free ⇒ effectively zero drift, while preserving CLAUDE.md-level authority for the hard rules.

Net: the heavy, frequently-revised methodology leaves the repo (no drift); the rare hard-rule anchor stays authoritative in CLAUDE.md; enforcement is structural via the blocking Stop hook.

## 5. Versioning, Update & Version Visibility

- **Version source of truth:** `plugin.json` `version` (mirrors `VERSION`). Read locally → version display works offline.
- **Update posture (user decision): auto-update everywhere, no *version* pinning.** Newest released version flows to all consumers via the marketplace. (This is about not freezing consumers at an old version — it is *not* about which branch they consume. The consumed **ref is explicitly `main`**; see §5b.)
- **Version-delta banner:** SessionStart hook compares `plugin.json` version against a per-repo last-seen marker (`.prawduct/.prawduct-version`). On change, it shows `Prawduct vX → vY` plus changelog highlights for the bump; otherwise it's quiet. This is the *safety net* for always-latest: every version move is at least made visible.

**Verified mechanism (resolves Open Risk #2):** keep a human-readable **semver `version`** in `plugin.json` (drives the banner) *and* get always-latest via **`autoUpdate: true`** on the committed marketplace reference — the marketplace auto-refreshes at session start and pulls the newest published version. Semver display and always-latest are therefore not in tension: `autoUpdate` drives the update, the semver drives the banner. (Escape hatch exists but is unused by default: `DISABLE_AUTOUPDATER=1`.)

### 5a. New gates activate on update — with attribution (DECIDED)
The learning on file (*"a plugin push must not silently activate enforcement that blocks existing repos"*) was raised and **deliberately overridden by the product owner**: a new gate that blocks on update is acceptable — *"no different than shipping an update to CI that blocks someone's push."* Governance is modeled as CI; updating CI can legitimately start blocking, and that is expected behavior, not a defect.

The one property we preserve from the learning is **attribution, not opt-in**. The CI analogy holds fully only if a new block is *explainable*:
- New enforcement **activates immediately on update** — no dormant state, no adopt step. Always-latest means always-current gates too.
- The **version-delta banner announces new gates** on the bump that introduces them (e.g. "v2.1 adds gate: cumulative-critic").
- A **blocking message names the version and gate** that caused it (e.g. "blocked by prawduct v2.1 gate: cumulative-critic"), so a surprise block is always traceable to the update, never mysterious.

No `/prawduct:adopt`, no `adopted_gates` flag. Code and enforcement ship together; visibility (banner announcement + attributed block messages) is the safety net, not opt-in. *Supersedes the "auto-enable belongs with visibility" learning for the explicit case where the owner models governance as CI — capture this nuance in learnings during Phase 5.*

### 5b. Release surface & gitflow (develop = integration, main = release)

The repo follows **gitflow**: feature branches → `develop` (integration) → promoted to `main` (release) periodically. Consumers must only ever see **release-quality code on `main`**; `develop` is never consumed. This holds identically for *both* distribution mechanisms, which is why the migration doesn't change the release contract — only the transport:

- **File-sync (legacy, until a repo migrates):** a product's framework checkout sits on `main`; `sync` runs `git pull --ff-only` on *that checkout's current branch* (`_try_pull_framework`, `tools/lib/core.py`). Products therefore only ever receive what is on `main`; `develop` is invisible to them. A fix merged to `develop` reaches file-sync products only at the next `develop → main` promotion.
- **Plugin (v2.0):** the consumer's committed install reference pins the marketplace **and** the plugin `source` to **`ref: "main"`** — *not* the bare repo, which silently follows GitHub's *default-branch* setting (a structural footgun if that ever points at `develop`). `autoUpdate: true` re-resolves `main` at session start. `develop` is never referenced by any consumer.

**The release event is `develop → main`.** One promotion does all of: merge `develop`→`main`; **bump `plugin.json` `version`** (mirrors `VERSION`); finalize the changelog (flip that release's entries from `status=merged` → `status=shipped`, add `release=`/`scope=` tags, run regen-views); tag `vX.Y.Z` on `main`; bump the banner. Nothing reaches users between releases. (This also defines the change-log status lifecycle: an entry is `status=merged` while it sits on `develop`, `status=shipped` once promoted to `main` in a tagged release — the `views.py` parser only rolls `status=shipped` entries into derived views, so `merged` entries are correctly inert until release.)

**`version` is a cache key — bump it every release (verified from docs).** Claude Code resolves a plugin's version from `plugin.json` `version` first, then the marketplace entry, then the source commit SHA. If `version` is set but *not* bumped on a release, `autoUpdate` sees the same string and **keeps the cached copy — a release that forgets the version bump does not ship.** The version bump is therefore the release trigger, not cosmetic. (Source: Claude Code "Plugins reference" + "Create and distribute a plugin marketplace" docs, retrieved 2026-06-01.)

**Decision: pin `ref: "main"` + bump semver `version` per release (not a tag-pinned marketplace).** Because prawduct's `marketplace.json` lives in the *same* repo as the plugin, tag-pinning the marketplace entry every release would mean editing `marketplace.json` (and arguably each consumer's pin) on every release — extra ceremony for no safety gain under gitflow, where `main` only ever holds releases. `ref: "main"` + a bumped `version` gives controlled, visible releases in a single promotion step. **Documented fallback:** `ref: "vX.Y.Z"` tag-pinning, used only if Chunk 2's spike finds `autoUpdate` ships non-version-bumped `main` commits in a way the version-cache-key gate doesn't catch.

**One documented unknown → Chunk 2 verify-api.** The docs specify `ref`/`sha` pinning and that `version` is the cache key, but do **not** state whether `autoUpdate` on `ref: "main"` re-resolves to *main's HEAD* or only to the *latest tag*. Both are fine for us (under gitflow, main HEAD == latest release), but Chunk 2 must confirm empirically: push a version-bumped commit to a test `main` → a consumer with `autoUpdate: true` picks it up; push a *non-*version-bumped commit → it does **not** ship; and confirm a `develop` commit is never consumed. (Source for the gap: claude-code-guide research, 2026-06-01.)

**Reaching users with an off-cycle fix.** A patch (e.g. the v1.8.0 `REBASE_HEAD` sync bugfix) lands on `develop` first and reaches file-sync consumers only at a `develop → main` promotion + `VERSION` bump (a patch release, e.g. v1.8.1). Under the plugin model the same is true via the version-bump trigger. So "get this fix to downstream now" = "cut a patch release," a deliberate `develop → main` event — never a direct push to `main`.

## 6. Skill Namespacing

All framework skills become `/prawduct:*` (`/prawduct:critic`, `/prawduct:pr`, `/prawduct:backlog`, …). Two consequences:
1. **Collision-proof.** Hallucinote keeps its own `/compose-part`, `/mix-review`, `/song-new` with zero risk of clashing with framework names. (Today they sit in the same `.claude/skills/` dir — namespacing structurally separates product from framework.)
2. **Doc/reference sweep required.** Every internal cross-reference (skills calling skills, methodology saying `/critic`, the CLAUDE.md governance text, README) must update to `/prawduct:*`. Per the *"removing a mechanism requires removing its name too"* learning, this sweep is part of the work, not a follow-up.

## 7. Coexistence & Migration (backward compat is paramount)

Legacy file-sync repos must keep working untouched until explicitly migrated. The hazard is double-governance: a repo with both the committed `product-hook` *and* the plugin would fire two SessionStart hooks and expose `/critic` + `/prawduct:critic`.

- **Mutual stand-down detection:** the plugin's hook detects legacy file-sync mode (committed `product-hook` wired in `settings.json`, or a sync-manifest with managed files) and stands down with a "run `/prawduct:migrate`" notice. The legacy committed hook symmetrically detects the plugin and stands down. Only one governs at a time.
- **Cutover (`/prawduct:migrate`, via prawduct-doctor):** verify/like plugin installed → commit the project-scoped install reference → strip committed framework files (framework skills, `tools/product-hook`, framework `tools/lib`, CLAUDE.md block) → drop committed hook wiring from `settings.json` → record `distribution: plugin` in `project-state.yaml`. One commit, fully reversible.
- **Shims stay** (standing instruction): `prawduct-sync.py`/`prawduct-init.py` shims remain for un-migrated repos.

## 8. Consumption Model for Products (answers the hallucinote question)

**prawduct-the-plugin is dev-time governance — it is never part of any product's shipped artifact.** It governs the *development* of a repo, orthogonal to what that repo produces (app, CLI, library, MCP server, or itself a plugin).

- **A normal product (hallucinote today):** developers install the prawduct plugin once; the repo commits only the install *reference* (in `.claude/settings.json`, project scope) so every contributor gets governance on clone — and commits *none* of the framework files. Hallucinote's repo keeps `compose-part`, `mix-review`, its `.prawduct/` state, its `hallucinote_mcp/` server. Migration = the §7 cutover.
- **A product that is itself a plugin/MCP server:** no conflict. The product's own `.claude-plugin/` (or `.mcp.json`) is **committed — it's the product.** prawduct-the-plugin is **installed dev tooling — out of tree.** Namespacing keeps the two skill sets distinct (`/prawduct:critic` vs the product's `/foo`). Hallucinote already demonstrates this: it ships an MCP server *and* is governed by prawduct; the two never touch.
- **Self-containment holds:** the product repo still carries all its own `.prawduct/` state; the plugin is read-only shared code. Parallel agents on the product don't share mutable state through prawduct (the v1 invariant, §2).

**The committed install reference (verified shape).** The product commits only this to `.claude/settings.json` — no framework files. The marketplace `source` pins **`ref: "main"`** so consumers track the release surface, never `develop` and never an accidental default-branch change (§5b):
```json
{
  "extraKnownMarketplaces": { "prawduct": { "source": { "source": "github", "repo": "brookstalley/prawduct", "ref": "main" }, "autoUpdate": true } },
  "enabledPlugins": { "prawduct@prawduct": true }
}
```
The plugin entry inside `marketplace.json` likewise pins its own `source` to `ref: "main"`. On first trusted open, Claude Code prompts each developer to install the marketplace + enabled plugin (one-time, skippable). Honest caveat: that's *one trust prompt per dev per repo* — not literally zero-touch — but it commits zero framework files and never drifts thereafter.

**Guidance to state in docs:** "Prawduct is a development dependency, not a runtime dependency of your product. Install it as a plugin; commit only the install reference and your `.prawduct/` state. Whatever you build — including another plugin — prawduct governs how you build it, not what you ship."

## 11. Plugin file-reference & runtime mechanics (verified via docs, 2026-06-01, during Chunk 3)

Verified via claude-code-guide against the plugins/skills/hooks reference. These constrain how Chunks 4–6 port the skill → agent → runtime stack, and they invalidate the naive "just reference `${CLAUDE_PLUGIN_ROOT}/…`" assumption:

- **`${CLAUDE_PLUGIN_ROOT}` is NOT substituted in skill `SKILL.md` *prose*** — only in hook `command`/`args` (and exported to the hook's process env). Skill prose gets `$ARGUMENTS`, **`${CLAUDE_SKILL_DIR}`** (the skill's OWN subdir, *not* the plugin root), `${CLAUDE_SESSION_ID}`, `${CLAUDE_EFFORT}`. ⇒ a skill body **cannot** portably say "Read `${CLAUDE_PLUGIN_ROOT}/agents/critic/SKILL.md`". The Chunk-3 ported skills work *only* because `agents/`/`tools/` exist at `${CLAUDE_PROJECT_DIR}`=this repo; they would break on a migrated or product repo. **This must be fixed before the plugin is self-contained.**
- **`bin/` is auto-added to the Bash tool's PATH while the plugin is enabled.** ⇒ put the runtime at `bin/prawduct-hook`; skills/hooks invoke it as bare `prawduct-hook` (no path prefix), and `allowed-tools: Bash(prawduct-hook *)` matches. (Chunk 5.)
- **Plugin Python importing a bundled `lib/` is NOT automatic** — the entry script must `sys.path.insert(0, os.environ["CLAUDE_PLUGIN_ROOT"])` before `from lib import …`. (Chunk 5.)
- **A plugin "agent" (`agents/<name>.md`, flat file, frontmatter `name`/`description`/`model`/`tools`) is a named, invocable subagent *type*** (shows in `/agents`). This is DIFFERENT from today's `agents/critic/SKILL.md`, an instruction *file* the `/critic` skill reads and feeds to a forked generic Agent.
- **A skill may bundle supporting files in its OWN dir** (`skills/critic/instructions.md`) and reference them by relative link / `${CLAUDE_SKILL_DIR}` (the latter in bash-injection blocks).

### DECISION (2026-06-01): Option A — proper plugin subagents
Owner chose A over the lower-churn B/C: "always do the right thing, even if it's more work." Convert `agents/critic/SKILL.md` + `agents/pr-reviewer/SKILL.md` into flat plugin-subagent definitions (`agents/critic.md`, `agents/pr-reviewer.md`) invoked by the `/prawduct:critic` / `/prawduct:pr` skills.

**Verified plugin-subagent mechanics (claude-code-guide, 2026-06-01) — shape the implementation:**
- **Frontmatter:** `name` (req), `description` (req), `tools` (allow-list), `disallowedTools` (deny-list), `model`, `effort`, `maxTurns`, `skills`, `isolation: worktree`. Plugin subagents **ignore** `hooks`/`mcpServers`/`permissionMode` frontmatter (security).
- **Namespacing:** `agents/critic.md` in plugin `prawduct` → subagent type `prawduct:critic`. A product's own `.claude/agents/critic.md` **overrides** the plugin's (plugin = lowest priority) — collision-safe; products can customize.
- **cwd** of an invoked subagent = the consuming repo, so it can `Write` `.prawduct/.critic-findings.json` there. ✓
- **No `${CLAUDE_PLUGIN_ROOT}` in subagent body** (same as skills) ⇒ **INLINE** the review protocol: `agents/critic.md` must absorb today's `agents/critic/SKILL.md` + `framework-checks.md` + `review-cycle.md` into ONE self-contained system prompt (can't portably reference siblings).
- **NO nested subagents** (hard one-level limit) ⇒ the Critic **coordinator pattern** (3 parallel dimension reviewers for medium/large) **cannot** live inside the critic subagent. It moves UP to the `/prawduct:critic` skill (main context), which orchestrates the parallel dimension reviewers. Real restructure of the coordinator.

**⚠️ SAFETY-CRITICAL constraint (must NOT regress):** the Critic must stay unable to run tests/builds or mutate the tree — read-only git verbs + `product-hook` helper subcommands only, **NO pytest**, **NO `git checkout`** (learning CRT-2M5P: a Critic with broad git once ran `git checkout` and corrupted the tree to detached HEAD; memory `feedback_critic_no_test_execution`). Today this is enforced by the SKILL's fine-grained `allowed-tools` (pure-allow list; pytest is unmatchable). **Docs indicate a subagent's `tools` may be bare-tool-names only (no `Bash(git diff:*)` sub-permissions) — UNVERIFIED; confirm empirically.** Implementation rule: keep the fine-grained restriction at the layer that supports it — the `/prawduct:critic` skill's `context: fork` + `allowed-tools` — and/or a PreToolUse guard. **NEVER give the critic subagent bare `Bash` without a guard.**

**Chunk 4 implementation order:** (1) empirically verify subagent `tools` Bash granularity AND how `context: fork` + `agent: prawduct:critic` + skill `allowed-tools` compose (does the skill's fine-grained restriction still bind the forked subagent?); (2) build `agents/critic.md` + `agents/pr-reviewer.md` (inlined, restricted); (3) move the coordinator fan-out into the skills; (4) rewire `/prawduct:critic`/`/prawduct:pr` to invoke the named subagents while the skill keeps owning mode-inference + findings read/report; (5) **test via `--plugin-dir` that the Critic still cannot run pytest** (the safety regression test); (6) `/critic` + commit. Keep `agents/critic/SKILL.md` etc. in place during the port — this repo's file-sync governance uses them until migration.
