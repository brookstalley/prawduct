# Learnings — core

**Reading a rule is not applying it.** For any rule below that bears on the decision in front of you, name the rule and say what it changes about that decision — or say that it does not apply, which is also an answer.

Each rule is one line of at most 250 characters. This file is capped, so a new rule is paid for by merging or retiring one.

- When a review finds the SAME class twice, stop fixing instances: enumerate every state the thing can be in and make each a case — two spot fixes in two rounds is one missing act. Tell: your fix cites the reviewer's example
- A zero from a scan is suspicious until the scan is shown able to return non-zero — feed it a case it must catch first (`getattr(x, "body", "")` on a missing field reported clean). Tell: a survey confirming exactly what you hoped
- When a criterion, plan or rule DESCRIBES an artifact, open the artifact before building to the description — it inherits its author's framing blind spot. Tell: you can satisfy it fully without ever reading the thing it names
- Before calling a behaviour change done, `grep -rn <new symbol> tests/` — an untested guard is one a regression deletes silently, and code written to FIX a finding is where this recurs
- Enumerate the sites answering a question by GREP, never memory — and the grep is only a PREFIX of the set where code BUILDS the string or emits it where the query can't see. Widen until falsifiable; have someone else run it
- Before implementing against a mechanism, grep the BACKLOG for its name; when claiming "provably equivalent", name the proposition proved — equivalence under one model is not under the one governing behaviour
- A fix for a review finding is a CODE commit: test it, red-verify it, and dispatch a delta review of the fix — correction work feels low-risk, so the verification reflex relaxes exactly where the last round proved it shouldn't
- Before clearing a reader/caller/path as unaffected, re-read what you just wrote about the mechanism's lifetime and test the clearance against it — a safety argument and its counterexample can sit two paragraphs apart in your own writing
- A governance change cannot supply its own authority: when an agent amends a binding norm mid-build, land the owner's confirmation somewhere the amendment isn't — a change that is its own only witness reads as laundering
- When you "correct" an inherited number, recount the SET, not just the count — re-measuring inside the inherited frame reproduces its error while feeling exactly like verification
- Surveying a shared thing takes TWO searches: grepping the thing finds copies, not DEPENDENTS — grep its shape, then its name and wrappers' names for callers; when relocating a fact, also grep prose naming its OLD HOME
- When defense-in-depth is the reason a risk needn't be verified, check the defense is REACHABLE from the failure — a guard downstream of the thing that fails never runs (`endswith` check behind a matcher that never fired)
- Before committing a consequential decision under momentum, do the cheapest check that could change it FIRST — read the mechanism before tuning it, search practice, re-read the artifact you rely on; the unchecked answer detonates later
- Uncommitted work in a worktree this session did NOT launch in is another session's territory — leave it alone; adopting sibling WIP collides with a possibly-live session and writes into clone-shared governance state
- When surfacing model-proposed candidates for owner confirm-or-correct, triage by decision-worthiness first: surface real forks individually, bulk-confirm the rest — a flat dump buries decisions and trains rubber-stamping
- Correcting a false claim is authoring a new claim — verify the replacement and what it cites; the trigger is WRITING it, not reading the original. Tell: this cell got a conclusion where every other got a query
- Before writing "X now covers/catches/handles Y" or "there is no Y", run the one query that would falsify it — coverage claims are the top error class here and checkable in a minute; the SENTENCE is the trigger
- A behavior change isn't done until every artifact that DESCRIBES it is updated — grep for summaries/enumerations ('produces', 'contains'), scope comments, templates, planning specs and test scenarios, not just the primary site; they drift silently
- Session-end signals ('ready for next session', 'complete') come AFTER the handoff — commit, tick the plan, reflect, file backlog items first — because users act on a completion signal immediately
- Removing a mechanism requires removing its NAME too — grep code, prose, tests and templates for every mention, or the survivors describe and route readers to a thing that no longer exists
- A channel that is produced and never consumed is a DEFECT, not an inefficiency — name the consumer in the same change that adds the producer, or don't produce
- Anything in a durable artifact one command could check is a CLAIM — identifier, count, `file:line`, facet value, not just rationale — so run its falsifying query first, above all for a rationale defending a decision already made, or a correction
- A sample you sliced for DISPLAY is not the set — if the command behind your impression had a `[:8]` or `head`, re-run it unsliced before writing 'all/every/entirely'; the slice is invisible in what you read back. Retractions bite hardest
- A fix lands at the instance a review named; the defect lives in the class — state why it broke in one sentence; if it doesn't name your fix site it defines a class whose members sit outside your diff. Route through one owner. Tell: one row fixed
- Routing a filing to the handoff is NOT filing it — file the item the moment you decide it should exist: the next session treats inherited instructions as context, and a crash or context exhaustion loses an unwritten handoff outright.
- A completeness claim means the falsifying COMMAND now returns nothing — never a count of sites fixed (true of any prefix). The query can carry the defect: normalize text first (lines aren't semantics); query the CONCEPT, not phrasings you found.
- A text-anchored edit changes a NEIGHBORHOOD, not a point — inserting at a `def` lands between the next function and its decorator; adding `else` to try/except strands the fallback. Both stay green: re-read the enclosing block after anchored edits.
- A rule you must RECALL at the right moment is its weakest form — if it governs a queryable claim, mechanise it (test, lint, rendered table); recall fails hardest on rules just written or read. Tell: this cycle's catches all came from mechanisms.
- When you fix a defect of a named class, re-run that class's own check on your fix — the likeliest place to reintroduce it, as attention is on content not mechanics. Tell: a citation renamed, then line-wrapped inside its backticks, still won't grep.
- When you add a member to an enumerated set in code (fact kind, waiver rule id, exit code), the registry DOCUMENTING that set is owed a row in the SAME commit — the gap is cheap to fix and costs a full review round to notice.
- A measurement with no POSITIVE CONTROL can't support a claim — before believing 'X costs nothing', confirm the instrument MOVES when it should; a dead one reads zero for treatment and control alike. Tell: confirmed first try, null case never run.
- Before writing the REASON for a choice ("X forces this"), open X — review checks code against claims, not claims. Gates short-circuit: read the function that RETURNS the verdict; test that it answers differently. Tell: reason cites an unopened gate
- A clean sweep usually indicts your QUERY — grep finds sites in your words; survivors paraphrase, assert the opposite, or stay silent. Name the state the change flips, search two disjoint vocabularies, pin positively. Tell: every hit used your words
- Bound a class by the PROPERTY that justifies it, never its container — a path prefix, line range, or fixture built from the feature's own subject looks complete while bounding the wrong set. Tell: boundary is a location, rationale is a verb
- Adding the right rule is not DELETING the wrong one — a superseded sentence keeps governing readers who stop at its file, and survives best in the paragraph you just edited. Remove it. Tell: the causing sentence still stands above your addition
- State that exists ONLY in context must be written down before the turn ends — .handoff-notes.md for the next batch (one hop, gitignored), a backlog item or artifact for what must outlive the session. Tell: "nothing else on disk records this"
- When you change a MECHANISM, cascade-search the CLAIM, not the code — edited tokens find what RUNS the old procedure, never prose DESCRIBING it. Enumerate the claims first, plural: more than your plan named. Tell: you can state the claim singular
- Verify a chunk against the PLAN's deliverable list, not the files you edited — work concentrates in one file and "done" gets judged from what's in front of you. Tell: a Tests/Deliverables line names several files and your edits concentrated in one
