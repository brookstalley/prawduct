## The finding that joins them

The two asks are one mechanism. On this repo's store, about 71% of the verify-resolutions rounds that
follow a blocker-free review are the last coverage before a PR (66 of 93 since 2026-10-23). No later
review exists to absorb them. So #1222's "the next review that runs anyway" exists only if #1223's
release-batch boundary review exists.

## 1. Why a WARNING fix buys a round (#1222)

**Mechanism today.**
- The PR gate composes coverage by tree from merge-base to HEAD (`plugin/lib/gates.py:3852-3879`).
- A fix that touches a judgeable file gets no free edge (`coverage_algebra.py:673-682`). With no review
  fact spanning anchor→HEAD, the verdict is `uncovered` (`coverage_algebra.py:1037-1043`).
- `coverage.diagnose_fix_churn` (`coverage.py:299-501`, wired at `gates.py:4112-4152`) detects this
  exact case and, by decision, only advises one verify-resolutions.

**Already free.**
- Non-judgeable deltas (`critic_consolidate.py:4603-4673`).
- A verify with nothing to verify (`:4478-4520`).
- Chunk/final when HEAD is already covered (`:4541-4570`).
- Base-advance transfer (`gates.py:3893-3919`) and doc-only PRs.
- Chunk/final reviews start at the covered frontier, so a fix made mid-plan rides the next review
  (`:4187-4225`). This is #167's interval extension.

**Already decided against.** #1222's first shape is a coverage grant when the fix touches only files
the review covered. It was built and reverted on 2026-09-20 (#167 thread), and a plan chunk doing the
same was cut (review-loop-termination Ch.03): file-level evidence is advisory strength, and a grant is
authority. On size thresholds, `review-cost-investigation-2026-09-19.md` §8.3 found that delta size
does not predict which verify rounds find something. The second shape, refusing a second verify, is
#167's D3. It was built and reverted because the refusal left the gate `uncovered`, with a
`cumulative` as the only route left.

**Measured here** (since 2026-10-23, 93 verify rounds after a blocker-free review). The next review on
the same scope was:

| Next review | Rounds |
|---|---|
| none (terminal) | 66 |
| another verify | 22 |
| cumulative | 4 |
| chunk | 1 |

The delta's judgeable-file count had a median of 4 and a p90 of 11.

**A small adjacent case.** `pending_actionable` counts warnings as well as blockers
(`critic_consolidate.py:4454-4456`). So a fix confined to records, made after a review with warnings, is
not refused as a free interval, and a verify round dispatches that the gate does not need. The code's
anti-deadlock reason (`:4596-4600`) concerns blockers only, and a free warning fix already has
`prawduct-hook disposition <review-id> <fid> --fixed <path>[,<path>...]` (`dispositions.py:527-556`). This repo had none in the window. A repo
where half the findings concern records may differ.

## 2. #1223 question 1: inner-stage facts already satisfy the PR gate

They do. "No mode label is consulted (CRT-J4PM)" (`gates.py:3704-3706`), `review_edges` reads no stage
(`coverage_algebra.py:625-670`), and `review-cycle.md:18` says the same.

`stage` controls rigor only. Its readers are severity and promotion (`critic_consolidate.py:121-135`,
`:8417`), record-lint grading (`:6277-6284`), the round-budget cadence (`:2994`) and `boundary_frontier`
(`gates.py:2485-2488`).

What buys a per-feature cumulative is prose, inference and a norm, not the gate:
- `pr/SKILL.md:11`, `:63` and `:93`;
- `LAST_CHUNK_BOUNDARY_STEP` (`critic_mode.py:2092`) and `_clean_tree_redirect` (`critic_mode.py:521`);
- the NFR "never skipped or inferred away" (`nonfunctional-requirements.md:117`, ratified 2026-09-17).

So #1223's "the PR accepts inner-stage coverage" is already true. The real change is a norm amendment.

## 3. #1223 question 2: derivable at release, but no gate runs there

- `pr/SKILL.md:40` stops at a release context.
- Here, promotion commits to `main` with no PR (release runbook lines 89-101), and `check-releasability`
  (`release_readiness.py:819`) checks no review coverage.
- It is derivable. For each first-parent merge M since the last tag, "boundary-covered" means a
  boundary-stage fact composes from tree(merge-base(M^1, M^2)) to `M^2^{tree}`: the existing
  `coverage_verdict` restricted to boundary facts.
  **Corrected 2026-11-23 (wave 1 build, pending the owner's ruling):** restricting to boundary facts
  reads half of this repo's per-PR merges as uncovered, because the fix tail after a cumulative is an
  inner verify pass. Wave 1 uses a boundary prefix plus a verify-only tail, and joins each pending
  fragment to the commit that added it rather than walking merges since a tag. The rule and its
  inferences are in `.prawduct/artifacts/build-plan-boundary-coverage-check.md` Goals. It breaks on squash merges and on branches not synced
  before review.
- A batch review that rates only the uncovered merges' files is not a valid edge, because `review_edges`
  requires every judgeable file to be reviewed. The release check needs its own relax-only rule,
  modelled on `excused_gap_verdict` (`coverage_algebra.py:1106-1207`).

## 4. Proposed shape: one deferral rule serves both

In an opt-in per-release mode, a PR into the integration branch passes when:
1. coverage composes from merge-base to a blocker-free review on this branch (any stage);
2. any tail after that review stays inside the files the review's findings or observations named
   (diagnose_fix_churn's conditions, used as a scope bound);
3. both the tail and any missing boundary review are owed to the release check.

This is a deferral, not a grant: a reviewer still reads the tail, one review later. BLOCKING findings are
untouched, because the deferral needs the verdict up to the anchor to be `covered`, not `blocked`.

**What must not break** (and the test that catches it):
- `test_free_interval_with_unresolved_findings_dispatches`
- `test_dispositions.py::test_blocking_is_refused_outright`
- `test_cumulative_gate.py`
- `tests/preferences/test_free_interval_prose.py`
- the NFR retirement grep in `test_v5_methodology.py`
- the `boundary_frontier` bounded-span tests

**Estimated saving** (low confidence; arithmetic on the issues' figures):
- #1222: at most about 110 discretionary verify rounds × 4.15 min ≈ 7.6 h a month.
- #1223: boundary reviews fall from 105 to the number of release batches. At several releases a day
  that is roughly 60-90, so 15-45 cumulatives × 9.3 min ≈ 2.3-7 h, less the cost of larger batch
  payloads. If batches average about one feature, the saving is close to zero.
- This repo releases about every 10 days (55 scopes in v3.9.0), and `../prawduct-live` runs develop. So
  a batch review here would be very large, and unreviewed boundary code would govern live sessions.
  This repo should stay per-PR.

## Decisions for the owner

1. Can a blocker-free fix tail reach the integration branch before any review reads it, deferred to the
   release review? *Recommend:* yes, as a deferral only and only together with the release check. No
   file-level grant.
2. Amend the NFR so the boundary is "per release batch, for eligible work"? *Recommend:* yes, as a
   per-repo opt-in, since the norm is ratified.
3. Is eligibility derived or declared? *Recommend:* derived: no risk surface touched, judgeable files at
   or under a bound, and the plan short-plan-eligible. A `Review lane: small` declaration would add only
   tax.
4. Is the opt-in one repo-level key (`boundary_review: per_pr | per_release`, default `per_pr`)?
   *Recommend:* yes.
5. Where does the release check live? *Recommend:* one `check-boundary-coverage` op, called by
   `check-releasability` and by the PR skill's release guard. Ship it advisory first, to count uncovered
   merges.
6. Should a free interval after a warnings-only review be refused as needing no round
   (`pending_actionable` counts blocking findings only)? *Recommend:* yes, as its own small change. It
   touches the "warnings are effectively blocking" stance, so it is ruled, not assumed.
